# 文档是地图，不是代码的镜像

文档的职责是**告诉读者东西在哪、先读什么、可以跳过什么**；把代码逐句翻译成散文就是镜像，写的时候浪费、
写完立刻开始漂移，读完还是不知道该看哪。

**第一读者是写代码的 agent**，人是看站点页面的监督者。agent 直接读 mdx，不另外维护一份机读副本；唯一的生成物是
生成正本（见后文）。两条随手用的判据：

- **段落自检**：删掉这句，读者会迷路吗？会就留；只是复述代码里也写着的事实，就钉码指过去，或者删掉。
- **每页第一句「本页回答：……」**。答不出一个问题的页就删掉。

这两条对任何项目都成立：代码库、论文、设备配置、仿真模型。docfirst 不规定页面的小标题，
各线自己的写法（比如某条产品线的包首页固定几段）写在那条线自己的说明书里。

# 分区

```
docs-site/content/
├── trajectory/   # 轨迹：怎么走到今天、每次取舍的理由。卡只增不改
├── future/       # 未来：还没发生的事
│   ├── roadmap.mdx        在等什么前提、到期再选的决定
│   ├── spec/<名字>.mdx     在途的实施方案，做完删
│   └── inbox/<日期>-<来源>-<标题>.mdx   别的仓投来的反馈，一条一个文件，处理完删
└── <其余目录>/    # 现状：此刻是什么。数量和名字随项目大小自定，小项目一个 docs/ 就够
```

`trajectory` 与 `future` 两个名字是固定的，**`content/` 下其余每个目录都是现状区**，都进 `docfirst check`，
不用在配置里登记。判据：**此刻是什么归现状，怎么走到今天归轨迹，还没发生的归未来。**为什么存在、刻意不做
什么也是此刻的边界，写在现状区；每条「不做」只写一句此刻的边界，理由链到轨迹卡。

现状区的根是入口页（通常是 `docs/index.mdx`），按这个顺序展开：是什么、为什么存在 → 主要流程走一遍 →
按来意怎么读 → 各部分的索引。术语表（`glossary`）也在现状区。

## 钉码只在现状区

**钉一处码，是在说「这句话跟着这段代码走，它变了就来找我」。**只有现状区的论断是这种性质。别的区不是：

- **轨迹**记的是当时的结论，代码后来怎么变都不该动它。钉了码，代码一改这张卡就变黄、要人复核，
  它就从「历史」变成了一份要维护的现状文档。这是硬性规定，`check` 会把卡里的记号当错误报出来。
- **未来**讲还没做的事，没有对应的代码可钉；spec 与 inbox 里的记号也没有任何东西去核对。

# 现状区怎么写

**只写现状，不写历史**：「原来怎样现在怎样」一律不出现，历史写进轨迹卡。正文用散文；只有契约引用、
spec 页头的验收清单、术语表这几类允许写成列表或表格。

## 写到哪为止

只写「错了难改」的：边界约束、依赖方向、接口契约（钉码）、状态机、取舍。像素、文案、字段清单、内部算法是
实现者的自由，写进文档是过早承诺，而且立刻开始漂移。判据一句话：**实现者剩下的自由里做任何选择都不违背
文档，就够了**，再写一行都多余。原理型内容（整体怎么运转、一次调用从头到尾、依赖方向为什么这样）
按同一个判据定厚薄：错了难改的讲透，错了好改的一句话。

依赖必须单向、隔离靠接口不靠自觉——写不出一块不知道什么，往往说明代码切错了，先去改代码，
别在文档里把环描述圆。目录结构用 `tree` 引用钉，不手画。

## 写作规则

- **论断可验证**：要么钉码，要么给确切路径。命令、配置项、数字这类事实以代码为唯一依据。
- **复述代码行为的段落是坏味道**，改成钉码；投影出来的代码块是论据不是正文，一段引用配一句「这段说明什么」。
- **AGENTS.md 与 skill 要精简**：前者每个会话都要读一遍，后者触发就读，每行都要有用——只留硬约束与
  「怎么做」，为什么写在站里。站上的页可以厚，它是按需读的。
- **引卡是说「有先例」，不是说「不许动」**。环境变了就写新卡推翻。
- **现状页少做站内链接**；对决策的说明写进轨迹卡再链过去。
- 手画目录树、手抄配置样例、给跑出来的数字写散文，都会很快过时；别钉生成物。

## 五类引用各钉哪种话

| 引用 | 该用在这种话 |
| --- | --- |
| 行段 `ref f:a-b` | 「某某是这样写的」——论断某段实现，或者钉住注释里的设计理由 |
| 整文件 `ref f` | 「整个文件就是……」——小而完整的模块或配置 |
| 目录树 `tree d` | 「这里有哪些东西」——结构陈述 |
| 存在 `exists` / 断言不在 `absent` | 「有 / 不该有 XX」——边界与红线 |
| 名字 `has f "…"` | 「里面写着 XX」——契约条目、导出名、测试名 |

新引用写草稿记号 `@@docfirst ref 路径:起-止 @@`，独立一行，路径相对项目根。确认后换成正式记号，
**确认时的记录就写在记号自己身上**（段哈希、blob 名），没有另外的记录文件：

```mdx
{/* ref file="../src/a.ts" lines="10-23" hash="3fa9c2e1b07d" blob="2689fa073ac6" */}
```

记号是 `confirm` 写的，不手改。状态点：绿是新鲜，实心黄是代码变了等复核，空心是还没确认，红是指向的东西没了。

# 钉码怎么保鲜

## 同一个提交里处理

**改代码的那个提交，同时处理这次改动引起的黄灯。**改代码的人最清楚改了什么、文档里哪句还成立，
隔几天再由别人成批确认就只剩走形式。

1. 改代码，跑内圈检查（类型、lint、测试；不带文档检查）
2. 提交前在站目录跑 `docfirst check`：钉住的文件在本仓有未提交改动、内容又变了的黄灯**算红**，拦下这次提交
3. `docfirst confirm`：机械写回，不需要判断——草稿换成正式记号；内容没变、只是挪了位置的，写回新行号；
   重新渲染生成正本。黄灯原样留着，逐条列出来
4. 逐条看剩下的黄灯：被钉的代码变了什么、正文哪句因此不再成立。论断还成立，
   `docfirst confirm <页…> --accept` 签掉；不成立，改论断再签
5. 代码、文档、记号上的新记录放进同一个提交

`--accept` 必须点名页，不能整仓签——同一个仓里别人没复核的黄灯不能替他签。确认不要求先提交代码。

已经提交的代码引起的黄灯、钉在别的仓里的代码引起的黄灯，`check` 只报告不拦；碰到了按下面的重写规则处理。

## 重写规则：现状漂移了

`docfirst check` 报红或报黄（要机读清单就 `docfirst check --json`，读 `docs[].items[]` 里 `status` 是
`changed` / `missing` 的那些）之后：

1. 逐页逐处看漂移：被钉的代码变了什么、正文哪句因此不再成立。
2. **只改漂移的段落**——不重排全页、不顺手润色别处、小标题原样保留、沿用本页已有的口吻与钉法。
3. 论断仍成立的 `--accept`；不成立的先改论断再 `--accept`；指向的东西没了（红）就改写或删掉那处引用。
4. 人审 diff 后提交，代码与文档同一个提交。

# 开发循环

```
一句话需求 → A 盘问（spec-grill）→ B 实验与选型（gwb-decide）→ C 实施方案（future/spec 页）
→ D TDD → E 全绿 → F 更新现状、spec 拆开写进各页后删页、写轨迹卡、重新渲染生成正本
```

A 之前不动代码：`spec-grill` 在对话里把想法问到能说清「回答什么 / 不做什么 / 成功判据」，人同意前不动代码。
它问需求边界，`gwb-decide` 问选型，两者不重叠。

**这一处的三份纪律随本插件一起发，各有触发条件**：`spec-grill`（A 那一步怎么问）、
`parallel-by-module`（任务大到要派子代理时怎么切、什么必须串行）、`docs-governance`
（文档与注释治理——代码自解释扫描、术语统一、清理历史、分清谁负责什么）。这一页不复述它们的正文。

| 代码动作 | 文档要跟着改的地方 |
| --- | --- |
| 动接口 / 状态机 / 依赖方向 | 讲这一块的现状页，先改或同一个提交 |
| 撞墙、做了选型、实验有结论 | 轨迹卡，当场写（`trajectory` skill） |
| 命令 / 配置变了 | 用法页，重新渲染生成正本 |
| 定了新术语 | 术语表 |
| 做 / 不做的边界动了 | 讲边界的那页，理由写进卡 |

真没有文档要改，说明这次改动连「错了难改」的边都没碰。

## spec：在途方案

判据：**跨会话、跨模块、有未定选型**，三条占一条才写 spec；一个会话做得完的直接改现状页开工。
spec 是 `future/spec/` 下的一页，**随做随提交**：中途每次提交都是能交给下一个会话的快照。页头列验收清单，
做完一项勾一项。做完把内容拆开：设计写进现状页、决定写成轨迹卡、剩下的删掉，然后**删页**；
git 历史就是它的存档。

## 给别的仓投反馈

在 A 仓工作时发现 B 仓的问题，当场写一个文件投进 B 仓：`<B 仓的站>/content/future/inbox/<日期>-<来源>-<标题>.mdx`，
文件名里的来源与标题用英文小写和短横线（git 会把中文路径显示成八进制转义），中文标题写进 frontmatter 的 `title`。
写清现场、期望、证据路径，然后在 B 仓里 `git add` 这个文件、`git commit --only` 这个文件。一条一个文件，
不会跟 B 仓里别人未提交的改动冲突。B 仓的会话处理完就删掉这个文件，结论写进现状页或轨迹卡。

# 术语表

站上配一张术语表，全站命中处自动标注、悬停显示定义。收三类：仓自己造的词、通用词在这里有特定含义的、
外来框架词（最该收，正是读者最容易卡住的地方）。不收通用编程词与单字词。

正本是一份数据文件（`src/glossary.ts` 一类），每条 `term / aliases / def / href`。**定义只写概念，
不写服务名、类型名、路径**——数据文件钉不住，写进去就会过时，具体名字留给 `href` 指的那一页。
自动标注发生在站构建的 remark 阶段，源文件保持干净；手写 `<Term>` 要在 `docfirst.config.mjs` 的名册里有一条
（`Term: 'children'`）。机制见 docfirst 站的 fumadocs 那一页。

# 生成正本

README、AGENTS.md、CLAUDE.md、包内 SKILL.md 都是生成物。正本是现状区里的 mdx（通常在 `docs/outputs/` 下），
`docfirst.config.mjs` 的 `outputs` 映射把正本对到落点，`docfirst render` 重新生成（`confirm` 也会顺带做）。
渲染按原文处理：去掉 frontmatter，每个钉码记号换成一个代码块，其余文字一个字节都不动。
所以正本里可以钉码，但不能用 JSX 组件。SKILL.md 的 `name` / `description` 从 frontmatter 带过去；
AGENTS / README 不带 frontmatter。改正本，不改生成物。

每仓的 AGENTS 正本只写本仓专属的（怎么跑、端口、检查命令、红线、从哪读起）加一行指回这份 skill，
生成出的 AGENTS.md 控制在 60 行内。CLAUDE 正本第一行固定是 `@AGENTS.md`，只给 Claude 的指令写在后面。

# 建站

建一个新站是**一条工作台命令**：`docfirst.create {"dir":"<仓>/docs-site"}`。站点插件的 `docs-site.create` 先跑官方脚手架
`create-fumadocs-app`、套本机约定并写盘；docfirst 在官方输出上改几份文件：三个集合（docs、trajectory、future）用 fumadocs-mdx
的 macro 写在 `src/lib/source.ts`，现状集合写 `mdxOptions: applyMdxPreset(docfirstMdxOptions({ root: process.cwd() }))` 与
`postprocess.includeProcessedMarkdown: docfirstMarkdownOptions()`，外加各区的路由、`docfirst.config.mjs`、mdx 接线、名册脚本、
各区的起始页，`package.json` 里带上依赖与 doc 脚本。只写文件不跑 install，端口不给就由站点插件挑。

**站目录必须还不存在**：已经有站的仓不能用这条命令，给已经运行很久的站加 docfirst 走人工接线。
站建好以后要改站的结构（加分区、加组件）或跑 `dev` / `build`，读站点插件的说明书 `docs-site`。

模板假设站在仓根 `docs-site/`、被钉的代码在仓根（引用写 `../src/…`），形状不同就改引用里的相对路径。

读一个站的顺序：**入口页 → 讲边界的页 → 各部分的页 → 术语表**；轨迹按需查。
入口处的钉码都在、`check` 是绿的，站上写的就没有和代码对不上的。

docfirst 自己那个仓的 `docs-site/` 是最全的示例站，写不准时去那儿找同类页照着写。
