# 按模块并行，不要一路走到黑

**反模式**：派一个写手从 A 模块改到 B 模块，再回头写全部文档，最后自己跑门禁。它把一件本来
能并行的事做成了串行，而且没有任何一步是可复核的——你只能全收或全丢。

**正形**三步：

1. **主会话把接口定死**，落一个提交。这是合拢面：类型声明、方法签名、谁认得谁。
2. **一模块一写手，并行**。每路只动自己那个模块的代码与**它自己的模块页**。
3. **合拢归主会话**：跨模块的页、门禁、确认、提交、卡。

## 切不开就是接口没定死

想派活时发现两路会改同一批文件，不要硬拆——那是设计在说话：接口还在漂，或者模块边界画错了。
回去把接口定死再派。这条判据比任何拆分技巧都值钱，它把「协作困难」翻译成了「设计问题」。

同理，一个模块的文档页写不出「不知道什么」那一段，通常也是代码切错了。

## 派单里必须写死的四样

* **只动哪几个文件**，逐个列出来。别写「相关文件」。
* **不提交、不跑确认、不跑门禁、不跑构建**。改完回报，合拢时统一跑。
* **禁区**：别的会话正在动的文件、别人黄着的钉，逐个点名，说清不许碰。
* **本轮的事实**：这次改了什么、接口长什么样、行号在哪。写手不该自己去猜刚发生过什么。

## 钉码用草稿记号

并行的几路都会动钉码，而确认要写记录簿——几个人同时写就撞了。所以：**并行路一律写草稿记号**
（写法见 `docfirst-docs` 的「五类引用各钉哪种话」，行号自己数准），**主会话合拢时统一确认一次**，
按页限定点名那几页。这正是草稿记号存在的理由：作者不维护指纹，工具来记。

## 合拢面有哪些

跨模块的总索引（system-map）、用法页、生成正本（README / AGENTS / SKILL.md 的 mdx 源）、
在途 spec 页、轨迹卡、全量门禁、确认、提交。这些东西**没有单一归属**，谁写都会跟别人打架，
所以归主会话。

## 复核，不要收自述

写手回报「跑绿了」不等于绿了。合拢时主会话自己跑一次门禁、自己看一眼产物。派出去的活越多，
这条越要紧——并行的收益会被一次未复核的返工吃光。

## 判据阶梯：什么必须串行

**必须串行的只有三样**，它们是全局状态，谁写都踩别人：共享配置文件（站配置、包清单、
锁文件）、记录簿（确认那一步写的那份）、全量门禁。

**除此之外，冲突的判据是文件，不是轮次。** 文件不重叠就照常并行，主会话也不例外——
「先等这一轮收完再派下一轮」是把文件冲突误当成了时间冲突，白白把并行做成串行。

隔离级别按这三档挑，够用就好：

* 文件不重叠、也不碰上面那三样共享基础设施 → **同一个工作树里并行就够**。
* 要碰站配置、要写记录簿、或者想各跑各的门禁 → **一路一个 worktree**。
* 动全仓的改造（改名、批量格式化）→ **谁都不能并行**，独占。

**跨仓派活时 worktree 要自己建。** 宿主的 worktree 隔离参数按**主会话所在的仓**建：坐在
A 仓派人去 B 仓干活，它建到 A 仓去了，等于没隔离。跨仓就自己 `git worktree add`，派单里
把工作目录写死。

**spec 一活一页。** 一页装多个活会人为造出冲突——两路都要改那一页；「做完删页」的语义
也跟着糊掉。
