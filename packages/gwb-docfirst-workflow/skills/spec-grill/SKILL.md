# 先盘问，再动手

**人点头前不动代码。** 一句话需求直接开工会中三个病根：agent 只盯人点的那一处改，边界外的
牵连没人问；上下文装不下就漏改，漏的正是没人说出口的那部分；做完才发现「不是这个意思」，
返工比盘问贵十倍。盘问把这三条压在动手之前，成本是几轮对话。

## 怎么盘

目标是把想法盘到能一句话说清三样：**回答什么**（做完之后哪个问题有了答案）、**不做什么**
（边界外明确排除的）、**成功判据**（怎么验收，能跑出来看的）。三样说不清，就还没盘完。

* **一轮把当前能问的全部问完。** 每问编号，每问给推荐答案与一句理由；人可以只答「都按推荐」。
  一次问一个是拖着人陪跑，问十个是把选择权交回去。
* **用对话问，不用宿主的提问工具。** 问题带上下文、带推荐、带理由，工具面装不下这些。
* **答案回来重算下一轮。** 前一轮的回答会关掉一些分支、打开一些新的；新分支再一轮，直到三样
  说清。通常两轮，三轮以上说明需求本身在漂，把这个观察说出来。
* **事实自己查，不问人。** 代码里现在长什么样、哪个模块管这块、测试怎么跑——派探子读，问人
  是把查得到的事推给记不全的人。只问人才知道的：意图、优先级、可接受的代价、边界。
* **列出你已经替人做的假设**，逐条标「按此进行，反对请说」——沉默也是一种回答，但要让人看见
  沉默默认了什么。

## 跟 gwb-decide 的分工

grill 盘**需求边界**：做什么、不做什么、算不算成。decide 盘**选型**：引哪个依赖、定什么契约
面、进内核还是做成插件。盘问中冒出选型问题，记为未定项、不在 grill 里推，盘完边界再走 decide。

## 结束条件与产出

三样说清、人点头，盘问结束。产出按升格判据二选一：

* **跨会话、跨模块、有未定选型**，占一条即升格为 spec 页。写进 `content/spec/`，骨架四段、
  随做随提交、做完拆解归梁删页——这几条的正本在 `docfirst-docs` 的「spec：升格件，住站在途」。
* 都不占：直接在模块页里改契约开工，盘问结论落在那次提交的信息里。

之后的循环（实验与选型 → TDD → 全绿 → 更新现状与落卡）见 `docfirst-docs` skill。
