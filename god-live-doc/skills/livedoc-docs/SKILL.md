# livedoc 文档怎么写

livedoc 仓的文档不是代码的复读，是**论断集**：每句话说的是「代码是怎样的、为什么这样」，
论断的可信度由引用钉在源码上——代码变了状态点变色，谎话立刻现形。写之前先记这条判据：

> **一句话如果能被代码推翻，它就该带引用；一句话如果只是在复述代码，它就不该存在。**

## 章节骨架

参考 livedoc 自家站的划分（入门 / 原理 / 格式与站 / 命令与测试 / 维护），按**读者的疑问**组织，
不按目录组织。插件仓的对应骨架：入门（这是什么、怎么跑）→ 主体（每个能力面 / 模块一页）→
契约（形态规矩）→ 维护（验证与发版）→ 生成物正本（README / CLAUDE 的源头页）。

主体章的组织法：**每节先给结论句，再钉证据**。结论句写「为什么这样设计、红线是什么」；
投影块是论据不是正文——一段引用配至少一句「这段说明什么」，光摆代码不说话就是白摆。

## 五类引用各用在哪种话

| 引用 | 该用在这种话 | 例子 |
| --- | --- | --- |
| 行段 `ref f:a-b` | 「某某是这样写的」——论断某段实现、或钉住注释里的设计理由 | 「写操作绝不上 HTTP，理由就在路由文件头」 |
| 整文件 `ref f` | 「整个文件就是……」——小而完整的模块 / 配置 | 「三条 bundle 的 id 全是包名，整个文件就这三行」 |
| 目录树 `tree d` | 「这里有哪些东西」——结构陈述 | 「仓根此刻的真实形状」 |
| 存在 `exists` / 断言不在 `absent` | 「有 / 不该有 XX」——边界与红线 | 「cordis.patch.yml 在」「包里不该出现的文件」 |
| 名字 `has f "…"` | 「里面写着 XX」——契约条目、导出名 | 「裸业务名的正本：export const name」 |

页面上的状态点：绿=新鲜；实心黄=代码变了待复核；空心黄=未确认；红=引用指向空气。
写完 `pnpm livedoc check` 全绿才算完，黄红都别留给读者。

## 工作流

1. 写草稿记号 `@@livedoc ref 路径:起-止 @@`（独立一行；路径相对项目根，站外可 `../`）。
2. 被钉的源码改动过？**先 commit**——git 记忆只对已提交且干净的内容钉，钉不住整篇拒。
3. `pnpm livedoc confirm`：草稿转正式记号、出记录、投影内容。
4. 改了挂 `outputs` 的页（README / CLAUDE 正本）：`pnpm livedoc render --target ai` 重摆生成物。
5. mdx 源、生成物、`.ledger.json` **同一个提交**；check 守着生成物跟源一致，红了就是没重摆。

## 反模式

- **代码罗列**：贴大段代码当正文。投影块自己会长大——你只写论断和理由，代码让引用去拿。
- **该钉不钉**：正文里出现具体路径、行号、文件清单、导出名、配置项——凡是「抄了一份代码里的
  事实」的句子都必须换成引用，否则代码一改它就成谎话。
- **手画目录树 / 手抄配置样例**：那是这套机制要消灭的腐化源；活树和整文件引用替你维护。
- **三处不动点**：别钉生成物（每次 render 都变）、别钉 `.ledger.json`（每次 confirm 都变）、
  目录树别钉站自己的项目根（`.ledger.json` 在里面，永远收敛不了）。
- **给跑出来的数字写散文**：「86 条测试」「20 个文件」——钉产生它的东西（如 tests 目录树）
  让读者自己数；数字写进散文必腐化。
