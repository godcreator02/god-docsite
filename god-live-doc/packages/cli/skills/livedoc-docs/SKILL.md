# 读者是谁——这决定了一切

**写给用 AI 写代码、正在造东西的开发者看。** 他不是在用一个产品，他在**造**一个东西；
他要指挥 AI 干活，所以必须自己搞明白这套系统是怎么回事。

关键的一点：**他的技术底子不一定深**，这个仓吃的那些框架概念（不管是 remark、loader、
peer 依赖还是别的什么）他未必熟。这不意味着少讲原理——**恰恰相反，正因为不熟，原理才要
从头讲透、不许跳步**。把话说浅、把原理省掉、只留「照这样敲」，是把他挡在门外，
不是照顾他。

# 一句判据

> **文档要回答的是：这套东西是怎么想出来的、由哪些部分组成、它们之间怎么说话、为什么是这样。**

「怎么用」是最不重要的一节。用法会变，设计不会；而且用法他可以现问 AI，
**设计只有你写下来才存在**。

配套的第二条判据，管每一句话该不该带引用：

> **一句话如果能被代码推翻，它就该带引用；一句话如果只是在复述代码，它就不该存在。**

# 六层骨架

一个仓的文档站按这个顺序排，前面的比后面的重要：

**一、整体原理。** 这套东西解决什么问题、凭什么这么解、拆成几层、一次调用从头到尾怎么走。
这一层要能让一个没见过这个仓的人读完说得出「哦，它是这么转的」。**篇幅上它应该是最厚的
一层**，不是三句话的引子。

**二、模块划分。** 有哪几块、各自的职责边界、**为什么这么切**。这一层最重要的不是清单，
是**依赖方向**——见下面「模块划分要写清依赖方向」，那是整份里最该花力气的一节。

**三、接口划分。** 块与块之间怎么说话：服务名、类型、命令名、事件、导出面。
**导出面就是契约**，逐条钉在真代码上——它变了文档就该变黄。这一层最容易写成流水账，
写的时候盯住一个问题：**这条接口为什么长这样，换一种设计会坏在哪。**

**四、关键代码。** 不是贴全文，是挑「看了这段就懂这个机制」的那几段，用行段引用钉住，
**每段配一句「这段说明什么」**——光摆代码不说话就是白摆。

**五、取舍与了断。** 试过什么、为什么否掉、什么时候改的主意、撞了哪堵墙。
**这一层最容易丢，丢了最贵**——半年后没人记得为什么不那么做，于是又那么做一遍。
形态见下面「记轨迹」。

**六、怎么用。** 一节，放最后。装什么、跑哪条命令、日志在哪。写短就行。

章节按**读者的疑问**组织，不按目录组织。一个仓的常见分法：入门（这是什么、怎么跑）→
主体（每个模块 / 能力面一页）→ 契约（形态规矩）→ 维护（验证与发版）→
生成物正本（README / AGENTS 的源头页）。

主体章的组织法：**每节先给结论句，再钉证据**。结论句写「为什么这样设计、红线是什么」；
投影块是论据不是正文——一段引用配至少一句「这段说明什么」。

# 模块划分要写清依赖方向

模块那一层写成一张「有哪几块」的清单，等于没写。真正要交代的是**块与块之间怎么依赖**：

**一、依赖必须是单方面的。** A 依赖 B，B 就不许回头知道 A。文档里要把箭头画出来——
「它们互相配合」「双向协作」这种话是把环描述圆，不是描述。**画出环就是切错了**：
那时该去改代码，不是在文档里把它说通。

**二、隔离靠抽象接口，不靠自觉。** B 交给 A 的应该是一个接口（类型），不是它的实现。
判据一句话：**换掉 B 的实现，A 要一行都不用改。** 写文档时逐个模块问一遍这句，
问不过去的就是没隔离。

**三、每个模块写清楚它「不知道什么」。** 比写它知道什么更能说明边界。
「转换器不知道文档库存在，输入一个文件路径、输出一段 md」——一句话就把边界钉死了。

**四、目录树用活树引用钉出来**，别手画。

## 为什么这一层值得花最多力气

**读者和他的 AI 是按模块下手改代码的。** 依赖单向、接口隔离，他就能只读一块、只改一块、
只测一块；耦在一起，改哪儿都得先通读全仓——那时文档写得再漂亮也救不了。

**而且写不出来，往往说明代码切错了。** 依赖方向画出一个环、某个模块的职责一句话说不清、
「换掉实现不用改调用方」这句问不过去——那是代码的问题。文档在这里是照妖镜：
**先去改代码，别在文档里把它描述圆。**

## 一个现成的正例

livedoc 自己就是这么切的，可以照着看：**核心零依赖**——它不读文件、不起子进程、
不认识任何文档格式，只**声明**自己需要什么外部能力（读取器、记录簿、比较器三个接口）；
**装配层**是真机器——盘、git、json 记录簿，实现那几个接口；**命令行**只剩接线与编排。

依赖方向是**实现 → 接口**，单向：核心不知道装配层存在。于是纯逻辑那半能单测
（喂一套假的实现就行），换一套实现也不用动逻辑一行。判据还是那句
——**「这段能不能不起进程、只喂输入看输出」，测试判据和隔离判据是同一条。**

# 讲原理不许跳步

读者不熟这些框架，所以：

- **每个外来概念第一次出现，要么当场解释一句，要么指一处解释。** 直接甩一句框架黑话
  就是跳步；「fiber 是这个框架给每个插件实例建的一条生命线，挂上、活着、撤销都记在它
  身上」才是不跳步。指路也行，但得指到具体页，不能只说「详见文档站」
- **不要求读者先读完别的东西再回来。** 「在开始之前请先了解 X」是把门关上
- **一次讲一条链，讲完再讲下一条。** 「从人点一下到 handler 被调用」这样一条完整的路，
  比六个孤立概念有用得多
- **抽象后面跟一个具体例子**，例子用仓里真有的东西，钉住

# 论断要钉住

对这个读者这条格外要紧：**他会照着文档去指挥 AI 改代码。** 文档里一个过期的接口名、
一条早就删掉的配置项，代价不是「他读到一句错话」，是「他和他的 AI 按错的前提干了半天」。

所以正文里凡是出现具体路径、行号、文件清单、导出名、配置项——**凡是抄了一份代码里的
事实的句子**，都换成引用。写完 `pnpm livedoc check` 全绿才算完，黄红都别留给读者。

## 五类引用各用在哪种话

| 引用 | 该用在这种话 | 例子 |
| --- | --- | --- |
| 行段 `ref f:a-b` | 「某某是这样写的」——论断某段实现、或钉住注释里的设计理由 | 「写操作绝不上 HTTP，理由就在路由文件头」 |
| 整文件 `ref f` | 「整个文件就是……」——小而完整的模块 / 配置 | 「三条 bundle 的 id 全是包名，整个文件就这三行」 |
| 目录树 `tree d` | 「这里有哪些东西」——结构陈述 | 「仓根此刻的真实形状」 |
| 存在 `exists` / 断言不在 `absent` | 「有 / 不该有 XX」——边界与红线 | 「补丁文件在」「包里不该出现的文件」 |
| 名字 `has f "…"` | 「里面写着 XX」——契约条目、导出名 | 「裸业务名的正本：export const name」 |

页面上的状态点：绿=新鲜；实心黄=代码变了待复核；空心黄=未确认；红=引用指向空气。

## 工作流

1. 写草稿记号 `@@livedoc ref 路径:起-止 @@`（独立一行；路径相对项目根，站外可 `../`）。
2. 被钉的源码改动过？**先 commit**——git 记忆只对已提交且干净的内容钉，钉不住整篇拒。
3. `pnpm livedoc confirm`：草稿转正式记号、出记录、投影内容。
4. 改了挂 `outputs` 的页（README / AGENTS 正本）：`pnpm livedoc render --target ai` 重摆生成物。
5. mdx 源、生成物、`.ledger.json` **同一个提交**；check 守着生成物跟源一致，红了就是没重摆。

记忆怎么按文件位置分派、四种状态各是什么意思，那是机制那一半，见站上的原理章；
这份只管写作。

# 术语表是站的标配

「每个外来概念第一次出现要么解释、要么指路」这条，靠人逐处记是记不住的——**站上配一张
术语表，全站命中的地方自动标出来，鼠标移上去就显示定义。**

## 收什么词

一条术语的价值，在于它替读者省掉一次「这词啥意思」的中断。三类该收：

- **这个仓自己造的词**：那些在别处查不到、只有读这个仓才会遇上的名字
- **通用词在这个仓里有特定含义的**：这里的「服务」「条目」跟别处不是一回事
- **外来框架的词**——remark、loader、peer 依赖、fiber 这一类。**这一类最该收**，
  正是读者最容易卡住、而写的人最容易忘了解释的地方

不收通用编程词（进程、接口、数组），不收单字词——单字词会命中一切，标得满页虚线。

## 正本是一份数据文件，不是那一页

术语页是**生成物**，正本是一份数据文件（站里一处，如 `content/glossary.ts`），
每条四个字段：

| 字段 | 装什么 |
| --- | --- |
| `term` | 词本身 |
| `aliases` | 别名、英文名、复数——自动标注按这些一起匹配 |
| `def` | 一两句定义。**只写概念，不写易变的具体名** |
| `href` | 详解在哪一页（可选） |

**定义里不写服务名、类型名、命令名、路径**——数据文件不是 mdx，钉不住，写进去就腐化。
具体的名字留给 `href` 指的那一页，在那儿钉。同「动画里不出现能被代码推翻的事实」一个道理。

## 自动标注必须做到的八条

remark 插件在站构建时扫正文、把命中的词包成 `<Term>`。这八条漏一条就出事：

1. **跳过代码**：`code` 与 `inlineCode` 一律不碰。livedoc 的投影块全是代码，天然安全
2. **跳过标题**：heading 里替换会动到 TOC 和锚点
3. **跳过链接文本**：链接里再套一层交互是坏体验
4. **跳过术语表自己那一页**：否则自我循环
5. **一页里同一个词只标第一次**（或每节第一次）。每次都标，正文变成一片虚线，读不下去——
   **标注是为了解释，不是为了统计词频**
6. **长词优先**：先匹配最长的。否则「总线」先命中，把「命令总线」切碎
7. **英文词要词边界**（`pane` 不许命中 `panel`）；中文没有词边界，直接子串匹配，
   所以更要靠「不收单字词」那条兜着
8. **已经在 `<Term>` 里的不再往里嵌**

## 组件本身

视觉是**点线下划线**，不抢正文——它是个可选的旁注，不是重点标记。

**hover 不能是唯一的打开方式。** 触屏没有 hover，键盘用户也够不着。所以：可聚焦
（`tabIndex`）、点击和回车都能展开、挂 `aria-describedby`。只做 hover 的组件，
在手机上等于把定义藏死了。

定义框里放一条「看详解」链接（那条术语的 `href`）。

## 跟 livedoc 的接线

**自动标注不进源文件**——它发生在站构建的 remark 阶段，mdx 源里干干净净。所以
`livedoc check` 和 `render --target ai` 看到的是没有 `<Term>` 的原文，机读版天然是纯文本，
不用做任何事。

**但手写的 `<Term>` 会进源文件**（自动没认出来、或者要强制标某一处），那时它就必须在
`livedoc.config.mjs` 的名册里有一条规则——**名册外的组件是硬失败**，报「第 N 行：
名册外组件 `<Term>`」。加一条最省事的就行：

```js
components: {
  ...fumadocs.defaultRoster,
  Term: 'children',   // 机读版只留术语原词，不留装饰
}
```

# 关键位置穿插动画

讲机制讲到卡住的地方，画一段 html 动画嵌进去——`iframe` 引一个自足的 html 文件。
一句话讲不清的顺序，动一遍就懂了。

## 什么时候值得画

**只画「时间上发生的事」**：一条调用穿过几层、状态怎么迁移、失败时在哪一步断、
两件事抢同一个东西时会怎样。这类东西写成文字必然是「先……然后……如果……」的长句，
正是动画的用武之地，也正是六层骨架第一层（整体原理）最需要的。

**静态关系不画动画**：有哪几块、谁依赖谁、目录长什么样——那用表、用图、用活树引用，
动起来没有任何增量，只是装饰。

一节最多一个。多了就从解释变成了表演。

## 怎么放

html 文件住站的 `public/` 下（Next.js 自动把 `public/` 挂在站根，不用配任何东西；
站里还没有这个目录就新建）：

```
docs-site/public/anim/<讲什么>.html
```

mdx 里嵌：

```mdx
<iframe
  src="/anim/mount.html"
  title="一次挂载从 import 到活着"
  style={{ width: '100%', height: 380, border: 0 }}
  loading="lazy"
/>
```

**`style` 在 MDX 里是对象不是字符串**——写成 `style="…"` 直接编译不过。

## 四条硬要求

**一、单文件，不引外部脚本。** 一个 html 把 css / js 全装在里面，不引 CDN、不引框架。
它住 `public/`、不参与站的构建——引外部的东西，在离线或 CSP 收紧时就是一块白板。
纯 CSS 动画或几十行原生 JS 足够。

**二、不画自己的背景色。** iframe 里是一份**独立文档，不继承站的亮暗主题**。
`body` 别设 background（不设就是透明的，站的底色透上来），线条和文字用两套主题下都读得清的
中性色；要更讲究就在动画里写一套 `prefers-color-scheme` 切色。**把站的背景色抄进动画**
是最常见的坏法：站一换主题它就是一块突兀的白斑。

**三、给「重播」和「下一步」，别自动循环。** 读者常常在中间某一步卡住，要停在那儿看；
自动循环的动画看第三遍就只剩烦躁。能单步的动画才是解释，不能单步的是动图。

**四、高度写死。** 跨文档拿不到内容高度（除非上 postMessage，不值得），动画按给定高度设计。

## 两条防腐化的纪律

动画是**手画的**，livedoc 钉不住一张图——所以它跟手画目录树一样，天然会腐化。两条约束
把这个风险压到最低：

**一、动画里不出现能被代码推翻的具体事实。** 不写具体的函数名、路径、配置项、行号、数字。
它画的是**机制的形状**：谁先谁后、在哪儿分叉、哪一步会断。具体名字留在正文里、钉住。
这样代码改了名字，动画不会因此说谎。

**二、动画所在那一节必须钉住它图解的那段代码。** 这是唯一能用的守卫：机制真变了，
那节的引用变黄，人复核正文的时候顺手就会看见旁边这张图该不该跟着改。**没有引用的那节
不许放动画**——那张图从落地那天起就没人再看它一眼。

还有一条来自机读版：**`.ai.md` 里动画什么都不剩。** 所以**动画不能是任何一条信息的唯一
载体**——正文必须把同一件事用文字讲完，动画是那段文字的图解，不是它的替代。
判据还是那句：为「人看着轻松」把判据挪进图里，等于坑了读者的 AI。

# 记轨迹

方向了断记进各仓自己的轨迹区，一次了断一张卡。**阈值是「改变下一步动作的事」**——
走死了、转向了、被取代、拍板采纳、实验有了结论，占一条就够格，宁滥勿缺。

三条必须知道的：

- **卡不许钉代码。** 轨迹区冻结历史，钉了活代码它就变成一份会变黄的现状文档，
  记的就不再是「当时的了断」。要说现状去写现状文档，在那儿钉
- **同主题不新建第二张卡。** 先列一遍轨迹区查重，有就追加——同一件事两张卡就是两份
  互相不同步的说法
- **动手权在人。** AI 觉得该记，只能在回复末尾一句话点出候选、等人点头；人没回应就跳过。
  档案的价值在于它反映**人的**探索意志

判据表、卡的形态与字段、里程碑怎么追——去读**旁边那份 `trajectory` skill** 与它的两篇
reference（跟这份住同一个 `skills/` 目录），这儿不复述。

# 两个出口

同一份正本出两个口，`livedoc render --target ai` 已经把机制给了：

| 出口 | 给谁 | 形态 |
| --- | --- | --- |
| 站上的页 | 人 | 有导航、有层次、代码块是投影 |
| `.ai.md` | 他的 AI | 同一份内容的机读投影：**代码现拿、带来源行**，喂进上下文就能用 |

**这两份的内容是同一份，不是「简版」和「详版」。** 这个读者读文档的常态就是把它喂给 AI，
所以别为「人读起来轻松」而在站上把判据删掉——判据删了，他的 AI 就少了那条判据。

# 写坏了的样子

1. **写成了使用手册。** 通篇「第一步装 X、第二步跑 Y」，读完不知道它凭什么这么转
2. **原理只有三句话的引子**，剩下全是 API 罗列。骨架的第一层最厚，不是最薄
3. **跳步**：默认读者知道那些框架黑话是什么，直接拿这些词解释设计
4. **代码罗列**：贴大段代码当正文。投影块自己会长大——你只写论断和理由，代码让引用去拿
5. **该钉不钉**：正文里出现具体路径、行号、文件清单、导出名、配置项，却是手抄的一份——
   代码一改它就成谎话
6. **手画目录树 / 手抄配置样例 / 给跑出来的数字写散文**（「86 条测试」「20 个文件」）。
   这些是这套机制要消灭的腐化源；活树、整文件引用替你维护，数字让读者自己数
7. **钉了三处不动点**：别钉生成物（每次 render 都变）、别钉 `.ledger.json`（每次 confirm
   都变）、目录树别钉站自己的项目根（`.ledger.json` 在里面，永远收敛不了）

# 起一个文档站

往一个**已经存在**的仓里铺一个接好 livedoc 的 fumadocs 站，一条命令：

```powershell
pnpm livedoc init --dir <仓的绝对路径> [--title <显示名>] [--port <端口>]
```

前置条件：**仓已经在**，而 `<仓>/docs-site` **还不在**（在了就拒，一个字不覆盖）。

**只铺文件**：不跑 `pnpm install`（替人装依赖，出错时现场在哪都不好找），
不改仓里任何已有文件（`.gitignore` 缺哪几条只打印出来，自己加）。铺完自己进
`docs-site/` 跑 `pnpm install`。

**端口自动挑**：扫一遍同级各仓已占的站端口，从 4310 起找第一个空位。**按脚本内容认，
不按目录名认**——站不一定叫 `docs-site`，认的是 package.json 里那个 `next dev -p <口>` /
`next start -p <口>`。`--port` 手给的一律让给你，被占了只警告一声。

**起手页的第一条引用**：仓根有 `src/index.ts` 且里面有 `export const name`，就钉那一行
（**行号是现找的，不写死**）；找不到就不钉，改成写一段「第一条引用怎么钉」——
**硬塞一条钉不住的引用，等于开局就给读者一条红的**。

**模板假设的仓形状**：站住仓根下的 `docs-site/`，被钉的代码在仓根（引用写 `../src/…`）。
换一种形状——站叫别的名字、代码在 `packages/` 下——`livedoc.config.mjs` 里的相对路径就得
跟着改。那是模板的前提，不是可有可无的巧合。

## 两条从实跑里换来的

**一、`format-fumadocs` 不许进 `serverExternalPackages`。** 它的 `/pre` 是客户端组件，
跟着站一起打包才是同一个 React。外置它的现象是构建期报 `ERR_PACKAGE_IMPORT_NOT_DEFINED`
（`#prehydration/...` 找不到，指着 `@base-ui/react` 里的文件）——**报错完全不指根因**，
会把人引去查 base-ui 的版本，而那儿根本没问题。`core` 与 `project` 要外置：它们读盘、调 git。

**二、turbopack 的 `root` 那行只有 `link:` 到站外的包才需要。** 从 registry 装的站不用，
照着别的示例站抄会抄进来一条没用的配置。

# 参考站

livedoc 自己那个仓（`@godcreator02/live-doc-*` 几个包所在的工作区）下的 `docs-site/`
是这套机制最全的示例站：五类引用全用上、README 与 AGENTS 挂 `outputs` 当生成物、
星轨盘接在一条独立的整页路由上。写不准的时候去那儿找同类的页照着抄结构。
