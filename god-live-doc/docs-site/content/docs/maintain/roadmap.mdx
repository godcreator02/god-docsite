# 待定与路线图

这一章回答：哪些地方跟方案不完全一样、为什么，哪些问题知道但没解决，下一步打算做什么。

**这一章不钉代码**——它讲的是「还没成为代码的东西」，钉了反而假。frontmatter 里写着 `livedoc: none`，
站测试按这个态度放行。

## 一、跟方案有出入的地方

方案里没定、这一版按「最保守」选了的，逐条记在这儿备查。

<Tabs>
  <Tab title="命名与产物">
    - **记录的类型名叫 `MemoRecord`**，不叫 `Record`——后者是 TS 内置的映射型别，撞名。清单项上的字段名还是 `record`。
    - **构建产物是 `.mjs` / `.d.mts`**（tsdown 的默认），`exports` 直接指过去，没去折腾扩展名。
  </Tab>
  <Tab title="发布与依赖">
    - 六个包**没写 `private`**，但也**没配发布流程**——能发，没发。真要发之前得先想清楚版本策略。
    - **`format-fumadocs` 把 `fumadocs-ui` / `react` 放进了 devDependencies**，只为编译和类型检查；
      `tsdown` 的 `deps.neverBundle` 守着它们不进产物。消费方最好装**同一个版本**，
      否则 pnpm 会摆出两份副本，React 的上下文可能对不上。
  </Tab>
  <Tab title="路径与渲染">
    - **没有「代码根」这个配置项**：引用路径一律相对项目根。所以这个站引工作区源码时写的是 `../packages/…`，
      标题栏上也就这么显示。要更好看得先给配置加一项，那是接口变更。
    - **`renderHuman` 没有实现**：fumadocs 那份人看的就是站本身，md / html 也没有第二种人看的形态。
      接口上留着这个口。
    - **`livedocMarkdownOptions` 的回调形参声明成 `unknown`**：fumadocs 那头要求的是完整 mdast 型别，
      这个包只认树上的几个字段，形参放宽才对得上它的签名。
  </Tab>
  <Tab title="判定与状态">
    - **hash 记忆的「有变动」没有 diff、没有旧内容、也定位不了**（记忆里只有段哈希）：报「位置不明」，行号停在旧位置，
      站上那一块不摆代码只留一句提示。想要 diff 就得存一份段文本，那是「仓里不存第二份内容」的反面，不做。
    - **记忆按文件位置分派**（默认 `auto`）：任何 git 仓里已提交的走 git（本仓外仓一样，脏了照样拒），
      被忽略的、不在仓里的走 hash。**文件改名不追**，改了名就是 `file-missing`，重钉。**绝对路径不认**；
      仓外路径（`../../别的单元/…`）在别的机器上会红，机器相关的路径该留在本地配置——那就是「代码根 / 命名根」，
      跟上面那条一起定。
    - **缺失的引用也走整篇拒**：`confirm` 时 snapshot 交回 problem，整篇不写。想确认就先把引用改对或删掉。
    - **红只有三种理由**：`vanished`、`file-missing`、`blob-missing`。方案草稿里提过的 `stale-pin`
      没有实现——它想说的情况（记录跟内容对不上）现在归到「报黄让人复核」里，宁可多问一句，不新造一种红。
  </Tab>
</Tabs>

## 二、写这个站时新踩出来的两条

这两条是这套机制**用自己写自己**才会撞上的，代码没问题，但得知道：

- **有些源码段不能钉**，因为它们的内容会撞站测试的断言。两处实例：`blocks.ts` 里造 diff 块那段，
  源码里带着 shiki 的增删标记，投影进 AI 那份会撞「AI 那份不该带 diff 标记」；名册默认表那段，
  注释里带着尖括号包住的组件名，会撞「组件没被名册压平」。绕法是钉邻近的另一段，正文照说不误。
- **记录簿不能钉自己**。`.ledger.json` 里每条记录都带着确认时的 commit，每跑一次 `confirm` 就会改写，
  钉上去就是一个永远收敛不了的不动点。所以 [命令行](/docs/cli/cli) 那一章的记录簿样例是普通围栏，不是引用。

这两条都不打算「修」——它们是自指带来的，不是缺陷。真要治，得让站测试的断言只看引用块之外的内容，
代价比收益大。

## 三、三条开放问题

方案第十节列的三条，原样还在，都不阻塞第一里程碑：

1. **`remarkInclude` 排在插件前**，所以被引入的片段里的引用，`check` 看不到（站上能渲染，因为那时片段已经并进来了）。
   两边口径不一致，暂时靠「别在被引入的片段里写引用」躲过去。
2. **行内组件规则只能交回行内节点，没有机制守**。规则作者在行内位置交回一个块级节点，
   序列化出来的 md 会是坏的。`helpers.inline` 告诉了规则「这处是行内」，但没人检查它交回了什么。
3. **记录簿一个 json 在并发构建下的写入时机**。站构建时几十个 loader 并发跑，靠 `save` 的
   「没变不写」躲过去——`check` 和站构建都不写记录簿，只有 `confirm` 写，而 `confirm` 是单线程逐篇跑的。
   哪天要支持并发确认，这条得重做。

## 四、下一步：目录型与存在性引用

第一里程碑只做**文件型引用**（文件 + 行段）。接下来两种，接口已经给它们留了位子：

<Tabs>
  <Tab title="存在性引用 exists">
    只断言「这个东西还在」，不展示内容。比如文档里说「配置项 `comparator` 在 `ProjectConfig` 里」，
    引的是「那个符号存在」这件事，不是某几行。它没有展示区，状态只有在 / 不在两种。
  </Tab>
  <Tab title="目录型引用 tree">
    引的是一个目录的形状：`packages/` 下有哪六个包、`content/docs/` 下有哪几篇。
    展示的是一棵树，判定是「树变了没有」。
  </Tab>
</Tabs>

留的位子有两处：**草稿记号的动作词**现在只认 `ref`，`exists` 和 `tree` 是给这两种留的；
**目标类型**现在只有文件加行段一种，加 `kind` 之后由比较器按 `kind` 分派。

设计上有一条已经想清楚：**记录还是带 `kind` 的那一套**，新种类的引用各自出各自的记录格式，
老记录一律不猜。别的（目录树怎么哈希、存在性怎么在没有语言服务的情况下判）等真做的时候再定，
先改方案正本那份草稿，再改代码——顺序见 [维护者手册](/docs/maintain/maintainers)。

## 五、老仓退役

老仓（git 记忆那条线的出处）的退役条件是：**除目录型、存在性引用之外，功能面对齐**。
对齐之后它就不再是参考，代码只看这一份。
