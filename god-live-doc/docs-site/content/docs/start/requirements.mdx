# 需求

这一章回答：文档里的代码为什么会烂掉，这套机制承诺治哪一段，又明确不治哪一段。

## 腐化的本质：手抄的副本不会跟着正本变

文档里贴一段代码，那一刻它是对的。三个月后函数改了名、参数多了一个、整个函数被删掉——文档里那段还在，
一个字没动，读的人照着它写，编译不过。

问题不在人懒。问题在**副本没有身份**：那段文字跟源码之间没有任何连接，谁也说不出「它引的是哪个文件哪几行」，
自然也没人能在代码改动时把它揪出来。

这套机制的做法是把副本换成**引用**：文档只写「我说的是某文件某几行」，代码在构建那一刻现拿。
文档里不存代码的副本，记忆只有一条指纹。

## 三条需求

<Tabs>
  <Tab title="① 文档能引真代码">
    作者写一行记号声明目标，站上那一块的内容从工作区的源文件里现拿——不是粘贴，不是快照。
  </Tab>
  <Tab title="② 代码变了看得出">
    每处引用都有状态。代码改了、段没了、文件没了，状态就变色，命令行也报得出来。
  </Tab>
  <Tab title="③ 人确认后才算数">
    工具不判对错，只报「变了」。改得对不对是作者的事，作者跑一次确认，这段新内容才成为新的记忆。
  </Tab>
</Tabs>

`extra` 是格式包自留的私货（展示区在哪、是不是草稿记号），核心原样带回、不看内容——这是核心不认识任何格式的那道口子。

## 确认下来的是一条指纹，不是一份副本

{/* ref file="../packages/core/src/types.ts" lines="27-34" */}

记录里没有代码内容，只有「那几行当时长什么样」的指纹，外加一个 `kind` 说明这条记录是哪个比较器记的。
git 比较器记的是 HEAD 里那个 blob——内容本来就在 git 的对象库里，仓里不必存第二份。
细节见 [git 原理](/docs/principles/git)。

<Note>
  **状态只有四种**：新鲜、有变动、缺失、未确认。「有变动」不是错，它是「等作者复核」，命令行退 0；
  只有「缺失」才退 1。四种状态怎么判出来的，见 [状态与比较器](/docs/principles/comparator)。
</Note>

## 明确不做的

- **目录型、存在性引用不做**。第一里程碑只有文件型。接口给它们留了位子（草稿记号的动作词 `ref` 之外还有
  `exists`、`tree`，目标类型也留了扩展的口），现在一律不实现。见 [待定与路线图](/docs/maintain/roadmap)。
- **不自动修复**。代码改了，工具报黄，等人来看；它不会替你把文档里的话改对。
- **不猜作者意图**。换了比较器，旧记录一律当「未确认」重新确认，不试图翻译；行映射跟内容对不上时报黄让人复核，
  不把红判成绿。
- **不做全文正则**。记号靠语法树或逐行扫认，写在围栏里、句子里的同样文字一律不算。见 [记号](/docs/principles/markers)。

另外四个：

| 词 | 意思 |
| --- | --- |
| 草稿记号 | 作者手写的那一行，四种格式一个写法：`@@livedoc ref 文件:起-止 @@` |
| 正式记号 | 确认时格式包换上的形态，各格式各长各的 |
| 格式包 | 一种文档格式一个包：认记号、写回记号、（可选）渲染 |
| 比较器 | 「记忆怎么记、变没变怎么判」全收在这个接口里 |
| 名册 | 组件在给 AI 读的那份 md 里怎么压平的一张表 |
