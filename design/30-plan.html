docsite 开发方案

2026-10-12 重写。这一版取代原先的「分步改造计划」与「ZCode 编排」两页（已删，历史在 git 里：快照提交 07704c2）。范围只有 docsite 自己；docfirst 与协作站以后各自另立方案，本页不排它们的步骤。

一、目标与范围

做好 docsite 自己：基础包 @godcreator/docsite-kit（站点骨架、集合接线、UI 外壳）、身份、评论、一次性建站、gwb-docsite 插件、自述站。开发对象就是 packages/ 与 site/ 里的正式代码。

二、工作流程（定死的规矩）

  • 直接写正式代码。packages/ 与 site/ 是工作对象，不做「先搭验证站、再收编」的两段式。
  • 探针（probes/）只在遇到不知道上游会怎么表现的问题时写。写之前说清要判什么、有哪几种可能；判完留 result.md。本来就该是正式代码的东西，不进探针。
  • 每完成一段就收口：改到的包 pnpm check 绿、自述站过一遍对应场景、AGENTS 与文档同步、提交一笔。每笔提交自成一体、可单独回退。
  • 测试一律 Vitest（真实文件、真实 dev/build，不 mock 文件系统）。
前几轮的教训：把「本来就该是正式代码」的功能先做成了探针与验证站，多出两段搬运与三套并存。从这版起，探针只留给「不知道上游行为」这一类问题。

三、技术底座（已定，不再重查）

3.1 运行环境

  • vite 8.3.4 + 仓内补丁（patches/vite@8.3.4.patch，记录在 AGENTS.md）：Windows 上 import.meta.glob 相对 base 的「运行中新增文件不进集合」缺陷已从根源修掉，Vite 原生 HMR 链路可用。升级 vite 前先跑 probes/2610121018_vite-add-discovery 的测试看上游修没修。
  • 版本基线（与官方 react-router 模板一致）：fumadocs-core / @fumadocs/base-ui 16.17.1、fumadocs-mdx 15.4.7、react / react-dom 19.3、react-router 8.4.0、tailwindcss 4.3.3。现站还在 16.16.2 / 15.4.4，第一步升齐。

3.2 用到的 fumadocs 原生能力（扩展点清单）

能力怎么用
集合定义source.config.ts 的 Config API：docs 与 comments 都定义成 async 集合；评论集合与页面集合同一编译链
双端生成物.source/server（服务端 loader()）与 .source/browser（客户端 createClientLoader / useContent）：按需正文、评论异步 chunk 都靠它
评论即 MDX 集合一个评论串一个文件夹：index.mdx 串头 + 回复 mdx + 同目录 tsx / 图片附件；评论里能写组件，渲染走集合编译，不做运行时编译器
React Router 框架模式loader 只交本页元数据（评论只交路径/作者/时间，不交正文）；action 承接写意图；8.4 自带文档 POST 的 Origin 核对，站点再做一道显式同源校验
页面树loader 里 serializePageTree；界面用 @fumadocs/base-ui 组件，不自造侧栏树
索引 target 选项PluginOptions.index.target（'vite' 默认 / 'default' 静态枚举）是文档未写的 B 类公开项。有 vite 补丁在，用默认 'vite' 形态；将来若撤补丁，可切 'default' 自保（N 线实测过两种）

五、清理清单（随步骤处理）

#对象处置
1packages/docsite-comments（K 时代形态）删。它 13 处依赖身份包，违反「评论不依赖身份」契约；其中的浏览器定位算法（comment-anchors、diff 定位、快照推算）拆借进收编后的模型/UI
2本体一体化旧实现（server/comments.ts、ui/comments.tsx、people.ts、page-sources.ts 等）被新包替代后删：一个事实一个正本，不留三套并存
3pageListRefresh 插件（vite/index.ts）它存在的主要理由（「目录增删新页 404」）已被 vite 补丁消除：删掉目录增删强刷那半截，跑自述站验证原生链路（probe 与自述站实测：补丁下新增 1 秒内被发现）；「改 TSX 页面树标题不更新」那半截单独验证后再定去留
4双源 MDX 校验评论提交校验与 mdx-problems 各自维护一份编译配置，宿主集合一改就漂移：收敛为单一来源（先查 fumadocs-mdx 有没有公开的「按集合配置编译单文件」入口；没有就保留一处、两处互指说明风险）
5自述站升 16.17.1 / 15.4.7，迁到新包格局（不再由一体化本体提供评论与身份）
6两处 compile(body) / mdx-problems 的默认配置随 #4 一并收敛

六、步骤（每步直接写正式代码，完成即提交）

步做什么验收

七、已否决的做法（别走回头路）

  • 运行时 MDX 编译器渲染评论（K 线）：评论走集合编译链，评论里能写组件本来就是集合的能力。
  • 评论包依赖身份包（K 线）：身份校验在站点 action 组合，模型包零身份概念。
  • 手工对抗 HMR（强刷、自建失效链、mtime 触碰、删除过滤器）：vite 缺陷已修，原生链路可用。
  • 「先写探针/验证站，再收编正式代码」的开发顺序：直接写正式代码，探针只判上游未知行为。
