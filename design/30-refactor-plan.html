分步改造计划

先做一个覆盖 docsite-kit 现有功能与计划新增功能的完整验证站，再收进正式基础包、迁自述站、切换实际托管，最后接入 docfirst 和协作站。第一步覆盖完整功能，内部仍按小段逐项交付。

派工、纠偏和定时续跑先读 ZCode 编排与续跑方案，实际会话状态以其台账为准。

2026-10-11。现有能力以 site/content/(kit)/ 和包、插件导出为准；新增范围来自下方 K/P 清单。依据：接口审计、集合与热更新复核、Markdown 复核。

当前实施：按Fumadocs原生机制重写。保留功能和数据，旧代码仅作行为基线；不把旧机制搬进新包，也不另造运行时MDX编译链。正文与评论遵守M2，身份和评论由站点组合，标志采用K-06覆盖层。旧K停止扩展，新会话N先在独立目录完成一个原生评论读写小段；当前边界。1.1的基础接线证据保留，其余功能不得据此冒充已验收。

第一步的总验收

  • 功能清单每条都记录“现有行为、目标行为、样本、接口依据、验收证据、状态”；状态分未开始、实现中、通过、未通过。计划淘汰的旧机制也必须写明能力的去向。
  • 真实浏览器检查正文、交互、站内导航、搜索、评论与面板；SSR 200、截图或单元测试中的任意一项，不能单独证明整条链通过。
  • MDX/TSX/HTML、评论与 JSON 的修改、删除、重新新增、改名按适用情况分别测；清单、路由、页面和索引一致。自动刷新是否丢状态必须有记录，评论草稿与 JSON 更新要求保留输入。
  • 三种页面、资源、评论与 feeds 在 dev 和 build/start 下的行为分别检查；快照和只读应符合已声明的契约，仍在运行时读本机文件的地方不能隐藏在“构建通过”里。
  • 人员/评论文件错误、MDX 编译错误、无身份和错误请求来源等失败路径可解释；服务重启后状态正确。配套插件只在隔离 home 验，停止本轮启动的进程。
  • 有未通过项就不把第一步标完成。功能验证通过后，正式打包、安装、迁站和实际托管切换仍需第 2、3 步各自验收。

接口边界与停止条件

新增接点注明官方来源及是否公开、弃用或实验性；不把“有导出”写成“稳定”。优先采用已文档化接口和自有标记，避免 Fumadocs 私有缓存、React 元素内部结构，以及未经说明的 DOM 假设。

遇到必须升级依赖、修改上游或操作底层运行器缓存才能继续的情况，保留最小失败复现，先列替代方案与代价，不顺带扩成跨仓重写。每小段做完先交付证据，再进入下一段；1.1 已交付，后续粗纲不自动变成派单。

当前仍未解决的缺口：内容/评论增删后的清单与浏览器更新、JSON 重新新增、稳定评论取字和侧栏组标识。已通过的 Config API 与 Markdown 样本可复用；它们不代表上表全部功能已经验收。

0. 源头机制

下面五条是设计的起点。后面每条改动都出自其中一条；「什么地方不能放什么」「什么模式只读」这类限制不单独定规则，都在 0.2 里从机制推出来。

编号机制说明
M1数据都是本机仓目录里的文件，写就是改文件正文、评论（连同评论文件夹里的 .tsx、图片）、日志、任务记录、人员列表、gwb 推给站点的数据都是文件；没有数据库，也没有只存在站点进程里的数据
M2文件到页面只有一个编译器：Vite 加 fumadocs-mdx正文、评论、日志、评论里的 .tsx 是 fumadocs-mdx 的集合；任务记录、推送数据这类 JSON 由 Vite 的 import.meta.glob 读进来。编译器有两种运行方式：跟着文件变（dev），或把某一刻的文件编译成一份固定的产物（build，叫快照；start 只送出这份快照）
M3身份是这台电脑上 gwb 的主人身份码在 gwb 设置里，一个 gwb home 一个；仓里的 people.json 写明码属于谁；gwb 启动站点进程时把码交给它，进程做的每次写入都记在这个人名下。agent 经同一接口写，用 as 声明自己是人员列表里标了 agent: true 的哪一个
M4每种内容的 Markdown 形式，在定义它的地方给出插件生成的节点（钉码）在插件里用 replaceSource 登记；作者写的组件（讲解组件、示意图）在组件里用 fumadocs 的 asMarkdown() 给出。搜索、llms、生成正本都经同一个编译器取
M5站点生成一次，之后归站点自己；库只是库库只导出组件、remark 插件、服务端函数和类型；路由、配置、组件表由站点自己写，在 fumadocs 原有的位置引用库（原则一、四）

0.1 由机制定下的做法

  • 插件按集合在编译期配置（M2、M5）：首选在 source.config.ts 通过 Config API 定义各集合的 mdxOptions，按需用 applyMdxPreset；运行时分别使用生成的 server/browser 入口。全局配置仍可承载共同插件。第 1 步把这条已通过小样本的路线整理成站点样板。
  • 钉码写法：<Pin file lines hash blob /> 和 <PinTree dir depth glob hash />，编译成 <PinBlock> 包一个普通 code 节点、<PinTreeBlock> 包 fumadocs 的 Files。
  • 评论照旧是集合（M1、M2）：评论文件夹里的 MDX、.tsx、图片都由编译器编译，示意图、动画想写多复杂都行。
  • 推送改成写文件（M1、M2）：gwb 把要给站点的数据写成站点目录下的 JSON 文件；站点在 *.server.ts 里用 import.meta.glob 读，只在路由的 loader 里调用。
  • 生成正本经编译器（M4）：用集合条目的 getText('processed', { components }) 取每页的 Markdown 形式写到落点，名册与 renderAi 删掉。
  • 任务记录照推送的写法读（M2，第 5 步）：collab/records/*.json 也由 *.server.ts 里的 import.meta.glob 读。

0.2 推出来的结果（不是另定的规则）

结果出自为什么
写完马上看到，只在 dev 下成立M2快照看不见拍完以后写进来的文件。快照站上的内容随 git 同步、重新 build 后出现，和正文一样
发布出去的站只读M2、M3发布的是快照，gwb 启动它时不给身份码；进程不知道把写入记在谁名下，就不写。代码里不判断运行模式

写接口核对请求来源（Origin）M3同上：本机浏览器里打开的别的网页也能向本机端口提交表单，要拒绝
