原则

一、站点生成一次，之后归站点自己

新建站点就是照模板生成一份 fumadocs + React Router 项目，和 create-fumadocs-app 一样。生成以后，站点里的每个文件都由站点自己维护、想怎么改就怎么改。基础包升级不负责让站点自动跟上，站点要用新功能就自己改代码。

二、站点固定依赖版本，旧站一直能运行

站点的 package.json 写明它用的每个库的版本，站点按这些版本运行。基础包、docfirst 发了新版，没升级的站点照旧运行，不会因为别人升级而坏掉。库的版本号照 gwb-release 的规矩：破坏站点用法的改动只随 x 升级，并附升级说明，站点要升级时由 agent 照说明改站点代码。

三、照 fumadocs 的框架和扩展点做，不另造机制

页面来源用 loader()，内容编译用 fumadocs-mdx 的 source.config.ts，组件表用 mdx-components，布局用 DocsLayout 和它的配置项，搜索用 createFromSource。需要的能力 fumadocs 已经有扩展点，就用那个扩展点；没有的，先回头问这个需求是否真的需要，再决定怎么做。

四、基础包、docfirst 的站点部分都是普通的库

像 fumadocs-openapi、fumadocs-typescript 那样：只导出组件、remark / rehype 插件、服务端函数、Vite 配置用的函数和类型。不导出路由模块，不往站点里写文件，不反过来读站点里的模块。路由文件由站点自己写，在 loader / action 里调用库的函数。

五、前端和后端按 React Router 框架模式原样分开

loader、action、资源路由是后端，组件是前端；两边只经 loader 的返回值和 action 的请求来往，返回值和请求的类型由库导出。不另起一个后端服务。

六、gwb 插件和站点之间只经写明的约定来往，并且向后兼容

gwb 插件会升级，站点不一定跟着升级（原则二），所以插件碰站点的每一处都是要守住的约定：启动站点时交给它的参数、调用的站点接口、读写的站点文件（人员列表、评论）的格式。这些约定写成文档、带版本号；插件升级后仍要能托管和读写按旧约定运行的站点。确实要改约定时，插件认出站点是旧约定，就明确报错说明站点要升级到哪一版，不按新约定硬读。凡是要按站点版本的规则做的检查（比如编译 MDX、核对评论格式），用站点自己装的那一版库来做。

七、能不能写只看身份

站点服务端拿到本机的身份码、并且在人员列表里认得出这个人，就能写评论；认不出就只读。和运行的是开发服务还是构建后的服务无关。

八、docfirst 的核心不依赖站点的代码，钉码的写法可以重新设计

钉码判定、记号、confirm、轨迹卡校验只对着仓库的文件工作，在命令行里运行。站点上显示钉码状态、生成正本，都属于站点一侧：docfirst 的站点库调用核心的公开函数，生成正本经站点的编译器取每页的 Markdown 形式（见改造计划 M4）；核心里不出现任何为站点写的东西。钉码现有的记号写法、记录存放方式、红黄绿的口径都不当作需求，需求里只写要做到什么，写法和这次重写一起重新设计。

九、错了就报错

只在系统边界校验：读文件、读配置、收请求、起子进程。校验不过就拒绝并说清楚错在哪，不替调用方修正、不静默跳过。

依赖方向

箭头指向被依赖的一方。站点在最上面，只有站点同时依赖多个库；库之间只沿箭头单向依赖。

  • docfirst 站点库依赖基础包，只用基础包公开导出的组件和类型；基础包不知道 docfirst。
  • gwb-docsite 依赖基础包的评论数据格式与读写函数、人员列表格式；不依赖任何站点的代码。
  • docfirst 核心只依赖 code-pin；code-pin 不依赖任何人。

站点怎么引用这些库

全部走 fumadocs 项目本来就有的位置，站点自己写，库只提供被引用的东西。

以 docfirst 站为例，站点自己的 source.config.ts 大致是这样，接哪些插件、接在哪一区都由站点写明：

import { defineConfig, defineDocs } from 'fumadocs-mdx/config'
import { remarkMath } from '@godcreator/docsite-kit/mdx'
import { remarkPinnedCode, remarkCardLinks } from '@godcreator/docfirst-site/mdx'

export const docs = defineDocs({ dir: 'content' })
export const cards = defineDocs({ dir: 'trajectory' })

export default defineConfig({
  mdxOptions: { remarkPlugins: [remarkMath, remarkPinnedCode, remarkCardLinks] },
})

示例里的导出名只是示意，真正的名字在逐章设计里定。

待定

  1. 通用正文组件归哪。术语标注、讲解组件（不含跟名册绑定的那部分）、文件树、Tabs、占满整个窗口的页面，推荐归基础包，docfirst 只留钉码显示和轨迹卡。
  2. agent 写评论要不要站点在运行。现在插件经站点的接口写，站点必须在运行。按原则五，写评论本来就是站点服务端的 action，插件调用它是正常做法（调用方式属于原则六的约定）；要改成不运行也能写，就得在插件里另做一份渲染页面算快照的逻辑。推荐维持经站点写，只把请求的类型由基础包导出、两边共用。
  3. 生成正本能不能用组件。已定：能。生成正本经站点的编译器渲染，组件自己给出 Markdown 形式（改造计划 M4、D-02）。
  4. gwb-docsite 托管开发服务还是构建后的服务。按原则七，能不能写已经和这件事无关，剩下的只是改了内容要不要即时看到。
