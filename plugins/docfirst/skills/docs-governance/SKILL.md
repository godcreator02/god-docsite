# 文档与注释治理

**总原则是分三层**（正本在各仓 AGENTS）：AGENTS 只写硬约束；文档站写「为什么」；注释只写现状。下面四类
操作都是把放错层的东西放回去——小到一个模块只做第一类，大到整仓或全部 gwb 仓，就按后面的治理循环逐仓做。

## 一：代码自解释扫描

**一个文件读一遍，四件事同时做**：注释怎么处理、名字够不够清楚、函数该不该拆、有没有设计思路要移进文档。
分几轮扫会让同一批文件被读好几遍，而读代码是这整件事里最花时间的一步。

范围一次一个模块，不要全仓一次做完——改动越大，「没改行为」越难证明。

### 注释只有三个去处

读到一条注释，只有三个去处：

**移到文档**：讲为什么这么切、否掉了什么、边界在哪、这个取舍的代价是什么。这些是设计思路，属于文档，
不属于代码。移走之后**文档必须钉回这段代码**，否则只是把漂移换了个地方发生。

**删掉**：复述代码在做什么的（`// 遍历列表` 下面跟着一个 for）、写着「原来是 xx 现在是 yy」的、为某次调试写的、
注释掉的旧代码。历史归轨迹卡，git 也记得住，代码里留着只会误导人。

**留下**：真正的现状约束——不变式、外部契约（那个 API 会返回 null）、以前出过的问题（这里不能用 map，
会吞掉 undefined）、以及为什么这段看起来笨的写法是必要的。留下的写成一行，只写现状。

判据一句话：**删掉这条注释，读者会做出错误的判断吗？**会就留下或移走，不会就删。

### 移到哪一页

- 模块怎么切、依赖往哪个方向、接口的语义与边界 → **讲这个模块的现状页**
- 一次选择、否掉了什么候选、判据是什么 → **轨迹卡**（choice 形态，一个结论一张）
- 怎么用、命令与配置 → **用法页**
- 一个词在这个仓里的确切含义 → **术语表**

每页写到哪为止，正本在 `docfirst-docs` 的「现状区怎么写」。

顺手订正碰到的过期注释（报错文本还说旧的情况、文件头注释还写着已经去掉的机制）——它们跟「写历史」一样误导人，
只是方向相反。

### 命名

**长度无所谓，清楚才重要。**最要避免的是看起来简洁、其实说不清自己是什么的名字。一个名字至少要回答
「它是什么 / 它做什么 / 什么时候用它」之一。

- 变量：`d` → `daysSinceLastConfirm`
- 函数：`check()` → `checkPlacementsAgainstDisk()`
- 布尔：写出它为真时的含义，`ok` → `everyPinIsFresh`
- 集合：复数加上装的是什么，`items` → `driftedReferences`

改名不顺手改逻辑。这是两次改动，混在一起就没人能复核。

### 拆函数

**拆到每个函数的名字就能说明它做什么。**一个函数里出现「这一段在做 X」这类注释，那一段就该是一个叫 `X` 的函数。
拆完之后原来的注释自然就没有了——不是删掉的，是名字已经说明了。

判据：读函数体时需要在脑子里给某几行起个名字，就把那个名字变成真的函数。嵌套超过两层、或者一个函数要滚屏才看完，
通常是拆得不够。但不要为拆而拆：**只在能起出一个准确的名字时才拆**，起不出名字说明那几行还不构成一个概念。

### 怎么证明没改行为

**测试改前通过，改后也通过，测试本身一个字不改。**这是唯一的证据。测试要改，说明你改的不只是形状。
没有测试的模块，先补测试再重构——补测试时按现在的行为写，不按你以为的行为写。

分两个提交：**文档改动**（移进去的页与钉码，过文档检查）与**代码改动**（精简、改名、拆函数，过测试）——
它们的验收方式不同，出问题时也要分别回退。

## 二：术语统一

把黑话从现状文档里去掉，换成正常的中文说法：

- 单字的简称逐句换：件→插件、井→窗格容器（第一次出现时注明 well / 代码模块名）、口→端口/入口/张、
  格→窗格、档→布局文件、照片→快照、门→入口、皮→皮肤、刀→第 X 阶段、枚→个
- **不机械替换**：「文件 / 事件 / 条件 / 接口 / 六件事 / 口径」是正常词；「格」按意思分别处理
  （窗格实例 / 数据目录 / 记录字段→「那个字段」）
- 不动：命令名、包名、代码标识符、模块名（`well-hub`）；界面上的原文用引号括起来（代码没改时文档跟着代码写）
- 术语表的「不再使用的词」一节收录旧词对照；**这次改名本身写一张轨迹卡**（名字定了就别再改——改名是历史）；
  扫描时别漏了「枚」这类量词

## 三：把历史清出现状页

现状页只写现状。规则与一句话的理由留下；带日期的经过、改名的经过、事故经过、版本演进史删掉——
轨迹区已有对应卡的直接删（正本在卡里），确实有长期参考价值又没有卡收录的才新建一张卡。记录踩坑教训的页
（症状与判据）本身不动，只换术语。轨迹区只增不改，旧卡里的旧词与失效的站内链接是历史原貌，不改。

## 四：每仓只写自己实现的东西

判据（正本在各仓的轨迹卡 docs-ownership-split）：

1. **归属**：谁实现谁写正本
2. **行为由实现方写，契约由定契约的一方写**：接口两端各写各的一半，不算复述
3. **边界声明是自己的**：「内核一条原生命令都没有」这类否定句留在本仓，不在后面附指路
4. **跨仓的内容钉不了码**：没有钉码又讲别的仓机制的段落，对方一改不会变黄——这些是最可能已经过时的地方

教程与手册（写插件手册这一类）可以引用、加一句概括、指路，不复述完整定义；专门讲边界的整页
（比如两个插件之间的边界页）可以这么写。

## 治理循环（整仓以上时用）

1. **先冻结写入、对齐范围**：做三类扫描（黑话的字符模式，包括「枚」；日期与版本号；讲别的仓机制的关键词），
   列出判据与方案，问清范围、幅度、判据，等用户同意
2. 对照表放总控台 `out/`（临时工作文件，gitignore；长期正本放各仓的术语表与轨迹卡）
3. **先在最小的仓上做一遍**，交给用户确认写法，再做其余的仓
4. 同类任务（比如逐仓替换术语）派子代理并行，派任务时写明：先读该仓 AGENTS、对照表、做样板的那个仓；
   需要逐处判断的自己做
5. 每仓的验证顺序：`pnpm doc` → `confirm`（写回挪了位置的钉码、重新渲染生成正本）→ 逐条复核黄灯、
   `confirm <页> --accept` → 再跑一次确认全绿 → 仓根门禁 → `git add` 精确路径 + `git commit --only`
6. **复核时不信子代理的回报**：用 rg 重新扫（黑话模式 + 白名单）、核对轨迹卡只增没改、并行会话中途新提交的内容
   要重扫（别人会写进新的黑话）
7. 收尾时看一遍各仓 `content/future/inbox/`；别人正在处理的红灯黄灯点名说出来，不替人处理

## 做过之后才知道的问题

漏掉「枚」字｜字段意思的「格」≠窗格意思的「格」｜精简注释会让下游钉码的行号整体移动，要跑一次 `confirm`
写回｜各仓的 render 脚本名不一样（读该仓的 scripts，有 `doc:render` 也有直接调 `docfirst render`；
`doc` 脚本有的在仓根、有的在 docs-site）｜AGENTS / README / SKILL 是生成物，只改正本｜「行为不变」的注释
提交也要改前改后都通过测试｜改完顺手订正碰到的过期事实（比如已经删掉的命令还被文档引用）｜并行会话在同一个仓
活跃时，别人未提交的改动不看、不收、不回退
