# 按模块并行，不要一路做到底

**反例**：派一个子代理从 A 模块改到 B 模块，再回头写全部文档，最后自己跑门禁。它把一件本来能并行的事做成了
串行，而且没有任何一步是可复核的——你只能全收或全丢。

**正确的做法**分三步：

1. **主会话先把接口定下来**，做成一个提交。类型声明、方法签名、谁依赖谁，都在这个提交里。
2. **一个模块交给一个子代理，并行做**。每一路只动自己那个模块的代码与**它自己的文档页**。
3. **收尾归主会话**：跨模块的页、门禁、确认、提交、轨迹卡。

## 切不开就是接口没定下来

想派活时发现两路会改同一批文件，不要硬拆——这说明设计有问题：接口还在变，或者模块边界画错了。
回去把接口定下来再派。这条判据比任何拆分技巧都有用，它把「协作困难」翻译成了「设计问题」。

同理，一个模块的文档页说不清它不依赖什么，通常也是代码切错了。

## 派活时必须写明的四样

- **只动哪几个文件**，逐个列出来。别写「相关文件」。
- **不提交、不跑确认、不跑门禁、不跑构建**。改完回报，收尾时统一跑。
- **不许碰的**：别的会话正在改的文件、别人还没复核的黄灯，逐个点名。
- **这一轮的事实**：这次改了什么、接口长什么样、行号在哪。子代理不该自己去猜刚发生过什么。

## 钉码用草稿记号

`docfirst confirm` 会顺带重新渲染所有生成正本，那几份生成物是全仓共用的——几路同时确认就会互相覆盖。
所以：**并行的每一路只写草稿记号**（写法见 `docfirst-docs` 的「五类引用各钉哪种话」，行号自己数准），
**主会话收尾时统一确认一次**，点名那几页。这正是草稿记号存在的理由：作者不维护记录，工具来记。

## 哪些东西归主会话

跨模块的总索引、用法页、生成正本（README / AGENTS / SKILL.md 的 mdx 源）、在途 spec 页、轨迹卡、
全量门禁、确认、提交。这些东西**不属于任何一个模块**，谁写都会跟别人冲突，所以归主会话。

## 复核，不要只听回报

子代理回报「跑绿了」不等于绿了。收尾时主会话自己跑一次门禁、自己看一眼产物。派出去的活越多，
这条越要紧——并行省下的时间会被一次没复核的返工全部抵消。

## 什么必须串行

**必须串行的只有三样**，它们是全局共用的，谁写都会影响别人：共享配置文件（站配置、包清单、锁文件）、
生成正本的生成物（确认与渲染会写的那几份）、全量门禁。

**除此之外，判断冲突看文件，不看轮次。**文件不重叠就照常并行，主会话也不例外——「先等这一轮收完再派下一轮」
是把文件冲突误当成了时间冲突，白白把并行做成串行。

隔离程度按这三档选，够用就好：

- 文件不重叠、也不碰上面三样 → **同一个工作树里并行就够**。
- 要碰站配置、要跑确认、或者想各跑各的门禁 → **每一路一个 worktree**。
- 动全仓的改造（改名、批量格式化）→ **不能并行**，独占这个仓。

**跨仓派活时 worktree 要自己建。**宿主的 worktree 隔离参数按**主会话所在的仓**建：在 A 仓派人去 B 仓干活，
它建到 A 仓去了，等于没隔离。跨仓就自己 `git worktree add`，派活时把工作目录写明。

**spec 一件活一页。**一页装多件活会人为造出冲突——两路都要改那一页；「做完删页」的意思也跟着说不清了。
