# 路线图

**本页回答**：这套东西分几个阶段、现在在哪一个、哪些问题知道但还没解决。

## 阶段

| 阶段 | 目标 | 完成的标志 |
| --- | --- | --- |
| 一 | 机制立起来 | 五类引用齐、`check` / `confirm` / `render` 三条命令齐，站自己用它写自己 |
| 二 | 能装到别的仓 | 包发本机 registry，`livedoc attach` 一条命令把六区装到一个已有骨架上，工作台件把命令行开给 agent |
| 三 | 嵌进写代码的循环 | 待重写页能被列出来、反馈能从别的仓投进来、`confirm` 能按页限定，改哪几页就确认哪几页 |
| 四 | 别的仓真在用 | 至少三个仓的门禁里挂着 `livedoc check`，投来的反馈进得了 `feedback/inbound` |

## 当前阶段

第三阶段。`livedoc attach`、随包发的两份 skill、工作台件的待重写页与反馈两条命令、`confirm` 的
按页限定都已经在；六区文档站的形状刚在这个仓自己身上立起来，还没在别的仓上验过第二遍。

阶段切换时：把新阶段写在这儿，落一张 [轨迹卡](/trajectory)，顺手复审
[明确不做](/future/not-doing) 的每一条还成不成立。

## 知道但没解决的

1. **`remarkInclude` 排在插件前**，所以被引入的片段里的引用，`check` 看不到（站上能渲染，因为那时
   片段已经并进来了）。两边口径不一致，靠「别在被引入的片段里写引用」躲过去。
2. **行内组件规则只能交回行内节点，没有机制守**。规则作者在行内位置交回一个块级节点，序列化出来的
   md 会是坏的。`helpers.inline` 告诉了规则「这处是行内」，但没人检查它交回了什么。
3. **记录簿一个 json 在并发构建下的写入时机**。站构建时几十个 loader 并发跑，靠 `save` 的
   「没变不写」躲过去——`check` 和站构建都不写记录簿，只有 `confirm` 写，而 `confirm` 是单线程逐篇跑的。

## 自指带来的两条

这两条是这套机制**用自己写自己**才会撞上的，代码没问题，但得知道：

- **有些源码段不能钉**，因为它们的内容会撞站测试的断言。两处实例：造 diff 块那段源码里带着 shiki 的
  增删标记，投影进机读版会撞「机读版不该带 diff 标记」；名册默认表那段注释里带着尖括号包住的组件名，
  会撞「组件没被名册压平」。绕法是钉邻近的另一段，正文照说不误。
- **记录簿不能钉自己**。`.ledger.json` 里每条记录都带着确认时的 commit，每跑一次 `confirm` 就会改写，
  钉上去就是一个永远收敛不了的不动点。

这两条都不打算「修」——它们是自指带来的，不是缺陷。真要治，得让站测试的断言只看引用块之外的内容，
代价比收益大。
