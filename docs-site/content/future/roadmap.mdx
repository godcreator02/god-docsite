# 路线图

**本页回答**：这套东西分几个阶段、现在在哪一个、哪些问题知道但还没解决、还欠着哪些活。

## 阶段

| 阶段 | 目标 | 完成的标志 |
| --- | --- | --- |
| 一 | 机制立起来 | 五类引用齐、`check` / `confirm` / `render` 三条命令齐，站自己用它写自己 |
| 二 | 能装到别的仓 | 包能从 npm 源装上，工作台插件一条 `docfirst.attach` 把各区装到刚生成的骨架上，说明书随插件注册给 agent |
| 三 | 嵌进写代码的循环 | 待重写的页能列出来、反馈能投进目标仓、改代码的那个提交里当场处理它引起的黄灯 |
| 四 | 别的仓真在用 | 至少三个仓的门禁里跑着 `docfirst check`，跨仓反馈真的在各仓站的 `future/inbox/` 里被处理掉 |

## 当前阶段

第三阶段收尾。[重设计](/future/spec/redesign-2026-09) 的代码与本站迁移已经做完：记录写在记号上、
确认不要求先提交、`check` 把本仓未提交改动引起的黄灯算红、`confirm` 分成机械写回与点名页 `--accept`、
分区按约定、生成正本按原文渲染、装配改铺三个区。还差发版，以及别的站迁到新结构。

第四阶段的前提大体已有：机器上已经有十几个站接了 docfirst。

阶段切换时：把新阶段写在这儿，写一张 [轨迹卡](/trajectory)，同时复审
[明确不做](/future/not-doing) 的每一条还成不成立。

## 知道但没解决的

1. **装配不核对要覆盖的文件是不是骨架原样。** `docfirst.attach` 只检查站里有没有 docfirst 配置、`content/` 下
   有没有骨架之外的内容；`content/` 以外跟模板同名的文件（根布局、`source.config.ts` 这类）被人改过也照样覆盖，
   只在回执的 `replaced` 里列出来。要核对，得拿到站点插件那份骨架模板的原样来比，需要站点插件配合提供，还没做。
2. **`remarkInclude` 排在 docfirst 的插件前面**，所以被引入的片段里的引用，`check` 看不到（站上能渲染，因为那时
   片段已经并进来了）。两边口径不一致，靠「别在被引入的片段里写引用」避开。
3. **行内组件规则只能交回行内节点，没有机制检查**。规则作者在行内位置交回一个块级节点，机读版序列化出来的
   md 会是坏的。规则知道「这处是行内」，但没人检查它交回了什么。
4. **取不到确认时的内容就少了 diff。** 记号上的 blob 名是确认时在进程里算的：确认之后、提交之前又改了文件，
   或者仓里按 CRLF 存，这个 blob 就不在对象库里，核对只能在整个文件里按指纹找，找不到报「位置不明」、不给 diff。
   这是有意的降级，记在这儿是为了碰到时知道原因。

## 自指带来的一条

这一条是这套机制**用自己写自己**才会碰到的，代码没问题，但得知道：

- **有些源码段不能钉**，因为它们的内容会触发站测试的断言。两处实例：造 diff 块那段源码里带着 shiki 的
  增删标记，投影进机读版会触发「机读版不该带 diff 标记」；名册默认表那段注释里带着尖括号包住的组件名，
  会触发「组件没被名册转换」。绕法是钉邻近的另一段，正文照常写。

不打算「修」——真要治，得让站测试的断言只看引用块之外的内容，代价比收益大。

## 欠着的活

- **别的站迁到新结构**：在各站目录跑 `docfirst migrate-ledger` 把旧记录簿迁进记号，把 spec / feedback / outputs
  三个旧区挪进 `future/` 与现状区，改配置与路由；经各仓站的 `future/inbox/` 通知。各站迁完后，`migrate-ledger`
  在下一个版本删掉。
- **装配防覆盖**：跟站点插件商定怎么拿到骨架原样（见上面第 1 条），两边一起改。
- **`/docs/principles/git`（取旧内容的原理）与 `/docs/cli/testing`（测试与边界）还是单独的页**，
  等内容复核完再决定是否并进对应的模块页。
