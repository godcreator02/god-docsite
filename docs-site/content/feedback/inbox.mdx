# 投来的反馈

**本页回答**：别的仓在用 docfirst 的过程中投来了什么意见。一条一节，处理完删——周转区不是档案，
定下来的判据落轨迹卡。本仓自己反复做的操作候选在 [hatch](/feedback/hatch)。

## 2026-09-11 `docfirst confirm --help` 不打帮助，直接就跑了

来源：总控台（做块笔记那一轮里撞上的）

想看 `confirm` 收哪些参数，敲 `pnpm exec docfirst confirm --help`——它没有打帮助，直接执行了
confirm。`--help` 是「我先问问」的标准手势，一条**会改文件**的命令把它当「照常跑」，等于把最谨慎
的一问变成最直接的一动。

**建议**：参数解析里先认 `--help` / `-h`，认到就打用法然后 exit 0，任何副作用不做；顺带，无参调用
也该打用法而不是照默认跑。

## 2026-09-11 `docfirst render` 把行内代码的收尾反引号转义成 `&#x60;`，而 check 抓不住

来源：块笔记仓（把两个件的 SKILL.md 改成从 mdx 生成时撞到）

mdx 源里正常的行内代码，render 摆出来的 md 把**倒数第二个行内代码的收尾反引号**转成 HTML 实体，
代码从此闭合不上，后面整句塌进代码里。触发条件（试出来的）：一个行内代码，后面隔着标点或空格
跟着一段 `**加粗**`，而那段加粗以另一个行内代码开头。

**最麻烦的一点**：check 拿产物跟重新渲染的源比，转义是确定性的——源和产物带同一个实体，check 报 🟢。
产物已经坏了，门禁还是绿的；肉眼扫生成的 SKILL.md 才发现。

**建议**：修渲染那步的转义判据（大概在 mdast-util-to-markdown 层的 handlers / unsafe 表）；在那之前给
check 加条产物自检——「源里没有实体、产物里有」基本可断定是转义事故，报黄让人看一眼。块笔记那边已把
加粗挪前绕开。

## 2026-09-10 `livedoc` 无参调用抛堆栈，不打印用法

来源：端到端验证那一轮（scratchpad 里的临时站）

还没接过 livedoc 的站目录里跑 `livedoc`（无参），抛一整页 Node 堆栈，末行「没有 livedoc.config.mjs」——
读起来是「崩了」而不是「你该给个子命令」。对照 `livedoc attach --help` 写得很好。

**建议**：无参调用打印一页子命令清单，跟 `attach --help` 一个规格。（改名后现状待复核——`docfirst`
无参眼下会打一句「不认识的命令」并退出，堆栈是没有了，但用法页仍没有。）

## 2026-09-10 `docfirst render` 撞到带图片导入的页就整条崩

来源：26090614yey/block-note-fumadocs，改名升级那次

站里某页有五张 `![](/ux-study/*.jpg)`，render 渲到这页抛 `ERR_UNKNOWN_FILE_EXTENSION: ".jpg"`，
整条命令退非零，排在它之后的页全没渲。崩点在 fumadocs-mdx 15.3.1 的 Node loader（`import("fumadocs-mdx/node")`
那条路）。当时没挡事（崩的只是 gitignore 的调试产物），但换一个站，只要图片页排在 outputs 前面，
生成物就摆不出来。

**期望**：renderAi 遇到加载不了的资源导入时跳过那一页、记一条警告，别让一页毁掉整趟。

## 2026-09-12 草稿钉码两种写法被静默忽略——写的人以为钉了，check 却不响

来源：总控台（单元 `26090520ntn/console`，hello 仓 self-explaining 扫描给现状区长真身时撞上）

hello 站写 20 条草稿记号，`check` 只认出 9 条，**不认的那 11 条连一条报告都没有**——不是红了等确认，是当它们不存在。两种形态：

1. **连续两行记号**：mdx 把相邻行并成一个段落，`draftIn` 只认「段落恰好一个 text 子节点」，整块失配。改法是每条记号前后留空行（已照做），但更根本的是：这种段落在 check 里报一条「第 N 行像记号但没认出」，别静默吞掉。
2. **路径含双下划线**：`@@docfirst ref ../py/gwb_hello_py/__main__.py:1-5 @@` 独占段落也没用——markdown 把 `__main__` 解析成强调节点，段落 children 不止一个 text，`draftIn` 返回 null。同理报一条比静默好；或者记号语法文档里写明这条路走不通、建议换钉同论断的别的文件。

判定建议就一句：**解析器遇到「差一点就是记号」的段落时告警**，别让「写钉码」这个动作本身有不会响的失败形态——静默不识别跟「不会响的闹钟」是同一种病。

## 2026-09-13 `docfirst confirm --help` 不显示帮助，直接执行了全量 confirm

来源：总控台（单元 `26090520ntn/console`，件仓 self-explaining 扫描那轮撞上）

想看 confirm 的用法说明，跑 `pnpm doc:confirm --help`——它没显示帮助，**把全站钉码直接确认了一遍**。CLI 似乎只认位置参数，`--help` 被当成了页路径之外的什么。风险：本想查用法的人替全站签了字，恰好当时有别人的未提交黄钉，侥幸被「confirm 只对已提交内容做」挡住才没替人确认。绕法：按页限定要写 `docfirst confirm content/docs/xxx.mdx`。建议：认得 `-h/--help` 并打印用法；全量 confirm 或许还该在没有显式参数时要求一个确认或 `--all`。
