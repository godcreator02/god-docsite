# 投来的反馈

**本页回答**：别的仓在用 docfirst 的过程中投来了什么意见。一条一节，处理完删——周转区不是档案，
定下来的判据落轨迹卡。本仓自己反复做的操作候选在 [hatch](/feedback/hatch)。

## 2026-09-11 `docfirst confirm --help` 不打帮助，直接就跑了

来源：总控台（做块笔记那一轮里撞上的）

想看 `confirm` 收哪些参数，敲 `pnpm exec docfirst confirm --help`——它没有打帮助，直接执行了
confirm。`--help` 是「我先问问」的标准手势，一条**会改文件**的命令把它当「照常跑」，等于把最谨慎
的一问变成最直接的一动。

**建议**：参数解析里先认 `--help` / `-h`，认到就打用法然后 exit 0，任何副作用不做；顺带，无参调用
也该打用法而不是照默认跑。

## 2026-09-11 `docfirst render` 把行内代码的收尾反引号转义成 `&#x60;`，而 check 抓不住

来源：块笔记仓（把两个件的 SKILL.md 改成从 mdx 生成时撞到）

mdx 源里正常的行内代码，render 摆出来的 md 把**倒数第二个行内代码的收尾反引号**转成 HTML 实体，
代码从此闭合不上，后面整句塌进代码里。触发条件（试出来的）：一个行内代码，后面隔着标点或空格
跟着一段 `**加粗**`，而那段加粗以另一个行内代码开头。

**最麻烦的一点**：check 拿产物跟重新渲染的源比，转义是确定性的——源和产物带同一个实体，check 报 🟢。
产物已经坏了，门禁还是绿的；肉眼扫生成的 SKILL.md 才发现。

**建议**：修渲染那步的转义判据（大概在 mdast-util-to-markdown 层的 handlers / unsafe 表）；在那之前给
check 加条产物自检——「源里没有实体、产物里有」基本可断定是转义事故，报黄让人看一眼。块笔记那边已把
加粗挪前绕开。

## 2026-09-10 `livedoc` 无参调用抛堆栈，不打印用法

来源：端到端验证那一轮（scratchpad 里的临时站）

还没接过 livedoc 的站目录里跑 `livedoc`（无参），抛一整页 Node 堆栈，末行「没有 livedoc.config.mjs」——
读起来是「崩了」而不是「你该给个子命令」。对照 `livedoc attach --help` 写得很好。

**建议**：无参调用打印一页子命令清单，跟 `attach --help` 一个规格。（改名后现状待复核——`docfirst`
无参眼下会打一句「不认识的命令」并退出，堆栈是没有了，但用法页仍没有。）

## 2026-09-10 `docfirst render` 撞到带图片导入的页就整条崩

来源：26090614yey/block-note-fumadocs，改名升级那次

站里某页有五张 `![](/ux-study/*.jpg)`，render 渲到这页抛 `ERR_UNKNOWN_FILE_EXTENSION: ".jpg"`，
整条命令退非零，排在它之后的页全没渲。崩点在 fumadocs-mdx 15.3.1 的 Node loader（`import("fumadocs-mdx/node")`
那条路）。当时没挡事（崩的只是 gitignore 的调试产物），但换一个站，只要图片页排在 outputs 前面，
生成物就摆不出来。

**期望**：renderAi 遇到加载不了的资源导入时跳过那一页、记一条警告，别让一页毁掉整趟。

## 2026-09-12 草稿钉码两种写法被静默忽略——写的人以为钉了，check 却不响

来源：总控台（单元 `26090520ntn/console`，hello 仓 self-explaining 扫描给现状区长真身时撞上）

hello 站写 20 条草稿记号，`check` 只认出 9 条，**不认的那 11 条连一条报告都没有**——不是红了等确认，是当它们不存在。两种形态：

1. **连续两行记号**：mdx 把相邻行并成一个段落，`draftIn` 只认「段落恰好一个 text 子节点」，整块失配。改法是每条记号前后留空行（已照做），但更根本的是：这种段落在 check 里报一条「第 N 行像记号但没认出」，别静默吞掉。
2. **路径含双下划线**：`@@docfirst ref ../py/gwb_hello_py/__main__.py:1-5 @@` 独占段落也没用——markdown 把 `__main__` 解析成强调节点，段落 children 不止一个 text，`draftIn` 返回 null。同理报一条比静默好；或者记号语法文档里写明这条路走不通、建议换钉同论断的别的文件。

判定建议就一句：**解析器遇到「差一点就是记号」的段落时告警**，别让「写钉码」这个动作本身有不会响的失败形态——静默不识别跟「不会响的闹钟」是同一种病。

## 2026-09-13 `docfirst confirm --help` 不显示帮助，直接执行了全量 confirm

来源：总控台（单元 `26090520ntn/console`，件仓 self-explaining 扫描那轮撞上）

想看 confirm 的用法说明，跑 `pnpm doc:confirm --help`——它没显示帮助，**把全站钉码直接确认了一遍**。CLI 似乎只认位置参数，`--help` 被当成了页路径之外的什么。风险：本想查用法的人替全站签了字，恰好当时有别人的未提交黄钉，侥幸被「confirm 只对已提交内容做」挡住才没替人确认。绕法：按页限定要写 `docfirst confirm content/docs/xxx.mdx`。建议：认得 `-h/--help` 并打印用法；全量 confirm 或许还该在没有显式参数时要求一个确认或 `--all`。

## 2026-09-24 建站模板没写页面元数据，浏览器标签页没有标题

来源：总控台（单元 00000-console），2026-09-24 给文档站加站点标题的 claude 会话。

机器上 20 个 docfirst 文档站的根布局都没有 `metadata`，各区页面也没有 `generateMetadata`，浏览器标签页一律没有标题（`document.title` 是空串），
几个站同时开着分不清哪个是哪个。根源在建站模板：docfirst 装六区时写的根布局 `packages/gwb-docfirst-workflow/template/attach/src/app/layout.tsx.tpl` 没有 `metadata`，六个区的页面模板没有 `generateMetadata`（本仓自己的站 `docs-site/` 也缺）。

内核仓、devkit 仓、界面插件仓的站已经各自补上，可以照着改（例：`gwb-devkit/docs-site/src/app/layout.tsx` 与 `src/app/docs/[[...slug]]/page.tsx`，提交 3ab1193）：

- 根布局加 `export const metadata: Metadata = { title: { default: '<站名>', template: '%s | <站名>' } }`，站名与侧栏 `nav.title` 用同一个
- 每个区的 `[[...slug]]/page.tsx` 加 `generateMetadata`：和页面本身一样 `getPage(slug)`、找不到就 `notFound()`，返回 `{ title: page.data.title, description: page.data.description }`
- 没有 `getPage` 的整页路由（比如轨迹区的星轨盘）写一句静态的 `export const metadata = { title: '轨迹' }`

期望：模板带上这几处，之后新建的站自带标题；已经建好的站由各仓自己补。

## 2026-09-25 用到的插件写 peer：从 dev 挪到 peer，gwb.requires 已删

来源：gwb-devkit（devkit 仓交接页「插件之间的运行时要求写 peer」，总控台会话），2026-09-25。插件管理 0.9.0、devkit 0.18.15 起生效，源上现在是插件管理 0.11.0、devkit 0.19.1。

插件运行时用到的别的插件，从 devDependencies 挪到 peerDependencies，范围写 `^x.y.z`，下限写开发、验证时用的那一版；同一个仓里的插件写 `workspace:^`，发版时换成 `^<版本号>`。「用到」指：经 `ctx.inject` 用它的服务、经命令总线 `@godcreator/gwb-commands` 登记命令、用外壳 `@godcreator/gwb-shell` 注册窗格或样式令牌、import 它的类型。只用 `ctx.inject([...], fn)` 局部注入、缺了只少一部分功能的，在 `peerDependenciesMeta` 里标 `optional: true`；只按命令名调它的命令的不用写。写进 peer 的插件不再另写 dev：插件仓里 pnpm 会把 peer 装进 `node_modules`，类型从那里取。

- peer 里只许三类：按值 import 的 `cordis`、内核包 `@godcreator/gwb-kernel-desktop`、别的插件（清单 `keywords` 含 `gwb-plugin`）。库、接口定义包、构建工具照旧写 dev 或 `dependencies`
- 清单字段 `gwb.requires` 已删：插件管理不再报它，发版检查也不再查
- 发版检查（devkit 0.18.15 起）：peer 里每个 `@godcreator` 插件的范围要是 `^x.y.z`，并且和源上 `latest` 在同一条线（0.x 比次版本号，≥1 比主版本号），不在同一条线就拒；peer 里有这三类以外的包也拒
- home 里关掉了 pnpm 自动补装 peer：插件管理、`devkit.home.new`、`devkit.dev` 在 home 里运行 pnpm 时都带环境变量 `pnpm_config_auto_install_peers=false`。peer 里的插件 home 里没装，不会被顺带装上，由 `plugin-manager.list` 每个包的 `unmetPeers`（`{ pkg, range, installed? }`）报出来，只报告、不拦加载；在隔离 home 里验证时，peer 里的插件要自己装上
- 升级一个插件时，peer 写了它的插件会被 pnpm 装进新目录，插件管理在同一次升级里把它们一起重新加载（回执里的 `dependents`）

本仓要改的：

- `@godcreator/gwb-docfirst-workflow` 的 peer 已经写了命令总线与说明书（说明书标了 `optional: true`），符合上面的写法；只剩 dev 里重复写的命令总线、说明书两项删掉

随适配内核 0.6 那一轮一起改、一起发，版本号照说明书 `gwb-release` 升。规矩正本是 devkit 文档站的规则页「用到的插件写 peer」与说明书 `gwb-release`（`run skill.read {"name":"gwb-release"}`）。

## 2026-09-25 要跟内核 0.7：gwb-docfirst-workflow 的 peer 里内核包改成 ^0.7.0

来源：gwb-kernel（内核仓 `D:\unitfolders\igldu-gwbkernel\gwb-kernel`），提交 `6ab4ed8`，2026-09-25；总控台会话代投。

内核包 `@godcreator/gwb-kernel-desktop` 马上从 0.6.2 发 0.7.0，这是破坏性版本：内核服务删掉了 `gwbKernel.launcherVersion`，home 里的 `runtime.json` 删掉了 `appDir`（内核仓轨迹卡 `2026-09-25-drop-launcher-version`）。此前 0.6.1、0.6.2 还给页面加了导航锁（内核仓 `docs-site/content/docs/seams/ipc.mdx` 的「页面保证」）：

- 页面的主框架只能是内核的 `index.html`：不带 `target` 的链接点击、拖进窗口的链接一律拒绝，页面上没有任何反应
- `window.open(url)` 与 `target="_blank"` 的链接不再开新窗口：`http:`、`https:` 地址交给系统默认浏览器打开，别的协议（`file:`、`javascript:`、`data:`、自定义协议）拒绝
- 页面经 `window.gwb.command` 调命令，只接收顶层框架发来的；iframe 里调用拿到的是 `ok: false` 的回执

本仓的情况：

- `@godcreator/gwb-docfirst-workflow`（`packages/gwb-docfirst-workflow/package.json`）：peer 第 40 行、dev 第 52 行写的都是 `^0.6.0`，不包含 0.7.0
- `launcherVersion`、`appDir`：没有用到
- 插件本身没有页面。`packages/docfirst-trajectory/src/react.tsx` 第 343 行有 `window.open(…, "_blank", "noopener")`（星轨盘点节点开卡页），那是文档站里的组件，不跑在工作台页面上；站被文档站插件的窗格用 iframe 显示时，这一下会交给系统浏览器打开，不用改

要做的：

1. 内核 0.7.0 发布后，在装了 0.7.0 的隔离 home 里验一遍插件，再把 peer 里内核包的范围改成 `^0.7.0`（dev 里那份跟着改），版本号照说明书 `gwb-release` 升，然后发版
2. 不改的后果：`plugin-manager.list` 会把插件标成 `kernelUntested`；`devkit.release` 发版前检查要求 peer 里内核包的范围包含运行中的内核，不改就拒发。运行时照常：删掉的两个字段本仓没有用到
