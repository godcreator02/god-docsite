## 仓布局

仓根 `docsite-kit/` 是 git 仓，同时是 pnpm 包工作区，住着地基、docfirst 工作流、协作站三族包；上一级的单元目录只有一张出生证 `unit.json`，不在 git 里。
布局照 devkit 的 workspace 仓：插件在 `plugins/`，不是插件的包在 `packages/`，再加上 `site/`（地基自述站，已收成骨架正本加最小示例）与 `docs-site/`（全仓文档站，本站）。

{/* ref file="../pnpm-workspace.yaml" lines="3-7" hash="2e977effc234" blob="1adc5d16d2cb" */}

三个插件：`plugins/docsite/` 是 `@godcreator/gwb-docsite`（身份码、一步建站、托管站点），`plugins/docfirst/` 是
`@godcreator/gwb-docfirst-workflow`（[docfirst 建站命令](/docfirst)与说明书），`plugins/collab/` 是 `@godcreator/gwb-collab`
（协作站的提交审核、通知、任务命令，规矩见 [collab 分区](/collab/plugin)）。协作站的三个包 `collab-model`、`collab-site`、
`collab-merge-check` 对基础包的依赖暂钉在 `^0.1.x`（组合包 0.3.0 出口重排，适配是 gitea 上 collab-site 仓的 issue #4），
适配完成前从源装旧版。`packages/` 下每个目录一个 npm 包：

{/* tree dir="../packages" depth="1" hash="409ee0a2b4ff" */}

**地基**（`docsite-*`）是文档站基础包的能力包与组合包，互不相识（唯一的组合在 `docsite-kit`），谁都不认识 docfirst。
docfirst 侧：通用包不认识 docfirst，谁都能单独使用：[钉码核心](/docfirst/pin) `code-pin`、[星轨盘](/docfirst/trajectory) `trajectory-disk`；
docfirst 自己的包有三个：`docfirst-workflow` 是[命令行与项目](/docfirst/workflow)，接到 fumadocs 站上的部分在它的子入口 `./fumadocs`；
`docsite-docfirst` 是文档站基础包 `@godcreator/docsite-kit` 的功能包，构建页面时用 `./fumadocs` 里的 remark 插件，另给 `Term` 与文件树组件、
星轨盘与卡页两条路由（两样见[站点接入](/docfirst/fumadocs)）；[讲解组件包](/docfirst/explainer) `docfirst-explainer` 是 docfirst 站上用的讲解组件，只有站用。
谁能依赖谁见[测试与边界](/maintain/testing)，搬进本仓的选型见轨迹卡 [gwb-docfirst 并入 docsite-kit](/trajectory/2026-10-12-merge-into-docsite-kit)。

两个站都是工作区成员，用 `workspace:*` 装工作区里的包，钉的都是工作区里的实际源码，所以仓里不另留示例项目：
`site/` 是**骨架的正本**（地基插件建站的模板从它派生，内容只剩最小示例与评论定位回归页）；本站是**全仓的文档站**——
地基、docfirst、协作站三族与 Gitea 部署都在这里讲（2026-10-13 自述站的说明与协作站的文档站并入，协作站的 Next 站已删），
要建 docfirst 站的照它看，`docsite-docfirst` 的模板起始物以它为参照。

站的 `app/`、`vite.config.ts`、`react-router.config.ts`、`source.config.ts`、`tsconfig.json`、`.gitignore` 与自述站的骨架同代（评论、
三种页面来源都是当前这一版），是手写的正本——地基升级骨架时对照 `site/` 改过来；站自己维护的还有 `content/`、`trajectory/`（轨迹卡）、
`src/components/`（站内组件）、`src/glossary.mjs`（术语表）、`docfirst.config.mjs`、`people.json`（评论署名用的人员列表）、`tests/` 与 `package.json`。

站的内容在 `docs-site/content/` 下，`meta.json` 写站名，每个目录是侧栏下拉框里的一组：`future/` 是未来区，其余目录都是现状区，
按能力分成 `docs/`（总览与原理）、`docsite/`（地基）、`docfirst/`（docfirst 的包与插件）、`collab/`（协作站的包与插件）、
`gitea/`（部署侧）与 `maintain/`（就是这一区，给改这个仓的人看）。轨迹卡不在 `content/` 里，在 `docfirst.config.mjs` 的
`trajectory` 指的站点根下 `trajectory/`——三族的卡并在一处。
站的 `src/components/` 下讲解组件的源码也算现状区，组件里照源码抄来的数据由引用钉在源码上，跟页面一起由 `docfirst check` 核对。

## 提交规矩

- 一个提交一件事。提交信息用中文。
- 同一个仓常有别的会话在改：新文件用 `git add <自己的路径…>`，提交一律 `git commit --only <自己的路径…>`。
- **代码、文档、轨迹卡放进同一个提交**。改了被钉的代码，本仓未提交改动引起的黄灯 `docfirst check` 算红
  （见[门禁](/docfirst/pin/gate)）：`docfirst confirm` 做机械写回，剩下的黄灯逐条复核，论断还成立就
  `docfirst confirm <页…> --accept` 点名确认。步骤照说明书 [docs-site](/docs/outputs/skills/docs-site)。
- 改生成物的正本（仓根 README、CLAUDE，插件里的 SKILL.md）后 `pnpm docfirst render`，正本与生成物同一个提交。

## 发布

`packages/` 下的包与两个插件都用工作台命令 `devkit.release` 发布。升哪一位、发版的每一步、发完怎么升级 default，
每次都先读说明书「gwb-release」（经 gwb MCP 入口 `run skill.read {"name":"gwb-release"}`），这里不复述。
发到哪个源由各自 `package.json` 的 `publishConfig.registry` 决定。

包与插件各发各的，没有先后：插件对 `packages/` 下的包零依赖，由插件的 `tests/artifact.test.ts` 检查。
协作站那一族按依赖序发：`collab-model` → `collab-merge-check` → `collab-site` → `plugins/collab`。
唯一的联系是 `plugins/docfirst/src/deps.ts` 那张表：建站时交给地基建站器的功能包版本取自它，表里写精确号。
`docsite-docfirst` 升了版本号就同时改表，忘了改这条测试当场失败：

`docfirst.config.mjs` 与起始页齐全、`pnpm doc` 能跑。
