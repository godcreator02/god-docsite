## 仓布局

仓根 `gwb-docfirst/` 是 git 仓，同时是 pnpm 包工作区；上一级的单元目录只有一张出生证 `unit.json`，不在 git 里。
工作区照 devkit 的 workspace 仓布局：插件在 `plugins/`，不是插件的包在 `packages/`，再加上 `docs-site/` 这个站。

{/* ref file="../pnpm-workspace.yaml" lines="3-6" hash="9cdc5208b7e9" blob="efc915f8e1de" */}

`plugins/docfirst/` 是[工作台插件](/docs/plugin) `@godcreator/gwb-docfirst-workflow`：建站命令与说明书。
`packages/` 下每个目录一个 npm 包：

{/* tree dir="../packages" depth="1" hash="73efed32eb31" */}

通用包不认识 docfirst，谁都能单独使用：[钉码核心](/docs/pin) `code-pin`、[星轨盘](/docs/trajectory) `trajectory-disk`。
docfirst 自己的包有三个：`docfirst-workflow` 是[命令行与项目](/docs/workflow)，
接到 fumadocs 站上的部分在它的子入口 `./fumadocs`；`docfirst-site` 是文档站基础包 `@godcreator/docsite-kit` 的功能包，
构建页面时用 `./fumadocs` 里的 remark 插件，另给 `Term` 与文件树组件、星轨盘与卡页两条路由（两样见[站点接入](/docs/fumadocs)）；
[讲解组件包](/docs/docfirst-explainer) `docfirst-explainer` 是 docfirst 站上用的讲解组件，只有站用。谁能依赖谁见[测试与边界](/maintain/testing)。

站也是工作区成员：它用 `workspace:*` 装工作区里的包，钉的是工作区里的实际源码，所以仓里不另留示例项目。
devkit 的建仓模板不收文档站，这是本仓有意的例外，理由见轨迹卡
[插件挪到 plugins/docfirst](/trajectory/2026-09-25-plugin-to-plugins-dir)。

站建在基础包上。站目录里的 `app/`、`vite.config.ts`、`react-router.config.ts`、`source.config.ts`、`tsconfig.json`、`.gitignore`
由 gwb-docsite 的 `docsite.site.init` 照基础包与功能包的模板写出，不手改；站自己维护的是 `content/`、`trajectory/`（轨迹卡）、
`src/components/`（站内组件）、`src/glossary.mjs`（术语表）、`docfirst.config.mjs`、`people.json`（评论署名用的人员列表）、`tests/` 与 `package.json`。

站的内容在 `docs-site/content/` 下，`meta.json` 写站名，每个目录是侧栏下拉框里的一组：`future/` 是未来区，其余目录都是现状区，
`docs/` 讲原理，`maintain/` 就是这一区，给改这个仓的人看。轨迹卡不在 `content/` 里，在 `docfirst.config.mjs` 的 `trajectory` 指的站点根下 `trajectory/`。
站的 `src/components/` 下讲解组件的源码也算现状区，组件里照源码抄来的数据由引用钉在源码上，跟页面一起由 `docfirst check` 核对。

{/* tree dir="content" depth="1" hash="8980573388af" */}

仓根的 `tests/` 是工作区级测试，星轨盘测试用的卡片 fixture 在 `tests/fixtures/trajectory/`。

## 提交前要通过的检查

每处都有自己的命令，全部通过才提交：

<Tabs>
  <Tab title="仓根">
    `pnpm test`、`pnpm typecheck`、`pnpm build`。`build` 与 `typecheck` 按 `./plugins/*` 与 `./packages/*` 过滤，插件在其中；
    `test` 先构建，再用仓根的 vitest 配置只运行 `tests/` 下的测试，不包括插件自己的测试。

  </Tab>
  <Tab title="plugins/docfirst/">
    `pnpm check`、`pnpm build`。`check` 依次运行 typecheck、oxlint、vitest；`test` 跳过打了 `slow` 标签的测试，`test:all` 不跳。
  </Tab>
</Tabs>

## 提交规矩

- 一个提交一件事。提交信息用中文。
- 同一个仓常有别的会话在改：新文件用 `git add <自己的路径…>`，提交一律 `git commit --only <自己的路径…>`。
- **代码、文档、轨迹卡放进同一个提交**。改了被钉的代码，本仓未提交改动引起的黄灯 `docfirst check` 算红
  （见[门禁](/docs/pin/gate)）：`docfirst confirm` 做机械写回，剩下的黄灯逐条复核，论断还成立就
  `docfirst confirm <页…> --accept` 点名确认。步骤照说明书 [docs-site](/docs/outputs/skills/docs-site)。
- 改生成物的正本（README、AGENTS、CLAUDE、插件里的 SKILL.md）后 `pnpm docfirst render`，正本与生成物同一个提交。

## 发布

`packages/` 下的包与插件都用工作台命令 `devkit.release` 发布。升哪一位、发版的每一步、发完怎么升级 default，
每次都先读说明书「gwb-release」（经 gwb MCP 入口 `run skill.read {"name":"gwb-release"}`），这里不复述。
发到哪个源由各自 `package.json` 的 `publishConfig.registry` 决定。

包与插件各发各的，没有先后：插件对 `packages/` 下的包零依赖，由插件的 `tests/artifact.test.ts` 检查。
唯一的联系是 `plugins/docfirst/src/deps.ts` 那张表：建站时写进新站的依赖版本取自它，表里写精确号。
`docfirst-workflow` 升了版本号就同时改表，忘了改这条测试当场失败：

{/* ref file="../plugins/docfirst/tests/create.test.ts" lines="380-388" hash="aea19349e525" blob="a48282005ff2" */}

表改了之后插件要再发一版，之后新建的站才装到新包。

插件发布前，在隔离 home 里用 `docfirst.create` 与 `docfirst.create-plain` 各建一个站验证一遍（步骤在说明书「gwb-devkit」）。
改了托管，在隔离 home 里用一个假站（build 脚本写 `.next/BUILD_ID`、start 脚本起一个监听写死端口的 node 服务）把 `add`、`restart`、插件重新加载、杀掉进程、`remove` 各走一遍，
看端口与进程有没有残留，再打开窗格「文档站」截图。
改了官方脚手架的版本或本机约定，先在 `plugins/docfirst/` 里运行 `pnpm test:all`：多出的那条实际运行官方脚手架、
跟存下的样本逐份比较，要联网。
