## 依赖方向：只有一个文件在检查

pnpm 严格的 `node_modules` 只保证没写进依赖的包 import 不到；「该不该写进依赖」没人管，workflow 包里
`marker/`、`reference/`、`mdx/`、`code/`、`pinning/`、`project/`、`cards/`、`cli/`、`fumadocs/` 之间编译器也不拦——`mdx/` 里写一句 `import "../project/load.ts"` 不会报错，
mdx 格式从此就跟读盘、git 绑在一起。补上这两项的是 `tests/boundary.test.ts`，它是包之间、workflow 目录之间**唯一**的边界检查。

## 自成一体的包与通用包

本仓的包分两类。**通用包**不认识 docfirst：`code-pin` 把文字钉在代码上，`trajectory-disk` 把一组卡画成项目方向演变的圆盘；
docfirst 只是它们的一个使用者。**docfirst 的包**有三个：`docfirst-workflow` 是命令行、项目装配与格式；
`docsite-docfirst` 是文档站基础包的功能包，用 workflow 与星轨盘，不碰钉码核心与讲解组件，别的包都不依赖它；
`docfirst-explainer` 是 docfirst 站上用的讲解组件，只有站用，workflow、`docsite-docfirst` 与插件都不依赖它。
包发出去的只有 `dist` 与样式，唯一的例外是 `docsite-docfirst` 的 `template/`：那是基础包初始化时写进站点的轨迹卡集合定义，不是建站模板：

{/* ref file="../tests/boundary.test.ts" lines="582-596" hash="978fea3f085b" blob="da1acdb8b833" */}

两张表管两件事。**自成一体的包**（两个通用包加上 `docfirst-explainer`）各自单独安装、单独升版：
清单里没有任何 `@godcreator/` 包；源码与产物不 import 它们，源码的相对 import 不出自己的 `src/`。
**通用包**另外要求包目录里（源码、产物、样式、构建配置、清单）一个 docfirst 字样都没有，清单里指向本仓的仓地址除外：
仓名是 gwb-docfirst，那一行说的是包放在哪，不是包认识 docfirst。

## git 那一侧：用实际的 git 仓，不用替身

这一侧的行为几乎全看 git：blob 取不取得到、`diff -U0` 的 hunk 头长什么样、`status --porcelain` 列出哪些路径。
用替身测的是对 git 的假设，所以这几组都调用实际的 git：

- `tests/git-history.test.ts`：比较器接上 git 版旧内容来源之后的跟随、退回滑窗、取对象的次数
- `tests/reader-tree.test.ts`：目录树按 `.gitignore` 过滤、软链接按真实路径读
- `tests/cli-uncommitted.test.ts`：本仓未提交改动引起的黄灯算红（见[门禁](/docfirst/pin/gate)）
- `tests/hash-text.test.ts`：自己算的 blob 名跟 `git hash-object` 逐字节相同

`tests/repo.ts` 建的临时仓一律 `core.autocrlf=false`，否则 Windows 上的换行转换会让工作区和 blob 逐字节不同：

## 装配、摆放、命令行

装配的归一（内容根、`outputs` 的两种写法、文档身份）经 `loadProject` 看，在 `tests/project-load.test.ts`。
摆放用 `PlacingHost` 的两个适配器测：`tests/placing-host.test.ts` 写进内存里的一张表，一个字节都不写磁盘；
`tests/placement.test.ts` 在临时目录建实际的项目，`loadProject` 之后直接调摆放的方法，不经命令行。
命令行把结果打印成什么、返回什么退出码，在 `tests/cli*.test.ts` 那几份。

星轨盘与卡格式的测试是 `tests/trajectory-*.test.ts`：卡格式的解析、扫描、校验在 parse、scan、validate、model 几份，fumadocs 卡集合在 server，
建模、布局、画布、组件在其余几份；在内存里造卡时经真实的卡格式换成中性输入（`tests/trajectory-helpers.ts`），星轨盘相关的几份用 `tests/fixtures/trajectory/` 下的卡片。
所以星轨盘的测试离不开 workflow 的卡格式：包本身是通用的，它的测试还不是。术语标注在 `tests/glossary.test.ts`，
fumadocs 适配不接 Next 的那一半在 `tests/fumadocs.test.ts`，讲解组件包在 `tests/docfirst-explainer.test.ts`，
各包能装、能出产物、出口解析得到在 `tests/skeleton.test.ts`。

## 插件那组

除了一条慢测试，插件的测试只传入输入看输出，不启动进程、不打开窗口：建站参数与模板（`create.test.ts`）、本机约定怎么改官方脚手架的输出
（`scaffold.test.ts`，对照的是存在 `tests/fixtures` 下的样本）、端口选择（`ports.test.ts`）、产物与依赖（`artifact.test.ts`）。
实际运行官方脚手架的 `scaffold.slow.test.ts` 要联网，只在 `pnpm test:all` 里运行。插件怎么工作见[工作台插件](/docfirst)。
