title: 实时推送与执行器
description: Gitea 上一有事件，怎样经同一台 NAS 上的 ntfy 推到每个成员的工作台（组织级 webhook 的期望配置、ntfy 怎么开、插件收到消息怎么分）；执行器只管协作仓：按 main 上的工作流跑合并检查包、以 collab-bot 合并或打回
---

别人在 Gitea 上做的事，靠实时推送让每个成员的插件知道：

1. Gitea 组织级的 webhook 把事件发到 NAS 上 ntfy 的 topic `collab-<组织>`
2. 每个成员的插件对列表里全部项目的 topic 开着一条长连接（`organization/events/ntfy-subscription.ts`），断了隔一会儿重连，每次连上都对全部项目做一次完整刷新，补上没连着时的事
3. 插件的 `organization/events/` 认出消息说的是哪个仓、什么事，按仓分给协作仓那一套或别的仓那一套，只去 Gitea 取那一处

`collab.repo.setup`、`collab.repo.create` 配好负责人后，由调命令的人的插件往同一个 topic 直接发一条 `leads changed`，不经 webhook。插件那一侧各步做什么，见 [检查与实时推送](/gwb-collab/checks)。

## 消息只带位置

每条消息只说哪个仓出了什么事：标题是 `<组织>/<仓>`，正文是种类、动作、编号或分支，没有提交说明、作者、评论原文（ntfy 的 topic 校内谁都能读）。事实都由插件自己去 Gitea 取，所以 ntfy 不设令牌：消息被人伪造，只会让每台电脑多取一次，或者多做一次完整刷新，同一个项目最快每 10 秒一次。插件认得的就是这几种：

## webhook 的期望配置

每个协作组织一个组织级 webhook。它该是什么样写在插件里（`plugins/collab/src/organization/events/webhook.ts`）：组织管理员调 `collab.org.setup {repo}` 照它写进组织，组织管理员的插件每次完整刷新也照同一份核对，不对就在提示栏「协作仓」组里列「组织 `<组织>` 的 webhook 没按插件要的配」。不是组织管理员的插件读不到组织的 webhook（Gitea 回 403），不核对。不在 Gitea 网页上手配。

| 部分 | 期望值 |
| --- | --- |
| 类型、请求体 | `gitea`，`POST`，请求体 JSON（ntfy 的消息模板只认 JSON） |
| 地址 | `http://ntfy/collab-<组织>?template=yes&t=<标题模板>&m=<正文模板>`（两个模板经 URL 编码）：NAS 上 Gitea 和 ntfy 在同一个 compose 里，Gitea 按服务名 `ntfy` 访问它 |
| 标题模板 | `{{.repository.full_name}}`，也就是 `<组织>/<仓>` |
| 正文模板 | 依次判断：有 `.ref` 写 `push <ref>`；有 `.comment` 写 `comment <动作> #<编号>`；有 `.pull_request` 写 `pr <动作> #<编号>`；有 `.issue` 写 `issue <动作> #<编号>`；都没有写 `repo <动作>`。评论的请求体里也有 `.issue`，合并请求上的评论还带着 `.pull_request`，所以最先认评论；审阅的请求体里有 `.pull_request`、没有 `.comment`，写成 `pr reviewed #<编号>` |
| 事件（写入时的名字） | `push`、`pull_request_only`、`pull_request_sync`、`pull_request_review`、`pull_request_comment`、`issues_only`、`issue_comment`、`repository` |
| 事件（读回来的名字） | `push`、`pull_request`、`pull_request_sync`、`pull_request_review`、`pull_request_comment`、`issues`、`issue_comment`、`repository` |
| 其余 | 启用，分支过滤 `*` |

## leads changed

Gitea 换协作者不发 webhook，所以 `collab.repo.setup`、`collab.repo.create` 配好负责人后自己发一条：地址是 gwb-gitea 的设置 `push-url` 加上组织的 topic，标题 `<组织>/<仓>`，正文 `leads changed`。发不出去不算命令失败，回执的 `leadsChanged` 写明原因，别的成员要等下一次完整刷新才看到新负责人：

## 收到消息以后

全部项目共用一条订阅；一个组织的消息交给订了这个 topic 的项目。认不出的消息记一行警告，对那个组织的项目做一次完整刷新；认得出的先等 2 秒合成一批，再按仓分给两边：

| 消息 | 说的是协作仓 | 说的是别的仓 |
| --- | --- | --- |
| `push` | 取回协作仓，能快进就自动同步 | 只取回那个仓 |
| `pr`（含审阅）、`issue`、`comment` | 不处理：协作仓的合并请求由执行器定论，提交审核自己等结论 | 重读那个仓的合并请求与 issue |
| `leads changed` | 重读项目负责人，再核对协作仓的规矩 | 重读那个仓，再核对它的规矩 |
| `repo created` | 组织里新建了仓：克隆进项目文件夹，读一遍、核对一遍 | 同左 |
| `repo` 的其他动作（删仓等） | 只记一行，本机的目录不动 | 同左 |

别的仓的合并请求被审阅（批准、要求修改、评论）、合并请求上有了新评论，都推过来一条消息，插件重读那个仓：「要你改」「评论了」这两种通知收到消息就出现、就消失，不等下一次完整刷新。

### Gitea 不发 webhook 的事要等多久

审阅被撤销 Gitea 不发 webhook（1.27 的 `services/webhook/notifier.go` 只对批准、要求修改、评论三种审阅发），要等**那个仓下一次有别的消息**、或**下一次完整刷新**才重读：撤销了那条要求修改的审阅以后，「要你改」这条通知要等到那时才消失。完整刷新在插件连上推送、加项目、调 `collab.check`、收到认不出的消息时做。

## 要配的几处

- **Gitea 的 webhook**：每个协作组织由组织管理员调一次 `collab.org.setup`。插件期望的事件是上面表里那八个（读回来的名字）；组织里的 webhook 和它不一样时——比如换了一版期望多订事件的插件，组织里的 webhook 还少订审阅与合并请求上的评论——组织管理员的插件完整刷新时核对出来，在提示栏「协作仓」组出一条 `webhook-setup` 通知「组织 `<组织>` 的 webhook 没按插件要的配」，原因里写明少订了哪些事件；组织管理员再调一次 `collab.org.setup` 配好。Gitea 要放行内网地址（`ALLOWED_HOST_LIST`），这一项写在 NAS 配置仓的 teamhub 篇
- **ntfy**：NAS 上 teamhub 里和 Gitea 放在一起的服务，和 Gitea 一起启动、停止，经 Lucky 的 `ntfy.tianshen02.online:28377` 对外，访问范围和 Gitea 一样，在校园网里。只开 `collab-*` 这类 topic 的读写，不设令牌；消息模板在 webhook 的地址里，ntfy 这边不用另配。部署和配置写在 NAS 配置仓的 teamhub 篇
- **成员**：什么都不用配。插件订的地址是 gwb-gitea 的设置 `push-url`（和 `base-url` 存在一处，默认就是这一台），topic 按协作仓 `origin` 的主人算出来：

## 为什么要一个机器人账号

Gitea 每次运行会自动发一个令牌 `GITEA_TOKEN`，但 AGit 开的合并请求触发的任务里，它只能读仓本身：读合并请求、合并、留言全部 404，
组织设置是「宽松」、工作流里要了写权限也一样。所以合并要用一个真实账号的令牌，存成组织密钥 `COLLAB_BOT_TOKEN`，实测见轨迹卡
[自动发的令牌合并不了 AGit 合并请求](/trajectory/2026-09-30-actions-token-readonly-on-agit)。

这个账号是 `collab-bot`。它在每个组织里只进一个团队 `bots`：团队只含协作仓，代码、工单、合并请求三项可写，其余没有权限（见 [权限怎么配](/gitea/permissions) 的「团队」）。
工作流用 `pull_request_target` 触发，读的永远是 main 上那份，成员在合并请求里改工作流也拿不到密钥；工作流只有项目负责人能改，别人改了它的合并请求被打回。

## 执行器在哪

执行器是 NAS 上全站共用的一个：`teamhub` 里的 `gitea-runner` 容器，只登记了主机方式的标签 `nas`，部署写在 NAS 配置仓。新项目不用再装，一个新组织要配的密钥、团队、工作流见 [建项目与人员变动](/gitea/setup)。

## 成员电脑上看到的

成员的 gwb-collab 不合并：提交前在本机先查记录格式与站点（执行器不查这两样），推送前用和执行器同一个函数查只有负责人能改的内容，推送后等执行器的结论，被打回就把改动退回工作区；执行器合并之后，组织 webhook 经 ntfy 告诉每个成员的插件协作仓有新提交，插件等 2 秒合成一批，再取回协作仓、能快进就把本地 main 快进过去（见 [实时推送的部署](/gitea/push)）。每一步见 [提交审核与同步](/gwb-collab/submit)。

## 不做的事

- **不留开着等人的合并请求**：每个合并请求立刻合并或打回，理由见 [执行器当场定论，打回就退回工作区](/trajectory/2026-10-02-runner-decides-at-once)
- **不用 Gitea 自动发的令牌**：理由见上面「为什么要一个机器人账号」
- **执行器不挂载 `/var/run/docker.sock`**：只用主机方式，任务就在执行器自己的容器里运行，理由写在 NAS 配置仓的 `docs/services/compose/teamhub.md`
