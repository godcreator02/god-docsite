一个项目是 Gitea 上的一个私有组织，权限分四层，从粗到细：

1. **团队**：一个人进了哪个团队，就对团队里的仓有团队给的权限。这一层只管「能不能推分支、传 LFS 文件、开合并请求」，不管能不能改 main
2. **每个仓的协作者**：协作者就是这个仓的负责人，权限是「管理」。所有仓都一样，协作仓也一样；项目负责人就是协作仓的负责人
3. **每个仓 main 的分支保护**：别的仓的推送与合并只许负责人；协作仓谁都不能直接推，合并只许执行器所在的团队 `bots`
4. **仓的合并方式**：合并请求以什么方式进 main

团队由人在 Gitea 网页上配；后三层都由 `collab.repo.setup` 一次设好。插件联网用的是每个人自己的**令牌**，令牌勾了哪几项，决定插件能替他做哪些事。下面各节都拿 `hybrid-mmc` 当例子，先拿几个人各试一件事，看四层里是哪一层放行或拦下：

## 团队

组织页 → 设置 → 团队，点进一个团队改「权限」和「仓库」两栏。每个项目组织里有三个团队：

| 团队 | 放谁 | 管哪些仓 | 权限 | 在组织里建仓 |
| --- | --- | --- | --- | --- |
| `Owners` | 组织管理员 | 全部 | 所有者 | 能 |
| `members` | 全部成员 | 全部（「所有仓库」） | 代码、工单、合并请求可写；Wiki、发布、包、Actions、项目只读 | 能 |
| `bots` | 机器人账号 `collab-bot` | 只有协作仓 | 代码、工单、合并请求可写，其余无权限 | 不能 |

- **`Owners` 只是组织管理员**：它是 Gitea 每个组织自带、删不掉的团队，管加人、管团队、改组织设置，对每个仓都是管理员。它不出现在任何仓的设置里，也不担任何仓的负责人；组织管理员要负责哪个仓，就和别人一样加成那个仓的协作者
- **`members` 的代码给成可写**：成员要推自己的分支、传 LFS 文件（Gitea 上传 LFS 要写权限）、开合并请求，也要能建仓；能不能改 main 由分支保护决定。团队的描述写「全部成员：推自己的分支、开合并请求，由各仓的负责人合并」
- **`bots` 只给协作仓、只给三项**：执行器用它的令牌合并或打回合并请求；为什么一定要一个真实账号，见 [实时推送与执行器](/gitea/push) 的「为什么要一个机器人账号」

## 每个仓的协作者：负责人

仓 → 设置 → 协作者。一个仓的负责人就是它的协作者，权限是「管理」，可以几个人：

- **别的仓能合并、能直接推 main 的就是负责人**。别人照旧在 `members` 团队里有写权限，推自己的分支、开合并请求，等负责人审
- **协作仓的负责人也不直接改 main**：负责人和成员一样经 `collab.submit` 用 AGit 推成合并请求，由执行器检查后合并；负责人改只有负责人能改的内容，执行器查到作者是负责人就放行，见说明书 collab 的附件 [other-repos](/docs/outputs/skills/collab/other-repos)
- **负责人给「管理」**：负责人自己就能改这个仓的保护、加减共同负责人，不用找组织管理员
- **只认协作者**：Gitea 只让仓的管理员读分支保护，成员读到 403；协作者列表成员都读得到。插件读协作仓的协作者作为项目负责人交给网站；别的仓的合并请求、轮到负责人回的 issue，只提醒这个仓的协作者。不看 Gitea 回的「能不能合并」：`Owners` 里的组织管理员在每个仓都能合并，照那个算，他会收到所有仓的合并请求。合并检查、删别人的任务与模块、头像星标认的项目负责人，也是协作仓的协作者

## 每个仓 main 的分支保护

仓 → 设置 → 分支 → 保护规则 `main`。项目里每个仓的 main 都要有这条保护：

| 选项 | 协作仓 | 别的仓（资料库、代码仓） |
| --- | --- | --- |
| 推送 | 关掉（接口里 `enable_push` 为假）：谁都不能直接推，负责人也不能 | 限定人（网页上叫「启用推送白名单」）：负责人的用户名，不写团队 |
| 合并：限定人（网页上叫「启用合并白名单」） | 只写团队 `bots`，不写人 | 负责人的用户名，不写团队 |
| 强制推送 | 禁止 | 禁止 |

- **协作仓的 main 只由执行器合并**：负责人仍是协作仓的协作者（管理），只是不在推送与合并许可里，在 Gitea 网页上点不了普通的合并，改动要经过执行器的检查。执行器是程序，不算负责人
- **别的仓没有执行器**：推送与合并许可都只写负责人，不写任何团队
- **提改动不需要在推送许可里**：推自己的分支、推 `refs/for/main` 只是开合并请求，不改 main。协作仓的合并请求由执行器合并；别的仓的由负责人审阅，他同意后由 AI 经 `gitea.http` 用他的令牌以合并提交合并
- 要求审批、状态检查、签名这几项插件不设、也不核对

## 仓的合并方式

仓 → 设置 → 合并请求。只开「合并提交」和「仅快进」，默认「合并提交」，压缩合并、变基合并都关掉。
这样成员的提交原样进 main，提改动的人合并后 `git pull` 一定是快进，不会在本地多出合并提交：

先核对，不满足就拒绝、什么都不改：仓里要已经有 main，调用的人要是这个仓的管理员，`leads` 不给时现有的协作者不能是空的。再依次做四步：合并方式只留「合并提交」与「仅快进」→ 把 `leads` 逐个加成协作者（管理）→ main 的保护照上一节写 → 删掉不在 `leads` 里的协作者。删协作者放在最后，调用的人自己不在 `leads` 里也改得完；某一步失败，报错写明前面做到哪一步，那些不回退：

配好以后它往组织的推送 topic 发一条 `leads changed`，各成员的插件随即重读这个仓的负责人、再核对规矩（见 [实时推送的部署](/gitea/push)）。Gitea 换协作者不发 webhook，在网页上直接改协作者没有这条消息，别人要等下一次完整刷新才看到新负责人，所以换负责人一律用这条命令。

## 插件怎么核对

协作者和分支保护是两处设置，有人在 Gitea 网页上只改了一处、或者直接在网页上建了仓，靠插件核对报出来。只有本机身份是这个仓的管理员、仓里已有 main 时才核对，别的成员读不到保护，当作没有问题：

{/* ref file="../plugins/collab/src/gitea-api/repo-rules.ts" lines="76-86" hash="06e28bf8323f" blob="631b1b85c24d" */}

核对的是协作者与 main 的保护，按这个仓的规矩比，每个问题一句。两种仓都查：没有协作者、main 没有保护、推送或合并没有限定人、允许强制推送。别的仓另查许可里的人和负责人对不上、许可里写了团队；协作仓另查推送许可里有人或团队、合并许可里写了人或 `bots` 以外的团队、合并许可里少了 `bots`——负责人出现在协作仓的推送或合并许可里也算问题：

{/* ref file="../plugins/collab/src/gitea-api/repo-rules.ts" lines="37-74" hash="d4644a137922" blob="631b1b85c24d" */}

什么时候核对：每次完整刷新，协作仓与项目文件夹里每个别的仓各核对一次；收到某个仓的 `leads changed`，只核对那一个仓；组织里新建了仓，克隆下来后核对它。有问题的仓在网站提示栏「别的仓」组里出一条「`<仓>` 没按规矩配好」（协作仓自己有问题时也在这一组，写协作仓的名字）；在协作窗格那个项目的一行上或网站提示栏里点「复制给 AI」，粘贴给 AI，AI 问清负责人后调 `collab.repo.setup`。协作仓那一套的核对：

## 令牌

| 谁的 | 在哪生成、放在哪 | 勾哪几项 | 用来做什么 |
| --- | --- | --- | --- |
| 每个成员自己的 | 自己在 Gitea「设置 → 应用」生成，填进 gwb-gitea 的设置 `token` | 全部权限，每项都勾读写 | 插件克隆组织、提交审核（推 `refs/for/main` 算写）、在组织里建仓、读各仓的协作者、配仓、读执行器的留言、读合并请求与它的审阅、读 issue 与它的评论、核对令牌是谁；组织管理员的插件读、写组织的 webhook（账号要是组织管理员）；AI 经 `gitea.http` 合并别的仓里他同意的合并请求 |
| `collab-bot` 的 | 项目负责人生成，存成组织密钥 `COLLAB_BOT_TOKEN`（组织设置 → Actions → 密钥） | 仓库读写、工单读写 | 执行器读协作仓的协作者、合并或打回协作仓的合并请求、留言 |

插件不检查令牌勾了哪几项。`collab-bot` 的令牌少勾一项，或成员的令牌没勾全，用到时 Gitea 回 403，原话里 `required=[…]` 写着缺哪一项，照它重新生成令牌。
人在终端或 VS Code 里运行的 git 不用这个令牌，用 Windows 凭据管理器里存的 Gitea 登录，登录的账号要和令牌的账号相同。

新建项目、加人、换负责人、有人离开时各改哪几处，见 [建项目与人员变动](/gitea/setup)。

## 这套配置接受的代价

- 成员对协作仓也有代码写权限，能往协作仓推 main 以外的分支；进不了 main，协作仓的流程也不用这些分支
- 协作仓负责人自己的改动也要等执行器合并：执行器没在运行时，协作仓的 main 就停着，负责人也只能等
- 协作仓 main 的保护不打开「管理员也要遵守保护规则」（接口里 `block_admin_merge_override` 为假）：负责人是这个仓的管理员，能在 Gitea 网页上强行合并、不经过执行器；用户决定不改，约定没人这样做
- 成员的令牌勾全部权限，令牌泄露时能做的事和这个账号本人一样多
- 负责人有「管理」权限，能删掉这个仓、改它的可见性；课题组内部互信，接受这个风险，理由见轨迹卡 [每个仓的负责人只认 Gitea 上的协作者](/trajectory/2026-10-04-repo-leads)
- 协作者与分支保护是两处设置，有人在网页上只改一处，要等这个仓的管理员下一次完整刷新时才在提示栏里报出来；合并方式被改了不报
- 在网页上直接改协作者不会通知别的成员的插件，要等各人下一次完整刷新才认新负责人
- 删别人的任务与模块、推送前的负责人检查都要联网读 Gitea 上协作仓的协作者
