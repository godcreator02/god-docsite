## 几个名字，各管哪一段

「docfirst」是这套做法的名字，不是哪个包：命令行 `docfirst`、配置 `docfirst.config.mjs`、建站命令 `docfirst.create` 都用这个名字。
做法由一个包实现，另一个包把它接到文档站基础包的站上，还有一个工作台插件负责建 Next 站：

| 名字 | 是什么 | 装在哪 | 什么时候运行 |
| --- | --- | --- | --- |
| `@godcreator/docfirst-workflow` | 这套做法的实现：核对、确认、渲染生成物、卡格式、命令行 `docfirst`，以及接到 fumadocs 上的 `./fumadocs` | 每个站的 `node_modules` | 站建好以后的每一次：在站里运行 `docfirst`、git hook、CI、站点构建 |
| `@godcreator/docsite-docfirst` | 文档站基础包 `@godcreator/docsite-kit` 的功能包：构建页面时的 remark 插件、侧栏入口与 MDX 组件、星轨盘与卡页两条路由、轨迹卡集合模板、样式 | 建在文档站基础包上的站的 `node_modules`，站点 `package.json` 的 `docsite.features` 声明它 | 站点构建与开发服务编译页面时 |
| `@godcreator/gwb-docfirst-workflow` | 工作台插件：建站命令 `docfirst.create` 与 `docfirst.create-plain`，托管站点的命令 `docfirst.site.*` 与窗格「文档站」，加上给 agent 读的说明书 | gwb 的 home | 建站那一次；托管的站在工作台开着时一直开着；说明书在 agent 写文档、改代码时随时读 |

插件建的是 Next 站：它运行官方脚手架、套上本机约定与 docfirst 的分区、把 `docfirst-workflow` 的精确版本写进新站的依赖，托管时由工作台运行登记过的站的 `pnpm start`，
改完文档调 `docfirst.site.restart` 重新构建并重启。建在文档站基础包上的站（本仓的文档站就是）不经这个插件：初始化与托管归工作台的 gwb-docsite 插件。
不管哪种站，核对、确认、渲染都由站里装的 `docfirst-workflow` 完成，工作台开不开都一样；插件不读核对结果，也不转发命令行，卸掉插件站照样能核对、能构建。
包与插件互不依赖，唯一的联系是插件里那张建站依赖表。判据是「这件事在哪儿发生」：要在仓里反复运行的归包，只在 agent 手上发生一次的归插件，
来历见轨迹卡[包给仓件给人](/trajectory/2026-09-10-package-serves-repo-plugin-serves-agent)。

## 钉码怎么工作

文档里讲到代码的地方，不贴代码副本，只写一行记号：「这句话说的是某个文件的某几行」。讲解组件里照源码抄来的数据也一样，
在组件源码里那段数据正上方写一行记号。新写的记号只带目标，确认时，记号上写进两个 hash：
`hash` 是那几行内容（去掉行尾空白）的 sha256 前 12 位，`blob` 是整个文件当时的 git blob 名前 12 位。之后每次核对都重算那几行的
`hash` 跟记号上的比；对不上时凭 `blob` 从 git 取回确认时的文件，分清那几行是挪了位置还是改了内容。页面上那一块代码在构建时现读。

## 内容分三个区

`content/` 下 `future/` 是未来区，轨迹卡目录不在配置里指定时是 `content/trajectory/`，其余目录都是现状：

| 区 | 放在哪 | 写什么 | 能不能钉码 | 核对 |
| --- | --- | --- | --- | --- |
| 现状 | `content/docs/` 是总入口；内容多了，在 `content/` 下再建顶层目录，需要几个建几个 | 此刻是什么：机制、模块、接缝 | 能，讲到代码就该钉 | 全部进 `docfirst check`，站的 `src/components/` 下讲解组件的源码也进 |
| 轨迹 | `docfirst.config.mjs` 的 `trajectory` 指的目录，没写就是 `content/trajectory/`；建在文档站基础包上的站放在站点根下的 `trajectory/` | 每次取舍的理由，一个结论一张卡，只增不改 | 不能，出现记号就报错 | 只校验卡的格式 |
| 未来 | `content/future/` | 路线图、在途方案、别的仓写来的反馈 | 不钉 | 不核对 |

一句话能不能被代码推翻，决定它该不该带引用；一句话如果只是复述代码，它就不该写。

## gwb 插件 gwb-docfirst-workflow

包 `@godcreator/gwb-docfirst-workflow`，在 `plugins/docfirst/`，源码在 `src/`，入口 `src/index.ts`，说明书在 `skills/`。
它是 god 工作台（gwb）的插件，不发成 npm 库。

建站经 gwb-docsite 的服务 `gwbDocsite`：地基骨架、功能包起始物、装依赖、探活都归它，这个插件只做 docfirst 特有的两件事——
认站名与选端口，再把功能包交出去。站的托管（`docsite.site.*`）也归 gwb-docsite。docfirst 经[站的功能包](/docfirst/site)接进站。

## 功能

**包的使用者是仓，插件的使用者是 agent。** 要在仓里发生的核对、确认、渲染归 npm 包，agent `cd` 到站目录里运行站装的
`docfirst` 命令行；只在 agent 手上发生一次的建站归插件。判据的来历见[包给仓、插件给人](/trajectory/2026-09-10-package-serves-repo-plugin-serves-agent)：

交给哪个版本写在 `src/deps.ts` 那张表里（精确号，`tests/create.test.ts` 盯着它与工作区版本一致）；起始物
（`docfirst.config.mjs`、README / AGENTS / CLAUDE 的 outputs 正本、轨迹与未来两区起始页、docfirst 系脚本）由功能包的
模板带进站。骨架写完就归站点，没有照新模板重写它的命令。

插件没有任何文件启动子进程：装依赖与探活在建站服务里发生，插件不转发 `docfirst` 命令行（`tests/artifact.test.ts` 检查）。

## 零依赖

插件对本仓 `packages/` 下的包零依赖——三档依赖都没有，源码里也不 import（同一条测试检查）。`deps.ts` 里出现包名只是
「写进别人 package.json 的字符串」：装出来的站要跑 docfirst、要渲染，站当然该装这个包。
