# 交接

**本页回答**：现在有什么活在路上、做到哪儿了、交给下一个会话要看什么。

这一区的规矩一句话：**有页 = 有活在路上，做完删**。一件活一页，页头是验收清单，正文是实施方案；
随做随提交，中途每次提交都是一份可交接的快照。做完把结论拆解归梁——设计进
[现状区](/docs)、决定落一张 [轨迹卡](/trajectory)、没做的回 [未来区](/future/roadmap)——
然后把那一页删掉。git 历史是它的档案。这一页本身是导读，不算活。

**路上的活各占一页**，侧栏上这一区有几页就是有几件。此刻只有一件：
[给 git 立一条接缝](/spec/module-boundaries)——git 那条线现在只有一个直接起子进程的实现，
测试得在临时目录里起真仓。

## 什么样的活才升格成一页

**跨会话、跨模块、有未定选型**，三条占一条才写 spec；装得进一个会话的直接进模块页开工。
盘需求边界先把想法盘到能说清「回答什么 / 不做什么 / 成功判据」，盘选型用 `gwb-decide`，
两件事不重叠。

## 一页的骨架

```text
---
title: <一句话说清这件活>
description: <验收标准，一行>
---

## 验收
- [ ] 条目一（能被机器或人当场验的）
- [ ] 条目二

## 方案
散文。改哪几处、顺序、门禁怎么跑。指回总方案（如果有）。

## 进度
一行一次提交或一次会话，新的在上。
```

`docfirst check` 不扫这一区——只有现状与生成正本两区对代码说话。所以 spec 页里写引用没人核对它，
真要钉码的论断，写进模块页去。
