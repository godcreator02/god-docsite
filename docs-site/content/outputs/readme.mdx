# god-live-doc

**本页回答**：这套包是什么、怎么装、怎么确认它在干活、文档在哪。

## 是什么

把文档里对代码说的话钉在源码上：文档说「我引的是 `src/greet.ts` 第 2 到 3 行」「src 下有这四个文件」
「store.ts 里还有 save」，工具替你盯着。变了就报黄等作者复核，引用指向空气就报红。**文档里不存代码的
副本**——页面上那块是构建时现拿的，记忆只有一条指纹。

五类引用把「文件系统这根轴」填满：行段、整文件、目录树、存在性（含「断言不在」）、名字。

另一摊是**轨迹卡**：live-doc 治现状文档撒谎，轨迹卡治历史被改写——一次方向了断记下来就该冻结，
谁取代了谁看得见。卡不进记录簿、不用 confirm，只要即时校验；星轨盘在站上是一条独立的整页路由，
不是塞进 mdx 的组件。

## 怎么装

```bash
pnpm add -D @godcreator02/live-doc-cli @godcreator02/live-doc-project @godcreator02/live-doc-format-fumadocs
```

写 md 或手写 html 就把 `format-fumadocs` 换成 `@godcreator02/live-doc-format-md` /
`@godcreator02/live-doc-format-html`，一个项目里几个格式包可以并存（各认各的后缀）。
fumadocs 在格式包里只是 **peer**——用你项目里装的那份。

还没有文档站的仓，一条命令铺一个接好的六区站：

```bash
pnpm livedoc init --dir <仓的绝对路径>
```

它不读 `livedoc.config.mjs`（那正是它要铺出来的东西），只往一个已经存在、且还没有 `docs-site/` 的仓里
铺文件——不跑 `pnpm install`、不改仓里任何已有文件。

## 怎么用

项目根放一份 `livedoc.config.mjs`（挂哪些格式包、哪几区进 check、生成物摆哪），文档里写一行草稿记号：

```md
@@livedoc ref src/greet.ts:2-3 @@                       行段
@@livedoc ref config.json @@                            整文件（末尾追加也算变）
@@livedoc tree src @@                                   目录树；可带 depth=2、glob=*.test.ts
@@livedoc exists src/store.ts @@                        在；absent 是「断言不在」
@@livedoc has src/store.ts "export function save" @@    文件里有这个字面量
```

然后：

```bash
pnpm livedoc check                     # 只读，报状态。红退 1，黄和白退 0
pnpm livedoc confirm                   # 出记录、清孤儿、换记号、投影内容
pnpm livedoc confirm content/docs/a.mdx   # 只确认点名的那几篇
pnpm livedoc render --target ai        # 出给 AI 读的那份 md；挂了 outputs 映射的摆到指定位置
```

**跑通了的样子**：`check` 打出一行一处引用，每行带一个状态符号（🟢 新鲜 / 🟡 有变动 / ⚪ 未确认 /
🔴 缺失）；`confirm` 把草稿记号换成正式记号并写进记录簿，站上每个代码块的标题栏里多一个对应颜色的点。
门禁里挂 `pnpm livedoc check` 就行，它只在「引用指向空气」这一类真错上拦人。

`confirm` 之前**先 commit**：git 记忆只对已提交、且工作区干净的内容钉。有一处钉不住就整篇拒。

## 文档在哪

`docs-site/` 是这套包的**六区文档站**，也是它唯一的消费方——装的是工作区里的这几个包，钉的是工作区里的
真源码，所以仓里不另留示例。

```bash
cd docs-site
pnpm build && pnpm start        # 看 http://localhost:4310
pnpm livedoc check
```

六区各是什么：`content/docs/` 现状（进 check）、`content/trajectory/` 轨迹卡、`content/spec/` 在途的活、
`content/future/` 未来、`content/outputs/` 生成正本（进 check）、`content/feedback/` 反馈。
先读现状区的**系统地图**，再读要改的那块的模块页。

文档本身怎么写、六区怎么分、每页写到哪为止，正本是随 `@godcreator02/live-doc-cli` 发的三份 skill
（`packages/cli/skills/`）：`livedoc-docs` 写文档、`trajectory` 落卡、`spec-grill` 盘需求。
装了这个包的仓把它的 `skills/` 挂给 agent 读就行。

**这份 README 是生成物**，正本是 `docs-site/content/outputs/readme.mdx`；仓根 `AGENTS.md` 同理。
改 mdx 源，`pnpm livedoc render --target ai` 重摆，两份一起提交。

## 这个仓自己怎么跑

```powershell
pnpm install
pnpm build          # 各包 tsdown，拓扑序
pnpm typecheck
pnpm test           # 先 build 再 node --test tests/*.test.ts

cd docs-site
pnpm livedoc check
pnpm test           # 站那头的接线（不起 Next）
pnpm build          # next build
node scripts/verify-roster.mjs

cd ../packages/gwb-live-doc
pnpm check && pnpm build      # 工作台件自成一摊，用 vitest
```

改了格式包的代码，站要**先删 `.next` 再 build** 才看得见——Turbopack 只按 mdx 内容缓存。
调试站用 `next build` + `next start`，不用 dev。
