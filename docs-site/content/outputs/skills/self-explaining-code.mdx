# 让代码自己说清自己

**一个文件读一遍，四件事同时做**：注释怎么处置、名字够不够长、函数该不该拆、有没有设计思路要
搬进文档。分成几轮扫会让同一批文件被读好几遍，而读代码是这整件事里最贵的一步。

范围一次一个模块，不要全仓一把梭——改动越大，"没改行为" 越难证明。

## 注释三分法

读到一条注释，只有三个去处：

**搬去文档**：讲为什么这么切、否掉了什么、边界在哪、这个取舍的代价是什么。这些是设计思路，
属于文档，不属于代码。搬走之后**文档必须钉回这段代码**（`@@livedoc ref 路径:起-止 @@`），
否则你只是把漂移换了个地方发生。

**删掉**：复述代码在干什么的（`// 遍历列表` 上面跟着一个 for）、写着 "原来是 xx 现在是 yy" 的、
写给某次调试的、注释掉的旧代码。历史归轨迹卡，git 记得住，代码里留着只会骗人。

**留下**：真正的现状约束——不变式、外部契约（那个 API 会回 null）、踩过的坑（这里不能用 map，
会吞掉 undefined）、以及为什么这段看起来蠢的写法是必要的。留下的写成一行，只写现状。

判据一句话：**删掉这条注释，读者会做出错误的判断吗**？会就留或搬，不会就删。

## 搬去哪一梁

- 模块怎么切、依赖往哪个方向、接口的语义与边界 → **模块页**（设计梁）
- 一次选择、否掉了什么候选、判据是什么 → **轨迹卡**（choice 形态，一次了断一张）
- 怎么用、命令与配置 → **用法页**
- 一个词在这个仓里的确切含义 → **术语表**

搬完检查一遍：模块页的「不知道什么」那段是不是变厚了？注释里最值钱的往往正是这类边界陈述。

## 命名

**长度无所谓，清晰才算数。** 忌讳短得像很优雅、其实说不明白自己的名字。一个名字要能回答
「它是什么 / 它做什么 / 什么时候用它」里的至少一个。

- 变量：`d` → `daysSinceLastConfirm`
- 函数：`check()` → `checkPlacementsAgainstDisk()`
- 布尔：加上它为真时的含义，`ok` → `everyPinIsFresh`
- 集合：复数加上它装的是什么，`items` → `driftedReferences`

改名不顺手改逻辑。这是两次改动，混在一起就没人能复核。

## 拆函数

**拆到每个函数名就是它的注释。** 一个函数里出现「这一段在干 X」这类注释，那一段就该是个叫
`X` 的函数。拆完之后原来的注释自然消失——不是被删掉，是被名字吸收了。

判据：读函数体时需要在脑子里给某几行起个名字，就把那个名字变成真的。

嵌套超过两层、或者一个函数要滚屏才看得完，通常是没拆够。但不要为拆而拆：**只在能起出一个
诚实名字时才拆**，起不出名字说明那几行还没形成一个概念。

## 怎么证明没改行为

**测试先绿，改完还绿，测试本身一个字不改。** 这是唯一的证据。测试要改，说明你改的不只是形状。

没有测试的模块，先补测试再重构——补测试时用的是现在的行为，不是你以为的行为。

## 提交怎么拆

产物是两种，分开提交：

- **文档改动**：注释搬进去的那些页 + 钉码。过 `livedoc check`。
- **代码改动**：注释瘦身、改名、拆函数。过测试。

同一次扫描里做，分两个提交落，因为它们的验收面不同，出问题时也要分别回退。

## 一次扫描的收尾

- 模块页的钉码是不是变多了（搬进来的论断都钉住了吗）
- 测试没改过，还是全绿
- 那些"留下"的注释，每条都是现状、都是一行
- 一张轨迹卡，如果这次扫描改变了某个模块的边界认识
