gwb-docsite 是 gwb 工作台和[平台包](/packages/god-docsite) `@godcreator/god-docsite` 之间的一层。站点模板、建站器、开发服务的端口挑法都在平台包里；插件做的是把它们接到工作台上：命令与服务 `gwbDocsite`、托管站点的开发服务、本 home 的身份码、随包的四份说明书。命令怎么用看说明书 [docsite](/docs/outputs/skills/docsite) 与 [docs-site](/docs/outputs/skills/docs-site)，这一页讲它的结构，给要改它的人看。

## 建站与加功能

图上第 4 号。建站器不打包进插件：它按自己模块的位置找平台包的 `template/`，打包进来就找不到。插件从自己的包根用 Node 的解析规则找 `@godcreator/god-docsite/scaffold`，经 `import(变量)` 加载；地址是算出来的，发版检查才不会把它当成产物里 import 的包名（插件产物只许 import peer 里的包）。

{/* ref file="../plugins/docsite/src/scaffold/platform.ts" lines="23-35" hash="242c7fc83e9c" blob="3fd3d79ed663" */}

建站器复制完模板，插件接着写站点的身份文件 `docsite.json`（格式见 [god-docsite](/packages/god-docsite) 页的「站点身份文件」）：`docsite.site.init` 写 `base`，`docfirst.create` 写 `docs`，gwb-collab 经服务 `init` 传 `collab`。身份文件的读写来自平台包的 `./identity` 出口，它不按自己模块的位置找文件，按值 import、打包进插件。

`docfirst.create` 把一个空目录变成 docfirst 站要走七步，前四步就是普通的 `docsite.site.init`（建基础站同样走这四步，站点目录必须还不存在或是空目录）。测试里 pnpm 与首页检查是假的、建站器是真的（`tests/site-fixtures.ts`）；画面终端里的说明行是为讲解拼的，不是命令输出：

## 托管开发服务

### 常驻的站只记在 gwb-data 的 hosted-sites

图上第 5 号。常驻的站只有一张表：gwb-data 的文档 `hosted-sites`，每项是站点目录与谁登记的 `{ dir, by }`。`docsite.site.add` 登记的记成 `by: "docsite.site.add"`；别的插件经服务 `add(dir, { by })` 登记时报自己的名字，gwb-collab 的项目站点记成 `gwb-collab`。插件每次加载时读一次表、逐个启动登记着的站，不等，没能启动的报一行警告；表的形状不对就一个也不启动、报一行，之后的登记与列表照样报这个错。没有这份文档就是一个站也没登记。

{/* ref file="../plugins/docsite/src/hosted-sites.ts" lines="33-110" hash="91a7ef3789b8" blob="b5b3e584fdbd" */}

表读进内存以后，改动排队写回，几处同时登记时后写的不覆盖先写的。`add` 先登记再启动，启动不了照样报错、登记留着，下次加载再试；已登记的站换了登记的一方就改过来，不重复登记。`remove` 去掉登记，在运行就停掉。服务的 `remove` 对没登记过的站回 `{ registered: false }`，命令 `docsite.site.remove` 对它直接拒绝。站点目录的比较键是解析成绝对路径再转小写：大小写、斜杠不同的写法算同一个站。进程的启停不在这张表里，归下面的 `SiteHost`。

`docsite.site.list` 把两边合成一张：常驻的站按登记先后在前，后面是 `SiteHost` 这次运行里启动过、却没登记的站（建站时的首页检查、自己验页面时启动的）。每行在进程状态之外带四样：`title` 是站点 `content/meta.json` 的 `title`（文件不在或没写为 `null`，不是合法 JSON 就报错），`kind` 是身份文件写的类别（没有这个文件为 `null`，写坏了报错），`hosted` 是登记了没有，`by` 是谁登记的（没登记为 `null`）。

### 站点窗格

图上第 9 号。插件注册一个窗格 `sites`（标题「站点」），列的就是 `docsite.site.list`：每个站一行，写站名（没有就用目录名，协作站的 `site` 带上上一级）、类别（协作站、文档站、基础站，没有身份文件的写「未标注」）、来源、状态与端口、站点目录，站点出错或这一行的操作失败时原因写在下面。窗格看得见时每 5 秒重读一次。

每行右边三个操作，都是调命令：「打开」调 `docsite.site.open`（见下一节）；「启动」「停止」调 `docsite.site.start` / `docsite.site.stop`。来源是「手动」的站（`docsite.site.add` 登记的）还有「不再托管」，点了要再点一次确认，调 `docsite.site.remove`；别的插件登记的站不给这个按钮，协作站要在协作窗格移出项目列表，不然 gwb-collab 下次加载又登记回来。建站、加功能这些事窗格不做，由人让自己的 AI 调命令。

{/* ref file="../plugins/docsite/src/pane/browser/sites.ts" lines="33-51" hash="f38bd645f7d8" blob="e7b9275b9c93" */}

浏览器侧照 gwb-collab 的窗格搭：React 与 lucide 从外壳的共享模块取，按钮是 shadcn 的那份，Tailwind 类名都带前缀 `docsite:`，只匹配本插件画出来的元素；外壳的主题令牌里没有表示「运行中」的绿色，在 `tokens.css` 里补了一个。

### 打开站点：Chrome 应用窗口

`docsite.site.open` 是站点窗格与 gwb-collab 协作窗格的「打开」共用的一条命令：先照 `start` 确保站点在运行，再用本机 Chrome 运行 `chrome.exe --app=<地址>`，开出一个没有标签栏和地址栏、在任务栏上单独一个图标的窗口，登录状态与 Cookie 和平时的 Chrome 共用。Chrome 只在 Program Files、Program Files (x86)、当前用户的 LocalAppData 下找，找不到就拒绝，不改用默认浏览器。

一个站只开一个窗口：打开前先运行随包的 `chrome-window.ps1` 找这个站已经开着的窗口，找到就恢复、切到前台，回 `window: "focused"`；没找到才新开，回 `launched`。窗口按两样认：应用身份 `Chrome.<主机>_<路径>`（Chrome 给应用窗口的身份不带端口），与窗口标题（站名，或「页面名 · 站名」，站点自己这样设标题；站名取 `content/meta.json` 的 `title`）。标题在窗口外框上，窗口被盖住、最小化时都读得到。站点没写站名时认不出窗口，每次都新开。刚启动的窗口页面还没加载出来、标题还不是站名，所以只用标题找开着的窗口，启动后不等窗口出现。同一个站同时点几次只打开一次。两个 home 开着同名的站时分不出是谁的窗口，切到的是先找到的那个。

`chrome-app.ts` 在打包时进 `dist/index.js`，它按自己旁边的路径运行 `chrome-window.ps1`，所以 `build.ts` 把脚本复制进 `dist/`。

### 一个站的三种状态

`SiteHost` 按站点目录记每个站：在跑的开发服务、上次没能运行的原因、正在启动的那一次。三种状态之间由哪些事件转换、哪些操作幂等，选一种情况看：

<SiteStates />

插件卸载时同步停掉全部：Windows 上 pnpm 经 cmd 启动、底下还有 node，停的时候用 `taskkill /T` 连同子进程一起停，等它跑完才返回。内核不等卸载回调里的异步操作，工作台退出时异步的停止来不及跑完：工作台一退出，直接起的 cmd 被一起结束，pnpm 与 node 却留下来占着端口。没经卸载就退出的，在进程的退出事件里同步再停一次。整棵进程树停掉以后端口还要片刻才放开，新实例沿用端口时要等它，见下一节。

### 一次 start 怎么走

图上第 6 号。启动前先核对：站点目录里有 `package.json`；有身份文件 `docsite.json` 且写对了（没有的是平台之外建的站，比如旧包 `@godcreator/docsite-kit` 上的站，或是有身份文件之前建的站，拒绝并写明补一份什么样的）；`node_modules` 里装着平台包；`scripts.dev` 没写死 `--port`。写死了会和启动时带的 `--port` 同时出现，站点认错自己的地址。

端口：gwb-data 的文档 `site-ports` 记着每个站上次用的端口。上次的端口在 127.0.0.1 与 ::1 上都空着，就带 `--port <端口>` 启动（平台的 vite 插件加 strictPort，被占就启动不了）；没记过就不带，由平台的 vite 插件在 10000–49151 里随机挑。上次的端口被占着时先每 0.5 秒再查一次、最多 10 秒：插件重新加载（升级、重载）时，旧实例卸载时停掉开发服务，新实例马上来查端口，端口这时可能还没放开。10 秒后还被占着才不带 `--port`、让站点随机挑。报出的端口和给的不同就停掉并拒绝。好处是书签与开着的页面重启后还能用：真站测试里停了再启动、插件升级以后，地址都不变。

{/* ref file="../plugins/docsite/src/site-ports.ts" lines="19-62" hash="0ba7a9be47b8" blob="0cb5b5c21893" */}

启动时经环境变量交给开发服务两样：本 home 的身份码 `DOCSITE_IDENTITY_CODE`（站点按它在 `people.json` 里认人，没有它站点只读），这次启动现生成的推送令牌 `DOCSITE_FEED_TOKEN`；然后等输出里出现 `Local:` 那一行的地址，60 秒内没等到就停掉、报错。

开发服务的输出一块一条写进 gwb 日志，日志名 `gwb-docsite-dev`，开头是站点目录：stderr 记 warn，Vite 的「Internal server error」、服务端渲染的报错都从这里出来，页面打开是「Error」时用 `logger.query` 按这个名字查；stdout 记 debug，默认不写进 gwb.log，改一个文件就刷一行的「page reload」不会把日志刷满。插件另在内存里留最后 4000 字，启动失败、退出时的报错原话从那里取。

{/* ref file="../plugins/docsite/src/dev-server.ts" lines="155-168" hash="60e364b8c09a" blob="48bea96ae7d0" */}

跑起来以后记下这次的端口；几个站同时记时排队写，后写的不覆盖先写的。记不下来只报一行警告，照样运行，下次重新挑（有意设计的降级）。选一种情况看看：

<StartCases />

启动前核对不过时不启动进程、直接抛错，状态转成 `failed`，`error` 记下拒绝的原话；开发服务没能启动、启动后退出也是 `failed`。

进程自己退出了（不是 `stop` 停的）就过一会儿自动重启：协作站常驻在后台，崩了往往要等人打开时才发现，所以不等人。连续崩溃时依次等 2 秒、10 秒、60 秒，`error` 末尾写着几秒后第几次；一次运行超过 5 分钟才退出的不算连续，重新从 2 秒算；三次用完就停在 `failed`、写明不再自动重启，免得一个起不来的站反复占资源。自动重启那一次没起来也算一次崩溃。人手动 `start` 取消等待、马上启动，`stop` 取消等着的重启；两者都把连续崩溃的次数清零。人手动 `start` 时起不来不自动重试：那多半是站点本身的问题，要人看。

## 推送与评论：经运行中的站点

图上第 7、8 号。推送：`push(dir, 频道, 数据)` 把一份 JSON POST 到站点的 `/__docsite/feed/<频道>`，请求头 `x-docsite-token` 带这次启动的令牌；频道只用字母、数字、`_`、`-`。站点没在运行就报错。协议定在平台包，插件照它推。站点每个频道只留最新一份、重启就没了，所以用推送的插件要在站点转成 running 时重推一次——这就是服务里有 `onStatus` 的原因。

订阅：`subscribe(dir, 频道, 收到时调的函数)` 反过来听站点的一个频道（GET 同一地址、要事件流、请求头带同一个令牌），站点由此知道启动方在听，网页上要插件做的事（gwb-collab 的一键提交）就写进这个频道。站点在运行就马上连上，先收到频道现在的值；之后站点每次启动（包括崩溃后自动重启）都重新连，站点还在运行时连接断了过 1 秒再连；调返回的函数撤掉订阅。

{/* ref file="../plugins/docsite/src/site-host.ts" lines="242-282" hash="db9d13099698" blob="7e3fcf6a0b05" */}

评论：读评论（`docsite.comments`）直接读站点目录的评论文件，不要站点在运行，网页上点的表情回应也一并列出；写评论（`docsite.comment.*`）不自己写文件，而是把表单 POST 到运行中站点的评论写入路由 `/comments.data`，`Origin` 头写站点地址，和网页评论面板走同一套规则。评论文件的格式与写入规则归 [comments](/packages/comments) 包的页，人员与身份码归 [identity](/packages/identity) 包的页。

## 服务 gwbDocsite

图上第 2、3 号。别的插件 `inject: ['gwbDocsite']` 后调用。接口分四组：建站（`init`、`addFeature`）、托管（`add`、`remove`、`start`、`stop`、`status`、`onStatus`）、推送与订阅（`push`、`subscribe`）、身份（`join`、`identityCode`）。命令 `docsite.*` 是同一份实现外面包一层参数校验，所以命令与服务的行为不会分叉；每个方法的参数与回执表在说明书 `docsite` 的「服务 gwbDocsite」一节。

{/* ref file="../plugins/docsite/src/service.ts" lines="7-48" hash="0ff9c07d4506" blob="2fce4a7e78d6" */}

服务对象只存闭包：cordis 读服务属性时会把属性里存的服务重新绑到调用方的上下文。`declare module 'cordis'` 写在包入口 `index.ts`：发版工具只读类型入口 `dist/index.d.ts` 认这个服务由谁提供。改方法签名就是改给别的插件 inject 的服务，要先问人、照 gwb-release 定版本号。

用它的就是图上第 3 号两端：gwb-collab（`plugins/collab/src/site-process/collab-sites.ts`）用 `init` 与 `addFeature` 建协作站，项目加进列表（以及每次插件加载）时 `add(dir, { by: 'gwb-collab' })` 登记、移出时 `remove` 撤销，`onStatus` 接到站点转成 running 就重推整份数据，`join`、`identityCode` 把本 home 加进项目的人员列表，细节归它自己的页；本插件自己的 `docfirst.create` 只用 `init` 与 `addFeature`。

## 打包与随包说明书

打包：`build.ts` 用 esbuild 把 `src/index.ts` 打成一个 `dist/index.js`，外置名单只有 cordis 与 peer 里的工作台包，其余按值 import 的都打包进来——平台包核心（推送通道的常量）、identity（身份码的环境变量名、`people.json` 读写、@ 提取）、comments 的 node 层（读评论文件）。它们按包的 `exports` 解析到各包的 `dist/`，所以改了这几个包要先构建，再构建插件。站点窗格的浏览器侧另打成 `dist/client.js`，外置名单是外壳共享的模块；类型入口与窗格样式表 `dist/style.css` 由紧接着的 `tsc`、`tailwindcss` 输出。

不打包的：平台建站器（运行时加载，见上文）；docfirst、code-pin、trajectory、explainer（只读文件）。七个包都写在 `dependencies` 里，随插件装在旁边，版本号「插件旁边装着的那一版」说的就是它们。

说明书：`skills/` 下四份 `SKILL.md`（docsite、docs-site、docs-writing、trajectory）是本站的生成物，正本在 `docs-site/content/docs/outputs/skills/<名>.mdx`，`pnpm doc:render` 生成，映射保留 `name` 与 `description` 两个 frontmatter 字段（工作台靠它们决定什么时候读）。trajectory 的两份附件 `skills/trajectory/references/*.md` 不在映射里，直接在插件目录里手写。`skills` 写在 `package.json` 的 `files` 里，测试 `tests/skills.test.ts` 查四份都在、frontmatter 开头是 `name`。
