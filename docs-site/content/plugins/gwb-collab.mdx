gwb-collab 是 gwb 工作台的插件，跑在每个成员自己的电脑上：管 git 与 Gitea（克隆、取回、同步、提交审核、读合并请求与 issue、核对仓的配置），把要人处理的事算成通知，再交给站点、协作窗格与 QQ。站点不跑 git、也不向插件发请求，只收插件推来的数据。

和别处的分工：记录格式、写入规则、合并检查判什么、`SiteFeed` 的形状在 [collab 包](/packages/collab)；ntfy 推送、执行器、权限在 [Gitea 与 NAS](/gitea) 分区；每条命令怎么用、每条通知怎么处理在说明书 [collab](/docs/outputs/skills/collab)。这一页只讲插件这一层。

这一页从头到尾用同一个例子：Gitea 组织 `hybrid-mmc` 的项目里，`bob` 是协作仓 `collab` 的成员、本机身份，`admin` 是管理员、项目负责人，`carol` 是另一个成员。推送以后 Gitea 开出的合并请求都是 #7。

| 目录或文件 | 做什么 |
| --- | --- |
| `collab-repo/` | 协作仓那一套：监视本机状态（`sync/watch.ts`、`sync/local-state.ts`）、取回与自动同步（`sync/`）、提交审核（`submit/`）、读项目负责人（`leads.ts`）、核对协作仓的配置（`rules.ts`）、任务与模块的命令和「找我的」（`records/`）、完整刷新与收到消息时做哪几步（`events.ts`） |

| `organization/` | 组织级：`events/` 订阅 ntfy、认消息、合成一批再调度、完整刷新、各步出错的记录、组织 webhook、`leads changed`（细节见 [实时推送与执行器](/gitea/push)）；`setup/` 克隆组织、加入、项目列表、建仓、配仓的命令（配仓见 [权限怎么配](/gitea/permissions)） |

| `site-process/` | 站点交给 gwb-docsite 托管与推数据（`collab-sites.ts`）、`collab.site.init`、在 `site/` 里装依赖与跑类型检查（`dependencies.ts`） |
| `pane/` | 协作窗格：`collab.projects` 与浏览器侧的 `ProjectsPane` |
| `ai-prompt/` | 把一个项目此刻的全部通知写成交给 AI 的提示词，`collab.ai.prompt` |
| `project/` | 打开项目、按本 home 的身份码认人（`project.ts`）、核对令牌账号就是这个人（`account.ts`）、设置 `projects`（`list.ts`）、QQ 任务组（`qq-task-groups.ts`）、仓的状态变化转给通知（`repo-change-relay.ts`） |
| `gitea-api/` | 调 Gitea 接口；两种仓共用的配置核对与写入（`repo-rules.ts`，见 [权限怎么配](/gitea/permissions)） |
| `git/` | 运行 git、解析 `git status`、判断能不能快进 |
| `index.ts` | 装配：建各目录的对象、把它们接起来、登记命令、窗格与说明书 |
| `commands.ts` | 登记命令的共用写法：参数只收声明的键、拒绝回 `{ ok: false, error }`、打开项目 |

## 两套操作：协作仓与别的仓

图上第 2、3、4 号。项目文件夹（以组织命名）里有一个协作仓（站点身份文件 `site/docsite.json` 写着 `"kind": "collab"` 的那个，格式见 [god-docsite](/packages/god-docsite) 页的「站点身份文件」；`collab/` 在没有任务记录时是空目录、git 不跟踪，不拿它认）和若干别的仓。两种仓进 main 的路不同，插件里各走一套，各自记着「此刻怎样」，通知只读这些记录：

| | 协作仓那一套 | 别的仓那一套 |
| --- | --- | --- |
| 本机状态 | 一直监视整个协作仓：还没提交审核的 `collab/`、`site/` 文件，冲突，当前分支 | 一直监视各仓的引用：HEAD 比服务器上同名分支多几个、少几个提交 |
| 取回以后 | 能快进就自动快进（下一节） | 只取回，不动分支与工作区；人要更新时由 AI 调 `collab.repos.update`，也只做快进 |
| 进 main | 只经 `collab.submit` 提交审核，由执行器合并 | 普通 git 仓：负责人直接推，别人推分支开合并请求，负责人同意后合并 |
| 读 Gitea | 协作仓的协作者，作为项目负责人交给站点 | 每个仓的协作者、开着的合并请求与审阅、issue 与评论 |
| 核对配置 | 协作仓的规矩：main 谁都不能直接推，合并只许团队 `bots` | 别的仓的规矩：main 的推送与合并只许负责人 |

完整刷新（插件连上推送、加进项目列表、`collab.check`）时，协作仓这边按顺序做四步：取回、读负责人、核对配置、自动同步；取回失败也照样试一次自动同步，本机已有的 `origin/main` 可能还没快进进来：

{/* ref file="../plugins/collab/src/collab-repo/events.ts" lines="24-31" hash="8a862822b72b" blob="2f7d37c4b1e8" */}

别的仓那边先补克隆组织里新加的仓，再对项目文件夹里每个仓并行做取回、读合并请求与 issue、核对配置。每一步出错不往外抛：按项目、按步名记下原话，那一步下次做成了就清掉；同一个项目同时只做一件，正在做时 `collab.check` 回 `busy`。这些原话合成一条「gwb 检查项目出错」的通知。收到 ntfy 消息时按消息说的仓只做那一处，见 [实时推送与执行器](/gitea/push) 的「收到消息以后」，这里不重复。

## 自动同步：只快进

图上第 2 号的完整刷新做完取回就接自动同步，git 都在本机的仓上跑（第 3 号）。协作仓不用 `git pull`：取回之后，在 main 上、能快进才快进——不能快进的原因按顺序判，停下的那格之后不再判；判定都过了才 `git merge --ff-only`。每种情况停在哪一格、仓里是什么样、网站提示栏里出现什么：

<SyncCases />

不能快进不是错误：什么都不动，原因记下来，成为「没能自动同步 main 上的新改动」的通知（图里不在 main、冲突没改好两种情况不列这条）；下一次完整刷新取回成功后再试。

自动同步之后协作仓没有东西可提交（`collab/`、`site/` 没有改动、没有冲突、本地 main 不领先），上次提交审核失败的那条通知就清掉。

本机状态的监视：协作仓里任何文件变了都重算，`.git/` 里只看 `index`、`HEAD`、`packed-refs`、`refs/`；`git status` 只跑一次，按路径分出 `collab/` 与 `site/`。监视事件的行为假设在 `tests/verified/watch.test.ts`，动了监视要跑 `pnpm test:verified`。

## 提交审核

图上第 5 号。`collab.submit` 只在 main 上做，不建分支。它把检查分成两半：**记录格式与站点只在本机查**（执行器不查）；**冲突与只有负责人能改的内容执行器查**，后者本机推送前也用同一个函数先查一遍，成员在本机就知道会不会被打回。

查格式的参照点有两个，都只算「这次带来的新问题」（`newFormatProblems`，规则见 [collab 包](/packages/collab) 的「读出状态与校验」）：提交前比的是本地 main 与 `origin/main` 的分叉点，那时就有的问题不算我的；把 main 合进来以后再比一次合进来的那个 `origin/main`，两个人各自没问题、凑在一起才出的问题只有这一步能发现。

站点检查此刻只查 `site/journal/` 的文件名（站点布局按它读，文件名不是真实日期整站打不开）；`site/package.json` 写了 `typecheck` 脚本就在 `site/` 里跑一次，没写就跳过。别的站点问题由 gwb-docsite 启动站点时查。

提交只带 `collab/` 与 `site/` 里有改动的那几个目录，暂存区里别的文件不带上（空的 `collab/` 不被 git 跟踪，不会写进提交命令；目录里的文件删光了，删除照样提交）；上次合 main 出的冲突已经改好时，这次提交就完成那次合并。推送用 AGit：`HEAD:refs/for/main`，主题固定是自己的身份，同一个人推的都进同一个合并请求；之后每 2 秒查一次合并请求，最多等 3 分钟。执行器那边怎么查、怎么合并见 [实时推送与执行器](/gitea/push)。

## 通知：每次从此刻的状态现算

图上第 6 号。通知不存。一个项目要算通知时，从各处读「此刻怎样」交给 `notificationsOf`，按 kind 造出通知，`id` 由 collab 包按事实算（同一件事在状态更新前后算出同一个 `id`），再按组排好。事情解决了，下一次算就不再出现。

三组的来源（kind 名与读取项、接线一一对应）：

| 组 | kind | 从哪来 |
| --- | --- | --- |
| 协作仓 | `unsubmitted`、`conflicts`、`off-main` | 协作仓的本机状态（监视着重算的那一份） |
| 协作仓 | `submit-failure` | 上次 `collab.submit` 拒绝的原话 |
| 协作仓 | `sync-problem` | 最近一次自动同步没能快进的原因 |
| 协作仓 | `check-error` | 刷新各步此刻的出错，一步一行 |
| 协作仓 | `record-problem` | 工作区 `collab/` 读不出的文件、重复的 id、所属模块不存在 |
| 协作仓 | `webhook-setup` | 组织管理员的插件核对组织 webhook |
| 别的仓 | `unpushed`、`unpulled`、`diverged` | 别的仓的 HEAD 与服务器同名分支比 |
| 别的仓 | `pull-to-review`、`issue-to-answer`、`my-pull-update`、`my-issue-answered` | 读各仓的合并请求、审阅与 issue |
| 别的仓 | `repo-setup` | 核对配置；协作仓自己没配好也在这一组，写协作仓的名字 |
| 找我的 | `task`、`mention`、`reply` | 现读工作区的 `collab/` 与 `site/comments/` |

协作仓组有两条让某些通知不列的规矩：冲突没改好时，提交失败与同步不了说的都是这件事，只列冲突；不在 main 时自动同步一定停着，不再列同步不了：

## 交给站点、协作窗格与 QQ

图上第 6、7 号。各目录的状态一变都调同一个入口：装配时先建一个中转 `RepoChangeRelay` 交给各目录，通知建好后再接上，接上之前就有变化直接报错（装配顺序错了）。它转给 `ProjectNotifications.changed`，也让 QQ 任务组按现状重新登记一次。

- **站点**：`changed` 先让 `CollabSites.feedChanged` 推一次。站点在运行就现算整份 `SiteFeed`（通知、提示词、项目负责人），经 gwb-docsite 的服务 `push` 推到频道 `collab`；没在运行就不推，站点转成运行时经 gwb-docsite 的 `onStatus` 回调再推一次。推送按项目排队，接连变化时后推的一定是新的；推不上记一行警告，同样的原因不重复记
- **协作窗格**：`collab.projects` 现算同一份通知，只回各组几条；「复制给 AI」调 `collab.ai.prompt`，和站点提示栏里复制的是同一份提示词
- **QQ 私聊**（设置 `qq-notifications` 打开、同 home 装了 gwb-qq-bot 才发）：提示栏里出现新的通知、连续存在满 1 分钟，就经 QQ 私聊主人，一条通知只发一次。什么时候发、什么时候不重发，这 160 秒的时间轴讲全（自己的 `unsubmitted` 不发；等待中的只在内存里，重启后从头等）：

## 站点交给 gwb-docsite

这一节讲图上第 7 号里站点那一路经过的 site-process。插件自己不启动站点进程。常驻的站只登记在 gwb-docsite 的 gwb-data 文档 `hosted-sites` 里（登记的一方记成 gwb-collab），启停、状态、起不来的原因、工作台启动时启动都由 gwb-docsite 做。插件只做三件事：项目加进列表、插件加载、自动同步改了 `site/` 之后登记站点（`add`，带上 `{ by: 'gwb-collab' }`：已登记、已在运行就不动）；项目移出列表时撤销登记（`remove`，在运行就停掉）；把数据推过去（上一节）。登记不了、起不来记成这个项目 `site:host` 一步的出错，经「gwb 检查项目出错」显示。`site/package.json` 还不存在时不登记，报错让负责人先 `collab.site.init`。

`collab.site.init {repo, title}` 只对新站点（`site/` 不存在或是空目录），按顺序：

1. 交给 gwb-docsite 的 `init` 建站（平台模板、身份文件 `site/docsite.json` 写 `"kind": "collab"`、装依赖、启动一次检查首页）
2. 建好仓根的 `collab/` 与站点的 `journal/`：站点运行时会写入它们，协作功能的样式表在 Tailwind 扫描里排除这两个目录，目录要在开发服务启动前就存在才生效，否则一写入就整页刷新、推送连接断掉
3. 仓里还没有 `.gitea/workflows/collab-auto-merge.yaml` 就照打包进来的模板写出，`MERGE_CHECK_RANGE` 写成 `^<打包时的 collab 版本>`；已有的是负责人管的，不覆盖
4. 站点此刻在运行（站点目录早已登记在 gwb-docsite、`init` 检查完首页后它保持运行）就先停掉：加功能要站点停着
5. 交给 gwb-docsite 的 `addFeature` 加 `@godcreator/collab`，范围是 `^<打包时的 collab 版本>`
6. 把平台模板的首页 `site/app/routes/home.tsx` 换成打包进来的项目首页（它 import 协作功能的接线文件，所以要等加完功能再写）
