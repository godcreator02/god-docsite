## 磁盘上：一串一个文件夹

评论目录下一串一个文件夹，文件夹名就是串 id；串头是 `index.mdx`，回复各一个 `<回复 id>.mdx`，同目录还能放附件。串 id 与回复 id 同一个形状：`20261012t153000-ab12`（本机时刻到秒，加几位随机的小写字母数字）。id 先过形状校验再拼路径，不会被拼出评论目录以外的路径。

{/* ref file="../packages/comments/src/core/comment-file.ts" lines="4-11" hash="1ba19392edd4" blob="b7004ae5ad12" */}

每个文件是 frontmatter 加 MDX 正文；作者只存人员 id（`author`），名字显示时再按名单换。

写文件时每个值写成 JSON 字符串，它同时是 YAML 的双引号标量：换行这类控制字符都被转义，每个字段占一行，读回得到原值。划字锚点的 JSON 很长、里面有引号，也只占一行。例子的串头在磁盘上是这样（就是上面组件第 4 步那份）：

```mdx
---
page: "index.mdx"
author: "zhou"
createdAt: "2026-10-12T07:30:00.000Z"
status: "open"
anchor: "{\"quote\":\"第二段话。\",\"start\":15,\"end\":20,\"snapshot\":\"标题文字第一段话，着重的部分。第二段话。￼后面还有字\"}"
---

这一句要不要举个例子？
```

## 批在哪：锚点的三种写法

串头的 `anchor` 字段决定批的是哪里，按字面认，不另加类型字段——同一个字段认成整页、元素、划字、认不出四种结果：

## 已解决只记在串头

串头 frontmatter 的 `status` 是 `open` 或 `resolved`（不写等于 `open`）；`resolved` 时 `resolvedBy`（人员 id）与 `resolvedAt`（ISO 时刻）都要有，`open` 时两项都不能有；回复不能带这三项。标为已解决、重新打开只改串头的这三项，别的字段与正文原样写回；已经是这个状态再标一次拒绝（409），写明是谁在什么时候标的：

## 表情回应记在被点的那条评论上

每条评论（串头或回复）下面可以点表情回应，只收固定的八个：👍 👎 😄 🎉 😕 ❤️ 🚀 👀，界面按这个顺序摆。别的表情只能写进正文：输入框右边的表情按钮列出一组常用的，点了插在光标处，存进去就是正文里的字。

{/* ref file="../packages/comments/src/core/reactions.ts" lines="1-9" hash="809dd760f5ef" blob="7a93044886c3" */}

回应存在被点的那个文件的 frontmatter 字段 `reactions` 里，值照样是一个 JSON 字符串：表情对点了它的人员 id，按点的先后排，没人点的表情不写，一个都没有时整个字段去掉。小王和小周都点了 👍、小周点了 🎉 的串头多出这一行：

```mdx
reactions: "{\"👍\":[\"wang\",\"zhou\"],\"🎉\":[\"zhou\"]}"
```

加上、撤掉都只改这一个字段，别的字段与正文原样写回；已经点过还加、没点过还撤都拒绝（409）：网页上的按钮按它看到的状态发「加」或「撤」，状态过时了就告诉它，不会把别人刚点的撤掉。读的时候不认识的表情、空列表、同一个人点了两次都直接报错并点名文件。

## 写入：唯一一份 action

图上第 1、2 号。全站的评论写入都提交到 `/comments`：这个路由既是全站评论页，它的 action 调 `handleCommentWrite`。路由文件由建站器写进站点的 `app/features/comments/`（只改本包 `template/`）：

{/* ref file="../packages/comments/template/comments.tsx" lines="14-17" hash="8ea0ded43bb4" blob="391d3c0bb103" */}

表单字段是界面与 action 之间的外部契约：八种 `intent`（建串、回复、删回复、删串、标为已解决、重新打开、加表情、撤表情），每种只收自己那几个字段，多写一个字段就拒绝；`as` 只给 agent 经命令用，网页界面里不出现。返回 `{ ok: true, intent, threadId?, replyId? }` 或 `{ ok: false, error }`。

{/* ref file="../packages/comments/src/site/action.server.ts" lines="7-37" hash="5928a9c4a996" blob="9272f5e66da8" */}

先核对来源与身份（identity 包的 `authorizeWrite`，细节归 identity 页），再写；来源或身份不对、字段不对、目标评论不存在，都回 `{ ok: false, error }` 带 4xx 状态码；别的错原样抛出，不吞。

{/* ref file="../packages/comments/src/site/action.server.ts" lines="126-143" hash="afdd150dbaa0" blob="9272f5e66da8" */}

建串时串头写 `page`、`author`、`createdAt`、`status: open`，批了东西再加 `anchor`；站点的第一条评论连评论目录一起建。`createdAt` 是 UTC 的 ISO 时刻，id 里的时刻是本机时间，两者在 UTC+8 的机器上差 8 小时（测试站的预置评论 `20261001t120000-seed1` 的 `createdAt` 是 `2026-10-01T04:00:00.000Z`）。回复只写 `author`、`createdAt`；删回复删一个文件，删串删整个文件夹（含附件）。写完不编译：评论是 fumadocs-mdx 集合里的文件，集合自己的文件监视会重新生成入口。

## 读回：从集合条目到评论串

图上第 3 号。平台模板在 `source.config.ts` 里把站点的 `comments/` 定义成集合 `comments`（怎么定义归 god-docsite 页）。页面 loader 用 `pageThreadsOf` 取本页的串，全站评论页用 `threadsByPageOf` 按页分组，再用 `commentsTableRowsOf` 排成表格的行：内容页的串写那一页的标题，功能包页面（报告页、协作页）的串标题写地址，归属的内容页已经不在站里的串不列。

{/* ref file="../packages/comments/src/site/threads.server.ts" lines="98-104" hash="9f4b7ea77281" blob="010d1168f315" */}

按文件夹分串：串按创建时间排，回复按文件名排（文件名就是带时刻的 id）。数据不完整就直接报错并点名文件：回复没有串头、串头缺 `page`、一个文件夹两个串头、回复带了已解决状态。

{/* ref file="../packages/comments/src/core/threads.ts" lines="52-94" hash="f867c2391e1b" blob="05c994a44769" */}

串头的 `page` 有两种写法：内容页写页面在 docs 集合里的路径（`plan/index.mdx`），功能包页面写地址（`/tasks`）。站点之外要拿它拼链接的（gwb-collab 的通知），用 `pageAddressOf` 换成站内地址：`/` 开头的原样返回，路径照 fumadocs 的 `getSlugs` 去掉扩展名、`index` 落到所在目录、括号分组目录不进地址，再逐段 `encodeURI`。

{/* ref file="../packages/comments/src/core/page-address.ts" hash="a7323e9f5118" blob="f2d1af612a7c" */}

交给界面前作者 id 换成名单里的 `{ id, name }`，只取这两项，身份码不会带出去；作者不在名单里直接报错。界面不认识身份码，只收「可写、署名是谁」或「只读、原因」（`commentsAccessOf`）。

## 正文里的位置：页面文字

图上第 4 号。划字的位置不按 DOM 存，按「页面文字」数：正文容器（带 `data-comment-scope` 属性，平台模板经 `commentScopeProps` 加在正文上）里的文字节点按顺序拼成的一个字符串：

<PageText />

划完字松手时，把选区换成页面文字里的位置，连同那一刻的整页文字一起存进锚点。所以换了界面语言、标题旁多一个隐藏的链接文字，位置都不受影响。

## 批一块：可批元素与稳定 id

批注模式里点正文，批的是离点击处最近的候选块：标题、段落、列表项、代码块、引用、表格、图片、figure 与图注、SVG、公式，加上任何显式写了 `data-comment-target` 的元素（组件想让自己整个可批就这么写）。布局用的 `div` 不是候选。

{/* ref file="../packages/comments/src/site/browser/annotate.ts" lines="19-23" hash="6d526f395470" blob="54bd19da4787" */}

浏览器里走一遍正文，给没有 id 的候选按内容算稳定 id（`dc-` 加内容指纹），标题保留自己的 id；同页内容相同的按出现次序加 `-2`、`-3`：

<StableIds />

不在候选块里的单放链接、按钮、画布这类也能批，id 用单独的前缀 `dc-s-` 与序号，不改变候选已经分到的 id。

## 正文改了以后：推算落点

图上第 4 号。正文每次变化（`CommentsDock` 观察整个文档的 DOM 变化，自己写的属性与自己的界面不算），都重新走一遍可批元素、重算页面文字，逐串推算落点。元素锚点按 id 找；划字锚点拿快照和现在的页面文字算逐字差异，再推算首尾。选一种改动看看：

<WhereItLands />

差异按词句整理过：碰巧相同的零星几个字不算没改，免得整段重写后，原文的首尾字对上新文字里不相干的字。差得太多时最多算 1 秒，用已算出的粗略结果，不卡住页面。同一份快照对同一版正文只算一次。首尾两个字都落在没改动的文字里才推算得出来；首尾之间有删改或插入，标「原文改过」。

## 界面：收件箱、浮窗、黄条

- 右下角工具条：可写时有「批注」开关；「评论」按钮弹出本页评论收件箱，按「正文里」「整页」「找不到原文」筛，可写时底部能批整页
- 点黄条、点高亮的字、或在收件箱点一行：被批的那一块正下方浮出这一串，不挤动正文；Esc 或点别处收起
- 地址带 `?comment=<评论串 id>` 时（gwb-collab 通知里评论的链接就是这样拼的），打开页面就浮出这一串，和在收件箱点那一行一样；这一页上没有那一串就不管
- 每条评论正文下面是它的表情回应，悬停能看到是谁点的；可写时自己点过的高亮，点一下撤掉，点别人的跟上，悬停一条评论露出的工具条里有「加表情」
- 被批的元素不铺底色，正文栏左边外侧画一道和它上下对齐的竖黄条；划的字用浏览器的 CSS Custom Highlight API 高亮（注册名 `docsite-comment`）
- 全站评论页 `/comments` 是只读表格，一行一串，按最近有人说话排，内容页与功能包页面的评论都列；那里不量落点，位置只按锚点的种类写

## 分层与谁在用它

建站、装完依赖后，建站器（平台包的 `addBaseFeatures`）把本包 `template/` 补进站点 `app/features/comments/`：全站评论页兼写入路由、侧栏入口、样式与正文高亮。评论目录不进 Tailwind 的源码扫描：扫到的文件一变，dev 下整页刷新，推送连接与页面状态都断掉。

| 层 | 导出 | 做什么 |
| --- | --- | --- |
| `core/` | `@godcreator/comments` | 评论文件的格式（读、写、状态、表情回应）、锚点的三种写法、按文件夹分串、`page` 换成站内地址（`pageAddressOf`）；不碰磁盘 |
| `node/` | `@godcreator/comments/node` | 评论目录的读写：建串、回复、删除、改状态、加撤表情，直接读整个目录（`readCommentThreads`，站点不在运行也能读） |
| `site/` | `@godcreator/comments/site` | `CommentsDock`、`CommentThread`、`CommentsTable`、`commentsAccessOf`、`commentScopeProps`；浏览器里的页面文字、稳定 id、落点推算在 `site/browser/`，不单独导出 |
| `site/` 服务端 | `@godcreator/comments/site/server` | `handleCommentWrite`、`pageThreadsOf`、`threadsByPageOf`、`commentsTableRowsOf`、`commentIntents` |

层之间的方向与不许有环由 `tests/dependency-rules.cjs` 检查；comments 只依赖 identity。

用它的四方就是总图右列。平台模板（god-docsite 的 `template/`）页面路由用 `pageThreadsOf`、`commentsAccessOf`、`CommentsDock`，正文组件加 `commentScopeProps`，头像用 identity 的 `Avatar` 包一层传给 `AvatarComponent`（怎么接归 god-docsite 页）；collab 的任务页与记录页把评论的 intent 转给 `handleCommentWrite`，站点接的也是那几样（`CommentsDock`、`commentScopeProps`、`pageThreadsOf`、`commentsAccessOf`、`commentIntents`），通知里评论的链接用 `pageAddressOf`；word-report 的报告页接 `CommentsDock`、`commentScopeProps`，站点的接线文件用 `pageThreadsOf`、`commentsAccessOf` 取本页评论，写入提交到 `/comments`；gwb-docsite 的评论命令与 gwb-collab 的收件箱都直接 `readCommentThreads` 读整个目录（图上第 5 号），前者还用类型 `CommentFileOnDisk`。
