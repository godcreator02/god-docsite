站点要知道「这台机器上是谁在看」，才能决定能不能写评论、署谁的名。identity 不做登录：名单是站点目录里进 git 的 `people.json`，每个 gwb home 有一个身份码，开发服务启动时由 gwb-docsite 交给站点；站点拿码在名单里找人。小周的电脑上码是 `zhoucode0001`，名单里 `zhou` 那一项带着这个码，所以他打开的站侧栏底部显示「小周」，能写评论。这一页从头到尾都用这份名单：小周（`zhou`）、小李（`li`，没有码）、Claude（`claude`，agent）。

## people.json：名单与身份码

名单是站点根目录的 `people.json`，一个数组，每项是一个人或一个 agent。公共字段 `id`、`name`、可选的 `gitea`（Gitea 账号，协作站核对权限用）与 `agent`；存在文件里的形状另外多一个 `codes`（这个人用过的身份码，每个 gwb home 一个）。两种形状在类型上分开：`StoredPerson` 带 `codes`，只在服务端用。

{/* ref file="../packages/identity/src/core/people.ts" lines="1-18" hash="a36c7d3705e3" blob="5d0cf38c6fe0" */}

身份码是 8 到 64 个小写字母或数字。校验一次列出全部问题，几条硬约束：id 不重复；一个码只能写在一个人名下；agent 不能有码（agent 写入时用 `as` 说明自己是谁，见「一次写入以谁的身份」）；写了认不出的字段也报错。

{/* ref file="../packages/identity/src/core/people.ts" lines="39-46" hash="cd11ac9fce65" blob="5d0cf38c6fe0" */}

文件每次都重新读，改了不用重启开发服务；写回时一项一行，加一个人或一个码，git 里的改动只有那一行：

```json
[
  {"id":"zhou","name":"小周","codes":["zhoucode0001"]},
  {"id":"li","name":"小李"},
  {"id":"claude","name":"Claude","agent":true}
]
```

## 身份码从哪来、怎么进名单

身份码由 gwb 插件 gwb-docsite 在本 home 第一次加载时生成、存在它的设置里，生成规则归 gwb-docsite 的页。把自己加进名单走它的命令 `docsite.people.join`，它调本包 node 层的 `joinSitePeople`。规则：名单里已有这个 id，就把码加进它的 `codes`——同一个人换一台电脑、一个新 home，就多一个码；没有就新加一项；码已经在别人名下、id 是 agent、`gitea` 和已写的不一样都报错；码已经在那个人名下时不动文件。

## 认人：dev 看身份码，发布版一律只读

认人的结果 `SiteIdentity` 只有两种：有人（公开形状的那个人），或没人加一句只读原因；原因里不写码本身。按码在名单里找：没有码，只读，原因是这个开发服务不是经 gwb-docsite 启动的；码不在名单里，只读，原因里写明调 `docsite.people.join`。

{/* ref file="../packages/identity/src/core/identity.ts" hash="ee7573cfb482" blob="7b82e260a0c2" */}

站点怎么跑决定看不看码：`dev`（本机由 gwb-docsite 启动的开发服务）按环境变量 `DOCSITE_IDENTITY_CODE` 找人；`start`（build 之后的发布版）一律只读，环境变量里有码也不看。所以写评论、改任务只在各人本机的 dev 里做，改完经 git 同步；为什么这样定，见轨迹卡 [只有本机 dev 能写，build + start 的发布版全面只读](/trajectory/2026-10-15-published-site-readonly)。

## 一次写入以谁的身份

认人只回答「这台机器是谁」；每次写入还要过 `authorizeWrite`：先核对请求的 `Origin` 头和站点的可信 origin 完全一样——可信 origin 由宿主配置，不从请求推导——再看有没有本机身份，最后看 `as`。被拒抛 `WriteAccessError`，带着要回给浏览器的状态码。选一种情况看看：

<WhoWrites />

`as` 只给 agent 用：agent 没有身份码，经命令写入时由人代它提交、写 `as: "claude"`；人不能用 `as` 换成别人，人的身份只取本机的身份码。`as` 是空字符串或不是字符串一律 400。返回的人也经白名单投影，调用方传进来的对象带着 `codes` 或别的服务端字段，也不会跟着返回出去。失败转成文本响应用 `writeAccessResponse`；评论的写入 action 不用它，自己把 `WriteAccessError` 转成 `{ ok: false, error }`，见 comments 的页。

## 交给浏览器的只有公开形状

`PublicPerson` 的 `codes` 写成 `never`，`StoredPerson` 在类型上不能直接当它用；要给浏览器只能经 `publicPersonOf` / `publicPeopleOf`，它们按白名单重造对象（只抄 `id`、`name`、`gitea`、`agent`），凡是进 loader 数据的人员列表都只能是 `publicPeopleOf` 的结果。

{/* ref file="../packages/identity/src/core/public-people.ts" hash="7f2a0fd0e311" blob="ec5d2ba8b743" */}

类型挡不住 `as` 断言，所以 `IdentityProvider` 渲染时再查一次：人员列表里有谁带着 `codes` 就直接报错。页面里的组件用 `useSiteIdentity()` 取本机身份、`useSitePeople()` 取名单。侧栏底部的 `IdentityBadge` 有人显示头像与名字，只读显示「只读」、鼠标停上去看原因；头像 `Avatar` 是名字第一个字加一个由 id 算出的底色（改名不变色），不联网取图。

## 在正文里 @ 人

评论正文里 @ 人写成 `@<id>`，id 要在名单里才算；按出现顺序、不重复。写 @ 时弹出的名单按 id 或名字筛，id 以输入开头的排前面。collab 的收件箱与 gwb-docsite 的评论命令都用 `mentionsOf` 认出 @ 了谁。

## 分层与谁在用它

{/* tree dir="../packages/identity/src" depth="1" hash="efe277dfc658" */}

| 层 | 导出 | 做什么 |
| --- | --- | --- |
| `core/` | `@godcreator/identity` | 名单的校验与加入规则、按码认人、公开投影、写入前核对、@ 的认法；不碰磁盘、不 import React |
| `node/` | `@godcreator/identity/node` | 读写站点的 `people.json`、按运行方式与环境变量认本机身份 |
| `site/` | `@godcreator/identity/site` | `IdentityProvider` 与两个 hook、`Avatar`、`IdentityBadge`；样式在包的 `styles.css` |

谁在用它（只写调哪个导出）：

- 平台模板（god-docsite 的 `template/app/lib/site.server.ts`）：`siteIdentity(dir, mode)`、`sitePeople(dir)`
- 平台模板的 `template/app/routes/layout.tsx`：`publicPeopleOf`、`IdentityProvider`、`IdentityBadge`；`template/app/lib/content.tsx`：`Avatar`
- comments：`authorizeWrite`、`personOf`、类型 `SiteIdentity`
- collab：`authorizeWrite`、`publicPeopleOf`、`mentionsOf`、`Avatar`
- gwb-docsite：`joinSitePeople`、`sitePeople`、`identityCodeEnvName`、`identityCodePattern`、`mentionsOf`
