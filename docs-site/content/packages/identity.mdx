站点要知道「这台机器上是谁在看」，才能决定能不能写评论、署谁的名。identity 不做登录：名单是站点目录里进 git 的 `people.json`，每个 gwb home 有一个身份码，开发服务启动时由 gwb-docsite 交给站点；站点拿码在名单里找人。小周的电脑上码是 `zhoucode0001`，名单里 `zhou` 那一项带着这个码，所以他打开的站侧栏底部显示「小周」，能写评论。这一页从头到尾都用这份名单：小周（`zhou`）、小李（`li`，没有码）、Claude（`claude`，agent）。

先看一张图，把身份码从哪来、名单在哪、站点怎么认人、谁在写入前核对摆清楚；后面每一节开头都会写它在图上的位置。

## people.json：名单与身份码

名单是站点根目录的 `people.json`，一个数组，每项是一个人或一个 agent。公共字段 `id`、`name`、可选的 `gitea`（Gitea 账号，协作站核对权限用）与 `agent`；存在文件里的形状另外多一个 `codes`（这个人用过的身份码，每个 gwb home 一个）。两种形状在类型上分开：`StoredPerson` 带 `codes`，只在服务端用。

{/* ref file="../packages/identity/src/core/people.ts" lines="1-18" hash="a36c7d3705e3" blob="5d0cf38c6fe0" */}

身份码是 8 到 64 个小写字母或数字。校验一次列出全部问题，几条硬约束：id 不重复；一个码只能写在一个人名下；agent 不能有码（agent 写入时用 `as` 说明自己是谁，见「一次写入以谁的身份」）；写了认不出的字段也报错。

{/* ref file="../packages/identity/src/core/people.ts" lines="39-46" hash="cd11ac9fce65" blob="5d0cf38c6fe0" */}

文件每次都重新读，改了不用重启开发服务；写回时一项一行，加一个人或一个码，git 里的改动只有那一行：

```json
[
  {"id":"zhou","name":"小周","codes":["zhoucode0001"]},
  {"id":"li","name":"小李"},
  {"id":"claude","name":"Claude","agent":true}
]
```

## 身份码从哪来、怎么进名单

图上第 1、2 号。身份码由 gwb 插件 gwb-docsite 在本 home 第一次加载时生成、存在它的设置 `identity-code` 里，生成规则归 gwb-docsite 的页。把自己加进名单走它的命令 `docsite.people.join`：它带上 id、名字（可选 `gitea`）与本机的码，调本包 node 层的 `joinSitePeople` 写回名单。加进名单时文件怎么变、什么时候被拒：

<JoinCases />

写回一项一行：加一个人或一个码，git 里的改动只有那一行；码已在名下时不动文件。这一节的名单比贯穿例子少小李一项——他还没把自己加进去，正好用他做「新的人」。

`dev`（本机由 gwb-docsite 启动的开发服务）按托管方上下文里的身份码找人：gwb-docsite 把它推进频道 `host`，站点模板取出来作为 `siteIdentity(dir, mode, identityCode)` 的第三个参数，身份包自己不读推送通道；`start`（build 之后的发布版）一律只读，给了码也不看。所以写评论、改任务只在各人本机的 dev 里做，改完经 git 同步；为什么这样定，见轨迹卡 [只有本机 dev 能写，build + start 的发布版全面只读](/trajectory/2026-10-15-published-site-readonly)。

## 一次写入以谁的身份

图上第 6 号。认人只回答「这台机器是谁」；每次写入还要过 `authorizeWrite`：先核对请求的 `Origin` 头和站点的可信 origin 完全一样——可信 origin 由宿主配置，不从请求推导——再看有没有本机身份，最后看 `as`。被拒抛 `WriteAccessError`，带着要回给浏览器的状态码。选一种情况看看：

<WhoWrites />

`as` 只给 agent 用：agent 没有身份码，经命令写入时由人代它提交、写 `as: "claude"`；人不能用 `as` 换成别人，人的身份只取本机的身份码。`as` 是空字符串或不是字符串一律 400。返回的人也经白名单投影，调用方传进来的对象带着 `codes` 或别的服务端字段，也不会跟着返回出去。失败转成文本响应用 `writeAccessResponse`；评论的写入 action 不用它，自己把 `WriteAccessError` 转成 `{ ok: false, error }`，见 comments 的页。

## 交给浏览器的只有公开形状

图上第 5 号。存在文件里的人带 `codes`（`StoredPerson`），交给浏览器前按白名单重造：`publicPersonOf` / `publicPeopleOf` 只抄 `id`、`name`、`gitea`、`agent` 四项，`PublicPerson` 的 `codes` 写成 `never`，`StoredPerson` 在类型上就不能直接当它用；凡是进 loader 数据的人员列表都只能是 `publicPeopleOf` 的结果，或在它上面补头像地址的 `publicPeopleWithAvatars`（见下一节）：

{/* ref file="../packages/identity/src/core/public-people.ts" hash="9427d3c772d6" blob="549e1217dda2" */}

<PublicShape />

类型挡不住 `as` 断言，所以 `IdentityProvider` 渲染时再查一次，人员列表里有谁带着 `codes` 就直接报错。页面里的组件用 `useSiteIdentity()` 取本机身份、`useSitePeople()` 取名单。侧栏底部的 `IdentityBadge` 有人显示头像与名字、点开是头像面板，只读显示「只读」、鼠标停上去看原因。

## 头像：一人一个文件

头像不进 `people.json`，按文件名约定放：站点根的 `public/avatars/<人员 id>.webp`，小周的就是 `public/avatars/zhou.webp`。`public/` 下是静态文件，dev 与只读的发布版都按 `/avatars/zhou.webp` 取，和页面一起进 git。服务端只收边长 128 的正方形 webp、不超过 64 KB；裁剪、缩放、转格式都在浏览器里做，服务端不带图片处理的依赖。

{/* ref file="../packages/identity/src/core/avatar.ts" lines="1-26" hash="aef65c1a20d9" blob="c3b06500619c" */}

**显示**。布局路由交给 `IdentityProvider` 的名单用 node 层的 `publicPeopleWithAvatars`：在公开形状上给有头像文件的人补一项 `avatar`，地址后面带文件修改时间（`/avatars/zhou.webp?v=1760680000000`），换了图地址就变，浏览器不拿缓存里的旧图。`Avatar` 照旧只收 `{ id, name }`，按 id 在 `IdentityProvider` 的名单里查 `avatar`：有就画图，没有就画名字的第一个字加一个由 id 算出的底色（改名不变色），所以评论、任务这些调用方不用管头像从哪来。`Avatar` 要在 `IdentityProvider` 里面用，外面用直接报错；协作站首页在整站布局之外，`ProjectHome` 自己在最外面放一个 `IdentityProvider`（见 collab 的页）。

{/* ref file="../packages/identity/src/node/avatar-file.ts" lines="10-22" hash="a304ad6b8842" blob="56e43e8f9bbc" */}

**上传**。小周在自己电脑上的 dev 里点侧栏底部的「小周」，弹出头像面板：

| 一步 | 在哪 | 做什么 |
| --- | --- | --- |
| 选图 | 头像面板（`IdentityBadge` 点开） | 只有认出本机身份时身份标记才是按钮；只读（含发布版）没有面板 |
| 处理 | 浏览器里的 `avatarWebpOf` | 居中裁成正方形、缩到 128×128、转 webp（SVG 也在这里画成位图），质量从高往低试到不超过 64 KB；浏览器转不出 webp 就报错 |
| 提交 | `PUT /identity/avatar`，正文是图本身 | 这个路由由本包的 `template/` 写进站点 `app/features/identity/`，交给 `handleAvatarWrite` |
| 核对 | `handleAvatarWrite` | 先 `authorizeWrite`（Origin 与本机身份，不收 `as`），再 `assertAvatarImage`：类型不是 `image/webp` 回 415，超过 64 KB 回 413，不是 webp 或不是 128×128 回 400，原因写在响应里，不替它修正 |
| 写入 | 站点目录 | 存成 `public/avatars/<本机身份的 id>.webp`，回 `{ avatar }` 新地址；面板记下新地址，页面上各处的 `Avatar` 跟着换 |

「改回首字」是 `DELETE /identity/avatar`，删掉自己的文件；没有文件回 404。只能改自己的：路由只认本机身份，没有 `as`。agent 没有身份码，它的头像由人做好一张 128×128 的 webp，直接放成 `public/avatars/<agent 的 id>.webp` 再提交；协作仓里谁能提交这些文件由合并检查管（见 collab 的页）。

## 在正文里 @ 人

评论正文里 @ 人写成 `@<id>`，id 要在名单里才算；按出现顺序、不重复。写 @ 时弹出的名单按 id 或名字筛，id 以输入开头的排前面。collab 的收件箱与 gwb-docsite 的评论命令都用 `mentionsOf` 认出 @ 了谁。

## 分层与谁在用它

{/* tree dir="../packages/identity/src" depth="1" hash="efe277dfc658" */}

| 层 | 导出 | 做什么 |
| --- | --- | --- |
| `core/` | `@godcreator/identity` | 名单的校验与加入规则、按码认人、公开投影、写入前核对、@ 的认法、头像的存放约定与核对；不碰磁盘、不 import React |
| `node/` | `@godcreator/identity/node` | 读写站点的 `people.json`、按运行方式与交来的身份码认本机身份、带头像的公开名单、头像写入路由的处理 |
| `site/` | `@godcreator/identity/site` | `IdentityProvider` 与两个 hook、`Avatar`、`IdentityBadge` 与它点开的头像面板、浏览器里的头像处理；样式在包的 `styles.css` |
| `template/` | （建站器复制进站点） | 头像写入路由 `/identity/avatar`，建站时由 `addBaseFeatures` 补进站点 `app/features/identity/` |

层之间的方向与不许有环由 `tests/dependency-rules.cjs` 检查；identity 不依赖任何别的功能包。

用它的三方就是图上的 gwb-docsite 与右列两方，图上画过的调用不再逐条列，另列几个图上没画的：gwb-docsite 另用 `identityCodePattern`、`mentionsOf`（评论命令里认 @）；comments 另用 `personOf` 与类型 `SiteIdentity`；collab 另用 `publicPeopleWithAvatars`、`mentionsOf`、`IdentityProvider`、`Avatar` 与头像文件夹的位置 `avatarsDirInSite`（合并检查用），平台模板的正文页也用 `Avatar`。
