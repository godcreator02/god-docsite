仓根的 README.md、AGENTS.md、CLAUDE.md，插件里的 SKILL.md，是现状区 mdx 正本的机读版：改正本、在站目录运行 `pnpm doc:render` 重新生成，两份放进同一个提交，`pnpm doc` 核对两边是否一致。doc-export 负责「正本 → 生成物」这一步与「生成物跟正本一致吗」的核对；读配置、选哪些正本、打印结果归 docfirst。

这一页从头到尾用同一个例子：正本 `docs/a.mdx`（frontmatter 写了 `name`、`description`、`secret`，正文一个 `# 摆放`、一处钉在 `src/greet.ts` 第 2–3 行的钉、一个三行写法的 `<Note>`），三个落点：`skills/x/SKILL.md` 点名 `name` 与 `description`、`PLAIN.md` 是字符串写法、`BAD.md` 点名的 `nope` 正本里没有。

## 一篇正本、几个落点

图上第 1、3 号。`docfirst.config.mjs` 的 `outputs` 是「正本 → 落点数组」的表。落点两种写法：字符串（相对项目根的路径，等于 `frontmatter: []`）、对象 `{ to, frontmatter }`；形状不对当场报错：

本站的写法是一个 `skill(name)` 帮手，把说明书正本对到 `../plugins/docsite/skills/<名>/SKILL.md`，点名 `name`、`description`——宿主靠这两个字段决定什么时候读这份说明书：

{/* ref file="docfirst.config.mjs" lines="21-21" hash="e6b80bdb8ff2" blob="ce0b89f792c2" */}

落点有三条规则：只认相对项目根的路径；不能落进正本所在的目录（内容根）；一个落点只许一篇正本写：

{/* ref file="../packages/doc-export/src/node/outputs.ts" lines="84-100" hash="b6797d754072" blob="37cec59bcc93" */}

例子的三个落点写成配置是：

```js
outputs: {
  'docs/a.mdx': [
    { to: 'skills/x/SKILL.md', frontmatter: ['name', 'description'] },
    'PLAIN.md',
    { to: 'BAD.md', frontmatter: ['nope'] },
  ],
}
```

## 渲染：一条管线

图上第 5 号。

<RenderPipeline />

组件里的六步就是 `renderMachineMarkdown` 的全部：remark 解析（gfm、frontmatter、数学公式、mdx），换行先统一成 LF；钉码标记换成 `codePin` 节点（调用 code-pin 的 `replacePinMarkers`，核对由调用方传进来的 `checkPins` 做）；查出渲染不了的地方；remark-stringify 加 `machineTextHandlers` 写出 Markdown，开头的空行去掉。handlers 不改树：`codePin` 写成 code-pin 的 `exportCodeOf` 交回的代码块（标题 `路径:起-止` 是今天的位置），组件写成名册交回的节点，frontmatter 不写。别的文字经 remark 重新写出：读出来的文字跟正本一样，个别转义的写法会变（测试里 `\}` 写出成 `}`）。

## 什么时候拒绝生成

能生成的条件是严的，而且一次列全：

| 正本里有 | 结果 |
| --- | --- |
| 钉：新鲜 | 写今天那几行 |
| 钉：有变动（黄灯） | 照写今天那几行，不拦 |
| 钉：没确认 | 拒绝：「第 n 行的钉还没确认，先确认再生成」 |
| 钉：缺失 | 拒绝：「第 n 行的钉缺失（缺失理由），先修好」 |
| 名册外组件 | 拒绝：「第 n 行有名册外组件 `<名字>`，先在名册里给它写机读规则」 |
| 名册内组件，但规则交回的内容里还嵌着名册外组件、写不了的钉，或规则本身出错 | 拒绝：「第 n 行的组件 `<名字>` 换不成机读文字：…」 |
| mdx 表达式，包括普通注释 `{/* … */}` | 拒绝：「第 n 行有 mdx 表达式 `{…}`，生成物只写 Markdown」 |
| import / export | 拒绝：「第 n 行有 import / export，生成物只写 Markdown」 |

正本里所有渲染不了的地方收齐后一次抛 `RenderRefusal`，一处一句；`drop` 掉的组件里面是什么不管。最容易踩的是正本里随手写的 `{/* 说明 */}`——它是 mdx 表达式，会让整篇生成失败。

黄灯的钉不拦生成：生成物写的是今天的代码，黄灯只说明正文那句话待复核；拦它的是 docfirst 的规则——本仓未提交改动引起的黄灯算红（见 code-pin 页）。

## 组件名册：组件在生成物里写成什么

图上第 1、6 号。名册是「组件名 → 规则」的表，规则三种：`"children"`（去掉外壳只留子内容）、`"drop"`（整个不进生成物）、函数 `(node, helpers) => 节点`：

{/* ref file="../packages/doc-export/src/core/roster.ts" lines="20-34" hash="1736fdbd2c61" blob="3e7d67c94a00" */}

函数规则的契约：只经 `helpers` 读节点（`attr`、`textOf`）、造节点（`text`、`heading`、`paragraph`、`quote`、`children`），不碰节点的字段；`helpers.inline` 说明组件是不是写在句子里。规则交回的内容里再嵌着组件，写出时各自再换。

三种规则把组件写成什么、名册外的组件是什么下场，选一种看：

<RosterRules />

doc-export 自带一份 fumadocs 名册（`Note`、`Files`、`Folder`、`File` 这四个），讲解组件的机读规则（`*.ai.mjs`）就是函数规则，写法见 explainer 页「机读文字」一节。

名册由使用方给：docfirst 在配置的 `fumadocsRoster: true` 时先放 fumadocs 名册，再用 `components` 里同名的规则盖过它；docfirst 只对生成正本查名册，别的页里用什么组件都不管。

## 分层与谁在用它

{/* tree dir="../packages/doc-export/src" depth="1" hash="40538faa6072" */}

| 层 | 导出 | 做什么 |
| --- | --- | --- |
| `core/` | `@godcreator/doc-export` | 渲染管线、名册机制与 fumadocs 名册、frontmatter、落点表与 `planOutputs`。钉的核对从传入的 `checkPins` 来，不读文件；fumadocs 名册是纯数据加纯函数，不 import fumadocs 与 React，只有命令行的环境也加载得动 |
| `node/` | `@godcreator/doc-export/node` | 读正本、读写落点、落点的地盘规则；钉经传入的 code-pin `Pinner` 核对 |

依赖方向：doc-export 只依赖 code-pin。

用它的只有 docfirst，就是总图上那一排：读配置时用 `placementsOf` 归一落点表、按 `fumadocsRoster` 合名册（第 1 号）；装配项目时用 `assertOutputTurf` 查落点的地盘；`render` 与 `confirm` 的最后一步用 `renderOutputs` 写生成物、`check` 对生成正本用 `unknownComponents` 查名册、用 `verifyOutputs` 核对生成物（第 2 号）。
