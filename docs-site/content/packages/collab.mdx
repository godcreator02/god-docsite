协作站没有服务器端数据库：任务与模块就是协作仓里 `collab/records/` 下的 JSON 文件，跟页面一起经 git 同步。collab 包规定这些文件长什么样、网站能怎么改它们、合并请求进 main 之前查什么，也提供站点上的任务页、日历、日志页。git、Gitea、通知从哪来都归 gwb-collab 插件，这个包自己不跑 git——合并检查除外，它只调 git 读。

## 协作仓里放什么

## 一条记录一个文件

记录只有两种：任务 `task` 与模块 `module`。模块只有截止日、不存状态，完没完成由归进它的任务算。

{/* ref file="../packages/collab/src/core/records.ts" lines="9-35" hash="989f4a552850" blob="76e7ac5ff4e8" */}

记录 id 是东八区（UTC+8）时间 14 位加 `-` 加 7 位小写字母数字，文件名就是 `records/<id>.json`；时间用 `@godcreator/utc8-time` 算，作者电脑设成哪个时区都一样。2026-10-19 以前建的记录，id 里是作者电脑当时的本地时间，不改名。新建一条就是新加一个文件，两个人各建各的不会碰到同一个文件。

这一页的例子取自测试夹具 `packages/collab/test/fixtures.ts` 第 4–17 行：人员列表里有 `godcreator`（负责人）、`bob-test`（小王）、`carol-test`（小李）和 agent `claude`；`godcreator` 建了任务 `20260925160530-t5v9w3d`「补 ADC 通道对比」，owner 是 `carol-test`、截止 `2026-10-10`；还有模块 `20260920090000-m1a2b3c`「采样板」。这条任务写成文件就是：

```json
{
  "id": "20260925160530-t5v9w3d",
  "type": "task",
  "author": "godcreator",
  "status": "todo",
  "title": "补 ADC 通道对比",
  "owner": "carol-test",
  "due": "2026-10-10"
}
```

编码是规范写法：字段按固定键序、两格缩进、一个字段一行、中文不转义、换行结尾，同一条记录每次编码出的字节相同。一个字段一行，两人的改动能不能自动合上就由 git 按行判：改不同的记录、各建各的新文件能合上；同一条记录里两人改的行中间隔着没人动的行也能合上，改到同一行或相邻两行就合不上。这几种情况是在仓外临时目录用 git 2.53（默认 ort 策略）实跑出来的：

<ConflictCases />

合不上时文件里留着 git 的冲突标记。解码时先找标记，找到就报出是第几行，让人（或 AI）按两边的意思改好，不猜；认不出的字段、认不出的类型都报错。

## 模块分组

一个项目里有几条线（比如 SST 与 MMC 并在一个协作站里）时，负责人在 `collab/groups.json` 里列出分组，模块的 `group` 字段写其中一组的 `id`，任务页就一组画一张甘特图。没有这个文件就不分组，任务页只画一张，和以前一样。

```json
[
  { "id": "sst", "title": "SST" },
  { "id": "mmc", "title": "MMC" }
]
```

- 列表至少一组；`id` 是小写字母、数字，用 `-` 连接；`id` 与 `title` 都不能重复；只有这两个字段。写错了整份读不出，报在 `groups.json` 上
- 模块写的 `group` 不在列表里（或者仓里没有这个文件），报在那条模块上；新建、修改时写入规则按它拦
- 先后就是各张图的先后。没有模块的组不画；没写分组的模块放进最后一张「未分组」。几张图共用一条时间轴，左列定宽，月份上下对齐
- 别人也能改模块的 `group`；分组列表本身只有负责人能改（见「合并检查」）
- 网页上新建模块时，有分组就要先选一组或「不分组」才能提交；模块那一页能换分组

## 读出状态与校验

图上第 1、4 号。核心层不碰磁盘：它只收一份 `CollabSnapshot`——`people` 是 `site/people.json` 的原文，`files` 是 `collab/` 下每个文件的原文。站点的 loader 与写入规则每次从磁盘现读这一份（第 1 号），gwb-collab 提交前从 git 的两个版本各取一份（第 4 号）。

`collabState` 读出任务、模块与分组，读不出的文件、重复的 id、所属模块不存在、模块的分组不在列表里都列成问题；`validateCollab` 只查格式：换行是 LF、能解码且是规范写法、文件名等于 id、作者与负责人在人员列表里、id 不重复、所属模块存在、分组列表读得出、模块的分组在列表里，不查谁改了谁的记录。

**只拦新问题**：`newProblems(before, after)` 只交回 after 有、before 没有的问题——同一个文件、同一句说法算同一个问题。`newFormatProblems(base, merged)` 是 gwb-collab 提交前在本机查的那一步，网站写入也按它拦。一个人不会因为别人留下的问题被挡住，原本就有的问题照旧显示在网站顶部的提示栏里。

## 合并检查

图上第 5 号。协作仓的合并请求由 NAS 上的执行器照协作仓 main 上的工作流跑包里的命令行 `collab-merge-check`；执行器怎么跑、谁合并归 Gitea 区的 [实时推送与执行器](/gitea/push)，这一节只讲检查本身判什么。

检查在内存里算出「把 head 合进 main」的树（`git merge-tree --write-tree`），不动工作区和分支；有冲突就停在第一条。没冲突时，改了哪些文件按 main 与**合并后的树**算，不按 head 算：head 落后于 main 时，main 后来加的文件不会算成 head 删的。

这一节换用合并检查测试里的仓：main 上有人员列表（alice 甲，带身份码；bob 乙）和甲的一条任务，bob 从 main 分出 topic 提交。选一种改动看看：

<MergeCases />

第二条「只有负责人能改的内容」逐个文件判：

- 整个文件算的：`.gitea/`、`.github/` 下的一切（工作流改了能绕过检查、拿到组织密钥）；`site/.npmrc`、`site/pnpm-workspace.yaml`（从哪个源装包、哪些包能跑安装脚本）；站点身份文件 `site/docsite.json`（gwb-collab 靠它认出协作仓）；模块的分组列表 `collab/groups.json`（项目分几条线由负责人定）；`site/` 根目录下 Node 会执行的 `*.config.*` 与 `.postcssrc*`
- `site/package.json` 逐处算：依赖两段以外的键（如 `scripts`）、`@godcreator/` 下的包（加、删、改版本都算）、写成网址或本地路径的依赖；别的库加、升级、删都放开；文件新建、删掉或读不懂时整个文件算
- `site/people.json` 只放行一种改动：提交人只给 `gitea` 是自己的那一项加减 `codes`，项数、先后、别的字段、别人的项都不变
- 头像文件夹 `site/public/avatars/`（身份包的头像约定）只放行一种改动：加、换、删 `<人员 id>.webp`，而 main 上的人员列表里这个 id 的 `gitea` 是提交人。别人的、agent 的（agent 没有 `gitea`）、别的文件名都只有负责人能改

改了哪些文件用 `git diff --no-renames` 算：改名的文件新旧两个路径都列出来，把只有负责人能改的文件挪走（比如把甲的头像改名成自己的）也查得到。

### 一键提交

平时的提交审核不用叫 AI：通知栏点开后的「要处理的事」里有「一键提交」，有本机还没提交审核的改动（`unsubmitted` 通知）时出现。有冲突、不在 main、`collab/` 里有读不对的记录时提交审核一定被拒，按钮不能点，旁边写明先处理什么（`submitBlockersOf`），这时用「复制给 AI」。

按钮和 gwb-collab 之间来回写推送通道的另一个频道 `collab-submit`（`submitChannel`），里面只有一份状态 `SubmitState`：

1. 按钮提交到任务页的 action（`intent=request-submit`）。核对过本机身份后，先问 gwb-collab 在不在听这个频道：不在听回 503，不写请求；已经在提交回 409；都没问题就写 `{ state: 'requested', by, at }`
2. gwb-collab 经 gwb-docsite 带着令牌订阅着这个频道，收到 `requested` 就跑提交审核，先写回 `running`
3. 合并了写 `merged`，带上合并请求的编号，提示栏显示 15 秒；被拒写回 null，原话照旧成为一条 `submit-failure` 通知，在频道 `collab` 里

AI 调 `collab.submit` 时 gwb-collab 也写 `running` 与结果，网页上同样看得到进度；一个项目同一时刻只跑一次。站点怎么接这个频道写在 `template/site.server.ts`：读、写用平台的 `siteFeedValue`、`publishSiteFeed`，「在不在听」用 `siteFeedHasLauncher`（机制见 god-docsite 包页的「推送通道」）。`CollabSite.submit` 是可选的：接线文件还是旧的站点没有这个按钮，action 回 501。

## 正文里的三种链接

页面与日志正文里写普通 Markdown 链接，remark 插件按地址换成组件：`[文字](/tasks/<记录 id>)` 换成 `RecordLink`，`[](/calendar/<日期>)` 换成 `JournalLink`（日期要真实），`[](repo:<仓>/<路径>)` 换成 `RepoLink`；链接文字留作组件的内容。

{/* ref file="../packages/collab/src/mdx/remark-collab-links.ts" lines="13-21" hash="af6c39e86e3a" blob="9007267aa9a5" */}

`repo:` 链接指向项目文件夹（协作仓的上一级，组织里的仓都克隆在这里）里某个仓的文件：PDF、图片、网页、视频交给浏览器，二进制文件用系统默认程序，文本文件在开着项目文件夹的 VS Code 窗口里打开（可带 `#L<行号>`）；只读的站点一律不碰项目文件夹。

记录那一页的「日志里的进展」是反向链接：在每篇日志里找 `<RecordLink id="…" />`，列出引用了这条记录的那几段文字，新的日子在前。

## 分层与谁在用它

| 层 | 导出 | 做什么 |
| --- | --- | --- |
| `core/` | `@godcreator/collab` | 记录格式、状态与校验、写入规则、SiteFeed 与通知的形状、仓里的固定路径、工作流模板的占位；不碰磁盘、不 import React |
| `node/` | `@godcreator/collab/node` | 从磁盘读快照、照写入计划改文件、读日志文件、合并检查（调 git，只读）、repo: 链接在本机打开 |
| `mdx/` | `@godcreator/collab/mdx` | 构建期的 remark 插件：三种链接换成组件 |
| `site/` | `@godcreator/collab/site`、`@godcreator/collab/site/server` | 页面组件；服务端的 loader 与 action |
| `cli/` | 命令行 `collab-merge-check` | 解析参数、调合并检查、按结论定退出码 |

层之间的方向与不许有环由 `tests/dependency-rules.cjs` 检查；collab 只依赖 identity 与 comments。

用它的三方就是总图右列：站点用 `template/` 下的接线文件，以及 gwb-collab 写出的项目首页；gwb-collab 用路径常量、`readCollabSnapshot` 与 `createRecord` / `updateRecord` / `deleteRecords`（命令改记录）、`newFormatProblems`（提交前检查）、`changedFilesBetween` 与 `leadOnlyProblems`（推送前检查）、`siteFeedChannel` 与通知相关的导出、`renderMergeWorkflow`（写工作流）；NAS 上的执行器按工作流里的 `MERGE_CHECK_RANGE` 装本包，运行 `collab-merge-check`。
