# 维护者手册

这一章回答：要改这个仓的代码，东西都放在哪儿、提交前得跑绿哪几条、提交怎么写、发布是什么状况。

## 仓布局

```text
单元目录                        只有 unit.json，不在 git 里
  god-live-doc/                 = git 仓，同时是 pnpm 包工作区
    AGENTS.md  CLAUDE.md  README.md
    packages/
      livedoc/                  主包：src 下四层 engine / host / fumadocs / cli
      trajectory/               轨迹包：卡与星轨盘，独立的一条包线
      gwb-live-doc/             工作台件：跟两个包同住，两边互不认识；铺六区与三份说明书在这儿
    docs-site/                  这个站：用这套机制写自己的文档，也是工作区成员
      content/docs/             文档
      content/trajectory/       轨迹卡
    tests/                      工作区级测试；fixtures/trajectory/ 是星轨盘的诗名 fixture
```

**没有陪绑的示例仓**：这个站自己就是消费方——它装的是工作区里的两个包，钉的是工作区里的真源码，
「装了这两个包的项目长什么样」在这儿是活的。

## 提交规矩

按步骤拆，一个提交一件事。文档章节和它带来的记录簿改动放在同一个提交里——记录簿就是那一章的记忆，
分开提交等于让中间那个提交自相矛盾。挂了 outputs 映射的文档（README、AGENTS.md、两份 skill）动的是 mdx 源：
`livedoc render` 重摆之后，mdx 源、生成物、记录簿同一个提交。提交信息中文，末尾带会话里给的 `Co-Authored-By` 与 `Claude-Session` 两行。

## 发布：手跑 pnpm publish

两个包发进本机 registry（Verdaccio）。devkit 的 `release` 是插件形态专用（门禁查 scope 之外还查
exports 指 lib/、cordis.patch.yml，且一仓一包一插件），这套多包工作区不适用——发版手跑：
工作区根 `pnpm build` → 逐包 `pnpm pack --dry-run` 核清单 → `pnpm -r publish --no-git-checks`
（docs-site 是 private 自动跳）→ `registry status` 核对 → 逐包 `git tag`。纪律照总控台
`registry.md`：版本人改、同版本号永不重发。消费方按精确版本引，不走 `dsh plugin add`。

抬版本号时**跟着改 `packages/gwb-live-doc/src/deps.ts` 那张表**——铺六区往目标站补的就是它，
件的 `tests/attach.test.ts` 里有一条守着它跟工作区各包的版本对得上，忘了抬当场红。

**两边各发各的，没有先后。**件对包零依赖：它不打包那个包、三档依赖面里也没有它，所以先发哪个
都不影响另一个。件那一摊照 devkit 的插件规矩发（一仓一包一插件的那套在它身上成立），跟两个包的
手跑发版互不干涉。
