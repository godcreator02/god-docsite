**本页回答**：五类引用各该用在哪种论断上，挑错了会漏掉什么。

文档对代码说的话只有三种：内容、形状、有无；说的对象只有两种：文件、目录。五类引用把这张矩阵填满：

| | 文件 | 目录 |
| --- | --- | --- |
| 内容 | 行段 `ref 文件:起-止`；整文件 `ref 文件` | 不做——目录的内容就是 git 树哈希，改一行就黄，没有文档需要这种话 |
| 形状 | 名字 `has 文件 "字面量"` | 目录树 `tree 目录` |
| 有无 | 存在 `exists 路径`；断言不在 `absent 路径` | 同左 |

这一章拿本仓的判定层 `packages/docfirst-workflow/src/engine` 说事：只用 `node:crypto` 的那一层，几个源文件。
**这一章自己就是那篇手册**——下面每一处引用都是活的，钉的是那一层的真文件。每一节两段：
**读者看到的**（引用放在这儿，代码块和小标签是活的）、**改了之后**（那处代码要是动了，`docfirst check` 会打出什么）。

写引用只有一种写法：单独一行 `@@docfirst 动作 目标 @@`。confirm 把它换成 mdx 的正式记号 `{/* … */}`，
确认时的记录写在记号的属性上；此后行号与记录由 confirm 维护，不手改。mdx 有构建，文件里只有这一行，
内容是站 build 时现取的。

## 一、这一层里有什么：目录树

**读者看到的**

{/* tree dir="../packages/docfirst-workflow/src/engine" depth="1" hash="3e5a21fa3ef9" */}

一个文件一件事：`types` 是接口正本，`marker` 是记号语法（草稿记号、正式记号的属性与记录），`span` 管归一化、
段哈希、名字表哈希与 blob 名，`diff` 管行段映射与 diff 文本，`compare` 是五种目标怎么判、确认时记什么，
`service` 是编排，`index` 只放导出。

**改了之后**：有人加了 `engine/trace.ts`（给编排加一条调用轨迹），这一段没提，文件还没提交：

```text
🔴 content/docs/start/handbook.mdx  tree ../packages/docfirst-workflow/src/engine depth=1  有变动，是本仓还没提交的改动引起的（8 项）——在同一个提交里复核，再 docfirst confirm content/docs/start/handbook.mdx --accept
```

目录树的记录只是名字表的哈希，所以只知道「变了」、今天有 8 项，说不出多了哪个；站上这一处放的是今天的名字表。
改动还没提交、又跟这篇文档在同一个仓里，`check` 算红，拦下这次提交：「一个文件一件事」那段得在同一个提交里
补一句 trace 是做什么的，再 `--accept`。目录树只管名字，不管内容。

## 二、这个包怎么构建：整文件

**读者看到的**

{/* ref file="../packages/docfirst-workflow/tsdown.config.ts" hash="cf8cbda04785" blob="9006217a429e" */}

整份就这么多：五个入口、只出 esm、平台是 node、出 dts、每次清干净，外加一条「宿主只 import
不内联」。这个包的构建面小到能一眼看完，这句话本身就是论断——它一旦变长，就说明包里开始有
别的形态要照顾了。

**改了之后**：有人在末尾追加一条 `external`，提交了：

```text
🟡 content/docs/start/handbook.mdx  ../packages/docfirst-workflow/tsdown.config.ts:all  有变动，等作者复核
```

要是当初钉的是 `entry` 那一段，末尾新加的那条在段外，算「没碰到」，页面还是绿的，读者永远不知道
构建面已经变了。所以说「这份文件长这样」的时候钉整个文件；说「这一段是这么写的」才钉行段。

<Note>
  整文件钉的对象要挑**不随发版变的**：钉 `package.json` 看着更有代表性，可它带着 `version`，
  每发一次版就黄一次，而那次黄跟这一章的论断毫无关系。噪音会训练人无视黄点，比不钉更糟。
</Note>

## 三、归一化与哈希：名字加行段

**读者看到的**

{/* has file="../packages/docfirst-workflow/src/engine/span.ts" text="export function normalizeLines" */}

{/* has file="../packages/docfirst-workflow/src/engine/span.ts" text="export function hashSpan" */}

「站展示什么就哈希什么」这条规矩落在这一对上：展示前做的归一化，就是哈希前做的那一份。
哈希本身先归一化再摘要，不是直接摘原文：

{/* ref file="../packages/docfirst-workflow/src/engine/span.ts" lines="31-34" hash="dcbe978b73f4" blob="349017fffa50" */}

所以行尾多几个空格、换行从 CRLF 变成 LF，段哈希都不动——站上看不见的差别，记录里也不该算差别。

**改了之后 A**：有人把 `hashSpan` 改名成 `digestSpan`，全仓替换，提交了：

```text
🔴 content/docs/start/handbook.mdx  has ../packages/docfirst-workflow/src/engine/span.ts "export function hashSpan"  缺失，引用指向空气（文件里没有这个名字了）
🟢 content/docs/start/handbook.mdx  has ../packages/docfirst-workflow/src/engine/span.ts "export function normalizeLines"  新鲜
🟡 content/docs/start/handbook.mdx  ../packages/docfirst-workflow/src/engine/span.ts:31-34  有变动，等作者复核
```

小标签变红，退 1，门禁拦下：上面那句「哈希本身先归一化再摘要」点名的函数不在了。行段那处只是黄——
改名对 git 来说是改了一行，diff 里一减一加。改名该是红不是黄，这就是名字引用存在的理由。

**改了之后 B**：有人把摘要算法从 sha256 换成 sha1，名字没动，提交了：

```text
🟢 content/docs/start/handbook.mdx  has ../packages/docfirst-workflow/src/engine/span.ts "export function hashSpan"  新鲜
🟡 content/docs/start/handbook.mdx  ../packages/docfirst-workflow/src/engine/span.ts:31-34  有变动，等作者复核
```

小标签还是绿的——名字在，`has` 只管这个。代码块黄、带 diff：所有记号上的旧哈希一夜之间全对不上，
这件事只有那一行 diff 说得出来。两种引用各盯各的。

这两个例子都是「提交了」：已经提交的改动引起的黄只报告、退 0。改动还没提交时，行段那处的黄会算红，
要在改代码的那个提交里复核。

<Note>
  为什么不写光秃秃的 `hashSpan`：`has` 是纯文本匹配，`hashSpan` 会命中别处的 `hashSpan(text)` 调用，
  写 `export function hashSpan` 才钉在导出上。只记「在」，不记出现次数——次数进注释、进字符串都会变，
  报出来是噪音。
</Note>

## 四、没有的东西：断言不在

**读者看到的**

{/* absent path="../packages/docfirst-workflow/src/engine/git.ts" type="absent" */}

git 那一半在环境层（`packages/docfirst-workflow/src/host/git.ts`），判定层里没有它。判定层只用
`node:crypto`、不起子进程：行段要的旧内容和 hunk 表由环境层从外面传入，不是它自己去取的。

**改了之后**：有人图省事把 git 那一半搬进判定层，提交了：

```text
🔴 content/docs/start/handbook.mdx  absent ../packages/docfirst-workflow/src/engine/git.ts  缺失，引用指向空气（断言它不在，它却出现了）
🟡 content/docs/start/handbook.mdx  tree ../packages/docfirst-workflow/src/engine depth=1  有变动，等作者复核（8 项）
```

小标签红，「判定层零依赖」这条边界当场作废，搬的人在门禁上就会看到上面那句「由环境层从外面传入」。
正向的 `exists` 用在「这个文件必须在」的话上——文件删了、或者变成了目录，就红。存在性没有黄：在就在，不在就不在。

## 这一章在盯什么

| 这一章里的话 | 用的引用 | 什么时候提醒你 |
| --- | --- | --- |
| 「一个文件一件事」 | `tree ../packages/docfirst-workflow/src/engine` | 这一层下多了、少了文件 |
| 「构建面小到能一眼看完」 | `ref ../packages/docfirst-workflow/tsdown.config.ts` | 这份配置改了任何一处，包括末尾追加 |
| 「归一化与哈希是一对」 | `has` 两处 | 这两个导出改名、删了 |
| 「先归一化再摘要」 | `ref ../packages/docfirst-workflow/src/engine/span.ts:31-34` | 那几行改了（挪了位置不算） |
| 「git 那一半不在判定层里」 | `absent ../packages/docfirst-workflow/src/engine/git.ts` | 这个文件出现了 |

分工一句话：**名字表、名字、有没有，交给引用盯着；散文只负责说为什么。**散文里不写「四个」「几项」这种会变的数，
读者看代码块自己数——跑出来的数字（几条测试、几个路由）更不进散文，那不是文件的话，是命令输出的话。

## 写手怎么挑

| 你想说的话 | 用哪类 | 为什么不用别的 |
| --- | --- | --- |
| 「这段代码是这么写的」 | 行段 `ref 文件:起-止` | `has` 看不见改动；整文件噪音大 |
| 「这份文件长这样」（配置、小脚本） | 整文件 `ref 文件` | 行段会漏掉末尾追加的行 |
| 「这个目录下有哪些东西」 | 目录树 `tree` | 行段钉不住目录；`exists` 一次只能说一个 |
| 「这个文件在」「已经没有了」 | `exists` / `absent` | 目录树会连带报出同目录别的文件的变化；行段会因为内容变而黄 |
| 「这个函数 / 配置项 / 导出还在」 | 名字 `has` | 行段太敏感，那行改个空格都黄；改名该是红不是黄 |

上面「改了之后」几段是 `docfirst check` 在人读模式下打出来的原文格式，一行一处引用；
再往下看一处引用从写下到变红的全过程，去 [一条引用的一生](/docs/start/lifecycle)；五类各自怎么判、
旧内容从哪取，去 [判定层](/docs/modules/engine) 与 [环境层](/docs/modules/host)。
