# 需求

**本页回答**：文档里的代码为什么会过时，这套机制承诺管哪一段，又明确不管哪一段。

## 问题：手抄的副本不会跟着源码变

文档里贴一段代码，那一刻它是对的。三个月后函数改了名、参数多了一个、整个函数被删掉——文档里那段还在，
一个字没动，读的人照着它写，编译不过。

问题不在人懒。问题在**副本没有身份**：那段文字跟源码之间没有任何连接，谁也说不出「它引的是哪个文件哪几行」，
自然也没人能在代码改动时把它找出来。

这套机制的做法是把副本换成**引用**：文档只写「我说的是某文件某几行」，代码在构建那一刻现取。
文档里不存代码的副本，只在记号上存确认时的指纹。

## 三条需求

<Tabs>
  <Tab title="① 文档能引真代码">
    作者写一行记号声明目标，站上那一块的内容从工作区的源文件里现取——不是粘贴，不是快照。
  </Tab>
  <Tab title="② 代码变了看得出">
    每处引用都有状态。代码改了、段没了、文件没了，状态就变色，命令行也报得出来。
  </Tab>
  <Tab title="③ 人复核后才算数">
    工具不判对错，只报「变了」。改得对不对是作者的事：只挪了位置的，确认时自动写回新行号；内容真变了的，
    作者复核后用 `docfirst confirm <页> --accept` 重新记下，这段新内容才成为新的记录。
  </Tab>
</Tabs>

## 引用指向什么：五类目标

行段、整文件、目录树、存在性（含「断言不在」）、名字：

一篇手册里怎么挑、各盯什么，见 [五类引用：一篇手册里怎么用](/docs/start/handbook)。

文档里的一处引用，除了目标，还带着记号上的记录（没确认过就是空）和「它写在文档第几行」。每处记号各带各的记录，
同一篇里两处指向同一段的引用各确认各的，写回也互不牵连：

`extra` 是格式自己用的字段（是不是草稿记号），判定层原样带回、不看内容——判定层不认识任何格式，靠的就是这个字段。

## 确认下来的是一条指纹，不是一份副本

记录按目标种类各一种，写在正式记号的属性上。行段与整文件记段哈希和确认时整文件的 blob 名，目录树记名字表的哈希，
存在性记类型，名字引用的正式记号本身就表示确认过：

{/* ref file="../packages/docfirst-workflow/src/engine/types.ts" lines="54-81" hash="c17852859b19" blob="beff25dfe17b" */}

记录里没有代码内容。blob 名是在进程里按 git 的算法算的，确认不用先提交；代码提交之后，
核对时能按这个名字从 git 对象库里取回确认时的内容，给出 diff、跟着行段挪位置。取不到也不算错，只是少了 diff。
来由见轨迹卡[记录进记号](/trajectory/2026-09-25-records-live-in-markers)。

<Note>
  **状态只有四种**：新鲜、有变动、缺失、未确认。「有变动」不是错，它是「等作者复核」，命令行退 0——
  只有一个例外：被钉的代码在本仓有未提交的改动，这个黄是这次改动引起的，`check` 算红，要在同一个提交里复核。
  「缺失」一律退 1。四种状态怎么判出来的，见 [判定层](/docs/modules/engine)。
</Note>

## 明确不管的

- **跑出来的数不管、行内不管**。「86 条测试」是命令输出的话，不是文件的话，靠约定不写进正文；
  句子里的反引号、文内链接的目标要行内记号，以后再做。见 [明确不做](/future/not-doing)。
- **不自动修复**。代码改了，工具报黄，等人来看；它不会替你把文档里的话改对。
- **不猜作者意图**。行段映射跟内容对不上时报黄让人复核，不把红判成绿；取不到确认时的内容、
  在文件里也找不到那一段时就说「位置不明」，不拿旧行号上的东西冒充。
- **不做全文正则**。记号靠语法树或逐行扫描认，写在围栏里、句子里的同样文字一律不算。见 [判定层](/docs/modules/engine)。

词都收在 [术语表](/docs/glossary) 里，接着读 [一分钟上手](/docs/start/quickstart)。
