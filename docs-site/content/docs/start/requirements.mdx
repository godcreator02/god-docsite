# 需求

**本页回答**：文档里的代码为什么会烂掉，这套机制承诺治哪一段，又明确不治哪一段。

## 腐化的本质：手抄的副本不会跟着正本变

文档里贴一段代码，那一刻它是对的。三个月后函数改了名、参数多了一个、整个函数被删掉——文档里那段还在，
一个字没动，读的人照着它写，编译不过。

问题不在人懒。问题在**副本没有身份**：那段文字跟源码之间没有任何连接，谁也说不出「它引的是哪个文件哪几行」，
自然也没人能在代码改动时把它揪出来。

这套机制的做法是把副本换成**引用**：文档只写「我说的是某文件某几行」，代码在构建那一刻现拿。
文档里不存代码的副本，记忆只有一条指纹。

## 三条需求

<Tabs>
  <Tab title="① 文档能引真代码">
    作者写一行记号声明目标，站上那一块的内容从工作区的源文件里现拿——不是粘贴，不是快照。
  </Tab>
  <Tab title="② 代码变了看得出">
    每处引用都有状态。代码改了、段没了、文件没了，状态就变色，命令行也报得出来。
  </Tab>
  <Tab title="③ 人确认后才算数">
    工具不判对错，只报「变了」。改得对不对是作者的事，作者跑一次确认，这段新内容才成为新的记忆。
  </Tab>
</Tabs>

行段、整文件、目录树、存在性（含「断言不在」）、名字：

文档里的一处引用，除了目标还带着「它写在文档第几行」。**身份不靠行号**：同一篇里两处指向同一段的引用，
共用一条记忆。

`extra` 是格式包自留的私货（展示区在哪、是不是草稿记号），核心原样带回、不看内容——这是核心不认识任何格式的那道口子。

## 确认下来的是一条指纹，不是一份副本

{/* ref file="../packages/core/src/types.ts" lines="59-66" */}

记录里没有代码内容，只有「那几行当时长什么样」的指纹，外加一个 `kind` 说明这条记录是哪个比较器记的。
git 比较器记的是 HEAD 里那个 blob——内容本来就在 git 的对象库里，仓里不必存第二份。
细节见 [git 原理](/docs/principles/git)。

<Note>
  **状态只有四种**：新鲜、有变动、缺失、未确认。「有变动」不是错，它是「等作者复核」，命令行退 0；
  只有「缺失」才退 1。四种状态怎么判出来的，见 [核心](/docs/modules/core)。
</Note>

## 明确不治的

- **跑出来的数不管、行内不管**。「86 条测试」是命令输出的话，不是文件的话，靠约定不进散文；
  句子里的反引号、文内链接的目标要行内记号，押后。见 [明确不做](/future/not-doing)。
- **不自动修复**。代码改了，工具报黄，等人来看；它不会替你把文档里的话改对。
- **不猜作者意图**。别家比较器记的记录一律当「未确认」重新确认，不试图翻译；行映射跟内容对不上时报黄让人复核，
  不把红判成绿；hash 记忆找不到那段就说「位置不明」，不拿旧行号上的东西冒充。
- **不做全文正则**。记号靠语法树或逐行扫认，写在围栏里、句子里的同样文字一律不算。见 [核心](/docs/modules/core)。

词都收在 [术语表](/docs/glossary) 里，接着读 [一分钟上手](/docs/start/quickstart)。
