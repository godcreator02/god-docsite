# 工作台插件

**本页回答**：`@godcreator/gwb-docfirst-workflow` 提供什么、对外的接口长什么样、依赖谁、为什么一个字都不依赖 `@godcreator/docfirst-workflow`。

包名 `@godcreator/gwb-docfirst-workflow`，源码在 `packages/gwb-docfirst-workflow/src/`，入口是 `src/index.ts`。

## 功能

这是 god 工作台（gwb）的一个插件，也是这个工作区里唯一不发成 npm 库的包。它提供两样东西：**一条命令 `docfirst.attach`**，给刚生成的 fumadocs 骨架装上 docfirst 的三个区（现状 `docs`、轨迹 `trajectory`、未来 `future`）与接线；**六份说明书**，随插件发布、注册给 skills 插件。分工写在入口文件的文件头上：

{/* ref file="../packages/gwb-docfirst-workflow/src/index.ts" lines="9-15" hash="fc66f678a0da" blob="ab455a957139" */}

判据一句话：**包的使用者是仓，插件的使用者是 agent。** 要在仓里发生的事（核对、确认、渲染，门禁与站构建都要运行）归 `@godcreator/docfirst-workflow` 那个包，agent 自己 `cd` 到那个仓里跑 `pnpm doc`；只在 agent 手上发生一次的事（读一份说明书、给一个新骨架装一次各区）归插件。这条判据怎么推出来的、否掉了哪几条候选，见 [包给仓、插件给人](/trajectory/2026-09-10-package-serves-repo-plugin-serves-agent)。

装配本身写哪些文件、怎么检查目标站、写盘失败怎么恢复，全在 [装配](/docs/modules/site)；插件这一侧只做参数检查与回执组装，入口文件往下只认识一个名字：

{/* has file="../packages/gwb-docfirst-workflow/src/index.ts" text="./attach.js" */}

六份说明书分两类。讲 docfirst 这套机制的三份：`docfirst`（插件自己怎么用）、`docfirst-docs`（文档站怎么写）、`trajectory`（轨迹卡怎么记）；讲通用开发纪律的三份：`spec-grill`（接到需求先盘问）、`parallel-by-module`（按模块派子代理）、`docs-governance`（文档与注释治理）。

{/* tree dir="../packages/gwb-docfirst-workflow/skills" depth="1" hash="c698adfead86" */}

六份的正本都在这个站的 `content/docs/outputs/skills/` 下（跟包在同一个仓才改得动，纪律那三份也要跟钉码写法、分区保持一致），由 `docfirst.config.mjs` 的 `outputs` 映射生成到插件的 `skills/`。纪律那三份为什么放回本仓，见 [三份纪律并回本仓](/trajectory/2026-09-10-dev-discipline-comes-home)：

{/* ref file="docfirst.config.mjs" lines="17-27" hash="c8718f9535ab" blob="fce0d84ad1f9" */}

生成物放插件、不放包：包装在 `node_modules` 里，没有任何说明指向它，agent 不会去读；说明书能被 agent 读到，全靠插件把自己包里的 `skills/` 目录注册给 skills 插件。

## 接口

对外只有**命令总线上的一条 `docfirst.attach`**，参数 `{ dir, title? }`。插件的身份是三个常量：插件名、命令名、一条必需的注入：

{/* ref file="../packages/gwb-docfirst-workflow/src/index.ts" lines="16-20" hash="aaeafc2ace00" blob="ab455a957139" */}

登记时的 `description` 与 `usage` 是公共接口的一部分——agent 只看得见这两段。`usage` 写清参数、只在刚生成的骨架上进行、被挡住的路径一个都不写、写盘途中失败恢复原样、只写文件不跑安装，以及回执各字段的意思：

{/* ref file="../packages/gwb-docfirst-workflow/src/index.ts" lines="69-80" hash="6f5a7771f8ae" blob="ab455a957139" */}

`dir` 必须是一个已经存在的目录的绝对路径——插件在工作台主进程里运行，不知道相对于哪个目录。「不是目录」这条错误文本点出最常犯的错：`dir` 给成了仓目录。别的检查（是不是 fumadocs 骨架、是不是刚生成的）归装配：

{/* ref file="../packages/gwb-docfirst-workflow/src/index.ts" lines="29-46" hash="f0712b8786f9" blob="ab455a957139" */}

装配拒绝时抛出的错误文本原样放进 `{ ok: false, error }`，插件不翻译、不分类——那些错误文本本身就是文档：

{/* ref file="../packages/gwb-docfirst-workflow/src/index.ts" lines="83-92" hash="fe6f9b333eda" blob="ab455a957139" */}

成功时的回执：站目录、站所在的仓、骨架用的端口、写了哪些文件（`written`）、其中覆盖了站上已有的哪些（`replaced`）、删掉了哪些骨架文件（`superseded`）、仓根哪些文件第一次 render 会被覆盖（`overwrites`），以及接着要在那个仓里跑的命令（`next`）。`overwrites` 非空时多一条 `warn`：先把仓根那份的内容移进 `content/docs/outputs/` 下对应的 mdx 正本，再 render。

## 依赖

两个运行时依赖都是 cordis 的注入。`gwbCommands` 是**必需注入**，写在 `export const inject` 里——没有命令总线，这个插件对外什么都提供不了，缺它整个插件不加载：

{/* ref file="../packages/gwb-docfirst-workflow/src/index.ts" lines="20-20" hash="397a91e60cb0" blob="ab455a957139" */}

`gwbSkills` 是**局部注入**，只在注册说明书的那个作用域里要它；没装 skills 插件的 home 里本插件照常加载，只是少了说明书：

{/* ref file="../packages/gwb-docfirst-workflow/src/index.ts" lines="116-118" hash="8a9dbe7a78c3" blob="ab455a957139" */}

依赖字段照 devkit 的规矩写：运行时从 home 里得到的写 peer——内核包 `@godcreator/gwb-kernel-desktop`（`GwbContext` 从它的包根 `import type`）、命令总线、skills 插件（标 `optional`）。cordis 对服务不做版本校验，peer 范围是唯一的版本校验点。本仓 `pnpm-workspace.yaml` 关了 `autoInstallPeers`，所以这三个包在 dev 里再各写一份，否则装不进 `node_modules`、类型检查找不到。构建产物里没有按值 import 的包，所以 peer 里没有 `cordis`。为什么不再用接口类型包 `@godcreator/gwb-plugin-api`，见 [适配内核 0.6](/trajectory/2026-09-25-adapt-kernel-0-6-drop-plugin-api)。

{/* ref file="../packages/gwb-docfirst-workflow/package.json" lines="36-56" hash="b26b412b100f" blob="f9e70cfe912d" */}

插件用 `tsc` 编译、跑在 TS 7 上、测试用 vitest；两个 npm 包是 tsdown + TS 6、测试用 `node --test`。两套工具链并存，各自的 `package.json` 说了算，不互相搬。

## 不做的事

**不依赖 `@godcreator/docfirst-workflow`。** 三类依赖字段一个都不写、`src/` 里一行都不 import：不启动子进程、不登记 node CLI、不查 home 里那个包的路径。装了插件就能注册说明书、能装配，不存在「装了插件没装包」那种只装了一半的状态。代价是 agent 要核对得自己 `cd` 到仓里跑，比调一条命令多一步。守卫在产物检查里：

{/* ref file="../packages/gwb-docfirst-workflow/tests/artifact.test.ts" lines="97-120" hash="daa3cc5f486d" blob="950285b9e9d9" */}

**不转发命令行。** 核对、确认、渲染都不经过插件——转发一条命令行，就是把要在仓里发生的事又挪回插件里：

{/* ref file="../packages/gwb-docfirst-workflow/tests/artifact.test.ts" lines="122-129" hash="7f5543f262d0" blob="950285b9e9d9" */}

**不读核对结果。** 判定、比较、报告的形状一样都不认识，连 `check --json` 的机读报告都不读。哪一页漂移了、一处钉码为什么黄，问的是仓里那条命令行。

**不管站。** 扫容器根找站、判断 build 是不是最新、挑端口启动停止、到时间关闭、站的窗格，全归站点插件 `@godcreator/gwb-docs-site`。两个插件互不依赖、各带各的模板，只剩一个使用顺序：先 `docs-site.create` 生成骨架，再 `docfirst.attach` 装各区，中间不要改文件。本插件这一侧的检查：

{/* ref file="../packages/gwb-docfirst-workflow/tests/artifact.test.ts" lines="138-143" hash="9d4ff70c4cec" blob="950285b9e9d9" */}

**不注册窗格。** 站点插件的窗格已经叫「文档站」，两个同名窗格分不清。所以本插件没有浏览器端的代码，`build` 只有一步 `tsc`：

{/* ref file="../packages/gwb-docfirst-workflow/package.json" lines="24-32" hash="b1e8f7ece99c" blob="f285e7cbd770" */}

**不装依赖、不渲染、不核对。** 装配只写文件；装完有没有人真去跑回执里那几条，是人和 agent 的事。
