# 装配

**本页回答**：`docfirst.attach` 背后的装配往目标站上写了什么、对外的两个函数是什么、依赖什么、刻意不做什么。

装配是工作台插件 `@godcreator/gwb-docfirst-workflow` 的一部分，源码在 `packages/gwb-docfirst-workflow/src/`（除 `index.ts` 以外的几份），入口是 `src/attach.ts`；模板在包根的 `template/attach/`。

## 功能

**在一个刚生成的 fumadocs 骨架上装 docfirst。** 装上去的是：`content/` 下三个区（现状 `docs/`、轨迹 `trajectory/`、未来 `future/`）各自的集合、路由、侧栏根节点与骨架页，`docfirst.config.mjs`，mdx 接线与组件名册脚本，外加往站的 `package.json` 里补依赖与 doc 脚本：

现状区预置的骨架页是入口页、术语表与 `content/docs/outputs/` 下的三份生成正本（仓根 README、AGENTS、CLAUDE 的正本）；轨迹区一页、未来区一页路线图。骨架页只规定每页都成立的第一句「本页回答」，不规定小标题，理由见 [骨架页不讲规矩](/trajectory/2026-09-25-skeleton-pages-dont-teach-rules)。三个集合里只有现状区生成机读版：

装出来的 `docfirst.config.mjs` 写的是内容根与三条 `outputs` 映射，没有别的区要登记——`content/` 下除 `trajectory/`、`future/` 之外的目录都是现状区：

站的 `package.json` **只加不减**：骨架写的 name、version、dev / build / start 脚本（端口就在这几条脚本里）与依赖一个字不动，补的是 doc 脚本、两条 docfirst 依赖（进 `devDependencies`，站构建与门禁都是开发期的事）和一句描述：

端口不由装配挑：骨架的 `next dev -p` / `next start -p` 写着几就是几，装配只把它认出来写进回执；认不出用 next 自己的默认端口。

**对外两个函数。** `planAttach` 只计算、不写盘；`attachSite` 计算后写盘。所有能失败的检查都排在写第一个文件之前，写盘途中仍然失败就恢复原样再抛出：

输入只有站目录是必需的；`title` 不给就从仓根 `package.json` 认，`template` 换模板目录，不给就是包里带的那份：

显示名的认法：给了 `title` 用给的，否则仓根 `package.json` 的 `title`，再否则包名去掉 scope，最后是仓的目录名：

## 依赖

装配只 import `node:fs`、`node:path`、`node:url` 三个内置模块，不 import 任何第三方包，也不认识 `@godcreator/docfirst-workflow` 的判定、环境、格式、命令行——它要能被插件在进程内直接调用，不能拖进整套判定。守卫在插件的产物检查里，见 [工作台插件](/docs/modules/plugin) 的「不做的事」。

它读的是盘上的事实：目标站的 `package.json`（认骨架、认端口、合并的底本）、站的 `content/` 目录（判断有没有人写过内容）、仓根的 `package.json`（认显示名）、包里的模板目录。

骨架由站点插件 `@godcreator/gwb-docs-site` 的 `docs-site.create` 生成，所以模板里没有骨架的那几份配置——留一份进去，就会把站点插件刚生成的那份覆盖掉：

{/* ref file="../packages/gwb-docfirst-workflow/src/template.ts" lines="1-6" hash="7598626b329f" blob="fdb257284a36" */}

往目标站 `devDependencies` 里补的依赖版本来自一张手写的表，一律精确号。工作区里那两份写的是 `workspace:*`，写进别人的站装不上，所以只能手写；两个包发版升版本号时跟着改，插件的测试检查它跟工作区各包的版本一致。这两个包名出现在这儿不算插件的依赖：它们是写进别人 `package.json` 的字符串。

{/* ref file="../packages/gwb-docfirst-workflow/src/deps.ts" hash="d04046ff7fe0" blob="43aa6c695d57" */}

模板假设站在仓根下一层（约定叫 `docs-site/`）、被钉的代码在仓根，所以引用写 `../src/…`，`outputs` 映射把生成物写到 `../`。形状不同就改装出来的配置里的相对路径，这是模板的前提，不是配置项。

## 不做的事

**不核对要覆盖的文件是不是骨架原样。** 目标站 `content/` 以外、跟模板同名的文件（根布局、`source.config.ts`、`next.config.mjs` 这类）直接覆盖，只在 `replaced` 里列出来。要核对就得拿到站点插件那份骨架模板的原样，这需要站点插件配合，还没做，记在 [路线图](/future/roadmap)。

**不读 docfirst 配置。** 那正是它要写出来的文件；核对、确认、渲染都是「对一个已经接好的站做事」，装配是「把线接上」，前提正相反。

**不给已有内容的站接线。** 站里已经有 docfirst 配置、或 `content/` 下有骨架之外的内容，就报「这个站已有内容，请人工接线」。给一个用了很久的站加 docfirst，比自动改写别人的文件安全。

**不改仓根。** 仓根的 `README.md` / `AGENTS.md` / `CLAUDE.md` 由之后的 `render` 生成；装配只把「仓根已经有、第一次 render 会覆盖」报出来。

**不装依赖、不渲染、不核对。** 只写文件；接着要在那个仓里跑的命令由插件写进回执。

**不生成骨架、不挑端口。** 那是站点插件的事。
