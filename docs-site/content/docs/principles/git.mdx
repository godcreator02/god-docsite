**本页回答**：行段与整文件的比较器凭什么说得出「这段代码变了没有、今天挪到哪儿去了」，它从 git 拿什么、不拿什么，
被引文件在**哪个仓**是怎么定的，以及 check 怎么认出本仓未提交的改动。

<SpanFollow />

## 记号上的 blob 名：在进程里算

确认一处行段或整文件引用时，记号上写两样：段哈希和确认时整文件的 **blob 名**，都取前 12 位十六进制。
代码内容一个字都不进记号，旧内容要用时去 git 的对象库里取。

blob 名不问 git：把工作区内容的换行统一成 LF，按 git 的 blob 算法在进程里算。仓的对象库存的是 LF 时，
算出来的就是这份内容提交后的 blob 名，所以**确认不要求先提交**，也一次 git 都不启动：

{/* ref file="../packages/docfirst-pin/src/span.ts" lines="41-57" hash="c2d846c84d20" blob="349017fffa50" */}

`tests/hash-text.test.ts` 拿真 git 的 `hash-object` 逐字节核对这个算法，它一旦算错，整站的绿灯会一起变黄。

代价是：确认之后、提交之前又改了这个文件，或者仓里的文件本来就存 CRLF，记号上的 blob 就不会进对象库。
这时取不到旧内容，比较器退回滑窗（见下文）。为什么接受这个代价，见[记录进记号](/trajectory/2026-09-25-records-live-in-markers)。

## 旧内容：按 blob 名去对象库取

报黄要给 diff、报红要显示确认时那段，都要旧内容。workflow 的项目装配拿 blob 名去 `cat-file --batch` 取，「在不在对象库」和
「内容是什么」一次问到。blob 名按内容寻址，所以取到的内容在进程里记住，一次 check 里同一个 blob 只起一次 git：

{/* ref file="../packages/docfirst-workflow/src/project/git.ts" lines="80-110" hash="a2badff969ea" blob="afd0fbdae4c4" */}

不在对象库、缩写有歧义、缩写认出的不是 blob，都只是「没有旧内容」，给 `null`，不报错。记号上**不记仓在哪**：
核对时从文件位置重新找仓就行。

## 文件在哪个仓：按文件自己的位置定

被引文件不限于项目自己的仓。另一个单元、上游 clone、工作区里别的仓，都能钉；所以「问哪个 git」不看项目根，
看**被引文件在哪**：

{/* ref file="../packages/docfirst-workflow/src/project/git.ts" lines="56-77" hash="0ac2f4371487" blob="afd0fbdae4c4" */}

两步：先取**真实路径**，再往上找第一个 `.git`。从哪儿起往上找，看目标是文件还是目录——文件从它
所在的目录起（`locate`），目录从**它自己**起（`locateDir`）：目标目录很可能自己就是仓根
（文档里写 `tree .`），先跳一级就跳出了这个仓，`.gitignore` 过滤会整个失效。

<Tabs>
  <Tab title="① 为什么先 realpath">
    pnpm 工作区里 `node_modules/@x/y` 是指向 `packages/y` 的软链（Windows 上是目录联接）。按写的路径判它在
    `node_modules` 里、被忽略；按真实路径它是本仓已提交的文件。同一份代码只能按一个位置算，所以按真实位置算。
    文件本身不存在（删了）时取最近一个存在的祖先的真实路径再拼回去，仓照样找得到。
  </Tab>
  <Tab title="② 往上找最里层的 .git">
    `.git` 可能是目录，也可能是子模块 / worktree 里的文件。找到的是**最里层**那个：子模块算它自己的仓。
    一直找到磁盘根目录都没有，就是「不在任何仓里」：取不到旧内容，比较器只能滑窗。
  </Tab>
</Tabs>

定位出来的是「仓根 + 仓根相对的 posix 路径」。取 blob、问 status、列被忽略的路径，cwd 一律是那个仓的根——
项目根是不是 git 子目录、被引文件在不在项目的仓里，都不影响结果。

## 变没变：先比哈希，不行再用 hunk 表

比较器按固定顺序判（见[钉码核心](/docs/modules/pin)），能用哈希下结论的不碰 git：

- **绿灯是常态**。记号上那几行的段哈希等于记录，就是绿；当前整文件的 blob 名等于记录，内容一字没变，旧内容就是当前内容。
  这两步都在进程里算，对象库不问。
- 真有差异、又取得到旧内容，才把旧内容和当前内容写成两个临时文件 `diff --no-index -U0`。**不往任何对象库写东西**：
  被引文件可能在别人的仓里。只有「有差异」那一种非零退出（退 1，输出在 stdout 里）能忽略，别的照原样抛出去。

{/* ref file="../packages/docfirst-workflow/src/project/git.ts" lines="153-187" hash="602913b7a3fd" blob="afd0fbdae4c4" */}

- 算出的 hunk 表按「旧内容的 blob 名 + 新内容的 blob 名」记住。一篇文档十几处引用钉同一个改过的文件是常态，
  同一对内容只 diff 一次。
- 这张表还存一份到盘上（系统临时目录下的 `docfirst-cache/hunks/`）：钉住的那段没变、只是文件别处改过的引用是绿的，
  没人会去重新确认，每次 check 都要为它算一遍。键按内容寻址，同一对内容的 hunk 表永远不变，不用管失效，所有项目共用一份；
  盘上那份认不出就报错并说是哪个文件，不当作没有：

## 取不到旧内容：按段哈希滑窗

文件不在任何仓里、确认后没提交就又改了、浅克隆、仓按 CRLF 存，都取不到旧内容。这时比较器按段长在整个文件里
逐行滑一遍，找段哈希相同的窗口；有几处相同时取离旧位置最近的一处，两处一样近就不猜：

{/* ref file="../packages/docfirst-pin/src/compare.ts" lines="37-56" hash="a53b5891c4bc" blob="29bf0bfed8b4" */}

找到就是绿，带今天的行号，确认时写回；找不到是黄 `unlocated`（位置不明），没有 diff，行号停在记号上的位置；
记号上那几行已经超出文件才是红：

## 红有两种理由

| 理由 | 什么情况 | 站上显示什么 |
| --- | --- | --- |
| `vanished` | 整段被删光，或者行段跟到文件外面去了 | 取得到旧内容时显示确认时那段 |
| `file-missing` | 文件不在了 | 取得到旧内容时显示确认时那段 |

取不到旧内容不是红，只是少了 diff。文件改名不追：改了名就是 `file-missing`，重新钉。

## 本仓未提交的改动：check 靠 status 认

check 要知道一处黄灯是不是这次改动引起的：被钉的文件（目录树是那个目录）跟文档在同一个仓里，并且在那个仓的
`git status` 里出现（工作区或暂存区跟 HEAD 不一样，或者未跟踪），这个黄就算红。每个仓一次 check 只问一次 status：

{/* ref file="../packages/docfirst-workflow/src/project/git.ts" lines="189-209" hash="519cd2928353" blob="afd0fbdae4c4" */}

被钉文件在别的仓里、或者改动已经提交，黄灯只报告不拦。命令行怎么报，见[命令行](/docs/modules/workflow/cli)；为什么这样拦，见
[同提交复核](/trajectory/2026-09-25-drift-handled-in-same-commit)。

## 归一化：站展示什么就哈希什么

{/* ref file="../packages/docfirst-pin/src/span.ts" lines="20-25" hash="b691171da610" blob="349017fffa50" */}

只做三件事：换行统一成 LF、去每行行尾空白、去掉末尾的空行。**缩进保留、注释保留**——JSDoc 是契约的
一部分，改了就该黄。

展示前和哈希前用同一个函数，否则会出现「页面上看着一样、状态却是黄的」这种没法解释的事。算 blob 名和送进 `git diff`
的整文件也先统一成 LF：对象库里存的是 LF，工作区是不是 CRLF 不该改变判定。
