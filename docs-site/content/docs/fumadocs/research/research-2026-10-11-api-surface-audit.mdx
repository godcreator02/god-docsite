日期：2026-10-11。范围：逐项检查计划的 47 条 K/P/D/C 改动、源头机制及第 1、2 节接线，重点核对来源、MDX 配置、UI、搜索和评论定位的公开契约。只读核对，没有修改计划、源代码、依赖，也没有运行 HMR/Markdown 实验。

## 结论

现有计划不能表述为“只依赖 Fumadocs 对外且稳定的接口”。绝大部分主接点是官方文档说明、包 exports 导出的公开 API；但 D-05/D-08 依赖未获公开文档承诺的编译器载体，K-12 保留渲染 DOM 耦合，K-09 的旧 E-6 实验仍解析反序列化 React 元素的内部形状。K-04 涉及 Vite Environment/ModuleRunner API，其成熟度不能由 Fumadocs 的公开导出证明。

“公开导出”“官方文档说明”“未标弃用/内部/实验”“明确的兼容承诺”分别取证。公开 API 不表示跨大版本不变，也不表示其每个输出对象的运行时表示都是公共契约。

取证基准是实验目录的 `_upstream`：HEAD 与 `fumadocs@16.17.1^{}` 相同，为 `d6cfc48d62aa9ea413f0fc5033617c0c923681ec`；core/base-ui 为 16.17.1，MDX 为 15.4.7。滚动官网仅辅助，发生冲突时以固定 tag 的源码、exports、类型、对应文档为准。例：固定 tag 的 Remark Structure 文档已经有 `node.data.structuredData` 注入说明；不要从旧网页上的 removed `stringify` 选项倒推当前接口。

## 分类

- **A 文档公开**：正式文档展示，且对应模块被包 exports 导出；本次未发现 internal/deprecated/experimental 标识。可作为正常集成入口，但未找到逐项永久稳定承诺。
- **B 导出公开、文档较薄**：公开模块/导出类型中存在，未标 internal 等；应锁版本并做针对性升级检查。
- **C 实现耦合/未文档化载体**：依赖实现字段、对象形状或 DOM 类名；不以“源码能调用”作为稳定承诺。
- **D 已弃用公开**：能够导入但明确标为 deprecated；采用推荐替代。
- **E 其他框架/浏览器 API**：不是 Fumadocs 的接口；成熟度与兼容性由所属平台决定。
- **O 自有逻辑**：文件协议、身份、迁移、路由安排、模板、包出口及业务策略；不能归入 Fumadocs 稳定 API。

## 对源头机制和交付表述的修正建议

1. M2 的“只有一个编译器”应理解为“统一通过站点的 Vite 内容构建链”。Fumadocs doc/meta、Vite TSX与资源加载是不同处理阶段；`loader()` 的官方说明是 server-side API，使用内存数据，不是构建魔法或自动文件 watcher。
2. M4 和 0.2 的“组件没给 Markdown 形式就报错”是自有强契约。应给它单独验收，说明使用公开路径如何检测；不要依赖 Fumadocs内部 optIn/store/NOT_OPTED_IN。默认保留 JSX可导致“没有报错但正本仍带组件”。
3. K-09 不只删 `#nd-*` CSS：应同时删除/改写旧 E-6 实验的 `nameTextOf`。记忆最近 root的状态归站点/React生命周期，不能把进程级变量当正式共享策略；同名根、刷新、新树实例也须覆盖。
4. K-12 的回归价值成立，但其表述应承认“版本锁定的 DOM适配”而不是“公开稳定 API”。若要求严格只用公共契约，应主动提供可控标识，由自有组件/编译标记管理读屏文字与公式边界。
5. 公共 `PageTree.name` 是 ReactNode；`$ref` 在类型里明确 @internal。`$id` 虽公开，只保证树内/语言间唯一，不保证跨HMR或重新生成生命周期不变。
6. “默认 public API且当前可运行”与“更新文件后的路由/浏览器/search全部刷新”分开验收。尤其 createFromSource cache按loader实例，不能拿前端页面更新当搜索索引更新的证据。
7. 如最终目标是“零私有依赖”，D-05/D-08需替换或明确承认 `_compiler` 例外；K-09的JSX解包与K-12的DOM约定需清除或列成受控例外。仅补升级测试不改变接口类别。

## 同轮实验回报的边界

以下是主会话转来的其他复核代理实测，不是本文件作者另行运行的实验，最终以各代理原始记录为准。

- HMR 复核已用公开 `source.config.ts` / Config API 按集合分别 `defineDocs` + `mdxOptions`；`.source/server` 经 `.server.ts` 仅进入 loader，`.source/browser` 经公开 `createClientLoader/useContent` 加载浏览器正文。服务端与浏览器正文均为集合 A 执行 `node:fs` 插件、B 不执行，hydration 按钮能从 0 加到 1。因此“15.4.7 不支持按集合挑插件”的概括应撤回；已经发现的问题限于旧 macro 与客户端共享模块的具体写法。K-03/D-07 可改为这条公开配置路线，完整项目迁移仍需另验。
- Markdown 复核回报 31 页新旧输出一致，但正则缺失组件检查漏行内 JSX、误报 fenced code；它不能满足 D-02/D-16 的严格报错要求。Pin 搜索早期实现会收整段代码；已实测的候选修正是：对原作者节点调用 `replaceSource`，新展示节点不携带作者 position，同时以 `node.data.structuredData` 只加入路径和标题。该修正使用公开 stringifier/Structure 契约，不能因此推导 `_compiler` 稳定。
- CSS 选择器不能一概判私有：固定 tag 的 Customize UI 文档明确允许选择提供的 `id` / `data-`，并说明它们可以有各自版本生命周期；其警告针对侵入结构与具体嵌套 DOM 假设。K-09 删除这些覆盖可降低维护成本，而 K-12 的 `.sr-only`/`.katex` 与解析 ReactNode 形状是另外的实现耦合。

- E-7 的 server-only `import.meta.glob` 修改和删除已有 feed 时，实际浏览器数据更新，计数器、未保存输入、window 标记和 timeOrigin 保留；删除后重新新增文件，SSR 已出现新值，浏览器却仍停留在缺失值。因此仅能确认已验证的修改/删除场景，不能把它当作独立 meta 宏或 E-9 新任务记录更新的验收。
- E-5 原版新增 MDX/评论清单不更新、删除后 500 的问题已复现。调用公开 `server.restart()` 的局部实验能恢复服务端清单，但浏览器删除后仍可能保留旧侧栏项；重启加立即 full-reload 的时序尚未形成可靠闭环。这不是已经完成的生产修复，也不能把低层缓存操作直接宣称为必要或稳定。
- Markdown 复核独立副本有 31/31 页基线一致，25 个针对性样本中 24 个正常、1 个预期抛错，12 组结果断言通过。生成函数已包装组件表，本组合中调用 `getText` 无需再显式包装 `jsxComponents`。Term 按现有无 position 子节点形态保留原词；真实 PNG、MDX/TS include、npm 块输出已补验，但没有把新素材与旧 renderAi 逐字节比较。

独立复核文件：`probes/2610111941_api-audit-markdown/README.md`、`probes/2610111940_api-audit-hmr/README.md`（仓里的文件，不在站上）。本轮三个复核代理均按用户指定使用 GPT-6.1-sol、high。主会话检查了 Markdown 脚本与输出、接口条目覆盖（47/47，无遗漏），并汇总上述实测边界。原改造计划和原实验记录未在本轮改写。
