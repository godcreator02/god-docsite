底座：Vite 与 React Router

fumadocs 自己几乎不发明机制，它的每一样能力都借了底下两样东西的机制。这一页先不提 fumadocs，只把这两样东西讲清楚。

先说 Vite 是什么

浏览器只认识 JS、CSS、HTML。可站点里写的是 .tsx（TypeScript 加 JSX）、.mdx（Markdown 里夹组件），浏览器一个都执行不了。Vite 就是把这些源文件转换成 JS 和 CSS 的工具。

说它是「打包器」只对一半：build 时它转换完所有文件，再打包成少数几个文件，这时它是打包器；dev 时它根本不打包，谁要哪个文件就当场转换哪个，这时它是一个开发服务器。

一个文件被导入时：三道工序，每道只调用写了这一步的插件

Vite 自己只会转换少数几种格式。遇到不认识的格式（比如 .mdx），就靠插件。每个文件进来时，Vite 按固定的三道工序处理：resolveId（这个 import 是哪个文件）、load（读出内容）、transform（改写内容）。这三个都是插件可以选写的函数（叫「钩子」）。每到一道工序，Vite 只按顺序调用写了这个钩子的插件，没写的根本不会被调用；写了的插件被调用后，看一眼文件不归自己管，就原样放过。这就是流水线。

下面每行是一个插件，每列是一道工序。实线格子表示这个插件写了这一步，虚线灰格表示没写：

插件本身没什么神秘的，就是一个 JS 对象，里面写好几个函数，Vite 在对应的工序调用它们。一个最简单的 MDX 插件只写 transform，大概长这样：

{
  name: 'my-mdx',
  transform(code, id) {
    if (!id.endsWith('.mdx')) return   // 不是我管的文件，跳过
    return compileMdx(code)            // 把 Markdown 文本改写成 JS
  }
}

fumadocs-mdx 就是这样一个插件，只是 transform 里写得复杂得多。React Router 的框架模式也是一个 Vite 插件。

这条流水线，dev 和 build 共用吗

共用。同一套插件、同一组钩子（resolveId → load → transform），dev 和 build 都走这条流水线，插件只写一次。区别只在谁来调用、调用多少次、前后还多了哪些步骤：

devbuild
谁调用插件Vite 开发服务器打包器（Rollup；新版 Vite 换成了 Rolldown），Vite 把插件交给它
什么时候调用谁要哪个文件，才对那个文件走一遍；结果缓存，文件没改就不再走从入口出发，顺着 import 把能到达的文件全走一遍
resolveId / load / transform同一套
只在这种模式下有的钩子configureServer（往开发服务器里加东西）、hotUpdate（热更新）renderChunk、generateBundle 等（打包之后合并、压缩、写文件）
Vite 自带的那部分把 import 路径改写成浏览器能直接请求的地址不用改写，打包器自己把文件连起来，最后压缩

插件也可以自己区分两种模式：写 apply: 'serve' 或 apply: 'build' 只在一种模式下装上，或者在钩子里看当前是哪种模式。fumadocs-mdx 就是后一种：它的 config 钩子按 env.command 是 'serve' 还是 'build' 决定要不要每次检查 lib/source.ts 改没改；configureServer 只在 dev 下被调用。所以编译 .mdx 的工序在两种模式下完全一样，不一样的只是 dev 下按需编译、有热更新，build 下一次编译完。

dev 和 build + start 下，Vite 一样吗

流水线和插件是同一套，区别在什么时候转换、转换多少，以及 Vite 在不在。上下两行同时往前播：

devbuildstart
Vite 在不在一直在，是个常驻的服务器进程跑一次就退出不在
什么时候转换文件谁要哪个才转换哪个一次把所有文件转换完不转换，只读 build 的成品
打不打包不打包打包，写进 build/—
插件（包括 fumadocs-mdx）每个文件被要时调用build 时全部调用一遍不在场
改了文件只重新转换那一个，热更新—不知道，要重新 build
产出什么每个文件转成一个 JS 模块；CSS 也包成 JS，运行时插进 <style>build/server 的 JS；build/client 的 JS、抽出来的 CSS 文件、图片。没有 HTML 文件HTML 在请求来时，运行组件现场渲染出来

先分清三种运行方式

同一个站点有三种跑法，下面每个机制都会标出它在哪种跑法下起作用：devbuild + start静态。点一种看看它是怎么跑的：

devbuild + start静态
命令react-router devreact-router build → react-router-servessr: false + 预渲染 → react-router build
有没有 Vite 在跑有，每个请求现场编译只在 build 时打一次包；start 时只是普通 Node 进程只在 build 时；之后连 Node 都没有
loader 什么时候跑每次请求每次请求只在 build 时跑一次
action（写入）能能不能
改了文档怎么生效马上重新 build 再重启重新 build
运行时变化的数据（评论、协作）能读能写能读能写，但必须在 loader 里运行时读，不能 build 时编译进包不行
用在作者和 agent 写文档时发布：工作台在本机或 NAS 上开服务放到没有 Node 的静态托管上
结论：静态这一种对我们没有实际意义。站点都由工作台托管，本机和 NAS 都有 Node；评论要写、身份要认、协作数据要推，都离不开服务器。以后只考虑 dev 和 build + start。
要记住的一点：build + start 下没有 Vite，fumadocs-mdx 编译过的内容已经固定在包里。所以凡是运行时会变的东西（评论、协作数据），都不能走「build 时编译」这条路。

服务器到底是谁：一个请求在 dev 和 build + start 下怎么走

服务器就是一个 Node 进程，负责接收浏览器的请求，两种方式都一样。Vite 不是服务器，是编译器：dev 时它装在这个进程里面，请求来了现场编译；build + start 时它不在进程里，编译早在 build 时做完了，进程只读现成的文件。左右两边同时播放，看哪里不一样：

Vite五个机制

1. 开发时不打包：浏览器要哪个文件，就现场编译哪个 devbuild+start静态

传统做法是先把所有代码打包成一个大文件再给浏览器。Vite 开发时反过来：浏览器自己按 import 一个一个地要，Vite 收到一个请求就编译一个文件。没打开的页面，代码永远不会被编译。

2. 插件流水线：每个文件都要过这几道工序 devbuild+start：build 时静态：build 时

Vite 收到一个文件请求后，依次问每个插件三个问题：这个地址对应哪个文件（resolveId）？文件内容是什么（load）？要不要把内容改一改（transform）？浏览器只认识 JS，所以 .mdx、.tsx 这类文件全靠某个插件在 transform 里把它变成 JS。

fumadocs-mdx 本身就是这条流水线上的一个插件。

为什么最后返回的是 JS，不是 HTML？

网页上看到的确实是 HTML 和 CSS。但在 React 网站里，HTML 不是直接写出来的：内容被编译进一个 JS 函数（React 组件），运行这个函数才得到 HTML。这个函数在服务器上跑一次，生成首屏 HTML；在浏览器里再跑一次，把页面接管下来。

3. import.meta.glob：一行代码导入一整个文件夹 devbuild+start：build 时展开一次静态：build 时展开一次

写一行 import.meta.glob('./content/*.mdx')，Vite 在编译时把它展开成「逐个导入每个文件」的代码。更关键的是：Vite 记住了这个模式，文件夹里新建或删除文件时，它会让写这一行的模块失效、重新展开。试试下面的按钮：

4. 模块图和热更新：改一个文件，最少要更新多少 devbuild+start静态

Vite 记着「谁导入了谁」，这叫模块图。改了一个文件，Vite 顺着「谁导入了我」往上找，直到找到一个能自己接住更新的模块，就只替换到这一层，页面状态保留；一直找到最顶上都没人接，就只好整页刷新。

谁能接住，不看文件后缀，看它导出了什么：React 的热更新插件只给「导出的全是组件」的模块加上接住更新的能力（图里虚线框），因为把一个组件换成新版、保留它的状态是安全的。main.tsx 虽然也是 .tsx，但它是入口，干的事是 createRoot().render()，一个组件都不导出；重新执行它等于再挂载一次整个应用，所以接不住。点任意一个方块，假装改了它：

5. 两套环境：同一个文件，服务器一份、浏览器一份 devbuild+start：build 时打两个包静态：只打浏览器包

站点要在服务器上先渲染一遍，再到浏览器里接管。所以 Vite 开发时同时有两套环境，各有自己的模块图，同一个文件会被编译两次。两边处理第三方库的方式不一样：

浏览器环境（client）

  1. 你的文件：按需编译，过插件流水线
  2. 第三方库：启动时预先打包成少数几个文件（optimizeDeps）

服务器环境（ssr）

  1. 你的文件：按需编译，过插件流水线，在 Node 里执行
  2. 第三方库：默认不经过 Vite，Node 直接从 node_modules 导入
第三方库在服务器端默认不经过 Vite。库里如果有 .mdx、.css 要编译，或者库要和站点共用同一份 React context，就必须让 Vite 处理它。
fumadocs 只会自动把名字以 fumadocs-、@fumadocs/ 开头的包加进这个名单；我们的 @godcreator/… 包要另外加，本仓由平台包的 godDocsite() 加。

React Router五个机制

先记住一件事：在框架模式下，React Router 自己就是一个 Vite 插件（vite.config.ts 里的 reactRouter()）。它的所有功能都搭在上面 Vite 的机制上。

React Router v7 的三种用法是什么服务器渲染
声明式只在浏览器里用 <Routes> 匹配网址没有
数据模式浏览器里 createBrowserRouter，loader 在浏览器跑没有
框架模式（我们用的）@react-router/dev 的 Vite 插件 reactRouter() + routes.ts + 路由文件有
「用 React Router 框架」和「装了 React Router 的 Vite 插件」是同一件事。fumadocs 本身不依赖 React Router：Next.js、TanStack Start、Waku、Astro 它都支持。它和 React Router 的关系只有两处：一是适配层 fumadocs-core/framework/react-router，界面要「当前网址」「站内链接」「刷新数据」时，通过它调用 React Router 的 useLocation、<Link>、useRevalidator；二是路由文件由站点自己写，站点在 loader 里调用 fumadocs。vite.config.ts 里 fumadocsMdx() 和 reactRouter() 两个插件并排放着，互不知道对方。

1. routes.ts：网址对应哪个文件 devbuild+start静态

站点在 app/routes.ts 里写一张表。一个网址会匹配一串路由（外层布局 + 里层页面），这一串路由的组件套在一起渲染，它们的 loader 同时运行。选一个网址看看匹配到谁：

import { index, layout, route } from '@react-router/dev/routes' export default [ index('routes/home.tsx'), layout('routes/docs-layout.tsx', [ route('docs/*', 'routes/docs.tsx'), ]), route('api/search', 'routes/search.ts'), ]

2. 一个路由文件，服务器和浏览器各拿一半 devbuild+start静态：loader 只在 build 时跑

路由文件里的 loader 只在服务器上运行（可以读文件、查数据库），组件两边都运行。构建浏览器的代码时，React Router 的插件会把 loader 和只有它用到的 import 整个删掉，所以服务器代码不会漏到浏览器。点按钮切换：

红底只在服务器上。浏览器版本里，这些行连同 import { readFile } 一起被删掉。
fumadocs 的页面索引表（loader 建的那张）只在服务器上，浏览器只拿到 loader 返回的那一小份数据。

3. 第一次打开：服务器渲染，浏览器接管 devbuild+start静态：build 时预渲染

第一次打开一个网址，服务器先跑匹配到的 loader，用拿到的数据把组件渲染成 HTML 发给浏览器，数据也嵌在 HTML 里。浏览器先把 HTML 显示出来，再下载 JS，用嵌进来的同一份数据把组件再渲染一遍、接上点击事件（hydration，下文叫「接管」）。

4. 站内点链接：只要数据，不要整页 devbuild+start静态：数据 build 时生成

接管以后，在站内点 <Link> 不会整页刷新。浏览器向服务器要的只是新页面的数据（网址后面加 .data），服务器只跑需要换的那几个路由的 loader。

5. 开发时，React Router 怎么借 Vite 跑服务器渲染 devbuild+start静态

开发时 React Router 插件往 Vite 开发服务器里挂了一个处理请求的函数（Vite 插件的 configureServer 钩子），页面请求就由它接手，路由代码向 Vite 的服务器环境现要。build + start 时这个函数换成从 build/server 导入的现成处理函数。完整的对照见上面的 「服务器到底是谁」。
