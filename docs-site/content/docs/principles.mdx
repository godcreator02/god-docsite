文档站基础包、gwb-docsite 插件与 docfirst 重写的第一份设计文档：先定原则和各部分的边界，后面每章需求都按这里的划分写。

范围：基础包 `@godcreator/docsite-kit`、插件 `@godcreator/gwb-docsite`、docfirst 各包与插件。协作站下一轮再做；本机现有的 Next 站不考虑。

## 原则

### 一、站点生成一次，之后归站点自己

新建站点就是照模板生成一份 fumadocs + React Router 项目，和 `create-fumadocs-app` 一样。生成以后，站点里的每个文件都由站点自己维护、想怎么改就怎么改。基础包升级不负责让站点自动跟上，站点要用新功能就自己改代码。

### 二、站点固定依赖版本，旧站一直能运行

站点的 `package.json` 写明它用的每个库的版本，站点按这些版本运行。基础包、docfirst 发了新版，没升级的站点照旧运行，不会因为别人升级而坏掉。库的版本号照 gwb-release 的规矩：破坏站点用法的改动只随 x 升级，并附升级说明，站点要升级时由 agent 照说明改站点代码。

### 三、照 fumadocs 的框架和扩展点做，不另造机制

页面来源用 `loader()`，内容编译用 fumadocs-mdx 的 `source.config.ts`，组件表用 `mdx-components`，布局用 `DocsLayout` 和它的配置项，搜索用 `createFromSource`。需要的能力 fumadocs 已经有扩展点，就用那个扩展点；没有的，先回头问这个需求是否真的需要，再决定怎么做。

### 四、基础包、docfirst 的站点部分都是普通的库

像 fumadocs-openapi、fumadocs-typescript 那样：只导出组件、remark / rehype 插件、服务端函数、Vite 配置用的函数和类型。不导出路由模块，不往站点里写文件，不反过来读站点里的模块。路由文件由站点自己写，在 loader / action 里调用库的函数。

### 五、前端和后端按 React Router 框架模式原样分开

loader、action、资源路由是后端，组件是前端；两边只经 loader 的返回值和 action 的请求来往，返回值和请求的类型由库导出。不另起一个后端服务。

### 六、gwb 插件和站点之间只经写明的约定来往，并且向后兼容

gwb 插件会升级，站点不一定跟着升级（原则二），所以插件碰站点的每一处都是要守住的约定：启动站点时交给它的参数、调用的站点接口、读写的站点文件（人员列表、评论）的格式。这些约定写成文档、带版本号；插件升级后仍要能托管和读写按旧约定运行的站点。确实要改约定时，插件认出站点是旧约定，就明确报错说明站点要升级到哪一版，不按新约定硬读。凡是要按站点版本的规则做的检查（比如编译 MDX、核对评论格式），用站点自己装的那一版库来做。

### 七、能不能写只看身份

站点服务端拿到本机的身份码、并且在人员列表里认得出这个人，就能写评论；认不出就只读。和运行的是开发服务还是构建后的服务无关。

### 八、docfirst 的核心不依赖站点的代码，钉码的写法可以重新设计

钉码判定、记号、confirm、轨迹卡校验只对着仓库的文件工作，在命令行里运行。站点上显示钉码状态、生成正本，都属于站点一侧：docfirst 的站点库调用核心的公开函数，生成正本经站点的编译器取每页的 Markdown 形式（见[改造计划](/design/plan) M4）；核心里不出现任何为站点写的东西。钉码现有的记号写法、记录存放方式、红黄绿的口径都不当作需求，需求里只写要做到什么，写法和这次重写一起重新设计。

### 九、错了就报错

只在系统边界校验：读文件、读配置、收请求、起子进程。校验不过就拒绝并说清楚错在哪，不替调用方修正、不静默跳过。

## 各部分管什么

| 部分 | 是什么 | 管 | 不管 |
| --- | --- | --- | --- |
| 站点 | 一个 fumadocs + React Router 项目，从模板生成一次 | 自己的路由文件、布局配置、组件表、`source.config.ts`、样式、内容、评论、人员列表；决定引用哪些库 | — |
| 站点模板 | 新建站点时复制的一份项目 | 给出一个能直接运行、已经引用好基础包的起点 | 生成以后的任何事 |
| 基础包 `@godcreator/docsite-kit` | 库 | 评论（数据格式、定位、界面组件、读写函数）、人员与身份、TSX 与 HTML 页面来源、链接卡片、中文界面文字、通用正文组件（术语、讲解组件、文件树等，待定见下）、公式 | 站点的文件结构、路由、站点生成以后的升级 |
| gwb-docsite | gwb 插件 | 本 home 的身份码、照模板新建站点、托管站点进程、给 agent 用的评论命令 | 页面怎么显示；站点里的代码 |
| code-pin | 库 | 判定一段被引用的代码是否变了 | 提示文字、命令行概念、站点显示 |
| docfirst 核心与命令行 | 库 + 命令行 | 记号、钉码核对、confirm、轨迹卡校验、`docfirst.config.mjs` | 站点 |
| docfirst 站点库 | 库 | 把钉码结果显示到页面上的 remark 插件和组件、生成正本（render、check）、轨迹卡页面要用的服务端函数和组件 | 站点的路由与配置（由站点自己写） |
| 星轨盘 | 库 | 画盘和盘上的交互，输入是一组节点和关系 | 轨迹卡的文件格式 |
| gwb-docfirst | gwb 插件 | 说明书（docs-writing、docs-site、trajectory） | 建站、托管（都删掉） |

- docfirst 站点库依赖基础包，只用基础包公开导出的组件和类型；基础包不知道 docfirst。

## 站点怎么引用这些库

全部走 fumadocs 项目本来就有的位置，站点自己写，库只提供被引用的东西。

| fumadocs 项目里的位置 | 站点在这里做什么 | 基础包提供 | docfirst 站点库提供 |
| --- | --- | --- | --- |
| `source.config.ts` | 定义内容集合，配置 remark / rehype 插件 | 公式插件的推荐配置 | 钉码显示插件、轨迹卡链接插件 |
| `app/lib/source.ts` | 用 `loader()` 组合页面来源 | TSX、HTML 页面来源 | — |
| `mdx-components` | 决定 MDX 里不用 import 就能写的组件 | 链接卡片、正文通用组件 | 被钉代码的显示组件 |
| 布局配置 | 侧栏链接、站名、底部内容 | 评论层、身份显示 | 「轨迹」入口由站点自己加一条链接 |
| `app/routes.ts` 与路由文件 | 写全部路由；loader / action 里调用库的函数 | 评论读写函数、搜索、内容文件送出 | 轨迹卡列表与单卡的读取函数 |
| `root.tsx` | RootProvider、界面语言 | 中文界面文字 | — |
| `vite.config.ts` | Vite 插件与配置 | 让基础包与站点用同一份 fumadocs 的配置函数（待核对是否需要） | — |
| 样式 | `@import` 需要的样式 | 评论、组件样式 | 钉码显示样式 |

以 docfirst 站为例，站点自己的 `source.config.ts` 大致是这样，接哪些插件、接在哪一区都由站点写明：

```ts
import { defineConfig, defineDocs } from 'fumadocs-mdx/config'
import { remarkMath } from '@godcreator/docsite-kit/mdx'
import { remarkPinnedCode, remarkCardLinks } from '@godcreator/docfirst-site/mdx'

export const docs = defineDocs({ dir: 'content' })
export const cards = defineDocs({ dir: 'trajectory' })

export default defineConfig({
  mdxOptions: { remarkPlugins: [remarkMath, remarkPinnedCode, remarkCardLinks] },
})
```

示例里的导出名只是示意，真正的名字在逐章设计里定。

## 前端与后端

按代码在哪里运行分五处。一项能力跨几处时，跨界的那一份数据形状由库导出类型。

| 运行位置 | 是什么 | 放什么 |
| --- | --- | --- |
| 构建时 | fumadocs-mdx 编译 MDX | remark / rehype 插件：公式、钉码显示、轨迹卡链接、术语标注 |
| 站点服务端 | loader、action、资源路由 | 读评论与人员列表、写评论、认身份、搜索、送出内容文件、轨迹卡读取 |
| 浏览器 | 组件 | 布局、正文、评论界面、链接卡片、星轨盘 |
| gwb 插件进程 | gwb-docsite | 身份码、新建站点、托管、agent 的评论命令 |
| 命令行 | docfirst | 钉码 check、confirm、轨迹卡校验；生成正本的 render、check 由 docfirst 站点库经站点的编译器做 |

## 按原则删掉的需求与机制

需求编号见前一轮整理的五章需求表。

| 删掉的 | 原因 |
| --- | --- |
| **改写** L-02、L-03 基础包或功能包升级后站点不用手改就能跟上 | 改成「站点固定版本，旧站一直能运行；插件和站点之间的约定向后兼容」（原则二、六） |
| **删** L-05 站点用了哪些功能包写在 `package.json` 的 `docsite.features` | 站点在代码里引用了什么，就是用了什么 |
| **删** L-14、L-15 功能包只能添加不能替换、用不到的出口不用写 | 没有自动装配，就没有冲突规则 |
| **删** L-19 插件把基础包版本固定成打包时那一版，靠它保证插件与站点不错位 | 站点自己管依赖版本；插件与站点不错位改由原则六的约定保证 |
| **删** 每次初始化整份覆盖 `app/`，模板分 `skeleton/` 与 `initial/` | 原则一，模板只在新建时用一次 |
| **删** 生成的 `app/site/*` 转接文件 | 站点直接 import |
| **删** `@site/*` 别名与 `site-modules.d.ts` | 原则四，库不反过来读站点 |
| **删** 功能包必须导出 routes / site / site-server / styles.css 四个出口，路由模块放在包里 | 原则四，路由由站点写 |
| **删** 自述站 `app/` 必须与模板一致的测试、`pnpm site:skeleton` | 自述站也是一个普通站点 |
| **删** docfirst 的建站命令、Next 托管命令与窗格、create-fumadocs-app 模板、只给 Next 站用的出口 | Next 站不考虑；新建与托管归 gwb-docsite |
| **删** 站点构建时给每页写机读文字（`stamp`、`docfirstAi`） | 没有读取方 |

## 待定

1. **通用正文组件归哪。**术语标注、讲解组件（不含跟名册绑定的那部分）、文件树、Tabs、占满整个窗口的页面，推荐归基础包，docfirst 只留钉码显示和轨迹卡。
2. **agent 写评论要不要站点在运行。**现在插件经站点的接口写，站点必须在运行。按原则五，写评论本来就是站点服务端的 action，插件调用它是正常做法（调用方式属于原则六的约定）；要改成不运行也能写，就得在插件里另做一份渲染页面算快照的逻辑。推荐维持经站点写，只把请求的类型由基础包导出、两边共用。
3. **生成正本能不能用组件。**已定：能。生成正本经站点的编译器渲染，组件自己给出 Markdown 形式（改造计划 M4、D-02）。
4. **gwb-docsite 托管开发服务还是构建后的服务。**按原则七，能不能写已经和这件事无关，剩下的只是改了内容要不要即时看到。

2026-10-12 重写。这一版取代原先的「分步改造计划」与「ZCode 编排」两页（已删，历史在 git 里：快照提交 `07704c2`）。范围只有 docsite 自己；docfirst 与协作站以后各自另立方案，本页不排它们的步骤。

## 一、目标与范围

做好 docsite 自己：基础包 `@godcreator/docsite-kit`（站点骨架、集合接线、UI 外壳）、身份、评论、一次性建站、gwb-docsite 插件、自述站。开发对象就是 `packages/` 与 `site/` 里的正式代码。

## 二、工作流程（定死的规矩）

- **直接写正式代码。**packages/ 与 site/ 是工作对象，不做「先搭验证站、再收进正式代码」的两段式。
- **探针（probes/）只在遇到不知道上游会怎么表现的问题时写。**守 AGENTS 里的 probes 规矩：一个实验一个目录（目录名 yymmddhhmm_描述），**目录 README 第一行就是能照着跑的复跑命令**；写之前说清要判什么、有哪几种可能；判完留 result.md、handoff 与精确版本/日志。本来就该是正式代码的东西，不进探针。
- **每完成一段就收尾：**改到的包 `pnpm check` 绿、自述站过一遍对应场景、AGENTS 与文档同步、提交一笔。每笔提交自成一体、可单独回退。
- **测试一律 Vitest**（真实文件、真实 dev/build，不 mock 文件系统）。

> **为什么**：前几轮的教训——把「本来就该是正式代码」的功能先做成了探针与验证站，多出两段搬运与三套并存。从这版起，探针只留给「不知道上游行为」这一类问题。

## 三、技术底座（已定，不再重查）

### 3.2 用到的 fumadocs 原生能力（扩展点清单）

| 能力 | 怎么用 |

### 4.1 组合点可复数（2026-10-12 补，用户确认）

- 大包的解体形态不是「摊平成小包组合」，而是**删掉重复的正本、拆走纯库、把组合点做薄**。终态三层：能力小包（identity、comments、writing、page-sources、feed，无站点形态）→ 组合包（各有各的站点形态）→ 具体站点与 gwb 插件托管。
- **组合点可复数。**docsite-kit 是「通用文档站形态」的组合包；docfirst 与协作站以后各自另立方案时，可以组合同一批能力小包做**自己的组合包**，而不是往 docsite-kit 里加站系专用配置。判据：组合包里开始长出「为某个站系服务的开关」时，就是那个站系分出去自己组合的时候。
- 三条分寸：① 组合包之间互不依赖，两边都要的东西必须下沉成能力小包或留在通用组合层；② 大多数站直接用 docsite-kit，不为差异小的站系建组合包；③ 现行功能包（挂在别人组合点上的功能，featureRoutes / ./content 约定）升级成自己的组合包，以「挂载式约定表达不下它的接线」为准，不提前升级。
- 清理顺序的依赖：删本体旧评论/身份实现，必须以自述站（及模板）不再引用旧出口为前置——迁移先行或同笔完成，先删会让自述站的检查变红。

## 七、已否决的做法（别走回头路）

- **运行时 MDX 编译器渲染评论**（K 线）：评论走集合编译链，评论里能写组件本来就是集合的能力。
- **评论包依赖身份包**（K 线）：身份校验在站点 action 组合，模型包零身份概念。
- **手工对抗 HMR**（强刷、自建失效链、mtime 触碰、删除过滤器）：vite 缺陷已修，原生链路可用。
- **「先写探针/验证站，再收进正式代码」的开发顺序**：直接写正式代码，探针只判上游未知行为。
- **把 docsite-kit 摊平成纯小包、不留组合包**（2026-10-12 定）：骨架的职责就是组合——布局、组件表、集合接线、action 组合要有一个正本持有者；摊平后每个站拼七八个包、版本矩阵无人兜底。解体见 4.1：删重复正本、拆纯库、组合点做薄但保留。
