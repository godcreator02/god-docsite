# 文档站的页面怎么写

这份只讲**写出来的内容**。建站、构建、核对与确认要执行的命令看同一个插件的说明书 `docs-site`；轨迹卡看 `trajectory`。

## 文档讲什么

文档的职责是**告诉读者东西在哪、先读什么、可以跳过什么**，不把代码逐句翻译成散文。

- **段落自检**：删掉这句，读者会找不到该看的代码、或做出错误判断吗？会就留；只是复述代码里也写着的事实，删掉
- **只写现状**：「原来怎样现在怎样」不出现在现状页，历史写进轨迹卡
- **只写「错了难改」的**：边界约束、依赖方向、接口契约、状态机、核心数据结构与关键算法、取舍。像素、文案、字段清单，以及给关键算法准备输入的辅助代码（算哈希、归一化、解析小工具、显示细节）留给实现者；命令、配置项、数字以代码为唯一依据
- 页面顶上已经按 frontmatter 渲染了 `title` 与 `description`，正文不写 `# 标题`

## 每一页做成讲清原理的网页

- **先想清楚**读者看完要明白哪一两件事、现在已经知道什么、会在哪一步看不懂
- **直接讲原理**，用实际的名字、数据结构、真实的命令与输出；一个具体例子贯穿全页
- **能看、能动的东西承担主要解释**，文字负责引出和收尾；每张图、每段动画都要讲清一件光读文字拼不起来的事，表格加一句话能说清的不画
- 图直接画（SVG、React 组件），不用 Mermaid；同一个角色在整页里固定一种颜色
- 讲电路、算法、数值方法的页写真正的数学公式（行内 `$…$`，行间 `$$…$$`），数学模式里的中文写进 `\text{}`

## 描述一个系统：先画接缝图

讲一个仓、一组插件、一套架构，先放一张接缝图把系统分成模块，再按接缝逐条讲。图用讲解组件包的 `SeamDiagram` 画：
虚线框是模块（包或层），框里的方块是能力（能力名加最关键的标识符），每条跨过模块边界的线带一个编号就是接缝（实线是调用或 import，虚线是读写磁盘上的文件），
系统之外的东西放在框外。图后面的正文用同一套编号逐条讲接缝，代码只在契约那一行出现。
图的内容用 `@godcreator/explainer` 的 `defineSeamGraph` 定义，坐标写成一张 `SeamLayout`，两样交给 `SeamDiagram`；放进生成正本时机读规则用 `seamGraphText`。

## 讲解组件

讲解组件包 `@godcreator/explainer`：`./site` 是组件，`.` 是给生成物用的机读文字规则（不 import React）。

- 三种外壳，控制条在画面上方、说明文字在下方：**分步** `Stepper`（有先后的过程）、**动画** `Timeline`（时间连续，画面写成「时间 → 画面」的函数）、**选情况** `CasePicker`（同一套规则下几种情况的差别）
- 零件有 `Pane`、`Terminal`、`Pill`、`Dot`、`CodeLines`、`Diff`；`stepsText`、`chaptersText`、`casesText` 把步骤、章节、情况的数据转成段落
- 组件只画这一页独有的部分，控制条与零件不重画

**组件的硬性规则**：

- **自包含**：画面和讲解文字都写在组件里，mdx 里只写 `<名字 />`；讲解文字是一份不依赖 React 的数据（`*.data.mjs`），画面读它
- **机读规则只给放进生成正本的组件写**：一份 `*.ai.mjs` 读同一份 `*.data.mjs`，交回它在生成物里的样子，登记进 `docfirst.config.mjs` 的 `components`；规则只写结论，不逐步展开
- **组件放进页面的同名文件夹，页面开头 `import`**，路径相对页面，如 `push.mdx` 里 `import { AutoMergeRun } from './push/auto-merge'`（几页共用时放哪看 `docs-site`）；`Term`、文件树 `Files` / `Folder` / `File` 与 fumadocs 自带的组件不用 import
- **组件自己 `import` 自己的样式** `./xx.css`；讲解组件包的样式由站点的 explainer 功能接进全站，不用再引
- 浏览器 API 放进 `useEffect`；组件最外层加 `not-prose`，宽窄屏用容器查询
- 颜色用 fumadocs 的主题色（`bg-fd-card`、`border-fd-border`、`text-fd-muted-foreground`）；自己的彩色定义成 CSS 变量、`.dark` 下另给一套
- 组件里的文字不进站内搜索：读者会搜的词写进页面标题、描述或正文

现成的例子：本仓 `docs-site/content/gitea/push/`，是 `push.mdx` 的同名文件夹（auto-merge 的数据、画面、机读规则各一个文件，数据里照抄源码的地方钉了码）。

## 设计说明怎么写

讲解组件由一方设计、另一方实现时（实现方是 ZCode 还是子代理都一样），设计方先读代码，写一份设计说明交给实现方，实现方照它写组件、正文与钉码。
说明写到实现方不用再读代码猜意图为止：每个数都能在代码里找到出处，每样画面都写清画什么。

**接缝图**写清：

- 有哪些模块：包名或目录名，加一句话的角色，按依赖方向从上往下排
- 几号接缝连着谁：每条接缝的编号、两端各是哪个模块的哪个能力，实线（调用或 import）还是虚线（读写磁盘上的文件）
- 中间传什么：类型名、文件名、命令名

**讲解动画**写清：

- **讲哪一件事**：一句话写出来，再写读者看完要明白的一两点。只讲一件；相邻的话题点名划出去，写明归哪一页的哪个组件
- **外壳与位置**：用哪种外壳、放在哪一页的哪两段之间、组件名与文件名
- **例子数据**：一组贯穿全图的数据写成表，从头用到尾：时刻、数值、每个数在每一步里去了哪。取随包默认值，写明出处
- **画面**：每条横道或每一步画面上画什么、标签写什么、哪几种标记要一眼分得清、图例写什么。同一个角色在整幅画里固定一种颜色，沿用站里已有的 CSS 变量
- **讲解文字**：画面下方的说明，按时间段或步骤分段写出原句，写明可以润色、意思不变
- **钉码**：照抄源码的数与行为各出自哪个文件的哪一段，实现方在数据文件里那段数据正上方钉上
- **验收标准**：截图验收时逐条查的清单。拖到哪几个关键时刻、各能看到什么；浅色、深色、375 宽都看得清，不横向滚动；
  播放中不长时间静止，开头和结尾的静止压在几秒内；标签与线都写全称、不缩写，每根线写清它是什么

分步、选情况照动画写，横道换成每一步或每一种情况的画面。验收怎么截图看 `docs-site` 的「验收一页」。

**实现方发现说明里的数或行为跟代码对不上，停下来回报**：写明说明里是什么、代码里是什么、在哪个文件，不自己改设计，也不照说明硬写。设计方核对后改说明再交回。

## docfirst 站额外的规矩

### 分区

```
<站目录>/
├── trajectory/      轨迹：怎么走到今天、每次取舍的理由。卡只增不改
└── content/
    ├── future/      未来：在等什么前提、在途方案（做完删）
    └── <其余目录>/   现状：此刻是什么。除 future/ 外的目录都是现状区
```

**此刻是什么归现状，怎么走到今天归轨迹，还没发生的归未来**。现状区按包、按读者拆目录，不按机制拆。轨迹卡目录由 `docfirst.config.mjs` 的 `trajectory` 指定。

### 钉码钉哪种话

**钉一处码是在说：这句话跟着这段代码走，代码变了就回来复核**。只在现状区钉，轨迹卡里出现记号直接报红。

**只钉页面的解释所依赖的代码**：核心数据结构、关键算法、对外的写法（标记与配置怎么写、命令、建站器写进站点的接线文件）、跨包的规则。
给它们准备输入、把各部分接起来的辅助代码不钉：算哈希、归一化、解析小工具、登记表、显示细节，用一句话讲它做什么就够了。
拿不准时问一句：**这段代码改了，页面上哪句话会不成立？** 指得出是哪句就钉，说不出就不钉。值得为它做讲解组件的算法就是关键算法，要钉。

关键算法整段钉住，只改写法不改逻辑也会亮黄灯：改它的人本来就该回来看解释还对不对。辅助代码钉了只会多出不用改正文的黄灯，让真该改的那一处不容易被看到。

| 引用 | 用在这种话 |
| --- | --- |
| 行段 `ref file lines` | 「这段代码做了什么」。钉测试钉整条，钉配置钉那一行 |
| 整文件 `ref file` | 「全部就这些」，只用在几十行以内的短文件 |
| 目录树 `tree dir` | 「这个目录下就这些」，可带 `depth`、`glob` |

新记号单独写一行，只写目标，路径相对站目录；确认时 `confirm` 在同一行写上记录，记录不手改：

```mdx
{/* ref file="../src/a.ts" lines="10-23" */}
{/* tree dir="../packages" depth="1" */}
```

讲解组件数据里照抄源码的地方也钉：在那段数据正上方单独一行写 `/* ref file="../src/a.ts" lines="10-23" */`（不带花括号）。
设计还在变的部分少钉。不钉码的页在 frontmatter 写 `docfirst: none`。

### 黄灯以后改正文

1. 逐处看被钉的代码变了什么、正文哪句因此不再成立
2. **只改对不上的段落**：不重排全页、不顺手润色别处、小标题原样保留
3. 论断仍成立的直接确认；不成立的先改再确认；指向的东西没了（红）就改写或删掉那处引用

### 术语表

正本是站点根的 `glossary.json`，每条 `term / aliases / def / href`。收仓自己造的词、在这里有特定含义的通用词、外来框架词，不收通用编程词与单字词。
**定义只写概念，不写服务名、类型名、路径**——数据文件里没法钉码，具体名字留给 `href` 指的那一页。

### 写代码时文档跟着改什么

| 代码动作 | 文档要跟着改的地方 |
| --- | --- |
| 动接口、状态机、依赖方向 | 讲这一块的现状页，同一个提交 |
| 某条路走不通、做了选型、实验有结论 | 当场写轨迹卡（`trajectory`） |
| 命令、配置变了 | 用法页，重新生成生成物 |
| 定了新术语 | 术语表 |

## 生成物的正本怎么写

README、AGENTS.md、CLAUDE.md、SKILL.md 的正本是现状区的 mdx（一般在 `content/docs/outputs/`）。渲染时记号换成代码块、组件换成它的机读文字，别的一个字节不改。

- **AGENTS 与 skill 要精简**：前者每个会话都读，后者触发就读，只留硬约束与「怎么做」，为什么写在站里；生成出的 AGENTS.md 控制在 60 行内
- CLAUDE 正本第一行固定是 `@AGENTS.md`，只给 Claude 的指令写在后面
- skill 的 `description` 写「什么时候读」，控制在 200 字以内

## 文档与注释治理

目标是把放错层的东西放回去：**AGENTS 只写硬约束，文档站写为什么，注释只写现状**。范围一次一个模块。

- 一个文件读一遍，注释去留、名字清不清楚、函数该不该拆、有没有设计思路要移进文档四件事同时做；判据见全局规矩（`~/.claude/CLAUDE.md` 的「写代码」一节）
- 注释移到文档时：模块怎么切、接口语义 → 现状页并钉回那段代码；一次选择与否掉的方案 → 轨迹卡；怎么用 → 用法页；词的含义 → 术语表
- 证明没改行为：测试改前通过、改后也通过，测试一个字不改；文档改动与代码改动分两个提交
- 去黑话照全局规矩的「写文档不说黑话」；把带日期的经过、改名经过清出现状页，轨迹区只增不改
- 精简注释会让下游钉码的行号整体移动，改完运行一次 `confirm` 写回
