# 文档站的页面怎么写

这份只讲**写出来的内容**：一页讲什么、怎么讲、组件怎么写、docfirst 站上哪句话该钉码。建站、构建、核对与确认这些要执行的命令，
看同一个插件的说明书 `docs-site`；轨迹卡看 `trajectory`。

## 文档讲什么

文档的职责是**告诉读者东西在哪、先读什么、可以跳过什么**，不把代码逐句翻译成散文——那样写的时候浪费，代码一改就对不上，
读完还是不知道该看哪。

**段落自检**：删掉这句，读者会找不到该看的代码、或做出错误判断吗？会就留；只是复述代码里也写着的事实，
docfirst 站就钉码引用那段代码，普通站就删掉。

**只写现状**：「原来怎样现在怎样」不出现在现状页，历史写进轨迹卡。

## 每一页做成讲清原理的网页

假设用户说「做个网页给我讲讲 git 的原理」，你会怎么做，每一页就怎么做。没有模板，页面怎么排、小标题怎么起按题目设计；
控制条与零件用讲解组件包里固定的那一套，读者学一次就会用。

- **先想清楚**：读者看完这一页要明白哪一两件事，读者现在已经知道什么、会在哪一步看不懂
- **直接讲原理**：是什么东西、按什么规则、在什么时候、变成什么。用实际的名字、数据结构、真实的命令与输出；
  类比只在实际的东西讲不清时才用，用了就说清哪一点对得上、哪一点对不上
- **一个具体例子贯穿全页**：同一个仓、同一组数据从头用到尾
- **能看、能动、能自己操作的东西承担主要解释**，文字负责引出和收尾；一次只推进一个概念
- **每张图、每段动画都要讲清一件光读文字拼不起来的事**：跨多台机器、多个时刻、多个文件的机制。
  表格加一句话能说清的不画；真实产品里能直接看到的界面默认不模拟
- **图直接画**（SVG、React 组件），不用 Mermaid；同一个角色（一台电脑、一个文件、一个包）在整页里固定一种颜色
- **讲电路、算法、数值方法的页写真正的数学公式**：方程、递推、判据、推导写成公式（行内 `$…$`，行间 `$$…$$` 或 `math` 代码块），
  不用代码块或文字代替。数学模式里的中文写进 `\text{}`；照着代码写出来的公式，旁边钉上那段代码。站怎么接公式看 `docs-site`
- 页面顶上已经按 frontmatter 渲染了 `title` 与 `description`，正文不写 `# 标题`

## 描述一个系统：先画接缝图

讲一个仓、一组插件、一套架构，**先放一张接缝图把系统分成模块，再按接缝逐条讲**。别一上来挑一段关键代码逐行讲：
读者还不知道它在系统里的位置。讲一个概念（比如 git 的原理）没有可切分的模块，不用这张图。

图用讲解组件包的 `SeamDiagram` 画，元素的意思固定：

- **虚线框是模块**（包或层），标包名和一句话的角色，按依赖方向从上往下排
- **框里的方块是能力**：能力名加最关键的标识符（文件名、类型名、命令名），不展开实现
- **每条跨过模块边界的线带一个编号，这就是接缝**。实线是代码调用或 import，虚线是读写磁盘上的文件；模块内部的线不画
- **系统之外的东西放在框外**（人、git hook、CI、别的系统），箭头指向它们进来的入口
- 悬停编号或模块浮出说明，点击固定高亮它连着谁——`SeamDiagram` 已经做好

图后面的正文用同一套编号：先**逐条讲接缝**（连着哪两端、中间传什么、哪边负责、改了会让哪边出问题），再讲**各模块对外能做什么**。
代码只在契约那一行出现。

系统大时分两层：首页的全局图只画包与包之间的接缝；每个包的模块页（目录怎么拆见「分区」）开头画包内接缝图
（虚线框是文件或目录，方块是文件对外给的函数，包外的调用方画成灰色实线框），用 frontmatter `full: true` 铺满宽度。

站只写每张图的内容与坐标：内容用 `@godcreator/docsite-explainer/seam-graph` 的 `defineSeamGraph` 定义，坐标写成一张 `SeamLayout`，
两样交给 `SeamDiagram`；图要放进生成正本时，机读规则把同一份内容交给 `seamGraphText` 写成段落。

## 讲解组件

**讲解组件包** `@godcreator/docsite-explainer` 给出三种外壳，控制条都在画面上方、排成固定的一行，说明文字在画面下方：

- **分步** `Stepper`：每一步是一个固定状态，讲有先后的过程
- **动画** `Timeline`：时间连续、能拖到任意一刻。画面必须写成「时间 → 画面」的函数，不能用一次性的 CSS 动画
- **选情况** `CasePicker`：画面高亮这种情况走过的路径与结论，讲同一套规则下几种情况的差别

零件有 `Pane`、`Terminal`、`Pill`、`Dot`、`CodeLines`、`Diff`；`@godcreator/docsite-explainer/text` 把步骤、章节、情况的数据转成段落。
组件自己只画这一页独有的部分，控制条与零件不重画。风格是现代开发者工具风：1px 细边框、大圆角，边框、标题栏、标签用同一个颜色调淡，
很轻的阴影与小动画，不用辉光、渐变、毛玻璃。

**组件的硬性规则**：

- **讲解组件自包含**：画面和讲解文字都写在组件里，mdx 里只写 `<名字 />`。讲解文字是一份不依赖 React 的数据（`*.data.mjs`），
  画面读它。`Tabs`、`Callout` 这类包着正文的排版组件照常用子元素
- **机读规则只给放进生成正本的组件写**：站上不出每页的机读版，组件要用在 README、AGENTS、SKILL.md 的正本里，才写一份 `*.ai.mjs`，
  交回的就是它在生成物里的样子，读同一份 `*.data.mjs`；规则登记进 `docfirst.config.mjs` 的组件名册 `components`
- **页面用到站内组件就在开头 `import`**（基础包上的站）：路径相对页面，如 `import { SeamMap } from '../../src/components/seam-map/seam-map';`。
  `Term` 与文件树 `Files` / `Folder` / `File` 由功能包 `@godcreator/docfirst-site` 提供，不用 import
- **组件自己 `import` 样式**：`./xx.css`，用了讲解组件包的再 import `@godcreator/docsite-explainer/styles.css`，不靠全局样式
- 浏览器 API 放进 `useEffect`：页面先在服务端渲染一遍
- 组件最外层加 `not-prose`，宽窄屏用容器查询（外层 `@container`，里面 `@2xl:` 这类前缀）
- 颜色用 fumadocs 的主题色（`bg-fd-card`、`border-fd-border`、`text-fd-muted-foreground`，SVG 里 `fill-fd-*` / `stroke-fd-*`）；
  自己的彩色定义成 CSS 变量、`.dark` 下另给一套，浅底用 `color-mix(in srgb, 颜色 12%, transparent)`。中性主题的 `fd-primary` 接近黑白，不能当强调色
- 动画：CSS 做得了的用 CSS，位移、弹簧、拖拽用 `motion`；同一个东西前后两步用同一个稳定的 `key`，读者看得见它移过去。
  颜色不交给 `motion` 插值（它解析不了 `var(--x)`），写在 `stroke` / `style` 上用 CSS `transition`；SVG 路径让端点各自 `useSpring`、
  `useTransform` 每帧算 `d`；要画成虚线的线只淡入，不做 `pathLength` 动画；外层包 `<MotionConfig reducedMotion="user">`
- 组件里的文字不进站内搜索：读者会搜的词写进页面标题、描述或正文

**还没迁到基础包上的 Next 站**写法不同：页面不 import 组件，组件登记进站的组件表（`src/components/mdx.tsx`）与名单；用到状态、事件、动画的组件
第一行写 `'use client'`，带 `'use client'` 的模块不给服务端组件导出常量；讲解组件包的样式在全局样式里引入一次。

写完组件怎么登记、怎么验收，看 `docs-site`。

## docfirst 站额外的规矩

### 分区

```
<站目录>/
├── trajectory/       轨迹：怎么走到今天、每次取舍的理由。卡只增不改
└── content/
    ├── future/       未来：roadmap.mdx（在等什么前提）、spec/（在途方案，做完删）。别的仓写来的反馈是 gitea 上的 issue，不放这里
    └── <其余目录>/    现状：此刻是什么。除 future/ 外的目录都是现状区，几个、叫什么按文档规模定
```

轨迹卡的目录由 `docfirst.config.mjs` 的 `trajectory` 指定（相对站目录），基础包上的站写 `"trajectory"`；不写时是 `content/trajectory/`，Next 站多是这样。

**此刻是什么归现状，怎么走到今天归轨迹，还没发生的归未来。**为什么存在、刻意不做什么也是此刻的边界，写在现状区，
每条「不做」一句话，理由链到轨迹卡。

**现状区按文档规模拆目录**，目标是读者在侧栏里一眼找到一个包、一类读者要的全部页：

| 规模 | 怎么拆 | 参考案例 |
| --- | --- | --- |
| 一个模块、几页就讲完 | 一个 `docs/`，页面平铺 | — |
| 几个包或模块 | `docs/` 下每个包一个子目录，目录首页 `index.mdx` 是这个包的模块页，讲它原理的页排在后面；入口页、术语表、生成物正本留在 `docs/` 顶层 | `docs/pin/`、`docs/workflow/` |
| 还有别的读者（维护这个仓的人、扩展插件的作者） | `content/` 下再建顶层目录，一类读者一个，侧栏里各是一个区 | `maintain/` 给改这个仓的人 |

按包、按读者拆，**不按机制拆**：按机制分会让同一个包的接缝页和原理页散到几个目录里。横跨几个包的机制，放进读者最先会去找的那个包的目录。
新加顶层目录照 `docs-site` 的「加一个分区」做（基础包上的站建目录、写 `meta.json`，Next 站还要加集合与路由），`docfirst check` 自动把它算进现状区。
现状区的入口页按「接缝图 → 逐条接缝 → 各模块」展开，术语表也在现状区。

### 写到哪为止

只写「错了难改」的：边界约束、依赖方向、接口契约、状态机、取舍。像素、文案、字段清单、内部算法是实现者的自由。
判据：**实现者剩下的自由里做任何选择都不违背文档，就够了。**写不出一块「不知道什么」，往往是代码切错了，先改代码。

- **论断可验证**：要么钉码，要么给确切路径；命令、配置项、数字以代码为唯一依据
- 投影出来的代码块是论据不是正文，一段引用配一句「这段说明什么」
- 现状页少做站内链接；对决策的说明写进轨迹卡再链过去。引用轨迹卡是说「有先例」，不是「不许动」
- 手画目录树、手抄配置样例、给运行出来的数字写散文都会很快过时；目录结构用 `tree` 引用，别钉生成物

### 钉码钉哪种话

**钉一处码是在说：这句话跟着这段代码走，代码变了就回来复核。**所以只在现状区钉：轨迹卡里出现记号 `check` 直接报错，未来区没有代码可钉。

| 引用 | 用在这种话 |
| --- | --- |
| 行段 `ref file lines` | 「这段代码做了什么」。钉测试钉整条（从 `test(` / `it(` 到它结束），只钉测试名的话断言改弱了照样是绿；钉配置钉那一行 |
| 整文件 `ref file` | 「全部就这些」，只用在几十行以内的短文件；大文件要说几件事，分别钉那几段 |
| 目录树 `tree dir` | 「这个目录下就这些」 |

新记号单独写一行，只写目标，路径相对站目录；确认时 `confirm` 在同一行写上记录，记录不手改：

```mdx
{/* ref file="../src/a.ts" lines="10-23" */}
{/* ref file="../src/a.ts" lines="10-23" hash="3fa9c2e1b07d" blob="2689fa073ac6" */}
```

**讲解组件里照抄源码的地方也钉**：数据里手抄的源码片段与行号、逐字照抄的测试名、命令行输出格式、接缝图上的函数签名。
在那段数据正上方单独一行写 `/* ref file="../src/a.ts" lines="10-23" */`（不带花括号，必须独占一行）。

### 黄灯以后改正文

黄灯是「被钉的代码变了，正文可能不成立了」。运行哪几条命令看 `docs-site`；正文这样改：

1. 逐处看被钉的代码变了什么、正文哪句因此不再成立
2. **只改对不上的段落**：不重排全页、不顺手润色别处、小标题原样保留、沿用本页已有的口吻和引用方式
3. 论断仍成立的直接确认；不成立的先改再确认；指向的东西没了（红）就改写或删掉那处引用

### 术语表

收三类：仓自己造的词、通用词在这里有特定含义的、外来框架词。不收通用编程词与单字词。正本是一份数据文件
（`src/glossary.mjs` 一类，基础包上的站在 `docfirst.config.mjs` 的 `glossary` 写它的位置），每条 `term / aliases / def / href`；**定义只写概念，不写服务名、类型名、路径**——数据文件里没法钉码，
具体名字留给 `href` 指的那一页。全站自动标注在构建时发生，不改源文件。

### 写代码时文档跟着改什么

| 代码动作 | 文档要跟着改的地方 |
| --- | --- |
| 动接口 / 状态机 / 依赖方向 | 讲这一块的现状页，同一个提交 |
| 某条路走不通、做了选型、实验有结论 | 当场写轨迹卡（`trajectory`） |
| 命令 / 配置变了 | 用法页，重新生成生成物 |
| 定了新术语 | 术语表 |
| 做 / 不做的边界动了 | 讲边界的那页，理由写进卡 |

确实没有文档要改，说明这次改动没碰到任何「错了难改」的东西。

需求要跨会话、跨模块、或有未定选型，三条占一条才写 spec：`future/spec/` 下一页，页头列验收清单，随做随提交。
做完把设计写进现状页、决定写成轨迹卡，然后删页。

## 生成物的正本怎么写

README、AGENTS.md、CLAUDE.md、SKILL.md 的正本是现状区的 mdx（参考案例在 `content/docs/outputs/`）。渲染时记号换成代码块、
组件换成它自己的机读文字，别的一个字节不改：正本里能钉码，也能放讲解组件。

- **AGENTS 与 skill 要精简**：前者每个会话都读一遍，后者触发就读，每行都要有用——只留硬约束与「怎么做」，为什么写在站里
- **正本里的解释交给讲解组件**：人在站上看分步、动画，生成物里只剩组件的机读规则交回的那几句。所以放进正本的组件，
  机读规则只写结论，不把每一步逐条展开
- 每仓的 AGENTS 正本只写本仓专属的（怎么运行、端口、检查命令、禁止事项、从哪读起），生成出的 AGENTS.md 控制在 60 行内
- CLAUDE 正本第一行固定是 `@AGENTS.md`，只给 Claude 的指令写在后面
- skill 的 `description` 写「什么时候读」，控制在 200 字以内：工作台的 `index` 会截断更长的描述

## 文档与注释治理

目标是把放错层的东西放回去：**AGENTS 只写硬约束，文档站写为什么，注释只写现状。**范围一次一个模块，改动越大「没改行为」越难证明。

**一个文件读一遍，四件事同时做**：注释去留、名字清不清楚、函数该不该拆、有没有设计思路要移进文档。这四件的判据正本在
全局规矩（`~/.claude/CLAUDE.md` 的「写代码」一节），这里不复述。注释「移到文档」时去哪一页：

- 模块怎么切、依赖方向、接口的语义与边界 → 讲这个模块的现状页，**并钉回那段代码**，否则只是把对不上换了个地方发生
- 一次选择、否掉了什么、判据是什么 → 轨迹卡，一个结论一张
- 怎么用、命令与配置 → 用法页；一个词在这个仓里的确切含义 → 术语表

**证明没改行为**：测试改前通过、改后也通过，测试一个字不改。文档改动与代码改动分两个提交。

**去黑话**：判据与写法照全局规矩的「写文档不说黑话」。收进术语表的「不再使用的词」一节；改名本身写一张轨迹卡。

**把历史清出现状页**：带日期的经过、改名经过、事故经过、版本演进史删掉，轨迹区已有卡的直接删，没有卡又有长期价值的才新建。
记录出错经验的页（症状与判据）本身不动。轨迹区只增不改，旧卡里的旧词与失效链接是历史原貌。

**每仓只写自己实现的东西**：谁实现谁写正本；行为由实现方写，契约由定契约的一方写；「内核一条原生命令都没有」这类边界声明留在本仓；
没钉码又讲别的仓机制的段落最可能已经过时，改成一句概括加指路。

**整仓以上的治理**：

1. 先冻结写入、对齐范围：扫黑话、日期与版本号、讲别的仓机制的关键词，列出判据与方案，等用户同意
2. 对照表放总控台 `out/`（临时文件）；长期正本放各仓的术语表与轨迹卡
3. 先在最小的仓上做一遍交用户确认，再做其余的仓；同类替换派子代理并行，任务说明里写明先读该仓 AGENTS、对照表、样板仓
4. 每仓按 `docs-site` 的「改了被钉的代码」处理黄灯，全绿再过仓根检查，精确路径 `git add` + `git commit --only`
5. 不信子代理的回报：自己用 rg 重扫、核对轨迹卡只增没改；并行会话中途的新提交要重扫
6. 收尾看一遍各仓在 gitea 上开着的 issue（`gitea-issues.list`）；别人正在处理的红灯黄灯点名说出来，不替人处理
