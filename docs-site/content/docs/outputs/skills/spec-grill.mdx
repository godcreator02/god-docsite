# 先问清，再动手

**人同意之前不动代码。**一句话需求直接开工，会出三种问题：agent 只盯着人点到的那一处改，边界外受牵连的
地方没人问；上下文装不下就漏改，漏的正是没人说出口的那部分；做完才发现「不是这个意思」，返工比事先问清贵十倍。
事先问清把这三种问题挡在动手之前，代价是几轮对话。

## 怎么问

目标是把想法问到能一句话说清三样：**回答什么**（做完之后哪个问题有了答案）、**不做什么**（边界外明确排除的）、
**成功判据**（怎么验收，能跑出来看的）。三样说不清，就还没问完。

- **一轮把当前能问的全部问完。**每个问题编号，每个问题给推荐答案和一句理由；人可以只答「都按推荐」。
  一次只问一个是让人陪着一轮轮等，问十个是把选择全部推回给人。
- **在对话里问，不用宿主的提问工具。**问题要带上下文、推荐和理由，工具的界面装不下这些。
- **答案回来重新想下一轮。**前一轮的回答会排除一些选项、带出一些新的；新问题再问一轮，直到三样说清。
  通常两轮，三轮以上说明需求本身还在变，把这个观察说出来。
- **事实自己查，不问人。**代码现在长什么样、哪个模块管这块、测试怎么跑——派子代理去读；问人等于把查得到的事
  推给记不全的人。只问人才知道的：意图、优先级、能接受的代价、边界。
- **列出你已经替人做的假设**，逐条标「按此进行，反对请说」——沉默也是一种回答，但要让人看见沉默默认了什么。

## 跟 gwb-decide 的分工

spec-grill 问**需求边界**：做什么、不做什么、怎样算做成。gwb-decide 问**选型**：用哪个依赖、定什么契约、
放进内核还是做成插件。问的过程中冒出选型问题，记为未定项，不在这里推进，边界问清后再走 gwb-decide。

## 什么时候结束、产出什么

三样说清、人同意，就结束。产出按下面的判据二选一：

- **跨会话、跨模块、有未定选型**，占一条就写成一页 spec，放在 `content/future/spec/`：页头验收清单、
  随做随提交、做完拆开写进各页再删页——这几条的正本在 `docfirst-docs` 的「spec：在途方案」。
- 都不占：直接改对应的现状页开工，问清的结论写进那次提交的信息里。

之后的循环（实验与选型 → TDD → 全绿 → 更新现状、写轨迹卡）见 `docfirst-docs`。
