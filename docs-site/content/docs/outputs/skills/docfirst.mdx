# docfirst 插件：两条建站命令，另带一组说明书

本插件有**两条命令**：`docfirst.create` 给一个仓建一个接好 docfirst 分区的文档站，`docfirst.create-plain`
建一个不接 docfirst 的普通 fumadocs 站。除此之外它只做一件事：把本插件带的其余说明书注册给你读。

**它对本仓发布的 npm 包零依赖**（通用包 `code-pin`、`trajectory-disk`、`explainer-player`，docfirst 自己的 `docfirst-workflow`），装了本插件不必再装什么包。判据是「这件事在哪儿发生」：
核对 / 确认 / 渲染要在**仓**里发生（那是门禁与站构建要运行的东西），你自己 `cd` 过去运行；只在你手上发生一次的
（读说明书、给一个仓建一次站）才归插件。**插件不转发命令行。**

**建站在本插件里一步做完**：运行官方脚手架 `create-fumadocs-app`（版本写死，要联网）、应用本机约定（端口并只监听 127.0.0.1、
页面语言、字体、站名等）、选端口、写文件。**本插件不管站的运行**：没有启动、停止站的命令，也没有窗格。
站建好以后要改结构（加分区、加组件）、要构建和看页面，读本插件的说明书 `docs-site`。

## 建一个新站

```
docfirst.create {"dir":"<仓>/docs-site"}
```

站约定放在仓根下的 `docs-site/`。本插件先运行官方脚手架、应用本机约定，再在官方输出上替换、删除、新增几份文件
（分区、`docfirst.config.mjs`、mdx 的接入配置、名册脚本、起始页），加上 docfirst 的依赖与脚本，一起写进目录。**站目录必须还不存在**：
已经有站的仓不能用这条命令，给一个已经用了很久的站加 docfirst，手动接入。

不要 docfirst 的普通站用 `docfirst.create-plain`，参数相同，写法见说明书 `docs-site`。

### `docfirst.create { dir, title?, port? }`

- `dir`：**站目录**的绝对路径（约定是 `<仓>/docs-site`）。它必须还不存在，上一级（仓目录）必须已经存在。
- `title`：站的显示名，不给就依次用仓根 `package.json` 的 `title`、包名去掉 scope、仓的目录名。
- `port`：站的端口。不给就在容器根（单元文件夹插件的设置 `unit-folder.units-root`）里找没被别的站脚本占用的，从 4310 起选；
  检查端口占用时没读取成功的目录或 `package.json` 列在回执的 `portScanIncomplete` 里。

多给别的键直接报错。回执是 `{ dir, repoDir, port, written, overwrites, portScanIncomplete, next, warn? }`。

建出来的东西：官方脚手架的站（搜索、llms 路由照旧），加上三个集合（`src/lib/source.ts` 里用 fumadocs-mdx 的 macro
写的 docs、trajectory、future，现状集合经 `applyMdxPreset(docfirstMdxOptions(...))` 接上 docfirst，这些接入配置从 `@godcreator/docfirst-workflow/fumadocs` 取）、各区的路由与侧栏三个根节点、
整页星轨盘 `/trajectory`（`loadTrajectory` 与 `StarDisk` 从 `@godcreator/docfirst-workflow/fumadocs/trajectory` 取，样式是 `@godcreator/docfirst-workflow/fumadocs/trajectory.css`）与卡页 `/trajectory/<卡身份>`、
`docfirst.config.mjs`（名册展开 `@godcreator/docfirst-workflow/fumadocs/roster` 的 `fumadocsRoster`）、mdx 的接入配置（`src/components/mdx.tsx` 里的状态点组件）、样式 `src/app/docfirst.css`、名册脚本、
起始页（`content/docs/` 下的入口页、术语表与 `outputs/` 下的生成正本，`content/future/` 一页；`content/trajectory/`
只有 `meta.json`，侧栏第一条链到星轨盘，根卡与其余的卡照说明书 `trajectory` 写），`package.json` 里
有 docfirst 的依赖与 `doc` / `doc:confirm` / `doc:render` / `verify:roster` 几条脚本。

**只写文件**：不运行 `pnpm install`、不 render、不 check。回执里 `next` 就是接着要在站目录里运行的那几条：

```
cd <站目录>
pnpm install
pnpm doc:render     # 生成仓根 README.md / AGENTS.md / CLAUDE.md（正本在 content/docs/outputs/）
pnpm doc            # docfirst check
pnpm dev
```

仓根已经有 `README.md` / `AGENTS.md` / `CLAUDE.md` 时回执里会多一条 `warn`：第一次 `doc:render` 会**覆盖**它们
——先把内容移进 `content/docs/outputs/` 下对应的 mdx（那是正本），再 render。建站本身不改仓根的任何文件。

## 核对 / 确认 / 渲染：自己在那个仓里运行

这几条**不经过工作台**。`cd` 到那个站目录（有 `docfirst.config.mjs` 的那个，约定是 `<仓>/docs-site`），运行：

```
pnpm doc                                       核对。有红时退出码 1——那是核对结果，不是命令失败
pnpm docfirst check --json                      机读报告：哪几页的钉码跟代码对不上了、哪个生成物过期了，一行 JSON
pnpm doc:confirm                               机械写回：给未确认的记号写上记录、挪了位置的写回新行号、重新渲染生成正本
pnpm doc:confirm content/docs/a.mdx --accept   复核过后，接受点名页里的黄灯
pnpm doc:render                                只重新生成生成物（README / AGENTS / SKILL.md 那类）
pnpm docfirst trajectory                        列出轨迹卡在星轨盘上的树与主干
```

**改了被钉的代码，就在同一个提交里处理它引起的黄灯**：钉住的文件在本仓有未提交改动、内容又变了的黄灯，
`pnpm doc` 算红。先 `doc:confirm` 做完机械写回，再逐条看剩下的黄灯，论断还成立就 `--accept`，不成立先改论断。
`--accept` 必须点名页，别人没复核的黄灯不替他接受。确认不要求先提交。

**要看哪几页跟代码对不上了就运行带 `--json` 的那条**，自己读那份报告：`docs[].items[]` 里 `status` 是 `changed`（内容变了）
或 `missing`（引用的目标不存在）的就是待重写；`line` 是记号在文档里的第几行、`lines` 是被引段今天在源文件里的
位置、`diff` 是变了的那几行——按这三样定位，**只改对不上的段落，不重排全页**。`unconfirmed`（还没确认过）不算对不上。
`doc` 也可能是站的 `src/components/` 下讲解组件的源码：组件里照抄源码的数据钉在源码上，变黄了就改那段数据或它的讲解文字。
只有名册外组件的页不用重写正文：在 `docfirst.config.mjs` 里补转成机读文本的规则。

## 跨仓反馈：放进目标仓文档站的 `future/inbox/`

在 A 仓工作时发现 B 仓的东西不好用，**直接放进 B 仓自己站的未来区**：新建一个文件
`docs-site/content/future/inbox/<yyyy-MM-dd>-<来源仓>-<英文短标题>.mdx`，不需要命令。文件名用英文小写和短横线
（git 会把中文路径显示成八进制转义），中文标题写进 `title`。格式：

```
---
title: <一句话标题>
description: 来源：<哪个仓 / 哪次会话>
---

<正文：碰到什么、期望怎样、证据在哪、你觉得该改哪儿>
```

然后在 B 仓里 `git add` 这个文件、`git commit --only` 这个文件。一条一个文件，所以不会跟 B 仓里别人未提交的
改动冲突，也不用等。处理完由收件的仓删掉这个文件，结论写进现状页或轨迹卡——inbox 只放待处理的条目，不是档案。

## 本插件还带着这些说明书

- **`docfirst-docs`**：文档站怎么写——分区怎么分、引用记号各钉哪种话、每页写到哪为止、钉码怎么确认。
  写或改任何仓的文档站之前先读它。
- **`docs-site`**：每一页怎么做成讲清原理的网页、站的组件怎么登记、怎么验收，两条建站命令、加分区、pnpm 与 next 的常见错误。
- **`trajectory`**：什么时候记一张轨迹卡、怎么写、卡的字段是什么。
- **`docs-governance`**：文档与注释治理——代码自解释扫描、术语统一、清除历史描述、分清谁负责什么。

这几份连同这一份，正本都在本插件所在的仓里（`docs-site` 的生成正本），生成物随本插件
发布——**包没有独立的途径让你读到**：它装在 `node_modules` 里，没有任何说明指向它，一份说明书能被你读到全靠插件
把自己包里那个目录注册给了 skills 插件。

## 出错时

- 报「dir 要是绝对路径」：给了相对路径，插件在工作台主进程里运行，不知道该相对于哪个目录
- 报「站目录的上一级要是已经存在的仓目录」：`dir` 多写或少写了一层，或者仓还没建
- 报「docfirst.create 没建成：……」：后面是建站那一步的原话。最常见的是站目录已经存在（这个仓已经有站，
  手动接入），其次是运行官方脚手架要联网没连上或超时，或脚手架的输出变了、本机约定或文件清单对不上
  （要替换的原文找不到、新增的已经有、替换或删除的没有，报错里会指向插件的 `src/scaffold.ts`），照原话处理
- 报「不认识的参数」：只接受 `dir`、`title`、`port` 三个
- 想核对却找不到命令：**本插件没有那条命令**，自己 `cd` 到那个仓里运行（见上面那节）
