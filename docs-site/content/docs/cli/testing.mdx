这一章回答：这套东西一共几组测试，各检查什么规矩，为什么边界测试要去读依赖图，以及文档本身怎么防止漂移。

## 三组，各自跑

| 在哪儿 | 怎么跑 |
| --- | --- |
| 工作区根 | `pnpm test`（先 build，再 `node --test tests/*.test.ts`） |
| `docs-site/`（这个站） | `pnpm test` |
| `plugins/docfirst/`（[工作台插件](/docs/modules/plugin)） | `pnpm check`（typecheck + oxlint + vitest） |

插件那组用 vitest，是 `node --test` 唯一的例外：它跟 devkit 生成的插件初始文件一致，不为一个插件改那套初始配置；
工作区根的 `test` 脚本因此不收它。建站参数的测试、插件对包零依赖那条规矩都由插件自己的测试检查，归
[工作台插件](/docs/modules/plugin) 那一页。

## 判定层单独测：三样假的

判定层的测试在 `tests/core.test.ts`，传入三样假的：**假格式**、**内存读取器**（它能读到的只有一张文件表）、
**内存里的旧内容来源**。判定层不读盘、不启动进程、不认识任何真格式，这样测正好把这几条也一并检查了：

{/* ref file="../tests/core.test.ts" lines="1-4" hash="bf9bca964602" blob="3f7f931c2523" */}

旧内容来源默认是什么都取不到的这一份：比较器只能滑窗，走到 hunk 表就说明判定顺序错了；要验 hunk 跟随的几条另传一份带旧内容的：

{/* ref file="../tests/repo.ts" lines="27-33" hash="fac97ce041a5" blob="1f63ee05e8b2" */}

假格式整份就是这一个文件。它是 `Format` 底下第二个真适配器（生产那个是 fumadocs 站用的 mdx），判定层、命令行、
摆放的测试都用它：

{/* ref file="../tests/fake-format.ts" hash="7bc5692991f1" blob="4a30e3e1941e" */}

这组测试证明的是：四种状态的完整来回；一篇文档两个格式都认领时报错；同一段被引两处各带各的记录；一处钉不住只是那一处不动；
草稿记号的哨兵；没写记录属性的正式记号算未确认；目录树、存在性、名字三种各自的黄红；滑窗的挪位、多处相同时取最近、
并列不猜、找不到时位置不明；黄灯不带 accept 不动、带了重新记；取得到旧内容时按 hunk 表跟随并给 diff；归一化与行段切片。

记号那条契约由 `tests/marker.test.ts` 拿两个适配器一起验：`parse(marker(t, r))` 必须认回 `t` 与 `r`。认得出只是一半，
什么时候不认才是这套写法能放进正文的理由——哨兵不齐的、写在句子中间的、动作词不认识的，一律不认：

## 装配与摆放

装配的归一（内容根、落点的两种写法、文档身份）全部经过 `loadProject` 看，在 `tests/project-load.test.ts`；
完整跑一遍命令行（真扫目录、分区按约定、配置里不认识的键报错）在 `tests/cli*.test.ts` 那几份。

摆放有两份测试，用的是 `PlacingHost` 的两个适配器：`tests/placing-host.test.ts` 的存放是内存里一张表，一个字节不落盘，
「写了什么、写到哪个键上、被改过之后判成哪种状态」直接看得见；`tests/placement.test.ts` 在临时目录里建一个真项目，
`loadProject` 之后直接调两个方法，不经命令行。命令行怎么把摆放的结果打印成人读的话、退什么码，归 `tests/cli-outputs.test.ts`。

一次性迁移 `docfirst migrate-ledger`（旧版 `.ledger.json` 写进记号）在 `tests/migrate-ledger.test.ts`。

## 站测试：不启动 Next，经过构建时的同一条处理流程

`register()` 把 fumadocs 的 Node loader 注册进 Node，`import` 一篇 `.mdx` 经过的就是站构建时的那条处理流程——
不用启动服务器，也不是另写一条模拟。集合用 macro 写在 `src/lib/source.ts` 里，导入时的查询参数写
`?macro_id=src/lib/source.ts#docs`（`#` 编码成 `%23`），loader 才找得到现状集合、用上它的 `mdxOptions` 与 postprocess。断言四样：每条引用在页面上都有一个带 `data-dot` 和来源标题的元素、
组件由 React 表画出来（没有裸标签漏出去）、`_markdown` 里有来源行且组件已转成纯文本、以及**这个站自己全绿**。

{/* ref file="tests/page.test.mjs" lines="124-132" hash="10ebafcc9456" blob="5ae8125b5dda" */}

<Note>
  站测试**不跟命令行比状态**：算状态的是同一个服务，比出来只能相等，比了也证明不了什么。
  跨调用方的比对留给启动站后请求 `.md` 路由。
</Note>

## 文档防止漂移：这个站自己就是测试

每一章都钉着本仓源码的真实行段。源码改了，那一章的状态点变色，`pnpm docfirst check` 报出来，
站测试那条「全是绿的」直接失败——**文档跟不上代码就过不了门禁**。本仓未提交的改动引起的黄灯，check 直接算红，
要在改代码的同一个提交里复核。

哪些文章允许没有引用，由 frontmatter 明说，测试按这个标记放行：

{/* ref file="tests/page.test.mjs" lines="50-51" hash="cfcbeab7ba70" blob="6563bf8b4551" */}

`docfirst: none` 是导读页（明说不钉），`docfirst: draft` 是还没写的章。两样都没写的，就必须至少钉一处。

门禁怎么跑、提交怎么拆，见 [维护者手册](/docs/maintain/maintainers)。
