轨迹卡是 `content/trajectory/` 下一卡一文件的 mdx，一张卡记一次取舍的结论，只增不改。星轨盘是这些卡的图：
一个项目一张盘，项目的根卡画在盘心，其余的卡按日期排在同心环上，半径表示时间、内旧外新。
从卡文件到站上的盘分六段，读盘在 `docfirst-workflow`，解析、建模、布局在 `docfirst-trajectory`，最后由站渲染：

## 分盘、建树、挑主干

`type: root` 的卡是根卡，每张根卡一张盘。**`parent` 里含哪张盘的身份，卡就在哪张盘上**，写几个就上几张盘；
`domain` 只用来分组配色，不决定卡在哪张盘。有 `parent` 的根卡是子项目：父盘列在它的 `merged-in` 里，它和它盘上的卡
整个并进父盘（逐层递归，遇到环跳过）；没列，它在父盘上画成**虫洞**，点进去换到子项目的盘：

{/* ref file="../packages/docfirst-trajectory/src/model.ts" lines="187-219" hash="125bf7072e32" blob="1ee72d0830da" */}

关系按盘求解，目标不在这张盘上的记进这张盘的 `broken`。用取代与转向连在一起的卡组成一棵树。树的**主干**在取代关系上挑：
几条取代链先比终点的 `born-at` 谁更晚，再比长短，最后按身份排；整棵树一条取代都没有，才在转向链上用同一个比法挑。
不在主干上的卡按连通分成**支线**；两种关系都没有的卡是**孤星**：

{/* ref file="../packages/docfirst-trajectory/src/model.ts" lines="326-353" hash="3efa5ab62617" blob="1ee72d0830da" */}

`buildTrajectory` 给每张盘建好模型就交出去，不算布局。盘的布局（`RingsLayout`）由浏览器里的画布按当前设置算，调设置不用再请求服务端：

## 卡里为什么不许钉码

钉一处码是在说「这句话跟着这段代码走，代码变了要回来复核」。卡记的是当时的结论，代码后来怎么变都不该改它；
卡里钉了码，代码一改卡就变黄，它就成了一份要维护的现状文档。所以两处把卡挡在钉码之外。

一是 `check`、`confirm`、`render` 遍历的文档不含 `trajectory/` 与 `future/`，卡上的记号不会被核对，也不会被确认：

{/* ref file="../packages/docfirst-workflow/src/project/load.ts" lines="86-87" hash="e60f111d117a" blob="485972d4fa88" */}

二是读卡目录时逐行查每张卡的正文，草稿记号、md 正式记号、mdx 正式记号三种写法出现任何一种，都记成一条问题：

{/* ref file="../packages/docfirst-workflow/src/project/card-refs.ts" lines="16-23" hash="6946a48e2d58" blob="23e24d936909" */}

这一条要认识钉码的记号，所以查在 `docfirst-workflow` 读卡目录的 `scanCardDir` 里，查出的问题并进轨迹包校验出的同一份清单；
`docfirst-trajectory` 不认识记号：
