**本页回答**：`god-live-doc` 是什么、这一区只写什么、从哪一页开始读。

这套机制把文档里对代码说的话钉在真实源码上：文档只写「我引的是哪个文件哪几行」「这个目录下有哪些
东西」「这个名字还在」，内容在构建那一刻从源码取。代码变了，页面上那处的状态点变色，作者复核过才回绿。
**文档里不存代码的副本**，确认时的记录就写在记号自己身上：一段指纹，加上确认时那份文件的 blob 名。

这一区只写**现状**：设计、原理、边界、接口。为什么变成这样去 [轨迹](/trajectory)，还没发生的事
（路线图、在途方案、别的仓投来的反馈）去 [未来](/future/overview)。判据一句话：一句话如果能被代码推翻，
它就该带引用；一句话如果只是在复述代码，它就不该存在。

## 从哪读

按这个顺序读：

1. [系统地图](/docs/system-map)：这套东西分成哪几块、各在哪、谁依赖谁、经哪几条接缝相连、先读哪块。
2. [入门](/docs/start)：它解决什么问题、一分钟接起来、五类引用怎么挑、一条引用的一生、
   怎么接进自己的 fumadocs 站。
3. [模块](/docs/modules/pin)：按包组织，一个模块一页，四段——功能 / 接口 / 依赖 / 不做的事。
   接口与边界逐条钉住。
4. [术语表](/docs/glossary)：这个仓里的词各指什么。

轨迹按需查。这几页上的钉码都在、`docfirst check` 是绿的，站上写的就没有和代码对不上的。

## 这个站自己就是使用者

站装的是工作区里的这几个包，钉的是工作区里的真源码——「装了这几个包的项目长什么样」在这儿就能直接看到，
所以仓里不另留示例。文档怎么写（读者是谁、分区怎么分、每页写到哪为止）由随工作台插件
`@godcreator/gwb-docfirst-workflow` 发布的说明书「docfirst-docs」规定，它的正本在
[生成正本](/docs/outputs/skills/docfirst-docs) 下；人写的那份总规范是
[文档规范](/docs/human-write-spec-dont-change)，agent 不改它，只在别处提建议。
