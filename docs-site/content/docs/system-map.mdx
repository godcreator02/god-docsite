**本页回答**：这套东西拆成哪几个模块、各在哪、谁依赖谁、经哪几条接缝连起来、新来的人先读哪个模块。

## 四个包，一个插件

布局照 devkit 的 workspace 仓：插件在 `plugins/`，不是插件的包在 `packages/`。`plugins/docfirst/` 是工作台插件
`@godcreator/gwb-docfirst-workflow`——它不发到 npm、四个包也不依赖它，只在桌面工作台里给 agent 提供两条建站命令和几份说明书。
`packages/` 下是四个 docfirst 的 npm 包，外加讲解组件的模板包 `docs-explain`：

{/* tree dir="../packages" depth="1" hash="06330e2d87df" */}

`docs-explain` 给文档站画分步、动画、选情况这几种讲解组件，不接 docfirst 的普通 fumadocs 站也能装；它不认识四个包，
四个包也不认识它，所以不在下面的接缝图里。四个包是两个核心、两个适配。两个核心不读盘、不认文件格式、不认站点框架，
要的东西全部作为参数传进来：

| 包 | 管什么 | 先读 |
| --- | --- | --- |
| `@godcreator/docfirst-pin` 钉码核心 | 引用模型、记号语法、比较器、编排服务；只用 `node:crypto` | [钉码核心](/docs/modules/pin) |
| `@godcreator/docfirst-trajectory` 轨迹核心 | 卡片格式与校验、建模、布局、缩略图；`./disk` 是星轨盘画布 `StarDisk` | [轨迹核心](/docs/modules/trajectory) |
| `@godcreator/docfirst-workflow` 命令行与项目 | 命令行 `docfirst`、项目装配（读盘、git、生成物、磁盘读卡）、mdx 格式 | [workflow](/docs/modules/workflow) |
| `@godcreator/docfirst-fumadocs` fumadocs 适配 | remark 插件、机读版、状态点与术语组件、fumadocs 组件的名册规则、卡集合、星轨盘服务端组件 | [fumadocs 适配](/docs/modules/fumadocs) |

**两个适配包的分界看调用链从哪里开始**：从 `docfirst` 命令开始的归 workflow，由 fumadocs 或 Next 调用的归 fumadocs 适配
（mdx 加载器编译页面时调的插件、集合的 schema 与回调、页面渲染时的组件）。两边都要的（`loadProject`、mdx 语法树上认记号）
按依赖方向归 workflow。来由见轨迹卡[按接缝拆四包](/trajectory/2026-09-26-split-by-seams-into-four-packages)。

workflow 包里再分四个目录，各一件事：

{/* tree dir="../packages/docfirst-workflow/src" depth="1" hash="fdc52981e029" */}

`cli/` 是命令行，`project/` 是项目装配，`mdx/` 是 mdx 格式，`format/` 是命令行要的格式接口 `DocFormat`。

包里没有建站：**建一个接好三个区的站**那部分在工作台插件里（[建站](/docs/modules/site)）。
包的使用者是仓，插件的使用者是 agent，判据见轨迹卡
[包给仓、插件给人](/trajectory/2026-09-10-package-serves-repo-plugin-serves-agent)。

## 依赖方向

包与包之间的依赖是**单向**的：钉码核心谁都不认识，轨迹核心也谁都不认识，workflow 认识两个核心，fumadocs 适配认识全部三个，
谁都不认识它。表里**列的是禁止的包，不是允许的包**——写成允许的话，新加一个包时它默认什么都不能依赖，放错位置反而更难发现：

{/* ref file="../tests/boundary.test.ts" lines="121-135" hash="6240de2040d1" blob="e450056cc091" */}

钉码核心自己不依赖任何包，只用 `node:crypto`。它不读文件、不启动子进程、不认识任何文档格式，运行要的三样全部由构造参数传进来：

{/* ref file="../packages/docfirst-pin/src/service.ts" lines="57-61" hash="e6d5208e0ea0" blob="33d8acf46386" */}

格式、读取器、旧内容来源（按 blob 取确认时的内容、算 hunk 表）都是构造参数，所以它不需要任何依赖。
轨迹核心的主入口产物里一条 import 都没有，卡片文件由调用方读好传进来。

**包与插件互不认识**：四个 npm 包的三类依赖字段里不许出现工作台插件，也不许出现任何
`@godcreator/gwb-*`——装这些包的人不该因此装上桌面工作台的插件；反方向，插件对四个 `@godcreator/docfirst-*`
包零依赖，由插件自己的 `tests/artifact.test.ts` 检查。

## 三条入口

三种使用者从三个方向进来，前两条走的是同一套判定：

<Tabs>
  <Tab title="命令行">
    `docfirst check / confirm / render / trajectory`，外加一次性的迁移命令 `migrate-ledger`，在 workflow 包里。命令行逐篇把文本交给编排服务，
    把回来的清单译成一行行人读的文字和一个退出码。git hook 与 CI 运行的就是它——**提交那一刻工作台
    不一定在运行**，所以判定与核对必须是 npm 包，不能要求任何桌面应用开着；那些仓也不一定装了 fumadocs，所以命令行不依赖 fumadocs 适配。
  </Tab>
  <Tab title="站构建">
    站的 `src/lib/source.ts` import `@godcreator/docfirst-fumadocs`，把它的选项传给现状集合，remark 插件在构建期
    装配一次项目、认引用、算清单、把状态点加到语法树上。人看的那份文档就是站本身。
  </Tab>
  <Tab title="工作台插件">
    `@godcreator/gwb-docfirst-workflow` 经命令总线提供 `docfirst.create` 与 `docfirst.create-plain`（运行官方脚手架、应用本机约定并写盘，
    `docfirst.create` 再在官方输出上增、换、删几份文件），另把说明书注册给 agent 读。**它对四个包零依赖**：不 import、不运行它们的命令行——要核对
    就 `cd` 到那个仓里运行包的命令行。
  </Tab>
</Tabs>

前两条入口共用同一份编排服务，这就是「判定只有一处」：站上看到的绿，跟命令行
`check` 退出码 0 说的是同一件事；第三条根本不做判定，它只建站。

## 边界靠什么检查

pnpm 严格的 `node_modules` 能拦住一部分——没写进依赖的包 import 不到——但「该不该写进依赖」没有人检查；
workflow 包里四个目录之间更是谁都能 import 谁。检查这些的是一个测试文件：

{/* ref file="../tests/boundary.test.ts" lines="1-32" hash="49411c4d80c6" blob="e450056cc091" */}

**它失败的时候，出错的是设计，不是测试。**各类检查分别在哪一页讲，见各模块页的「不做的事」；测试怎么分组见
[测试与边界](/docs/cli/testing)。

依赖单向的好处是替换一个模块只改一处：换一种文档格式，新写一份 `Format` 实现，钉码核心一行不动；
旧内容不从 git 取，实现 `History` 的两个方法；换站的宿主，只换 fumadocs 适配这一个包。

## 站也是使用者

`docs-site/` 就是「装了这几个包的项目」：项目根是站目录，被钉的代码在工作区的 `packages/` 与 `plugins/` 下，
记号写 `../packages/…` 或 `../plugins/…`。

{/* ref file="docfirst.config.mjs" lines="4-6" hash="ec944a1565bb" blob="3271a37f8bd2" */}

所以仓里不另留示例项目——这几个包对外的样子由站自己展示，站上的状态点绿着，就是它们在真源码上
核对通过了。

## 每个模块一页

上面每个模块在这一区有自己的一页，四段顺序固定：功能 / 接口 / 依赖 / 不做的事。开头一句写包名、
源码目录与入口文件。写到「错了难改」为止——边界、依赖方向、接口契约、状态机、取舍讲透；
字段清单、内部算法、内部命名是实现者的自由，不写。测试集中在 [测试与边界](/docs/cli/testing)。

## 读序

按依赖方向倒过来读：**先 [钉码核心](/docs/modules/pin)**——接口正本、记号语法、比较器、编排服务、四种
状态都在那儿，别的包只认这一份；**再 [workflow](/docs/modules/workflow)**——[项目装配](/docs/modules/workflow/project)
讲装配的全貌、旧内容怎么按 blob 取回、一篇正本怎么渲染到落点，然后是[命令行](/docs/modules/workflow/cli)与
[mdx 格式](/docs/modules/workflow/mdx)。[轨迹核心](/docs/modules/trajectory) 自成一个模块，[fumadocs 适配](/docs/modules/fumadocs)
是站构建那条入口，[工作台插件](/docs/modules/plugin) 与它的 [建站](/docs/modules/site) 在包外面，各从自己那一页进，
只关心命令行的人整个跳过。

两处边界值得在读代码之前先知道，免得照目录名猜错：

**摆放在 `project/`**，全部在 `placement.ts` 里——一篇 mdx 正本渲染成生成物、加回指定的
frontmatter 字段、写到每个落点、核对盘上那份是不是最新，都在那一份。它在项目装配而不是
钉码核心，是因为要写盘、要调用格式的渲染，钉码核心两样都不做；也不在命令行，是因为放进命令行
别的调用方就只能启动子进程从 stdout 取结果。

**命令行只负责打印**：它拿到摆放的两个方法与编排服务，把回来的清单译成一行行人读的文字和一个退出码，
引用的状态一件都不在那儿算。它另外只问项目装配一件事：被钉的文件在本仓有没有未提交的改动，
有的话那处黄灯算红。
