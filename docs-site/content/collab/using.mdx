协作站是一个项目的网站。课题组每个人在自己电脑上打开同一个网站，看项目的设计页面，在页面上评论、讨论，排模块和任务；
写下的东西经 Gitea 同步给所有人，别人一合并，十秒左右就出现在自己的网站上。

网站由 gwb 工作台托管（基础插件 gwb-docsite 在后台运行它的开发服务），不用自己开。日常的提交审核、照评论改页面，都是对 AI 说一句话，由 AI 调插件去做；别人的改动由插件自动同步过来。

## 看项目页面

- 打开网站先到任务页。左边是侧栏：最上面是站名，接着是切换页面分组的下拉框（一组是 `site/content/` 里一个顶层文件夹），下面一横排是搜索和「任务」「日历」「评论」，再下面是当前这一组的页面；侧栏底部写着本机是谁（认不出时写「只读」）和浅色深色切换
- 在任务、日历、评论这几页上，下拉框和页面列表停在最近看过的那一组，点一下就能回到刚才那组的哪一页；换组只用下拉框
- 搜索能搜到全部页面的标题与正文
- 网站上不列项目里有哪些仓。要在 VS Code 里打开整个项目文件夹，在 gwb 工作台的协作窗格里点这个项目那一行的 VS Code 按钮（命令 `collab.project.open`）

## 评论

- 右下角「批注」打开批注模式：鼠标下的元素画虚线框，点一下就评论这个元素（一段、表格、一张图、一个公式）；拖选几个字，浮出「评论」按钮，评论这几个字；Esc 退出
- 右下角「评论」打开右侧栏，列出这一页的全部评论，分未解决、已解决；也能写一条评论整页的
- 一串评论下可以回复，讨论完点「解决」；已解决的还能重新打开
- 评论和回复的正文里写 `@<id>`（id 就是这个人的 Gitea 用户名）就 @ 了他，被 @ 的人在自己网站顶部的提示栏「找我的」一组里看到这一条
- 侧栏横排里的「评论」进全部评论页，列出整个项目的评论串，按最近活动排，可以按状态、页面、和我有关的筛；不属于任何页面的评论也在这里写

一串评论一个文件夹，放在协作仓的 `site/comments/` 里，和页面一样提交审核。评论的格式、页面改了以后怎么找回原来批的位置，归文档站基础包管。

## 模块与任务

- **模块**是一块有截止日的大工作，不写开始日，先后由负责人自己安排；**任务**是具体的一件事，可以归进某个模块
- 任务页从上到下是人员、模块甘特图、任务看板：人员卡片上写着每人还有几个任务没做完、几个过了截止日；甘特图每个模块一行，在截止日画一个菱形，全部做完换成勾，过期加红框，左边写着做完几个、共几个；
  看板按未开始、进行中、已完成分三列，点一个人或一个模块就只看他的任务
- 每条任务、每个模块有自己的一页：状态、负责人、截止日、所属模块、链接的页面在这一页上就能改；任务内容按 Markdown 排版，写清楚要做什么、做到什么程度算完成
- 别人的任务也能改状态、负责人、截止日、标题和所属模块，内容只有作者能改；只有作者和项目负责人能删

## 日历与日志

- 侧栏横排里的「日历」是月历：写了日志的日子有一个点，模块截止的那天画着同色的菱形，点任何一天进那一天的日志
- 日志全项目一天一篇，是一段段自由的文字：做了什么、结果、卡在哪、下一步，写到任务、模块、评论或某一页就插一个能点的小标签，标签上是它现在的标题和状态
- 日志由 AI 写：对 AI 说「把今天的工作记进日志」，它写好给你看，你同意了再提交审核。网页上不能写，也不记是谁写的
- 每条任务、每个模块那一页的最下面是「日志里的进展」：哪几天的日志提到了它，每天那一段写了什么

任务页、日历的布局见 [网站内部](/collab/collab/collab-site) 的「任务页与任务那一页」与「日历与日志」，能改哪些字段见 [数据模型包](/collab/collab-model) 的「任务模型」。

## 顶部提示栏：要处理的事都是通知

要人处理的事都是一条条通知，列在网页顶部正中的提示栏里：有就一直显示，处理好了自己消失，不用点「已读」。通知分三组，各一种颜色：

| 组 | 有哪些事 |
| --- | --- |
| 协作仓 | 还没提交审核的文件、合 main 的冲突、上次提交审核没成功、没能自动同步、gwb 检查项目出错、协作仓不在 main、记录读不对、组织 webhook 没配好 |
| 别的仓 | 没推送、没拉取、和服务器分叉，等你审阅的合并请求、等负责人回的 issue，你开的合并请求被要求修改或有了新评论、你提的 issue 负责人回了，仓没按规矩配好 |
| 找我的 | 指派给我的任务、@我的、回复我的 |

收起时只写各组几条，比如「协作仓 2 件事 · 别的仓 1 件事 · 3 条找我的」，点开是每一条的短句，有原文的（文件清单、报错原话、评论正文）写在短句下面；「别的仓」组一个仓一行。
点短句去它该去的地方：任务去那条任务的一页，@我、回复我的去评论所在的那一页并打开那串评论，合并请求与 issue 打开 Gitea，还没提交审核的那一条不能点、只显示，是哪些记录、哪些站点文件就列在短句下面。

有通知时这一行有「交给 AI 处理」，点了把这个项目的全部通知写成一份提示词交出去（每条写明照说明书 collab 哪一节处理），交给哪个 AI 由工作台设置 `ai-handling` 定；提示栏列表顶上也写着这一句。

## 提交与合并

网页上写的评论、建的任务，AI 照评论改的页面，都只在自己电脑上，要让 AI 提交审核才会交给大家：

- 有还没提交的文件时，提示栏「协作仓」组里一直有一条「本机有 N 个文件还没提交审核（记录 x 个，站点文件 y 个）」；一条新评论是两个站点文件（评论本身和发起时那一页的文字快照）
- 提交审核以后，NAS 上的执行器通常十几秒就给出结论：没有冲突、没改到只有项目负责人能改的内容，就自动合并；否则打回，并留言写明原因，改动退回自己电脑上，提示栏里出现「上次提交审核没成功」，下面是原话，改好再提
- 和别人改了同一处时，提示栏里是「提交审核合 main 出了冲突，N 个文件还没改好」，下面列着文件；AI 按两边的意思改好，拿不准的由人决定留哪个
- 谁都能改：评论、任务、模块、日志，页面与页面里的组件、图片，给站点加库，给人员列表里自己那一项加减身份码。只有项目负责人能改：人员列表的其余部分、站点的配置文件与脚本、功能包的版本、自动合并的规则；负责人改这些也一样提交审核，执行器查到是负责人提交的就合并。协作仓的 main 谁都不能直接推，负责人也一样

## 看到别人的改动

- 别人的改动合进服务器以后，十秒左右就出现在自己的网站上，不用手动拉取：任务与模块不用刷新就更新；页面与评论是站点里的文件，文件一变网站自己整页刷新一次
- 自己电脑上有还没提交的改动、又碰到同一个文件时不会自动合进来，提示栏里出现「没能自动同步 main 上的新改动」，下一次提交审核时一起处理

这只管协作仓。项目里别的仓插件只取回、不替你更新，见下一节。怎么做到的，见 [组织事件与实时推送](/collab/collab-repo)。

## 项目里别的仓

资料库、代码仓是**别的仓**，按普通的 git 仓管理：开不开分支、什么时候拉取由各人自己定，插件只取回、只出通知，不改它们的分支与工作区。

- 有人往哪个仓推了提交，插件就取回那个仓。它拿当前分支（HEAD）和服务器上的同名分支比：本地多出提交是「X 有 N 个提交还没推送」，服务器上多出提交是「X 服务器上有 N 个新提交还没拉下来」，两边都有是「X 和服务器分叉了：……」，都在提示栏「别的仓」组这个仓那一行。工作区里没提交的文件不算，那是正常干活的状态。分支推上去以后就算一样，等审阅时 main 往前走不提醒。要处理就在协作窗格里点「交给 AI 处理」，或者自己 `git pull`
- 每个仓都有负责人，就是 Gitea 上这个仓的协作者
- 谁都能在项目里建仓（对 AI 说「建一个仓」），建仓的人是那个仓的负责人；换负责人、加共同负责人也对 AI 说，不在 Gitea 网页上改，别人的插件才能马上知道
- 负责人直接改自己的仓；别人推自己的分支、开合并请求，等那个仓的负责人审阅。负责人的提示栏里出现「X #N「标题」等你审阅（谁开的）」，交给 AI 时 AI 先整理改动问他，他同意后由 AI 合并
- 自己开的合并请求被审阅人要求修改、或别人在上面发了新评论，自己的提示栏里出现「谁 要你改 / 评论了 X #N「标题」（你开的合并请求）」；新评论那一条在自己回复以后消失，要求修改那一条在审阅人改成批准以后消失。审阅与评论一发生 Gitea 就推送消息，几秒内出现、消失；审阅人撤销要求修改的审阅 Gitea 不推送消息，那一条要等这个仓下一次有消息、或下一次完整刷新才消失
- 在 Gitea 上给哪个仓提的 issue，最后发言的不是那个仓的负责人时，出现在负责人的提示栏里；交给 AI 时 AI 整理在问什么、按负责人的意思起草回复，负责人确认原文后才发出；负责人回了这一条就消失，提 issue 的人那边出现「谁 回了 X 的 issue #N「标题」（你提的）」，自己再回复以后消失
- 别的仓的 main 只有负责人能推、能合并，靠 Gitea 上的分支保护（协作仓的 main 谁都不能直接推，只由执行器合并）；没按规矩配好的仓，仓管理员的提示栏里出现「X 没按规矩配好」；组织的 webhook 没配对，组织管理员的提示栏里也会提醒

## 和 AI 配合

网页负责看和写评论、任务，其余的事对 AI 说。提示栏里的事在 gwb 的协作窗格里点那个项目的「交给 AI 处理」就行，别的直接说：

- 「照这条评论改一下页面」「回答一下这条评论里的问题」：AI 找到那串评论和页面上的位置，改页面，或者在那串评论下回复；改完由人在网页上点「解决」
- 「给 carol 建个任务，周五前做完」「把这个模块延后一周」「把今天的工作记进日志」
- 「提交审核」「看看我有什么待办」「站点打不开了」
- 「建一个仓放 xxx」「把 carol 加成这个仓的负责人」；给别人的资料库、代码仓提改动，也是让 AI 推成合并请求，等那个仓的负责人审阅

AI 能做哪些事、怎么做，写在随插件发布的说明书 [collab](/docs/outputs/skills/collab) 里：主文件是通用规矩，附件分三个，协作仓里写页面、任务与提交审核看 [collab-repo](/docs/outputs/skills/collab/collab-repo)，项目里别的仓看 [other-repos](/docs/outputs/skills/collab/other-repos)，加入项目、设置与组织 webhook 看 [organization](/docs/outputs/skills/collab/organization)。提示栏里每种通知怎么处理，也写在这三个附件里。

## 项目负责人多做的事

项目负责人就是协作仓的负责人（协作仓在 Gitea 上的协作者），头像上带星标：

- 往人员列表 `site/people.json` 里加人，在 Gitea 上把他加进成员团队；加进去就能建仓、给每个仓提改动。新成员在自己电脑上运行 `collab.project.join`，插件把他这台电脑的身份码写进他那一项，他再提交审核
- 只有项目负责人能改的那几处（人员列表、站点配置、功能包版本、自动合并规则），项目负责人自己提交审核就放行
- 能删别人的任务与模块

协作仓上的合并请求由执行器决定合不合并，它在 Gitea 上的 issue 与评论插件不读、不出通知：协作仓里要讨论的事写成网站上的评论与任务。

系统由哪几块组成、刻意不做什么，见 [系统组成](/collab)；下面几页是具体的使用案例。

## 场景速查（原「场景速查」页）

一处改动从写下到出现在别人的网页上，要经过四方：成员在自己的电脑上让 AI **提交审核**，插件先把 main 合进来再推送，Gitea 建出合并请求；NAS 上的**执行器**立刻给出结论：能合就合进 main，不能合就留言写明原因、关掉合并请求；提交审核一直等到这个结论，被打回就把改动退回成员的工作区。会在每个人电脑上执行代码的、会改变合并规则的那几处（站点的 `scripts`、配置文件、功能包版本、执行器工作流、人员列表 `site/people.json` 等，每个人给自己那一项加减身份码除外）只有**项目负责人**（Gitea 上协作仓的协作者）能改；项目里别的仓（资料库、代码仓）各有负责人（那个仓的协作者），合并请求由负责人审阅，同意后由 AI 合并。Gitea 上一有事件，每个人的工作台经实时推送收到一条只说位置的消息，插件按它去取那一处：协作仓有新提交就取回，能快进就把自己的本地 main **自动同步**到 main。
这一页用同一个项目里的四方讲各种情况：bob、carol 是成员，admin 是项目负责人，执行器在 NAS 上。每个命令各做什么见 [提交审核与自动同步](/collab/collab-repo)，执行器的规则见 [合并检查包](/collab/collab-merge-check)。

| 谁 | 在哪 | 做什么 | 从哪知道出了事 |
| --- | --- | --- | --- |
| 成员 | 自己电脑上的工作台与网站 | 写记录、让 AI 改页面、提交审核 | 自己网站顶部的提示栏：「协作仓」组里是还没提交审核的文件、合 main 的冲突、提交审核失败的原话、没能自动同步的原因，「找我的」组里是任务、@我、回复我的；提交审核的回执；协作窗格里自己项目那一行写着各组几条通知 |
| 项目负责人 | 同上，Gitea 上协作仓的协作者 | 和成员一样；另外改只有负责人能改的那几处，审阅他负责的别的仓的合并请求 | 同上，另外提示栏「别的仓」组里列着别人在他负责的仓开的、等他审阅的合并请求，和那些仓里等负责人回的 issue |
| 执行器 | NAS 上的 Gitea Actions，以 `collab-bot` 合并 | 每个合并请求推上来就检查，能合就合，不能合就留言写明原因、关掉 | 不通知人：结论写在合并请求上，提交人的 collab.submit 读出来 |
| Gitea | 课题组的服务器 | 存 main 与合并请求；每个仓只有它的负责人能合进 main，协作仓另有执行器 | — |

## 按情况看

选一种情况，再一步一步往下看（上一步、下一步，或者播放）：每一步写着谁做了什么、运行了哪条命令、合并请求变成什么状态，下面是这一刻每台机器上的提交图。Gitea 上画 `main` 和开着的合并请求；每个人的电脑上画本地 main（`bob/main`）、上次取回的 `origin/main`、领先落后几个提交，以及工作区里有没有没提交的改动。圆点按谁做的这个提交上色，这一步在哪台机器上做的，那张卡片描边加深。

一条记录一个文件，所以只要两人改的不是同一条记录，git 合并时就互不相干；会冲突的只有两人改了同一条记录（或同一个页面文件）的同一处或相邻处。冲突出在后提交的人提交审核、把 main 合进来的那一步，插件不推送、不替人选，冲突交给人配合 AI 改。
页面改动、评论和记录经过同一套提交审核与合并检查：页面、组件、评论、加库检查通过就合并；站点检查或类型检查不过的，谁提交都在本机就拦下；改了只有负责人能改的，不是项目负责人提交时在本机就拦下。两人同时加库时锁文件 `site/pnpm-lock.yaml` 会冲突，同样出在把 main 合进来那一步：用 main 那份锁文件、在 `site/` 里重新运行一次 `pnpm install`，再提交审核。

提交审核时本地 main 落后 main，推上去的就是一个把 main 合进来的合并提交，执行器合并后它留在 main 的历史里。自动同步只快进，本地 main 上不会生成只在本地的合并提交；本地 main 上有还没进 main 的提交，只出现在提交审核等执行器的那一会儿、或者合 main 的冲突还没改好时，这两种时候不自动同步。

## 提示栏里出现什么

上面各种情况里提示栏出现的都是通知：插件按此刻的状态算，解决了就不再出现。同一件事有好几条原因时只列最根本的那条：合 main 的冲突没改好时，不另列提交审核失败与没能自动同步；协作仓不在 main 上时，不另列没能自动同步。
