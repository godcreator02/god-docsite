包 `@godcreator/gwb-collab`，源码在 `plugins/collab/src/`。目录按它管哪种仓分：协作仓那一套在 `collab-repo/`，别的仓那一套在 `other-repos/`，组织级的在 `organization/`；共用的是通知、站点、协作窗格、交给 AI，两个可替换接口的实现放在定义接口的那个目录里，最底下是只封装外部系统的 `git/`、`gitea-api/`。

{/* tree dir="../plugins/collab/src" depth="2" hash="9f1442332d0e" */}

入口 `index.ts` 只做装配：定义设置，从工作台拿到命令总线、设置、数据文档、gwb-docsite 的服务与计时器，局部注入 gwb-gitea、gwb-zcode、gwb-qq-bot，按依赖顺序建好各目录，把每个目录「状态变了」的回调都接到通知的 `changed(repo)` 与 QQ 任务组的重新注册上，再交给各目录自己的 `commands.ts` 登记命令（登记函数、按本 home 的身份码打开项目、几段共用的参数说明在 `src/commands.ts`），最后登记窗格与说明书。别的文件只收入口交给它们的参数，不自己取工作台服务。

## 接缝图

左边浅底是协作仓那一套，右边浅底是别的仓那一套，每个目录只管一种仓：它在 Gitea 上那一头在正上方，本机那一头在正下方。中间是组织级的与共用的。两边各自把此刻的状态交给通知（17、18），通知再交给站点、窗格与 AI。下边沿的半圆缺口是可替换的接口。最下一排左边是 gwb-docsite：站点交给它初始化与托管、推给网站的数据经它推（27），身份码也由它保管（28）；项目登记 `project/` 在它右边，把起了 QQ 命令的项目注册成 QQ 机器人的任务组（26）。项目登记打开项目、核对令牌这些别的用处和底层目录一样，几乎每个目录都用、不传数据，图里不画。鼠标停在编号或方块上看说明，点击固定高亮它连着谁：

**两边不互相引用**：`collab-repo/` 不引用 `other-repos/`，`other-repos/` 也不引用 `collab-repo/`，都要用的只放 `project/` 与底层目录；两边的 `events.ts` 也不引用 `organization/`，由组织这一层引用它们；各目录不认识通知，通知读它们。这一条靠约定，插件里没有边界测试守着（数据模型包有）。

## 功能

成员（或成员的 AI）经 gwb 调命令，不自己写 git 命令、不自己写记录文件。网站上没有提交、同步、更新的按钮，也不向插件发请求：要处理的事都成为通知，列在网站顶部的提示栏里；交给 AI 在协作窗格那个项目的一行上点，一次交出这个项目的全部通知；提交由人让 AI 调 `collab.submit`；协作仓跟上 main 靠插件取回后的自动同步。命令做完，插件监视着的状态变了就重算通知推给站点，网站不用刷新就显示新的状态。评论由网站与 gwb-docsite 的 `docsite.comment.*` 写，本插件只读评论串算找我的。

## 接口

### 命令

## 不做的事

- 不写站点骨架、不运行站点的开发服务、不管打开站点的窗口：都交给 gwb-docsite，本插件只给初始化写明功能包的范围、在托管前查站点、往它的推送通道推数据
- 不写评论：评论由网站和 gwb-docsite 的 `docsite.comment.*` 写，本插件只读评论串算找我的
- 不改仓库配置：身份是本 home 的身份码在 `site/people.json` 里认出的人，不读写 git 配置；克隆出来的仓只在自己的配置里开 `core.longpaths`，不设凭据配置，终端里的 git 照常用凭据管理器
- 不另存令牌，不读写 Windows 凭据管理器：令牌由当前 home 的设置插件保管
- 不另记谁是负责人：以 Gitea 上各仓的协作者为准，`site/people.json` 里不记
- 不自动处理冲突：冲突如实报出来，由人配合 AI 改；自动同步只做快进，不在本地合并
- 不合并合并请求：协作仓的合并与打回只由 NAS 上的执行器做，插件只在执行器到时限还没给结论时关掉自己那个；别的仓的由它的负责人同意后，AI 经 `gitea.http` 以合并提交合并
- 只提交 `collab/` 与 `site/`；哪些改动只有负责人能改由合并检查定，插件推送前调它的 `leadOnlyProblems`，不另写一份规则
- 任务与模块命令不提交：只改工作区，提交只用 `collab.submit`；不自己生成记录文件、不另写一份写入规则或待办筛选
- 不建分支、不切分支：协作仓只用 main，提交审核、自动同步都在本地 main 上做
- 不替人管理别的仓：只取回，不切分支、不快进、不改工作区；人同意后 AI 调 `collab.repos.update` 才快进那一个仓
- 不按固定间隔刷新：别人的改动靠实时推送让插件去取；不把实时推送收到的消息当数据，事实都由插件自己去 Gitea 取
- 不替负责人回 issue：交给 AI 时 AI 起草回复给人看，人确认原文后才发
- 待办与通知没有「已读」：按此刻的状态算，处理好了就不再出现
- 不弹 Windows 通知、不自动交给 AI：要人处理的事都在网站顶部的提示栏里；新出现的通知另可经 QQ 私聊主人，默认关闭；只在人点了「交给 AI 处理」时交，交出去就回执，不要回报、不记下交出去的事。理由见轨迹卡 [提示栏取代通知](/trajectory/2026-10-03-notice-bar-replaces-notifications)
- 不把 QQ 命令写进协作仓、不从项目名自动截短：QQ 命令按 home 存，没起的项目不注册任务组；任务组的要求只指向说明书 collab，不另写提交规矩。理由见轨迹卡 [按项目注册 QQ 任务组](/trajectory/2026-10-08-qq-task-groups-per-home)
- 不自己在项目目录里找项目：列表里只有人加进去或克隆的；协作仓不在以组织命名的项目文件夹里就拒绝
- 调 Gitea 接口的只有这几处：查令牌对应的账号；加项目时查 `origin` 的主人是不是组织；克隆与刷新时列组织里的仓；读协作仓的协作者（刷新、`leads changed`、提交审核推送前、删任务与模块时）；管理员身份时读各仓的 `main` 保护与组织的 webhook 核对；读别的仓的协作者、有没有 `main`、开着的合并请求与审阅、开着的 issue 与评论；`collab.repo.create` 建仓；`collab.repo.setup` 限定合并方式、加减协作者、建或改 `main` 的保护；`collab.org.setup` 读、建、改组织的 webhook；提交审核查自己那个合并请求的状态、读最后一条留言、到时限还没结论时关掉它。不读执行器的运行记录
