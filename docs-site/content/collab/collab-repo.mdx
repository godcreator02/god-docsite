网站只改工作区里的文件，不改 git 历史：网页上建的任务写进 `collab/`，写的评论写进 `site/comments/`；AI 照评论改的页面也是工作区里的文件。一条记录、一条评论或一处页面改动要进 main、再到别人的网页上，要经过三步：成员用插件**提交审核**（`collab-repo/submit/`），NAS 上的**执行器**立刻合并或打回（见 [执行器与自动合并](/gitea/push)），每个人的插件把本地 main **自动同步**到 `origin/main`（`collab-repo/sync/`）。自动同步在插件取回协作仓之后做：实时推送说协作仓有新提交时，以及完整刷新时；没有单独的同步命令，要立即同步就让 AI 调 `collab.check`。
这一页用两个成员 bob 和 carol 讲这几个动作怎么配合，它们在插件里的位置见 [gwb-collab 的接缝图](/collab/plugin) 左边那一列。

## 本地 main 与主题

协作仓只用 `main` 一条分支，插件不建任何分支。网站写的、显示的都在本地 main 的工作区里：已合并的、还没提交的记录都在同一个工作区，网站不用去 git 里找别的东西。
提交审核只在 main 上做，当前在别的分支上（或者是分离的 HEAD）就直接拒绝，写明当前在哪；自动同步不在 main 上就不动，提示栏里有「协作仓不在 main」那条通知。

{/* ref file="../plugins/collab/src/collab-repo/submit/submit.ts" lines="13-17" hash="0029e25a2550" blob="92a88843de16" */}

提交审核推送 `HEAD:refs/for/main`，主题固定是自己的身份（接缝 5）。推到这里的提交不进任何分支，Gitea 用它建合并请求（AGit）。执行器对每个合并请求立刻给出结论：合并，或者留言写明原因再关掉（打回）。协作仓没有开着等人的合并请求，所以每次提交审核都新建一个，里面只有 main 里还没有的改动。

{/* ref file="../plugins/collab/src/collab-repo/submit/submit.ts" lines="153-153" hash="770f3420697e" blob="d6f41b5784e7" */}

执行器按「合并提交」方式合并，成员的提交原样进 main。提交审核的结果只有两种：合进 main，或者改动退回工作区。所以本地 main 平时没有 main 里没有的提交，自动同步只要把本地 main 快进到 `origin/main`，不会在本地生成合并提交。
只有两种时候本地 main 上有 main 里没有的提交：提交审核正在等执行器的结论，和提交审核把 main 合进来出了冲突、还没改好；这两种时候都不自动同步。为什么这样定，见轨迹卡 [执行器当场定论，打回就退回工作区](/trajectory/2026-10-02-runner-decides-at-once)。

这几个动作在各种情况下怎么配合，每种情况谁做了什么、提交图变成什么样，见案例 [各种情况下怎么协作](/collab/using/situations)。

## 提交审核

`collab.submit` 一条命令提交记录和页面：

{/* ref file="../plugins/collab/src/collab-repo/submit/commands.ts" lines="6-30" hash="a18250268448" blob="7c726cdd88d4" */}

按这个顺序做，哪一步不过就停在那里，后面的都不做：

1. **确认在 main 上**：不在 main 上（或者是分离的 HEAD）就直接拒绝，写明当前在哪
2. **取回远端并校验 `collab/`**：`git fetch origin`（`git/git.ts` 的 `fetchOrigin`，自动同步取回用的也是它），再只报这次改动带来的格式问题，参照是本地 main 与 `origin/main` 的分叉点（`git merge-base HEAD origin/main`）：那时就有的问题不算我的，不查谁改了谁的记录。用的是数据模型包的 `newFormatProblems`。我的改动和别人后来合进 main 的记录凑在一起才出的问题（比如我的任务归进的模块被别人删了），这里查不到，第 6 步把 main 合进来之后再查
3. **`site/` 有改动时校验站点**：两样，有一样不过就不提交、报出原话。一是日志页的文件名：数据模型包 project-model 的 `journalProblemsOf` 查 `site/journal/` 里只能放 `<真实日期>.mdx`——站点布局的 loader 也按它读，不合规矩整站打不开；站点的其余问题（依赖装没装、页面起不起得来）由 gwb-docsite 启动时查。二是类型检查：`site/package.json` 写了 `typecheck` 脚本，就在 `site/` 里运行 `pnpm run typecheck`，退出码不是 0 就把输出报出来；页面、组件能不能编译由它管
4. **在本地 main 上一起提交 `collab/` 与 `site/`**（接缝 10）：`git add --all -- collab site`，暂存区里别的文件不带上。提交说明按带了什么写：只有 `collab/` 的记录是「`<身份>` 的协作记录」，只有 `site/` 的改动（页面、评论、人员列表）是「`<身份>` 的页面改动」，都有是「`<身份>` 的协作记录与页面改动」。上次提交审核把 main 合进来出了冲突、冲突已经改好时，这一步完成那次合并
5. **把 main 合进来**：本地 main 上没有 `origin/main` 里还没有的提交就拒绝，说没有要提交的；本地 main 落后 `origin/main` 就 `git merge --no-edit origin/main`，推上去的就是和最新 main 合好的结果。有冲突就让这次合并停在没做完的状态、不推送：冲突标记留在文件里，回失败、列出冲突的文件，网站顶部的提示栏也列出这些文件（`conflicts` 通知），冲突标记所在的记录文件网站还会报出第几行；在协作窗格那个项目的一行上点「交给 AI 处理」，把它们连同别的通知一起交给 AI。AI 按两边的意思改好后再运行 `collab.submit`，第 4 步完成这次合并。两人同时加了库、`site/pnpm-lock.yaml` 冲突时，锁文件不手改：用 main 那份，在 `site/` 里重新运行一次 `pnpm install`，再提交审核
6. **合进 main 之后再查一遍**：记下这时的 `origin/main`，合并后的 `collab/` 比它多出的格式问题；合并后的 `site/` 比它有改动时，再做一遍站点检查（这时工作区里的 `site/` 就是合并的结果）。两个人各自没问题、凑在一起才出的问题（别人删了我回复的那串评论这类）只有这一步能发现，执行器不查记录格式与站点。有问题就不推送：本地 main 退回记下的 `origin/main`（`git reset --mixed`），改动回到工作区，逐条写明文件
7. **查只有负责人能改的内容**：调合并检查包的 `leadOnlyProblems`，参照是记下的 `origin/main`、比的是本地 main，和执行器用的是同一个函数；自己是不是项目负责人，经 gwb-gitea 读 Gitea 上协作仓的协作者算出来交给它（这里直接读，不经 `collab-repo/leads.ts`）。改到了、自己又不是项目负责人，就不推送：本地 main 退回记下的 `origin/main`，改动回到工作区，回失败写明是哪几处。哪些算只有负责人能改，见 [合并检查包](/collab/collab-merge-check)
8. **推送**（接缝 5）：`git push origin HEAD:refs/for/main -o topic=<身份> -o title=<标题>`。标题按推上去的改动比 main 多了记录、页面还是两样都有，和提交说明同一套写法：不给标题的话 Gitea 取最后一个提交的说明，先合了 main 时就成了「Merge remote-tracking branch」。推送失败就把本地 main 退回记下的 `origin/main`，改动回到工作区，报出 git 的原话
9. **等执行器的结论**：从推送的输出里认出合并请求的地址与编号，经 gwb-gitea 每 2 秒查一次，直到它关闭，最多等 3 分钟（执行器通常十几秒）。结论怎么处理见下一节

格式检查要比两个版本：`git cat-file --batch` 一次读出某个版本里的全部记录与 `site/people.json`，交给数据模型包的 `newFormatProblems`：它只认「一组文件」，不认识 git。站点检查只查工作区，不读 git 里的版本。

回执是 `{ commit, siteFiles, siteTypecheck, pull }`：`commit` 是这次新建的提交，没有改动、只推送已有提交时为 `null`；`siteFiles` 是这次提交里 `site/` 下改了几个文件；`siteTypecheck` 是 `passed`（运行过且通过）或 `no-script`（站点没写 `typecheck` 脚本，没有运行），`site/` 没有改动时为 `null`；`pull` 是合并了的合并请求 `{ number, url }`。

类型检查只在成员本机运行：它要先装好站点依赖，执行器上不装，理由见轨迹卡 [页面也走提交审核、按路径自动合并](/trajectory/2026-10-01-pages-auto-merge)。没写 `typecheck` 脚本的站点，提交前不查类型。校验为什么看合并之后，见 [提交前校验看合进 main 之后](/trajectory/2026-09-26-submit-checks-merged-result)。

## 执行器的结论

执行器只查两条：没有冲突；没改只有负责人能改的内容，详见 [合并检查包](/collab/collab-merge-check)。记录格式与站点它不查，上面第 2、3、6 步在本机查过。`collab.submit` 等到的结论有三种：

| 结论 | 合并请求 | 本地 main 与工作区 | 命令回什么 |
| --- | --- | --- | --- |
| 合并了 | 执行器以 `collab-bot` 合并 | 合并后推来协作仓的 `push` 消息，插件取回协作仓、把本地 main 快进到 `origin/main` | 回执，`pull` 是合并请求的编号与链接 |
| 打回 | 执行器留言写明原因，再关掉 | 退回推送时的 `origin/main`，这次的改动回到工作区、变回没提交的改动 | 失败，附合并请求上最后一条留言 |
| 3 分钟没结论 | 插件关掉它 | 同上 | 失败，说 NAS 上的执行器可能没在运行，让人告诉项目负责人去看 |

{/* ref file="../plugins/collab/src/collab-repo/submit/submit.ts" lines="161-171" hash="1b71d9f90dfc" blob="d6f41b5784e7" */}

命令回失败时，`collab-repo/submit/` 的 `SubmitFailures` 记下时刻与原话，交给通知成为 `submit-failure`「上次提交审核没成功」（合 main 出冲突时只列冲突那条）。两种时候清掉：下一次提交审核成功；或者已经没有东西可提交了，比如照拒绝的原话把改动撤掉了，这时下一次自动同步之后（见下面「自动同步」）就清掉。只记在内存里，重启工作台后就没了，改动还在工作区，提示栏照样列出没提交的文件。

{/* ref file="../plugins/collab/src/collab-repo/submit/submit-failures.ts" lines="3-27" hash="fff7be51a1f5" blob="3b93800dff2e" */}

打回之后照留言改好，再提交审核。记录、页面、组件、静态文件，加库、升级库、删库，谁提交都行；只有负责人能改的那几处，不是项目负责人的提交时在第 7 步就拦下、不推送，这类改动交给项目负责人提交。
插件关掉的合并请求，执行器恢复运行后也不处理：它动手前先看合并请求还开不开着。协作仓的合并请求、issue 与评论推来的消息插件都不处理：合并请求由执行器当场定论，提交审核自己等结论（见 [组织事件](/collab/collab-repo)）。

## 本机状态

`collab-repo/sync/watch.ts` 一直监视协作仓（项目加进列表、插件加载时开始，移出列表、插件卸载时停）：工作区的文件或 `.git` 里的 index、HEAD、引用一变，停 300 毫秒没有新变化就重算本机状态（接缝 11），只运行一次 `git status`，按路径分出 `collab/` 与 `site/`，冲突也从状态码里读：

{/* ref file="../plugins/collab/src/collab-repo/sync/watch.ts" lines="7-13" hash="070d50c6120b" blob="3515445fb314" */}

算出来就调通知的 `changed(repo)`，状态没变也调：`collab/` 里的记录可能改了内容，找我的待办要重算。通知取的是监视着的最新一份，还没算出第一份（刚加载、刚加进列表、没能开始监视）就现算一次。开始监视失败记成一步出错，成为「gwb 检查项目出错」那条通知，下一次完整刷新再试。

{/* ref file="../plugins/collab/src/collab-repo/sync/state.ts" lines="58-77" hash="6938ae8f76d4" blob="3ab4352a66da" */}

本机状态写成三种通知：还没提交审核的文件 `unsubmitted`、冲突 `conflicts`、不在 main `off-main`（见 [通知](/collab/notices-site)）。页面改了却一直没提交，别人看不到；网站顶部的提示栏里一直有一条「本机有 N 个文件还没提交审核」，协作窗格那一行的「协作仓 N 条」也算上它，由人看到后让 AI 提交审核，或者点那一行的「交给 AI 处理」。

## 自动同步

插件每次取回协作仓之后（接缝 6；推来协作仓有新提交时，以及完整刷新时）都试着**自动同步**：当前在 main 上、`origin/main` 有新提交，就 `git merge --ff-only origin/main` 把本地 main 快进过去，工作区里没提交的改动照留（接缝 11）。不满足就不动工作区，原因记下来，交给通知成为 `sync-problem`「没能自动同步 main 上的新改动」：

- 提交审核把 main 合进来出了冲突、还没改好：让 AI 改好冲突、再提交审核
- 本地 main 上有还没进 main 的提交：提交审核正在等执行器，或者上次提交审核中途断了（比如工作台被关掉），再运行一次 `collab.submit`
- 工作区里没提交的改动和 main 上的新改动碰到同一个文件：git 拒绝快进、什么都不动；提交审核时会把 main 合进来，冲突由人配合 AI 改
- 当前不在 main 上；本机没有 `origin/main`（取回失败过）

冲突没改好、不在 main 上时，通知里已经有冲突那条或不在 main 那条，不另列「没能自动同步」。

{/* ref file="../plugins/collab/src/collab-repo/sync/sync.ts" lines="29-60" hash="fd37477624be" blob="b434a84b1ae2" */}

自动同步没有跳过（快进了或本来就一样新，说明在 main 上、没有没做完的合并、本地 main 不领先 `origin/main`）时，插件接着重新算一次本机状态（不用监视着的那份，它可能还在等 300 毫秒）：`collab/`、`site/` 都没有改动、也没有冲突，就是没有东西可提交了，调 `onNothingToSubmit`，由插件入口交给 `SubmitFailures` 清掉上次提交审核的失败。只在自动同步之后看，不在每次文件变化时看：判断本地 main 领不领先要多运行一次 git，自动同步已经算过它。

{/* ref file="../plugins/collab/src/index.ts" lines="134-143" hash="cdbbe5874bbc" blob="afcf0a62693d" */}

自动同步是协作仓跟上 main 的唯一途径，没有单独的同步命令；要立即同步，让 AI 调 `collab.check` 立即完整刷新一次。

快进进来的改动动了 `site/package.json` 或 `site/pnpm-lock.yaml` 时，插件接着在 `site/` 里 `pnpm install`：站点先停，装完再启动、推一次数据。只动了 `site/` 别的文件时，插件确保站点在运行并推一次数据（见 [站点](/collab/notices-site)）。

## 组织事件与检查（原「组织事件」页）

`organization/events/` 是两种仓之间唯一的分发处：它订阅组织的消息、决定什么时候刷新，再按仓把事情交给协作仓那一套（接缝 3）或别的仓那一套（接缝 4），自己不读 git、不算通知。做哪几步由两边自己定：协作仓的在 `collab-repo/events.ts`，别的仓的在 `other-repos/events.ts`，各给出「完整刷新时做哪几步」与「收到这个仓的消息做什么」，每一步经组织这一层传进来的函数做，出错由组织这一层按步记下；两个文件不互相引用，也不引用 `organization/`。项目列表的加减也在这里（见 [加入项目](/collab/other-repos)）。

| `organization/events/` 里的文件 | 管什么 |
| --- | --- |
| `project-events.ts` | `ProjectEvents`：项目列表的加入、移出与加载时启动；把刷新要求交给调度；完整刷新与按消息处理时按仓分给两边；组织 webhook 的核对这一步 |
| `project-step-runner.ts` | 按项目、按步记出错，同一个项目同时只做一件 |
| `project-topics-subscription.ts` | 全部项目的 topic 合成一条订阅，跟着项目列表换连接，收到消息、连上时交给调度 |
| `ntfy-subscription.ts` | 只管 ntfy 的长连接：连接、读消息、断了重连 |
| `scheduler.ts`、`messages.ts` | 把要求合成一批、限制完整刷新的频率；认消息、去掉要做的事一样的 |
| `webhook.ts`、`leads-changed.ts`、`commands.ts` | 组织 webhook 的期望配置与核对；发 `leads changed`；命令 `collab.check`、`collab.org.setup` |

## 推来什么、交给谁

别人在 Gitea 上做的事，靠实时推送让插件知道（接缝 1）。推来的每条消息只说位置：哪个仓、出了什么事、哪个编号或分支，不当数据用；事实由插件自己去 Gitea 取，而且只取消息说的那个仓。`messages.ts` 的 `pushEventOf` 认消息，`ProjectEvents.applyEvents` 按仓分：消息说的是协作仓（仓名和协作仓 `origin` 里的仓名一样，大小写不论），交给协作仓那一套的 `applyCollabRepoEvent`；`repo <动作>` 交给别的仓那一套的 `applyRepoEvent`；别的都交给别的仓那一套的 `applyOtherRepoEvent`：

| 消息正文（标题是 `<组织>/<仓>`） | Gitea 上出了什么事 | 协作仓 | 别的仓 |
| --- | --- | --- | --- |
| `push <ref>` | 有新提交 | 取回，接着自动同步（见 [协作仓](/collab/collab-repo)） | 只取回那一个仓，不动它的分支与工作区 |
| `pr <动作> #<编号>`、`issue <动作> #<编号>`、`comment <动作> #<编号>` | 合并请求打开、关闭、重新打开、编辑、推了新提交、被审阅（批准、要求修改、评论，正文是 `pr reviewed`）；issue 打开、关闭、重新打开、编辑；issue 或合并请求上有了评论（组织 webhook 订了哪些事件见 [实时推送的部署](/gitea/push)） | 不处理：合并请求由执行器当场定论，提交审核自己等结论 | 重读这个仓的合并请求与 issue |
| `leads changed` | 有人用 `collab.repo.setup` 或 `collab.repo.create` 配好了负责人 | 重读项目负责人，再核对规矩 | 重读这个仓，再核对规矩 |
| `repo created` | 组织里建了仓 | — | 把组织里项目文件夹还没有的仓克隆进来，接着取回、读、核对克隆下来的仓 |
| `repo deleted` 等 | 组织里删了仓 | — | 只写一行日志，本机的目录不动 |

消息说的别的仓在项目文件夹里没有，只写一行日志。认不出的消息（标题里的组织和 topic 对不上、正文不是上面几种）写一行警告，对订了这个 topic 的项目各做一次完整刷新。

## 什么时候做完整刷新

完整刷新把一个项目从头读一遍（下一节），在这些时候做：

- 实时推送每次连上（插件加载后第一次连上、断线后又连上）：列表里的全部项目各一次，补上没连着的那段时间里发生的事；连不上推送就是连不上 NAS，Gitea 也连不上，这时不刷新
- 项目加进列表之后
- 人或 AI 调 `collab.check`
- 收到认不出的消息

{/* ref file="../plugins/collab/src/organization/events/commands.ts" lines="9-36" hash="5a7574a6419e" blob="15024fddb7fd" */}

`collab.check` 立即做，回 `[{ repo, check }]`：`check` 是 `{ at, error }`，`error` 是这次各步出错的原话（一步一行），这个项目正在刷新时是 `"busy"`；给了 `repo` 这个项目要在列表里，不在就拒绝。别的都经同一个调度 `EventScheduler`：

- 收到要求先等 2 秒，这 2 秒里同一个项目来的要求放进同一批：一次合并的 push 与「合并请求已关闭」几乎同时到，合成一批
- 一批里有完整刷新，就只做完整刷新，消息说的那几处它都会取到；没有就按消息逐处取，要做的事一样的只做一次（同一个仓的合并请求、issue 与评论都是重读那个仓）
- 完整刷新同一个项目最快每 10 秒一次，没到时间就等到时间再做；按消息取不受这个限制
- 轮到时项目正在刷新（命令触发的，或上一批还没做完）就过一会儿再排；已经移出列表就不做（做了会给它重新记下状态）

## 一次完整刷新做什么

先打开项目并核对（见 [加入项目](/collab/other-repos) 的令牌那一段），两边还没在监视本机的仓就先开始监视。之后依次：

1. **协作仓那一套**：取回协作仓（接缝 6）；读协作仓的协作者作为项目负责人（接缝 8）；核对协作仓的规矩（接缝 7）；自动同步，取回失败也照样试一次，本机已有的 `origin/main` 可能还没同步进来
2. **别的仓那一套**：列出组织里的仓，项目文件夹里还没有的用令牌克隆进来，克隆了哪些写进日志（接缝 13）；项目文件夹里协作仓以外的每个仓并行做三样：取回（接缝 13）、读合并请求与 issue（接缝 14）、核对规矩（接缝 15）；已经不在项目文件夹里的仓，读到的、核对出的都去掉
3. **组织 webhook**：本机身份是组织管理员时读组织的 webhook，照插件里写好的期望配置核对（接缝 2）

每一步各做什么、各自交出什么，见 [协作仓](/collab/collab-repo) 与 [协作仓和别的仓](/collab/other-repos)；组织 webhook 的期望配置见 [实时推送的部署](/gitea/push)。

## 各步出错怎么记

每一步各有名字（`collab-repo:fetch`、`other-repos:review:<仓>` 这样），出错时记下这一步的原话、写进日志，别的步照常做，不影响别的项目；那一步下次做成了（完整刷新里，或按消息再做那一步）就清掉，完整刷新先清掉这个项目全部的出错，按这一次重新记。此刻的出错一步一行，合成一条 `check-error`「gwb 检查项目出错」通知（接缝 19），窗格那一行的数也算上它。打开项目这一步失败（协作仓不在以组织命名的项目文件夹里、令牌的账号和身份不一样这类），这一次别的步都不做。开始监视本机的仓失败也记成一步出错，下一次完整刷新再试。

**第一次完整刷新做完之前不交给接口 B**：插件加载后，两边读 Gitea 的结果要等这次加载第一次完整刷新做完才齐；之前交给 QQ 私聊，还没读到的合并请求、issue 会被当成消失了。做完那一刻调一次 `changed(repo)`，之后每次状态变了才交（见 [通知](/collab/notices-site)）。

两边读到、记下的都只在内存里：协作仓那一套记项目负责人、规矩问题、最近一次自动同步的结果与上次提交审核失败；别的仓那一套按仓记读到的合并请求与 issue、规矩问题，按消息取只换掉那一个仓的；组织这一层记 webhook 的问题与各步的出错。重启工作台后从推送连上时的那次完整刷新重新算。本机状态不等刷新：协作仓还没提交审核的文件、冲突、当前分支，别的仓的 HEAD 和服务器上同名分支比的结果，两边各自监视文件与引用，一变就重算。

## 多久能看到

Gitea 那边一有事件，消息 1 秒内到每个人的工作台，再等 2 秒插件就去取。

| 什么时候 | 要等多久 |
| --- | --- |
| 别人的评论、任务、页面合进 main，出现在我的网站上 | 合并后约 10 秒 |
| 有人给我指派任务、@我、回复我，出现在我网站顶部的提示栏里 | 那条记录合进 main 后约 10 秒（本地 main 能自动同步时） |
| 我自己的提交合进去，本地 main 跟上 | 执行器合并后约 10 秒 |
| 项目里别的仓有人开了合并请求，出现在负责人网站顶部的提示栏里 | 合并请求一开，十秒上下 |

从成员提交到别人看见，其余的时间主要花在 NAS 上的执行器检查合并请求，通常 5 到 15 秒。表里的数字是 2026-10-02 在 hybrid-mmc 上实测的，当时插件收到消息就做完整刷新：订阅端和 Gitea 上的事件同一秒收到消息，7 秒后做完。按消息取做的是完整刷新里的一部分，还没另外测过。

别的仓的合并请求被审阅、合并请求上有了新评论，组织 webhook 都推过来，「要你改」「评论了」两种通知和合并请求开出来一样快。审阅被撤销 Gitea 不发 webhook，「要你改」要等这个仓下一次有别的消息、或下一次完整刷新才消失。

## 实时推送

推送服务 ntfy 和 Gitea 在同一台 NAS 上、一起启动和停止，算 Gitea 的一部分：Gitea 组织级的 webhook 把事件发到 ntfy 的 `collab-<组织>`。webhook 订哪几种事件、消息模板、由谁写进组织，见 [实时推送的部署](/gitea/push)。
插件对列表里全部项目只开一条长连接（`organization/events/ntfy-subscription.ts`），订阅 `<push-url>/<topic>,<topic>…/json`：地址是 gwb-gitea 的设置 `push-url`（和 `base-url` 存在一处，成员不用填），每个项目的 topic 是 `collab-` 加协作仓 `origin` 的主人。

- **消息只当位置用**：里面只有种类、仓、动作、编号或分支，没有提交说明、作者、评论原文（ntfy 的 topic 校内谁都能读）。事实都由插件自己去 Gitea 取，所以 ntfy 不设令牌：消息被人伪造，只会让插件多取一次，或者多做一次完整刷新（同一个项目最快每 10 秒一次）
- **`leads changed` 由插件自己发**（接缝 25）：Gitea 换协作者不发 webhook，`collab.repo.setup` 与 `collab.repo.create` 配好负责人以后，往这个组织的 topic 发一条（`POST <push-url>/collab-<组织>`，请求头 `Title: <组织>/<仓>`，正文 `leads changed`），格式和 webhook 推来的一样。在 Gitea 网页上直接改协作者不会发这条消息，别人要等下一次完整刷新才看到新负责人，所以换负责人一律用 `collab.repo.setup`
- **断线重连**：连不上 ntfy 就是连不上 NAS，和连不上 Gitea 是一回事，不单独当一种故障。连不上或断开时，隔 1 秒、2 秒……重连，最长隔 1 分钟；2 分钟收不到任何数据（ntfy 每 45 秒发一条空消息保持连接）就当连接已经失效、主动重连，电脑睡眠醒来、换了网络后靠这一条接上。重连上之后完整刷新全部项目一次，断开期间漏掉的消息不再重新获取
- **换连接**（`project-topics-subscription.ts`）：插件加载时、每次完整刷新之后、项目移出列表时，按当前的项目列表和 `push-url` 算出该订哪些 topic；和正在连的一样就不动，不一样（加了别的组织的项目、改了设置）就换一条。读不出组织的项目（目录不在了、没有 `origin`）不订、写进窗格顶上那个标签的原因里，别的照常订；没装或没启用 gwb-gitea、或者 `push-url` 写错了，就不连，标红写明原因。推送的状态只在窗格顶上显示（`collab.projects` 的 `push`），不成为通知
