`collab-site` 还有哪些事没发生，各在等什么前提、前提到了要选什么。此刻是什么、为什么存在、边界在哪都是现状，放在 [现状区](/docs)。
一条做成了：现状写进现状区、取舍记一张 [轨迹卡](/trajectory)，再从这里删掉这一行。

| 事 | 在等什么前提 | 前提到了要选什么 |
| --- | --- | --- |
| 附件、决策记录 | 两个项目真用起来之后，有人提出需要 | 各自是新的记录类型，还是独立的功能 |
| 站点协议号只写一处 | 现在数值写在数据模型包的 `siteProtocol`，功能包 `package.json` 另写一份 `collabSiteProtocol`，gwb-collab 托管站点前比的是 `site/` 里装的功能包那份，没有测试守着两处相等；协议号加到 5（论坛）时人决定先不动，加到 6（帖子并进评论）时照这个决定也没动，加到 7（模块去掉开始日）、8 时都没有拿出来一起定，还没问人 | 留哪一处，另一处怎么从它得到 |
| 网页上写、改日志 | 日志现在只由 AI 写进 `site/journal/<日期>.mdx`，人在 VS Code 里改；等有人确实要在网页上改 | 网页编辑器怎么做（源码加预览、保存前编译），写入走哪条接口 |
| 日志显示是谁写的 | 现在不记作者，要查只能看 git 历史；等有人要按人看日志 | 每段记作者，还是网页上读 git 历史 |
| 「今天还没写日志」的提醒 | 先用一两周，看靠说明书 collab 的「写日志」一节能写起来多少 | 做成一种通知放进哪一组，什么时候提醒 |
| 任务的做完日期 | 现在要知道哪天做完，看那天的日志；等有人要按做完日期统计 | 任务记录加字段，还是从日志里读 |
| 插件的边界测试 | 「`collab-repo/` 与 `other-repos/` 不互相引用、两边的 `events.ts` 不引用 `organization/`」只靠约定，只有数据模型包有边界测试，插件没有；要不要补还没问人 | 照数据模型包 `test/boundaries.test.ts` 的写法补一条，还是继续靠约定 |
| 提交审核经 `collab-repo/leads.ts` 读负责人 | 提交审核查只有负责人能改的内容时，自己经 Gitea 读协作仓的协作者（`collab-repo/submit/submit.ts`），没经过 `collab-repo/leads.ts`；读到的是同一份，要不要统一还没问人 | 统一由 `leads.ts` 读，还是提交审核照旧自己读 |
| 协作仓上的 issue 出通知 | `issue-to-answer` 只由 `other-repos/review.ts` 读别的仓，协作仓上的 issue 不出通知，协作仓的事走网站上的任务与评论；等有人真在协作仓上开 issue、需要提醒 | 在协作仓那一套另起一处读协作仓的 issue，放进哪一组 |
| 推送订阅断了出通知 | 实时推送没订上、连不上只在协作窗格顶上的状态标签显示，不成为通知，网站提示栏与 QQ 都看不到；等有人因为没注意到推送断了而漏了事 | 做成一种通知、放进哪一组，还是照旧只在窗格里显示 |
| `check-error` 的分组 | `check-error` 通知在「协作仓」组，但它合的是刷新各步此刻的出错，别的仓的步（`other-repos:review:<仓>` 这类）出错也记在这一条里；等有人因此在提示栏里找错了地方 | 按出错的步拆到两组，还是改成单独一组 |
