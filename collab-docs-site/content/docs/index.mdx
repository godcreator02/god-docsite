一个项目就是 Gitea 上的一个私有组织，本机的项目文件夹以组织命名，组织里的仓都克隆在这里。组织里有一个**协作仓**：`site/` 是项目站点（评论在 `site/comments/`，人员列表是 `site/people.json`），`collab/` 是任务与模块的记录，只用 main，改动经合并请求由 NAS 上的执行器检查后合并；其余是**别的仓**（代码、资料），按普通代码仓由人自己管。
两种仓各有一套操作，图里上下分成两行：Gitea 上的仓、插件里管这种仓的能力、本机的克隆，线只连同一行的两头；只有组织的 webhook 不分仓。右上是另一个仓里的两块：文档站基础包，和初始化与托管站点、保管身份码的基础插件 gwb-docsite。
线带方向，线旁写送的是什么；插件下边沿的两个半圆缺口是可以替换的接口。鼠标停在编号、字母或模块框上看说明，点击固定高亮它连着谁：

## 四个包与两块外部依赖

| 包 | 是什么 | 装在哪 | 什么时候运行 |
| --- | --- | --- | --- |
| [`@godcreator/collab-model`](/collab-model) | 数据模型包：项目仓的布局与项目负责人、`collab/` 里任务与模块的格式与写入规则、待办筛选、通知与推给网站的数据。不送东西，定了几条线上送的东西长什么样（图上的紫色点线） | 功能包与合并检查包的普通依赖，随它们装；插件发版时打包进去 | 被调用时：网站读写记录、插件算通知与提交前检查 |
| [`@godcreator/collab-site`](/collab-site) | 功能包：接在基础包上的任务页、任务与模块那一页、日历与日志页、通知栏，照基础包的功能包约定交给站点骨架的路由、侧栏入口与布局数据，以及站点检查 `./site-check` | 每个项目协作仓 `site/` 的依赖，写在 `site/package.json` 的 `docsite.features` 里；插件发版时打包 `./site-check` | 成员的站点开着的时候 |
| [`@godcreator/collab-merge-check`](/collab-merge-check) | 合并检查包：协作仓的合并请求有没有冲突、有没有改只有负责人能改的内容；命令行 `collab-merge-check`，另带自动合并工作流模板 | 执行器按工作流文件写的版本装；插件发版时打包进去 | 执行器检查合并请求的时候；插件推送前 |
| [`@godcreator/gwb-collab`](/gwb-collab) | gwb 插件：协作仓那一套（提交审核、自动同步、读负责人、任务与待办命令）、别的仓那一套（取回与快进、等我处理的）、组织级的（收位置消息、建项目），把两边的状态写成通知交给站点、协作窗格、QQ 与 AI | 每个成员的 gwb 工作台 | 工作台开着就在：连着 NAS 上的推送服务，Gitea 一有事就去取那一处 |
| `@godcreator/docsite-kit`（单元 `oz47p-docsite-kit`） | 文档站基础包：站点骨架的模板、页面、开发服务、评论、人员列表、推送通道。不在这个仓里 | 协作仓 `site/` 的依赖；功能包、数据模型包写成 peer 依赖；插件打包它的 `./files` | 成员的站点开着的时候；插件读评论串、查站点时 |
| `@godcreator/gwb-docsite`（同一单元） | gwb 基础插件：照基础包与功能包的模板初始化站点、托管站点的开发服务、往站点推数据、本 home 的身份码。不在这个仓里 | 每个成员的 gwb 工作台，gwb-collab 注入它的服务 `gwbDocsite` | 工作台开着就在 |

依赖方向只有一种：数据模型包不依赖这个仓里别的包，只引用基础包里人员列表与评论的格式（可选的 peer 依赖）；合并检查包只依赖数据模型包里项目仓的布局；功能包依赖数据模型包与基础包；插件依赖三个包，另注入 gwb-docsite 的服务。数据模型包有一份边界测试守着自己目录之间的方向，见它的首页。

## 逐条接缝

| 接缝 | 负责的一方 | 改了会让哪一边出问题 |
| --- | --- | --- |
| 1 初始化、托管与推数据 | 插件的 `collab.site.init` 交给 gwb-docsite 初始化站点、照新模板重写骨架；插件查过站点协议号与站点检查才交给 gwb-docsite 托管，之后通知或项目负责人一变就整份推到频道 `collab`；数据模型包定 `SiteFeed` 的形状与频道名 | 两边：形状一改就加站点协议号，插件要重新发版、项目要升功能包的范围；两边协议号对不上，插件就不托管，报错写明改哪一边。见 [站点](/gwb-collab/site) |
| 2 身份码 | gwb-docsite 保管本 home 的身份码；插件按它在 `site/people.json` 里认人 | 码不在人员列表里插件打不开项目、站点只读；`collab.project.join` 把码加进自己那一项。见 [加入项目](/gwb-collab/project) |
| 3 运行站点 | gwb-docsite 在 `site/` 里运行 `pnpm dev`、常驻与重启；基础包的开发服务收推送 | 不经 gwb-docsite 启动的站点没有身份，只能看 |
| 4 推来的数据 | 功能包从推送通道读出、按数据模型包的形状逐项查 | 同 1 |
| 5 记录文件 | 数据模型包，`collab/` 的格式只有这一份实现 | 网站与插件都读写这些文件，格式一改两边都要换成同一版数据模型包 |
| 6 评论与人员 | 基础包，评论与人员列表的格式只在那里 | 插件读评论串算找我的、提交前查评论格式，都用基础包的函数 |
| 7 提交审核、9 在 main 上提交 | 插件的提交审核 | 协作仓只用 main：在本地 main 上提交 `collab/` 与 `site/`，用 AGit 推成合并请求，主题是身份；被打回就把改动退回工作区 |
| 8 自动合并 | 协作仓 main 上的工作流；NAS 上的执行器；机器人账号 `collab-bot` 的权限 | 执行器对每个合并请求立刻合并或打回，不留开着等人的；只查冲突与只有负责人能改的内容，见 [执行器与自动合并](/gitea/runner) |
| 10 取回 main、11 快进本地 main | 插件的自动同步 | 本地 main 平时没有 main 里没有的提交，取回后只做快进；快进不了出 `sync-problem` 通知 |
| 12 负责人 | 插件读协作仓在 Gitea 上的协作者 | 项目负责人随推给网站的数据交给站点，也当参数传给写入规则；人员列表不记谁是负责人 |
| 13 取回别的仓、14 快进与看 HEAD | 插件的取回与快进 | 别的仓由人自己管：插件不自动动它们，人要求时才快进；HEAD 和服务器同名分支不一样各出一条通知 |
| 15 等我处理的 | 插件读别的仓的合并请求与 issue | 别的仓的合并请求由负责人审，不经执行器 |
| 16 仓里出了事、17 位置消息 | 组织 webhook 与 NAS 上的 ntfy，见 [实时推送](/gitea/push)；插件订阅 | 消息只说位置，插件按仓分给两套操作，只取那一处；消息格式变了插件认不出，只能做完整刷新 |
| 18 地址与令牌 | gwb-gitea 插件 | 插件不存令牌，每次联网现读 |
| A 交给 AI、B 发通知 | 插件开的两个可替换接口 | 换实现不动别的目录：ZCode 或 Claude Code、QQ 私聊，由设置选 |

网站不连 Gitea、不动 git 历史，所以一个成员的网站出了问题，最多是这个成员自己的工作区里多了、改了几个文件。
合并能不能做由合并检查包定，执行器运行它；记录格式与站点由插件提交前在本机查，推送前再用合并检查包「只有负责人能改的内容」那一条在本机先查一遍，推送后等执行器的结论。记录、评论和页面走同一条路：页面、组件、静态文件、评论、加库检查通过就自动合并；会在每个人电脑上执行代码的（站点的配置文件、`scripts`、装包设置）和会改变合并规则的（工作流、人员列表、功能包版本）只有项目负责人能改，别人提交时本机就拦下；例外是每个人给人员列表里自己那一项加减身份码。

## 要人处理的事都是通知

两套操作各自只交出此刻的状态，插件把它们写成一条条通知，再交给四处：网站顶部的提示栏、协作窗格里的计数、QQ 私聊、交给 AI 的提示词。
一条通知只带事实（`kind` 和这种 `kind` 的字段），句子、去处、分组、计数都由数据模型包的通知模型按 `kind` 算，四处用同一份；按此刻的状态算，解决了就不再出现，同一件事前后 `id` 不变。19 种 `kind` 分三组：

| 组 | 有哪些事 |
| --- | --- |
| 协作仓 | 还没提交审核的文件、合 main 的冲突、提交审核失败、没能自动同步、检查出错、协作仓不在 main、记录读不对、组织 webhook 没配好 |
| 别的仓 | 没推送、没拉取、分叉，等我审阅的合并请求、等负责人回的 issue，我开的合并请求与我提的 issue 有了回应，仓没按规矩配好 |
| 找我的 | 指派给我的任务、在评论或回复里 @我的、回复我的 |

字段与规则见 [数据模型包](/collab-model) 的「通知模型」，网站怎么显示见 [功能包](/collab-site)，插件怎么算、什么时候发见 [gwb-collab](/gwb-collab)。一条评论怎样一步步从一个成员的网站走到另一个成员的网站，见案例 [一条评论从 bob 到 carol](/cases/comment-flow)。

## 刻意不做什么

- **没有站点服务器，也没有数据库**：每人在自己电脑上运行站点，数据只在 git 仓的文件里，Gitea 是唯一的远端；NAS 上只有一个执行器负责合并，不存任何数据。理由见 [一条记录一个文件](/trajectory/2026-09-25-one-file-per-record) 与 [协作站](/trajectory/2026-09-25-collab-site)
- **网站不运行 git、不连 Gitea、不算通知**：提交审核、自动同步在插件，自动合并在 NAS 上的执行器；通知与项目负责人也由插件算好推给站点，网站只显示。理由见 [AGit 与 gwb 分工](/trajectory/2026-09-25-agit-lanes-and-gwb) 与 [git 状态交给插件追踪](/trajectory/2026-09-30-git-status-in-plugin)
- **网站只在自己电脑上打开**：手机和别的电脑访问不到；写下的东西署的是本 home 的身份码在人员列表里认出的那个人
- **站点的骨架、运行与评论不在这个仓里实现**：站点骨架与它的初始化、开发服务、常驻、打开窗口、评论与人员列表都是基础包与 gwb-docsite 的，协作站只加上自己的功能与检查
- **不弹 Windows 通知，不自动交给 AI**：要处理的事都列在网页顶部的提示栏里，人在协作窗格里点了「交给 AI 处理」才交出去；新出现的通知另可经 QQ 私聊本人，默认关闭。理由见 [提示栏取代通知](/trajectory/2026-10-03-notice-bar-replaces-notifications)
- **不替人动别的仓**：别的仓的分支与没提交的改动由人自己管，插件只取回、人要求时才快进，和服务器不一样时出一条通知
- **不自动处理冲突、不替人纠错**：git 冲突、校验不过、读不出的文件都如实报出文件与问题，由人配合 AI 解决。理由见 [记录行可改，冲突交给 git](/trajectory/2026-09-25-editable-record-lines)
