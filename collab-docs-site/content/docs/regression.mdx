发了数据模型包、功能包、合并检查包、gwb-collab，或者文档站基础包与 gwb-docsite 之后，照下面 11 项从头走一遍，确认日常用法没坏。每次的结果与发现写成轨迹卡，这一页只写清单。

清单只测日常一定会走到的主流程，和两人协作时常碰到的冲突与无法合并。令牌出错、各种拒绝、计数与样式这类边界情况不专门造出来测：它们该怎么处理写在各模块页里，平时用的时候碰到了就修，恢复正常以后再把这 11 项走一遍。

## 准备

- **负责人**：日常用的 default home，项目列表里有 MMC，本 home 的身份码在 `site/people.json` 的 godcreator 那一项里，gwb-gitea 里是负责人自己的令牌
- **成员**：隔离 home carol 当成员的电脑（长期保留，不用每次重开），装 `@cordisjs/plugin-timer`、gwb-gitea、gwb-docsite、gwb-collab、gwb-qq-bot；令牌是 carol-test 的，经 `credentials.copy` 复制进这个 home，AI 不读原文；组织 `hybrid-mmc` 已用 `collab.project.clone` 克隆在总控台的 `out/collab-e2e/carol/` 下，这个 home 的身份码已经用 `collab.project.join` 写进 carol-test 那一项并合进 main
- **成员的网站**：成员克隆的 `site/` 装好依赖，站点在另一个端口（4331），免得和负责人自己的站点冲突
- **QQ**：两个 home 各用一个 QQ 机器人，`owner-openid` 填各自主人私聊那个机器人时的 openid，`qq-notifications` 打开；负责人的 MMC 用 `collab.project.qq-command` 设好命令 `/mmc`
- **资料库仓**：挑负责人那边工作区干净、没有没推的提交的仓（MMC 里负责人是 godcreator 的 `submodule-board-test`）；有人正在用的仓不碰
- **点界面**：成员的工作台用 `devkit.cdp` 真实点击；default 上 `devkit.cdp` 只许截图，负责人窗格上的按钮改调同一条命令、再截图核对；两边的网站在 Chrome 里打开 `127.0.0.1` 上的地址来点
- **看本地 main**：在协作仓里运行 `git rev-parse HEAD origin/main` 比两行
- 测试里写的任务标题与评论正文带「【实验】」，测完由负责人把任务标为已完成、评论点「解决」，一起提交合并

## 主流程

| 项 | 做什么 | 通过 |
| --- | --- | --- |
| 1 自动检查 | 仓根 `pnpm build && pnpm check`；`collab-docs-site` 里 `pnpm doc`、`node scripts/verify-roster.mjs`、`pnpm build` | 类型检查、测试全过；没有黄灯、红灯；名册一致；构建通过 |
| 2 站点 | 重启成员的工作台，不做任何操作看协作窗格；点那一行的站点端口，再点一次 | 站点由 gwb-docsite 自动启动，端口是绿点；侧栏底部写着成员的显示名，不是「只读」；第一次照 gwb-docsite 的设置 `site-window` 打开站点窗口，第二次不新开、切到前台 |
| 3 写与提交 | 成员在网站上点右下角「批注」，批一段文字，写一条正文带 `@godcreator` 的评论；在任务页新建一条任务，负责人一栏选负责人；`collab.submit` | 写完顶部提示栏出现「本机有 N 个文件还没提交审核」；`collab.submit` 十几秒内回执，`pull` 带合并请求的编号与链接；Gitea 上提交人是成员、合并人是 `collab-bot`；合并后提示栏里这一条自己消失 |
| 4 对方收到 | 负责人什么都不做，等十几秒 | 负责人的本地 main 和 `origin/main` 一样；网站上任务不用刷新就出现，评论文件进来后网站自己整页刷新一次，出现那串评论；提示栏「找我的」组有「成员名 在评论里 @了我」和「指派给我的任务：任务标题」，点任务那一条打开它那一页；协作窗格那一行「找我的 2 条」 |
| 5 别的仓的合并请求 | 成员在资料库仓建分支、提交、推上去，在 Gitea 上开一个合到 main 的合并请求 | 几秒内负责人的提示栏「别的仓」组出现「资料库仓名 #N「标题」等你审阅（成员名 开的）」，点它打开 Gitea 上那个合并请求；成员自己的提示栏没有这一条 |
| 6 QQ 通知 | 看两边的 QQ | 负责人的 QQ 收到第 5 项那一条，第一行是 `协作站 <站名>`；成员的 QQ 没收到；第 3、4 项里只存在几秒的中间状态谁都没收到 |
| 7 交给 AI | 负责人的 `ai-handling` 是 zcode，在协作窗格点 MMC 那一行的「交给 AI 处理」 | 那一行写「已把 N 件事交给 ZCode，会话 …」，N 和那一行三组计数加起来一样；ZCode 在协作仓多一条会话；AI 先列出每条打算怎么处理、等人回复，没改文件、没调 `collab.submit`。看完回复它「第 5 项的合并请求关掉不合，别的不动」，它照做 |
| 8 QQ 派任务 | 负责人在手机 QQ 私聊机器人，打「/」；发 `/mmc 【实验】列出协作仓里还没完成的任务，只读不改` | 「/」面板里有 `/mmc`；先收到「【mmc】已接收」与会话行，ZCode 在项目文件夹里多一条会话；做完收到「【mmc · 第 1 轮】」开头的结果，没改文件 |

## 冲突和无法合并

每项最后都恢复正常，下一项从干净的状态开始。

| 项 | 做什么 | 通过 | 恢复正常 |
| --- | --- | --- | --- |
| 9 两人改同一处 | 负责人和成员改同一条记录的同一行，负责人先提交审核并合并，成员再提交审核 | 成员的 `collab.submit` 回失败、列出冲突的文件，没有推送、没有开合并请求；提示栏出现「提交审核合 main 出了冲突，N 个文件还没改好」并列出文件；协作窗格那一行标红 | 成员按两边的意思改好冲突标记，再提交审核，`collab-bot` 合并，提示栏里这几条消失 |
| 10 本机改动挡住同步 | 成员改一条记录不提交；负责人改同一处并合并，等十几秒 | 成员的本地 main 不快进，提示栏出现「没能自动同步 main 上的新改动」，下面写明原因（工作区的改动和新改动碰到同一个文件）；成员工作区没被动过 | 成员把自己的改动提交审核，冲突照第 9 项处理；合并后本地 main 跟上、这一条消失 |
| 11 成员改了只有负责人能改的内容 | 成员改 `site/package.json` 的 `scripts`，提交审核 | `collab.submit` 回失败「没有推送，改动留在工作区（没提交）：」加上是哪几处；Gitea 上没有新的合并请求；改动回到成员的工作区、没提交 | 成员撤掉这处改动；要改 `scripts` 由负责人提交审核 |
