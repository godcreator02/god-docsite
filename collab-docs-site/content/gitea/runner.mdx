合并这一步不在任何人的电脑上做，协作仓的 main 谁都不能直接推，负责人也一样。成员与负责人都用 `collab.submit` 推出合并请求，Gitea 按协作仓 main 上的工作流给 NAS 上的执行器派一个任务；
执行器装上合并检查包，两条都过就以机器人账号 `collab-bot` 合并，不过就把原因留在合并请求上、再关掉它（打回）。协作仓的合并请求不会开着等人；成员那边的 `collab.submit` 一直等到这个结论，打回的改动退回成员的工作区。负责人的电脑开没开都一样。
执行器只管协作仓：工作流文件只放在协作仓里，别的仓的合并请求由负责人审、负责人同意后合并，不经执行器。
两条检查各查什么、哪些内容只有负责人能改，见 [合并检查包](/collab-merge-check)；这一页只讲检查以外的部分。

## 每条接缝由谁负责

| 接缝 | 负责的一方 | 改了会让哪一边出问题 |
| --- | --- | --- |
| 1 推成合并请求 | gwb-collab 的 `collab.submit` | 主题是身份：同一个人推的都进同一个合并请求，改了主题会开出好几个 |
| 2 派任务 | Gitea；工作流里的 `runs-on: nas` 与执行器登记的标签 | 标签对不上，任务一直排队、没有执行器领取 |
| 3 读工作流 | 每个协作仓 main 上的工作流文件，照合并检查包的模板放 | 各仓的文件不一样，合并规则就不一样；只有 main 上那份算数 |
| 4 取代码 | 工作流；令牌要能读协作仓 | 令牌看不到仓，「核对令牌」一步就报出来，不往下做 |
| 5 装检查工具 | 协作仓 main 上工作流文件里的 `MERGE_CHECK_RANGE` | 执行器每次按这个范围安装合并检查包（连同它依赖的数据模型包，不装功能包），和站点用的功能包版本无关，升版本就是负责人改这一行；模板用机器人令牌读协作仓的协作者，把提交人与这些负责人作为 `--author`、`--leads` 传给检查，两个都必填，装到的命令行不认 `--leads` 时检查以退出码 2 失败、不合并也不留言；协作仓没有协作者时这一步报错，同样不合并 |
| 6 合并检查 | 合并检查包的命令行 `collab-merge-check` | 规则改在合并检查包里，负责人改了工作流里的版本范围，检查就按新规则；gwb-collab 推送前用的是它打包的那一版 |
| 7 合并或打回 | 工作流；`collab-bot` 在组织的团队 `bots` 里，协作仓 main 的合并许可里只有团队 `bots`，负责人也不在里面（`collab.repo.setup` 配协作仓时写上，见 [权限怎么配](/gitea/permissions)） | 权限不够时 Gitea 拒绝合并，执行器把 Gitea 的原话留在合并请求上、打回 |
| 8 等结论 | gwb-collab 的 `collab.submit` | 等不到结论（执行器没在运行）时插件 3 分钟后关掉合并请求、退回改动；执行器恢复后看到合并请求已关就不处理 |

## 为什么要一个机器人账号

Gitea 每次运行会自动发一个令牌 `GITEA_TOKEN`，但 AGit 开的合并请求触发的任务里，它只能读仓本身：读合并请求、合并、留言全部 404，
组织设置是「宽松」、工作流里要了写权限也一样。所以合并要用一个真实账号的令牌，存成组织密钥 `COLLAB_BOT_TOKEN`，实测见轨迹卡
[自动发的令牌合并不了 AGit 合并请求](/trajectory/2026-09-30-actions-token-readonly-on-agit)。

这个账号是 `collab-bot`。它在每个组织里只进一个团队 `bots`：团队只含协作仓，代码、工单、合并请求三项可写，其余没有权限（见 [权限怎么配](/gitea/permissions) 的「团队」）。
工作流用 `pull_request_target` 触发，读的永远是 main 上那份，成员在合并请求里改工作流也拿不到密钥；工作流只有项目负责人能改，别人改了它的合并请求被打回。

## 执行器在哪

执行器是 NAS 上全站共用的一个：`teamhub` 里的 `gitea-runner` 容器，只登记了主机方式的标签 `nas`，部署写在 NAS 配置仓。新项目不用再装，一个新组织要配的密钥、团队、工作流见 [建项目与人员变动](/gitea/setup)。

## 成员电脑上看到的

成员的 gwb-collab 不合并：提交前在本机先查记录格式与站点（执行器不查这两样），推送前用和执行器同一个函数查只有负责人能改的内容，推送后等执行器的结论，被打回就把改动退回工作区；执行器合并之后，组织 webhook 经 ntfy 告诉每个成员的插件协作仓有新提交，插件等 2 秒合成一批，再取回协作仓、能快进就把本地 main 快进过去（见 [实时推送的部署](/gitea/push)）。每一步见 [提交审核与同步](/gwb-collab/submit)。

## 不做的事

- **不留开着等人的合并请求**：每个合并请求立刻合并或打回，理由见 [执行器当场定论，打回就退回工作区](/trajectory/2026-10-02-runner-decides-at-once)
- **不用 Gitea 自动发的令牌**：理由见上面「为什么要一个机器人账号」
- **执行器不挂载 `/var/run/docker.sock`**：只用主机方式，任务就在执行器自己的容器里运行，理由写在 NAS 配置仓的 `docs/services/compose/teamhub.md`
